§3硬件（领夹）

设备只做拾音、门控、压缩、缓冲、打时间和传感器特征；ASR、声纹、播放声判定都放云端。二期整机平均功耗估算 2.2–5.2 mW，建议电池 60–80 mAh。

麦克风阵列

方案提供什么结论
单麦相对机主基线的声级、直达/混响比一期现状
双麦（上向 + 外向）方向先验、直达/混响比二期基线
三麦及以上更好的波束与定位不做：功耗、尺寸

近场线索：机主约 20 cm、他人约 1.5 m，声级差约 17.5 dB估算（等声功率、自由场的距离衰减；实际受音量、朝向、衣物与 AGC 影响）；近处他人和开大的电视会破坏它。

§4手机端

手机是中间处理层：拼时间线、校时钟、做 L1 拒识、记场景、调度上传、管删除链。L1 只跑 VAD、只丢高置信非语音，在 BLE 收到数据后增量运行。

分片与时间线

  • 上传分片固定 5 分钟设备时间（15,000 帧），不按语音切；立即同步时把未满的当前分片截断上传，下一片从截断处起算。
  • 主键 (device_id, boot_generation, frame_seq)，乱序与补传都能拼回原位。
  • 缺口不压缩时间轴；开启 DTX 时只按帧序号推算时间。
  • 原样保存设备码流，L1 只解一份临时 PCM。

时钟校准

  • 同步点：每次连接 + 连接中每 5 分钟。
  • 线性拟合 offset、drift_ppm；日漂移 ≤1.7 s估算。
  • 异常：重启（世代变化）、手动改时间、拟合残差过大 → 分段重拟合，标 sync_quality_ms。
  • 录音时刻还原误差 ≤200 ms目标。

L1 拒识

  • 只丢：VAD 高置信非语音，前后各留 500 ms 后仍为非语音；间隔 <2 s 的语音段合并。
  • 不做声音事件分类：云端的 CPU 小模型已包含；本机外放由场景事件记录。
  • 运行时机：BLE 收到数据后增量运行，每个 5 分钟分片约数秒 CPU估算，不依赖系统择机执行的后台任务。
  • 一期是第一道丢弃闸：留出前后余量后，约丢掉 65% 的佩戴时长，每佩戴 1 小时上传约 0.35 小时假设；二期只复核。

平台机制待确认

  • iOS：BLE 中心后台模式接收，在唤醒时间内增量跑 VAD；BGProcessingTask 只补跑积压；后台 URLSession 上传。
  • Android：connectedDevice 前台服务负责接收与 VAD；WorkManager 约束负责上传。

平台 API 与已知盲区待确认

iOS：外放 AVAudioSession.isOtherAudioPlaying / secondaryAudioShouldBeSilencedHint，路由 currentRoute.outputs，通话 CXCallObserver，日历 EventKit。中国大陆区的 VoIP 应用通常不接入 CallKit，微信等通话可能观测不到，此时 call.kind=unknown，回退到声学判断。

Android：外放 AudioManager.getActivePlaybackConfigurations / isMusicActive，通话 getMode()、TelephonyCallback（需电话权限），路由 getCommunicationDevice，日历 CalendarContract。

暂存上限 2 GB、最长 7 天；超期删除并登记缺口。隐私上限优先于完整性。
