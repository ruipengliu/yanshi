# 审核基础设施故障时，Run 可恢复地等待

> **已实现（2026-11-15）。** 2026-11-14 写为提案，2026-11-15 批准；"待回答的问题"的答复见该节，实现见 `internal/runtime/moderation_wait.go`。来源：[ADR 评审](../review/2026-11-14-adr-review.md) §3.1。下文"现行行为"一段描述的是实施前的状态。

ADR-0021 规定内容安全在写日志之前检查、失败即拒绝；"内容安全服务不可用时一律不放行：输入返回 503，输出重试直到 Run 因持续出错而失败"。不放行是对的，但"失败"的方式与章程 G3（小时级 Run、节点故障不丢进度）和 §8 的"故障透明"冲突。现行行为（2026-11-14 核对代码）：

- **输出**：模型回复与调用参数合在一起送检（`internal/runtime/worker_model.go` 中 `callModel` 的 `moderation.Check`）。提供商出错时 `Check` 返回 `moderation.ErrUnavailable`，Worker 不写任何事件，直接把错误交回 `Step`。
- **失败方式**：这条错误不计入 `MaxModelErrors`，而是走通用的 Step 出错路径：同一 Run 的 Step 连续出错满 `StepErrorBudget`（默认 2 分钟）后，写 `RunFailed{reason: "internal error: moderation unavailable: …"}`。
- **重试的代价**：两次出错之间只等 `IdleWait`（默认 100 ms），没有退避。每次重试都重新调用模型；而用量在模型返回后、审核之前就已计量（ADR-0019），所以审核服务故障的 2 分钟里，同一轮会被反复生成、反复计费，最后 Run 仍然失败。
- **输入**：`service` 的检查点在审核不可用时返回 `ErrUnavailable`，HTTP 映射为 503，不写日志；ask_user 的回答、通话转写、定时的创建同样如此。
- **attested 结果**：审核出错时整个结果写为工具错误（"旁听页的内容安全检查暂不可用，稍后再读"），模型能看到，不触发 Step 的出错预算。
- **已有的缓解**：`moderation.Failover` 可以配置主备提供商，全部失败时仍算不可用；故障注入有 `faults.ModerationDown`，模拟测试以小概率注入审核故障。

## 提议的决定

1. **区分三种情况，各走各的路径。**
   - **内容违规**：照旧，输出替换为拒答文本、丢弃调用并记录 `ContentModerated`；输入拒绝。
   - **输入未被接受**（审核不可用时的提交、回答、转写）：照旧返回不可用（503），不写日志，由客户端重试。输入方是在线的人或业务线服务端，有能力重试。
   - **输出审核遇到服务故障**：Run **挂起等待恢复**，不消耗 `StepErrorBudget`，不因此失败（第 2 条）。
2. **挂起的最小方案：记录不含正文的等待状态，恢复后重新生成。**
   - Worker 丢弃未通过检查的回复（它从未写入日志，其中的调用也从未执行），写入 `RunSuspended{reason: "moderation_unavailable", until}`，然后停放 Session（复用配额挂起的 `suspendWith` 与 `park`）。事件中**不含**回复正文、调用参数或提供商的错误信息。
   - `until` 按指数退避增长并有上限（例如从 30 秒起、上限 10 分钟，具体数值在批准时确定），期间新的输入、审批或中断照常唤醒 Session。
   - 恢复时开启新的 Attempt，重新调用模型并重新送检。被丢弃的那次调用已经计量，按 ADR-0019 保留（token 确实消耗了），但退避消除了现在每 100 ms 重试一次的重复计费。
   - **等待有总上限。** 超过上限（可配置，例如数小时）仍不可用时，Run 以明确的原因失败（`moderation_unavailable`），而不是 `internal error`。不放行的原则不变。
3. **待审正文不进入正式日志。** 如果以后要保存待审结果以免重新生成，必须另行定义隔离存储：期限、授权、按 Session 删除（ADR-0015、`app.SessionData` 登记、`lifecycle.Recheck`），不能把它悄悄放进 Event。最小方案不需要它。
4. **挂起原因与配额区分。** 现在 `session.Run.QuotaSuspended` 把任何非空、非 `handoff` 的挂起原因都当作配额挂起。新原因必须单独判断：恢复时不走 `reparkOverQuota`，而是直接开始新的 Attempt 并重新送检（配额检查照常在调用模型之前进行）。
5. **客户端可见。** 挂起事件让客户端显示"内容安全检查暂不可用，稍后继续"。此前推送的实时增量是可被覆盖的草稿（ADR-0021）：Worker 在模型返回之后、送检之前就发出结束增量，SDK 收到它即丢弃草稿（`sdk/web` 的 `Draft`），挂起时草稿已经不在，客户端不需要改动。

## 待回答的问题（批准前须给出答案）

> **2026-11-15 批准时的答复：**
> 1. 退避从 30 秒起翻倍、至多 10 分钟；从第一次挂起起累计等待上限 6 小时（`runtime.Config` 的 `ModerationRetry`、`ModerationRetryMax`、`ModerationWaitMax`）。交互与后台 Run 用同一上限：用户可以随时中断，分开设置没有依据，按线上数据再调。等待计数跨 Attempt 保留，写入 AssistantMessage 时清零（`session.Run.ModerationWaits`）。退避未到期时被其他事件唤醒，只重新停放、不写事件。
> 2. attested 结果遇到审核故障时**维持现行**：作为工具错误交给模型，由模型决定稍后重读。它不重新调用模型，没有重复计费的问题。
> 3. 委托的子 Run 挂起时，父调用的时限**照常计时**，与子 Run 因其他原因挂起时相同。
> 4. 定时开启的 Run、后台调用了结开启的 Run，都在同一处（调用模型之后的送检）挂起，处理相同。
> 5. 合规确认仍列在上线检查清单中；实现上挂起期间不展示任何未经审核的完整回复。

1. 退避的起点、上限与等待总上限的取值；交互类 Run（用户正在等）与后台 Run 是否用不同的总上限。
2. attested 结果遇到审核故障时，是继续作为工具错误交给模型（现行），还是同样挂起等待。前者让模型决定是否稍后重读，后者语义更一致。
3. 委托派生的子 Run 挂起时，父调用的时限（`delegation.timeout`）是否照常计时。
4. 定时开启的 Run 与后台调用了结（ADR-0035）在审核故障时的处理是否相同。
5. 与合规确认：挂起期间不向用户展示任何未经审核的完整回复，只展示已推送过的草稿并随即撤回，是否满足监管要求（[上线检查清单](../launch-checklist.md)中已列此项）。

## 必须验证

- 模拟测试（`internal/sim`）：审核故障期间挂起、恢复、取消、中断与删除的竞争；恢复后不重复执行任何调用（被丢弃的回复中的调用从未执行）；不重复计量同一次模型调用；等待总上限到期时的失败；日志中没有未经审核的内容（现有的 `checkModeration` 不变量）。在覆盖统计中加入"审核故障挂起"。
- 故障注入：`faults.ModerationDown` 下，Run 挂起而不是失败；恢复后完成。
- 计量：同一轮因审核故障被重新生成的次数可观测（指标只记 ID 与次数，不记内容）。
- 评测：不涉及给模型看的文本，不需要新增用例；若挂起改变了 Transcript（不应改变），以缓存命中列确认。

## Considered Options

- **维持现状**：实现最省，但长 Run 因一次 2 分钟以上的审核故障就失败，且故障期间反复调用模型、反复计费。
- **审核不可用时放行、事后补审**：可用性最好，但违反"写日志前检查、失败即拒绝"（ADR-0021），违规内容一旦写入日志就要在每条读取路径上过滤。
- **保存待审结果，恢复后只补审不重新生成**：省掉一次模型调用，但要新增一个保存未审核内容的存储，并解决它的期限、授权与删除；收益只在故障期间出现。留待需要时另立。
- **只给 Step 出错加退避**：能消除重复计费，但 Run 仍会在出错预算用完后失败，没有解决"故障透明"。

## Consequences

- 批准后修订 ADR-0021 的"失败方式"一句，并更新[内容安全设计](../design/m4-moderation.md)与上线检查清单。
- `RunSuspended` 增加一种原因；投影中挂起原因的判断要区分配额与审核，递增 `session.ProjectionVersion`。
- 审核服务的可用性不再直接决定长 Run 的成败，但仍决定输入能否提交与 Run 何时继续。

## 重审条件

- 批准、实施或放弃本提案时更新状态；
- 若决定保存待审结果（第 3 条），另立 ADR。
