# 定时是内核的原语，到期输入的来源是平台

> **只在一条业务线（xinli）上验证过**（2026-11-14）：机制按通用设计，需求与使用目前都来自 xinli；第二条业务线接入时按重审条件复核。

按钟点做的事（每天整理、每周回顾、心力优先、用户要求的"每周五给我周报"）现在由业务线到点以服务令牌提交输入（ADR-0040 第 5 条）。服务令牌提交的输入在投影中是用户原话：Agent 依据外部内容写下的定时文字，到期后就成了"用户亲口说的"，绕过写入闸门。这正是 ADR-0037 拒绝推入摘要的理由。

## 决定

（设计见 `docs/design/m7-kernel-primitives.md` §5）

- 定时属于一个 Session：由 Agent 经内置能力 `schedule` 创建，或由业务线经 HTTP 创建；一次性（`at`）或周期（RRULE 子集），时区由创建方显式给出。
- 没有窗口：静默判断依据原文，原文在业务线（ADR-0050），当天整理由业务线提交固定指令。时区默认取创建 Session 时给出的 `time_zone`。
- 记为 Event（`ScheduleCreated`、`ScheduleCancelled`、`ScheduleFired`），投影记下下次到期时间；唤醒复用 Worker 的停放：Session 没有活跃 Run 时，Worker 把它在工作队列中停放到最早的到期时间，与 ADR-0035 的后台调用同一机制（`State.NextScheduleDue`）。到期时 Worker 写入带定时标记的 `RunRequested`，**来源为平台**，客户端不能伪造该标记。（2026-11-14 修订：原写"复用后台调用与触发的停放（ADR-0035、ADR-0040）"；ADR-0040 的触发没有实施，停放只依赖 ADR-0035。）
- 定时的输入在来源推导中是平台定时（`FromSchedule`）：不是用户原话，写入闸门不把它当作依据；也不是外部内容，不进入注入判断。准入与配额照常；工作类别按 ADR-0029 照常判定，没有专门的类别。（2026-11-14 补充：承接 ADR-0040 第 4 条中已实施的部分。）
- 有活跃 Run 时等它结束；超额时照常开启 Run，由配额与准入挂起或排队；Session 关闭后失效，有有效定时的 Session 不按空闲关闭。

这修改了 ADR-0040 第 5 条：那里担心的时区与一天的边界由创建方给出；定时只在本 Session 内开启 Run，不跨 Session 创建。

## Considered Options

- **维持业务线提交**：内核不变，但来源被洗成用户原话，每条业务线还要各写一套调度。
- **给服务令牌的输入加"不可信"标记**：堵住了来源问题，但每条业务线仍要自己调度、自己判断窗口与静默。
- **独立的调度服务（cron）**：要跨 Session 创建、知道每个 EndUser 的时区，越过平台与业务线的边界。

## Consequences

- 投影新增定时，递增 `ProjectionVersion`；模拟测试覆盖到期前后崩溃不重复、不遗漏。
- 定时的输入文字在创建时经过内容安全检查，到期时不再检查。
- 用户可以对 Agent 说"取消周报"；应用层也可经 HTTP 列出、取消。

## 重审条件

（2026-11-14 补充）任一出现即重新评估：

- 第二条业务线接入：按它的需求复核定时的语义（一次性与周期、时区、到期时有活跃 Run 的处理、超额的处理）；
- xinli 的新需求超出现有语义，例如需要跨 Session 的定时，或需要按内容而不是按钟点触发。
