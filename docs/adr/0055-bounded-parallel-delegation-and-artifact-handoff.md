# 有界并行委托与工件交接

> **提案。** 本文记录已认可的方向与必须先回答的问题，不是"已经支持"。批准之前，ADR-0031 的当前能力边界照旧适用：同一个父 Run 同时未完成的委托至多一个，父子之间只传文字。来源：[ADR 评审](../review/2026-11-14-adr-review.md) §3.3。

ADR-0031 把委托做成路由到派生子 Session 的调用，送达、去重、超时、删除都复用路由调用的机制。它留下两处当前边界：

- **串行。** Worker 每一步只推进一个未完成的调用（`session.Run.PendingCall`），父 Run 等到一个调用有结果才派发下一个。`delegation.max_fanout`（默认 4）照常检查，但实际扇出至多为 1（[委托设计](../design/m5-multi-agent.md) §9）。模型同一轮请求三个子任务，就要等三个子 Run 依次跑完。
- **只传文字。** 工件只对其所属 Session 可见（[工件设计](../design/m2-artifacts.md)），父 Run 打不开子 Run 产出的 `artifact://` 引用，`context` 也只能是文字。

小时级的长任务（章程 G3）与跨节点多 Agent 协作（G7）都会碰到这两处边界。

## 提议的决定

1. **同一轮的委托调用可以一起派发，数量有界。** 模型在一轮中请求的多个委托调用，Worker 依次提交各自的 `ToolCallStarted` 并创建子 Session，不必等前一个出结果。上限仍是 `delegation.max_fanout`，按"同一个父 Run 同时未完成的委托"计数；超出的调用返回错误结果而不派发（与现行检查相同）。设备、沙箱、MCP 等其他调用的推进顺序**不在本提案范围**，仍逐个推进。
2. **三件事分别定义，不预先规定"全部返回后才唤醒"：**
   - **结果的持久化**：每个子 Run 进入终态时，由子 Session 的 Worker 写回父调用的外部结果（ADR-0031 第 3 条，不变），各自幂等、互不等待。
   - **队列唤醒**：每次写回都唤醒父 Session（`CommitAndWake`，不变）。父 Session 被唤醒但仍有未完成的委托时，Worker 不调用模型，重新停放。
   - **模型何时继续**：默认在本轮所有调用都有结果之后再调用模型（与现在一轮内的语义一致）。是否允许"部分结果先继续"，由 AgentDef 显式声明，并且必须先回答下文"待回答的问题"第 2 条。
3. **部分失败照常是结果。** 某个子 Run 失败、超时或被拒，都作为该调用的错误结果写回；不连带取消同一轮的其他委托。父 Run 被中断时，经 `Canceler` 中断全部未完成的子 Run（ADR-0031 第 5 条，扩展为多个）。
4. **工件经显式复制交接，不共享。**
   - 父 → 子：委托参数中引用的父 Session 工件，在派发时由平台复制为子 Session 的新工件，子 Run 只看到副本的引用。
   - 子 → 父：子 Run 最后一条回复引用的工件，在写回时复制为父 Session 的新工件。
   - 复制在事件中留下记录（来源工件、目标工件、调用 ID），两份各属于自己的 Session，按 Session 删除互不影响（ADR-0015、ADR-0028 的一个事务只涉及一个键）。不默认把整棵委托树的工件互相共享。
5. **不扩大权限。** 子 Run 的能力仍是自身与每个祖先白名单的交集（ADR-0031 第 4 条）。工件复制只发生在已经允许委托的父子之间；子 Run 不能因此读到父 Session 中未被引用的工件。

## 待回答的问题（批准前须给出答案）

1. **并行的审批与提问。** 多个子 Run 同时请求审批或 `ask_user` 时，客户端怎样展示与排序；"输入框文字作为唯一待回答提问的回答"这条客户端规则（委托设计 §4）在多个子 Session 同时有提问时怎样处理。
2. **部分结果先继续的语义。** 如果允许，模型继续之后迟到的结果怎样进入上下文：作为一条输入（与 ADR-0035 的后台调用相同），还是只在下一轮可见；请求前缀如何保持只在尾部追加。
3. **配额与准入。** 并行使同一 EndUser 的子 Run 同时运行，日配额的检查点与超额时的处理（挂起哪一个）。
4. **工件复制的成本与上限。** 大工件的复制方式（对象存储内复制，或引用计数）与单次委托的大小上限；复制失败时委托如何报错。
5. **客户端。** 网页与 Go SDK 的 `PendingTracker`、调试控制台的 `pendingWithDelegations` 需要按多个进行中的委托改写；移动端由原生侧自行实现。

## 必须验证

- 模拟测试（`internal/sim`）：重复回写、乱序完成、父 Run 中断时多个子 Run 的级联、父子删除的竞争、子 Session 已删除时的重新派发不复活。
- 删除不变量：复制出的工件随各自的 Session 删除，Janitor 级联删除父 Session 时，子 Session 中的副本一并删除。
- 权限：子 Run 无法经工件复制读到未被引用的父工件；白名单交集不变。
- 评测：新增并行委托的用例（`evals/delegation-*`），比较完成时间与结果质量；缓存命中列不退化。

## Considered Options

- **全部调用都并行推进（含设备与沙箱）**：收益更大，但设备离线挂起、审批与后台调用（ADR-0035）的交互要整体重做。先只放开委托，设备调用的并行另行评估。
- **父子共享工件（按委托树授权）**：不复制、省存储，但工件的可见性与删除要跨 Session 计算，违背"工件只对其所属 Session 可见"，删除父 Session 时还要判断子 Session 是否仍在引用。
- **子 Run 的结果在全部返回后一次写回**：实现简单，但一个慢的子 Run 拖住所有结果，而且需要一个跨 Session 的汇总点。

## Consequences

- 批准后修订 ADR-0031 的"当前能力边界"，更新委托设计、端侧 SDK 设计与调试控制台的验证场景（`scenarios.js`）。
- 投影要能表示一个 Run 中多个同时未完成的委托调用，递增 `session.ProjectionVersion`。

## 重审条件

- 批准、实施或放弃本提案时更新状态；
- 设备与沙箱调用也需要并行推进时，另立提案。
