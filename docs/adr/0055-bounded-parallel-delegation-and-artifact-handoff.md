# 有界并行委托与工件交接

> **第一期（同一轮的委托并行派发）已实现（2026-11-16）；第二期（工件交接）尚未实现**，在它实现之前父子之间仍只传文字。实施记录见文末。来源：[ADR 评审](../review/2026-11-14-adr-review.md) §3.3。

ADR-0031 把委托做成路由到派生子 Session 的调用，送达、去重、超时、删除都复用路由调用的机制。它留下两处当前边界：

- **串行。** Worker 每一步只推进一个未完成的调用（`session.Run.PendingCall`），父 Run 等到一个调用有结果才派发下一个。`delegation.max_fanout`（默认 4）照常检查，但实际扇出至多为 1（[委托设计](../design/m5-multi-agent.md) §9）。模型同一轮请求三个子任务，就要等三个子 Run 依次跑完。
- **只传文字。** 工件只对其所属 Session 可见（[工件设计](../design/m2-artifacts.md)），父 Run 打不开子 Run 产出的 `artifact://` 引用，`context` 也只能是文字。

小时级的长任务（章程 G3）与跨节点多 Agent 协作（G7）都会碰到这两处边界。

## 提议的决定

1. **同一轮的委托调用可以一起派发，数量有界。** 模型在一轮中请求的多个委托调用，Worker 依次提交各自的 `ToolCallStarted` 并创建子 Session，不必等前一个出结果。上限仍是 `delegation.max_fanout`，按"同一个父 Run 同时未完成的委托"计数；超出的调用返回错误结果而不派发（与现行检查相同）。设备、沙箱、MCP 等其他调用的推进顺序**不在本提案范围**，仍逐个推进。
2. **三件事分别定义，不预先规定"全部返回后才唤醒"：**
   - **结果的持久化**：每个子 Run 进入终态时，由子 Session 的 Worker 写回父调用的外部结果（ADR-0031 第 3 条，不变），各自幂等、互不等待。
   - **队列唤醒**：每次写回都唤醒父 Session（`CommitAndWake`，不变）。父 Session 被唤醒但仍有未完成的委托时，Worker 不调用模型，重新停放。
   - **模型何时继续**：默认在本轮所有调用都有结果之后再调用模型（与现在一轮内的语义一致）。是否允许"部分结果先继续"，由 AgentDef 显式声明，并且必须先回答下文"待回答的问题"第 2 条。
3. **部分失败照常是结果。** 某个子 Run 失败、超时或被拒，都作为该调用的错误结果写回；不连带取消同一轮的其他委托。父 Run 被中断时，经 `Canceler` 中断全部未完成的子 Run（ADR-0031 第 5 条，扩展为多个）。
4. **工件经显式复制交接，不共享。**
   - 父 → 子：委托参数中引用的父 Session 工件，在派发时由平台复制为子 Session 的新工件，子 Run 只看到副本的引用。
   - 子 → 父：子 Run 最后一条回复引用的工件，在写回时复制为父 Session 的新工件。
   - 复制在事件中留下记录（来源工件、目标工件、调用 ID），两份各属于自己的 Session，按 Session 删除互不影响（ADR-0015、ADR-0028 的一个事务只涉及一个键）。不默认把整棵委托树的工件互相共享。
5. **不扩大权限。** 子 Run 的能力仍是自身与每个祖先白名单的交集（ADR-0031 第 4 条）。工件复制只发生在已经允许委托的父子之间；子 Run 不能因此读到父 Session 中未被引用的工件。

## 实施前核对的现状（2026-11-16）

- **投影与客户端大体已经支持并行。** `session.Run.Calls` 是列表，`Apply` 不要求按顺序推进调用；Go 与网页 SDK 的 `PendingTracker`、控制台的 `pendingWithDelegations` 已能展示多个委托、提问与审批；"输入框文字作为唯一待回答提问的回答"在多于一个提问时不选中、文字交给父 Session；父 Run 被中断时 `cancelDispatched` 遍历全部已派发的调用。
- **串行只来自 Worker。** `Worker.advance` 每次只推进 `Run.PendingCall()`（第一个未完成的调用）。
- **三处真正的缺口：** 父 Session 被子 Run 的结果唤醒时会写一对 `AttemptStarted` / `RunSuspended`，并把委托重新派发一遍；停放时间只取正在处理的那个调用的截止时间；`artifact.BlobStore` 没有复制操作，委托的参数与结果只有文字。
- **后台调用（ADR-0035）明确排除委托**，`runtime.Transcript` 在下一条回复时把仍在途的调用记为未执行，所以"部分结果先继续"不能直接复用后台调用。

## 定稿的答案（2026-11-16）

0. **分两期。** 第一期：同一轮的委托并行派发（不新增事件）。第二期：工件交接（新增存储操作与事件）。
1. **同一轮内的顺序。** 按模型给出的顺序，相邻的委托调用一起派发；其他调用（设备、沙箱、MCP、`ask_user`）仍等它之前的委托都有结果后再推进。这保留"同一轮的委托与 `ask_user` 先委托、后提问"的现行语义（[委托设计](../design/m5-multi-agent.md) §4）。
2. **部分结果先继续：不支持。** 本轮所有调用都有结果后才调用模型，AgentDef 也不能改变这一点。需要时另立提案，届时一并处理 `Transcript` 的未执行补齐与 ADR-0035 对委托的排除。
3. **并行的审批与提问。** 客户端规则不变：待处理项按 Session 深度优先、先审批后提问；多于一个待回答提问时，输入框文字不选中任何一个，作为普通输入交给父 Session。服务端照旧不沿委托链转发。HTTP 的 `waiting` 视图改为列出全部已派发的调用；控制台的验证场景用真实的并行委托取代合成的第二个提问。
4. **配额。** 不新增机制：每个子 Run 在调用模型前各自检查日配额、各自挂起（软上限，ADR-0019），超出量受 `max_fanout` 约束；子 Run 挂起期间父 Run 继续等待，直到 `delegation.timeout`。不规定"挂起哪一个"。
5. **父 Session 的唤醒。** 被唤醒但仍有未完成的委托时，不开始 Attempt、不写事件，重新停放（与配额挂起的重停相同）。停放前仍按 `call_id` 幂等地重新派发未完成的委托（实施时修订：派发是子任务丢失时的恢复路径，子 Session 被删除、上次的回写失败时由它写回错误结果；去掉它，父 Run 要等到委托时限，模拟测试发现）；停放到全部已派发调用中最早的截止时间，醒来时对每个已派发的调用检查超时。模拟测试新增不变量"同一个父 Run 同时已派发的委托数不超过 `MaxFanout`"，并让模拟世界真正产生同一轮的多个委托。
6. **工件交接（第二期）。**
   - 父 → 子：委托参数新增显式的 `artifacts` 列表（父 Session 的工件引用），平台不从文字中扫描 `artifact://`；子 Run 只看得到父 Run 点名的工件。
   - 子 → 父：子 Run 最后一条回复的媒体附件，以及其文字中属于子 Session 的 `artifact://` 引用。
   - 复制：`BlobStore` 新增 `Copy`（S3 用服务端复制，文件与内存实现流式复制）；副本在目标 Session 的槽位中生成新的工件 ID；顺序是先复制内容、再建元数据、再"先写后查"删除记录（ADR-0015）。
   - 上限：单个工件沿用 512 MB；一次委托至多复制 8 个。复制失败时该委托调用返回错误结果，不派发。
   - 复制写入事件（来源工件、目标工件、调用 ID），递增 `session.ProjectionVersion`。
7. **评测命名。** 现有用例名是 `delegate-*`（原文写作 `delegation-*`），新增的并行用例为 `delegate-parallel-*`。

## 必须验证

- 模拟测试（`internal/sim`）：重复回写、乱序完成、父 Run 中断时多个子 Run 的级联、父子删除的竞争、子 Session 已删除时的重新派发不复活。
- 删除不变量：复制出的工件随各自的 Session 删除，Janitor 级联删除父 Session 时，子 Session 中的副本一并删除。
- 权限：子 Run 无法经工件复制读到未被引用的父工件；白名单交集不变。
- 评测：新增并行委托的用例（`evals/delegate-parallel-*`），比较完成时间与结果质量；缓存命中列不退化。

## Considered Options

- **全部调用都并行推进（含设备与沙箱）**：收益更大，但设备离线挂起、审批与后台调用（ADR-0035）的交互要整体重做。先只放开委托，设备调用的并行另行评估。
- **父子共享工件（按委托树授权）**：不复制、省存储，但工件的可见性与删除要跨 Session 计算，违背"工件只对其所属 Session 可见"，删除父 Session 时还要判断子 Session 是否仍在引用。
- **子 Run 的结果在全部返回后一次写回**：实现简单，但一个慢的子 Run 拖住所有结果，而且需要一个跨 Session 的汇总点。

## Consequences

- 批准后修订 ADR-0031 的"当前能力边界"，更新委托设计、端侧 SDK 设计与调试控制台的验证场景（`scenarios.js`）。
- 投影要能表示一个 Run 中多个同时未完成的委托调用，递增 `session.ProjectionVersion`。

## 重审条件

- 批准、实施或放弃本提案时更新状态；
- 设备与沙箱调用也需要并行推进时，另立提案。

## 第一期实施记录（2026-11-16）

- **Worker**（`internal/runtime/worker.go`）：`advanceDelegations` 推进 `session.Run.DelegationFront`（从第一个未完成调用起相邻的委托）：逐个开始，都开始后检查各自的超时，再全部派发、写一次 `RunSuspended`，停放到最早的截止时间。挂起中的 Run 只在等未到期的已派发委托时（`awaitingDelegations`），被唤醒后幂等地重新派发、不写事件，再重新停放。投影的字段没有变，没有新事件，`ProjectionVersion` 不变。
- **上下文**：`runtime.Transcript` 把一条助手消息的调用结果按调用顺序写出，与完成顺序无关；结果按顺序到达时（此前的全部情形）输出不变。
- **HTTP**：Run 视图的 `waiting` 仍是第一个未完成的调用；同时等待多个已派发调用时另给出 `waiting_all`。
- **模拟测试**：sim Agent 的 `max_fanout` 取 2，模型偶尔整轮返回两三个委托；新增不变量 `checkFanout`（同一个 Run 同时已派发的委托不超过上限）与覆盖统计 `ParallelDelegations`。另加一种故障，把时钟拨到后台调用的截止时间之后，使后台调用到期不依赖随机分布。
- **端到端与控制台**：`TestParallelDelegation`（两个子 Run 同时运行、`waiting_all`、父日志中只有一次挂起）；控制台场景 `delegation-parallel` 用真实的两个子 Agent 同时提问，取代原先合成的第二个提问。
- **评测**：新增 `delegate-parallel-independent` 与断言 `same_turn`（同一条助手消息中一起发出）。
