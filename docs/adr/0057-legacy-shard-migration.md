# 存量分片迁移：在维护窗口内把旧数据迁离库 0

> **不实施（2026-11-15）。** 负责人决定在上线前删除旧格式 ID 的兼容（ADR-0051 的 2026-11-15 修订），不再有需要迁离库 0 的旧式 ID，本提案作废，保留为历史记录。迁槽只剩 ADR-0051 §5.4 的停写迁移。

> **方向已批准（2026-11-15），有前提，尚未实现。** 只有决定**保留**旧格式 ID 的兼容（库 0 回退、兼容清单）时，本提案才需要。系统尚未上线，[ADR 评审](../review/2026-11-14-adr-review.md) §2.7 建议先评估在上线前删除这部分兼容：删除后不再有需要迁离库 0 的旧式 ID，只需按 ADR-0051 §5.4 实现停写迁移工具，本提案作废。来源：评审 §3.5。

ADR-0051 §5 规定 P4 只支持新建单元，或全部槽位留在库 0 的既有单元，"把旧数据迁离库 0"是阶段缺口。原因写在 §5.3 的"保留的写入限制"：

- 旧 Session 下新产生的工件仍是旧式随机 ID，旧父 Session 的委托仍保持旧的派生身份；
- 静态的兼容清单只能列出迁移时已经存在的对象，定位不了这些**未来**的旧式对象；
- 所以仍可能产生这类对象的旧 Session 搬离库 0 后，不能恢复写入，也不能关闭它们所需的库 0 回退。

## 提议的决定

1. **先支持有维护窗口的迁移，不预先决定双写或在线迁槽。** 迁移在停写窗口内完成，步骤沿用 ADR-0051 §5.4：盘点并备份 → 停入口及全部写入者（Worker、控制器、Janitor）→ 迁移并校验 → 部署同一映射与格式版本 → 验证后恢复。
2. **解决"未来旧式对象"，三个候选择一，批准时决定：**
   - **A. 迁出的旧 Session 只读。** 迁移时关闭这些 Session（不再接受新输入），只允许读取、清理与删除。最简单，代价是用户的旧对话不能继续。
   - **B. 迁出后改用带槽位的新格式生成。** 迁出的旧 Session 此后产生的工件与委托使用新格式 ID（内嵌真实槽位），不再需要库 0 回退。代价是要改动生成语义，并保证旧派生对象的重试仍命中原对象（ADR-0051 §5.4"旧派生 Memory 和委托 Session 的重试仍须命中原对象"）。
   - **C. 在线目录。** 为未来的旧式对象维护一个在线定位表。最通用，但新增一个必须按 Session 删除、"先写后查"的存储（ADR-0015），ADR-0051 明确不做。
3. **回滚同样在停写窗口内进行**，恢复数据与映射的一致版本（ADR-0051 §5.4）。

## 待回答的问题（批准前须给出答案）

1. 选择 A、B 还是 C；若选 B，旧派生对象重试的定位怎样保证。
2. 停写窗口的时长预算：按目标环境的数据量实测，超出预算即触发 ADR-0028 / ADR-0051 的重审条件。
3. 迁移制品（兼容清单、迁移报告）含真实 EndUser 与对象 ID，它们的保留与退役（ADR-0051 §5.3）。

## 必须验证

- 唯一写入权：迁移前后任一时刻，同一键只有一个分片接受写入；
- 日志与队列一致：`eventlogtest.RunWaking` 的同事务提交在迁移后仍成立；
- 删除屏障：迁移过程中写入的删除记录生效，迁移后"先写后查"（`lifecycle.Recheck`）仍拦得住；
- 出站流连续：出站的 epoch、键与水位不倒退（ADR-0051 §9）；
- 恢复写入后新对象的位置与映射一致；
- 在 `internal/sim` 的差分测试中加入迁移前后的对比。

## Considered Options

- **上线前删除旧格式 ID 兼容**（评审的首选）：没有真实用户的数据，删除后整个问题消失。若采纳，本提案作废。
- **双写迁移**：不停写，但要处理两个分片同时接受写入时的冲突与回滚，ADR-0051 明确不做在线迁槽。
- **永远不迁出库 0**：已有单元的扩容只能靠新建单元，第一个单元的容量上限就是库 0 的容量。

## Consequences

- 若批准，修订 ADR-0051 §5 的"阶段缺口"，并更新[部署设计](../design/deployment.md)。
- 若评审 §2.7 的评估结论是删除兼容，本提案标为"不实施"。
