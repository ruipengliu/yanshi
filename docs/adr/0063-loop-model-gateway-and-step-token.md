# 外部循环经内核调用模型，每步请求携带平台签发的步令牌

> **2026-11-25 定稿；已实现（2026-11-25）。** 已实现：步令牌（`extloop.SignStep`、`VerifyStep`，登记的 `token_keys`）、内核模型端点（`extloop.Endpoint`，`POST /v1/loop/chat/completions`）、AgentDef 的 `loop.models`、启动检查（`cmd/yanshi/loops.go`、价格表）、评测替换 `loop.models`、`looptest` 的步令牌与模型检查（`-step-token`）、每步请求的 `models`、评测驱动外部循环（`yanshi eval -loop`）、参考适配按端点配置模型（`sdk/python`，2026-11-25）。没有声明 `loop.models` 的 AgentDef 照旧按 [ADR-0062](0062-external-loop-contract.md) 执行：外部服务自带模型，平台按步计量，自报用量不记录。来源：外部循环接入方式的回顾（2026-11-25，`looptest` 合入之后）。补充 ADR-0062，修订其 Consequences 中"平台不计量外部服务自己的模型用量"；修订 [ADR-0014](0014-business-line-signed-tokens.md) Consequences 中"yanshi 无需保存任何签名私钥"（第 2 条）。[m5 设计](../design/m5-inputs-triggers-loops.md) §7 与[模型调用](../design/model-calls.md)已同步（2026-11-25）。

ADR-0062 让业务线的服务决定 Run 的每一步，但外部服务自己调用模型，这部分完全在内核的治理之外：

- **计量与配额只看步数。** 平台按步计价（`usage.LoopPrice`），金额配额看不到外部服务消耗的 token；自报用量（`LoopStepResponse.reported_usage`）是外部服务填写的任意数字与模型名，ADR-0062 决定不记录。
- **换模型与评测失效。** 评测运行器对外部循环的 AgentDef 不覆盖模型（`internal/eval/runner.go` 的 `derive`），模型由业务代码决定；提供商的准入、限流与"已输出过增量的调用不重试"（`docs/design/model-calls.md`）也不覆盖这些调用。
- **章程 G9 的理由在这里同样成立。** ADR-0047 把单次调用放进内核，理由是"业务侧直连提供商，治理全部失效，换模型要改业务代码"；外部循环重新打开了这扇门。
- **外部服务无从确认请求来自平台、为谁而发。** 平台对外部服务的认证只有登记中的静态请求头（`extloop.Server` 的 `Headers`）。外部服务若要以用户的身份调用业务线自己的接口（如 Persona），只能相信请求中的 `end_user` 字符串。

`looptest` 已经要求被测服务能配置模型地址（ADR-0062 第 8 条，2026-11-25 的实施说明），把这个地址换成内核的端点，对通过套件的服务是一项配置改动。

## 决定

1. **内核提供 OpenAI 兼容的模型端点，只给外部循环用。** 端点接受 Chat Completions 请求（含流式与工具定义），经 `model.Gateway` 转给提供商：准入、限流、重试规则与内置循环相同。外部服务在框架里把 base URL 指向它，把步令牌（第 2 条）当作 API key：OpenAI 兼容的客户端以 `Authorization: Bearer` 发送 API key，框架不需要专门适配。端点的调用与 Run 的交互调用同类准入，所以另有进程内的合计并发上限（`-loop-model-concurrency`，须小于提供商的并发上限）与每步至多 2 个并发调用（2026-11-25 评审补充：没有上限时，一个外部服务凭一张令牌就能占满提供商、让其他业务线排队）。
2. **每步请求携带步令牌，以按循环登记的 HMAC 密钥签发。** `LoopStepRequest` 新增一个字段（向后兼容），内容是平台签发的短期令牌（HS256 JWT），声明业务线、Session、Run、Attempt、Turn、EndUser、AgentDef 与循环名，有效期与这一步的时限相同。
   - **密钥按循环登记各一组，与运行这个循环的业务线共享。** 密钥写在循环登记中，与 `headers` 一样从环境变量注入；令牌头带 `kid`，登记可列多把密钥：签发用第一把，验证接受全部。轮换分两次发布：先在所有进程加上新钥（排在后面），再置首；等旧令牌过期（一步的时限）后删旧钥（2026-11-25 评审修订：签发与验证在不同角色、各读自己的登记，一次发布里置首会让 worker 签出 gateway 还不认识的令牌；见[部署](../design/deployment.md) §9a）。没有选平台级的 Ed25519 私钥：ADR-0014 没有选"业务线服务端调用 yanshi 换取令牌"，理由之一是 yanshi 要持有签名私钥、成为高价值目标；一把平台级私钥泄露，所有业务线的步令牌都可伪造。按登记分开的共享密钥把影响限制在一条业务线的一个循环，而循环本身就由这条业务线运行，共享密钥不扩大它已有的信任。代价是验证方只能确认令牌出自"平台或持有这把密钥的一方"。
   - **ADR-0014 的修订：** yanshi 保存按循环登记的 HMAC 密钥，仍不保存能为业务线签发用户令牌或服务令牌的密钥；步令牌不被 yanshi 的其他接口接受。
   - **持有密钥的一方能签发任意声明**（2026-11-25 评审补充），验证方因此不全信令牌：有效期不得长于登记的一步时限（按 `exp - iat` 核对，`iat` 必填），EndUser 不得为空，令牌中的 AgentDef 须指向令牌所属的循环、且业务线的 `agents.allow` 允许它；密钥只能从环境变量注入。
   - **内核的模型端点只接受有效的步令牌**，只看签名、有效期与删除记录：Session 已有删除记录时拒绝（与 ADR-0062 第 7 条每步之前的删除检查一致，ADR-0015）；调用返回后再查一次，调用期间被删除的不把输出交给外部服务。不核对 Attempt 是否仍是 Run 当前的 Attempt：被接管的旧 Attempt 至多多用一步时限的调用，照常计量与计入配额，回答经 ADR-0062 第 2–5 条的提交规则丢弃；每次调用读一次日志会把模型调用的延迟与日志库的负载绑在一起。
   - **外部服务可以用同一把密钥验证令牌**，并转交给业务线自己的接口，证明"平台为这个 EndUser、在这个 Session 中请求了这一步"。业务线是否这样做由业务线决定。
3. **模型由 AgentDef 声明。** `loop` 下增加可用模型的列表；端点只接受列表中的模型，评测的模型覆盖替换这个列表，`make eval` 因此能像内置循环一样换模型评测外部循环。每步请求的 `models` 带上这个列表（2026-11-25 实施时补充）：外部服务从中选择、默认用第一个，不写死自己的模型，否则评测换模型后它的调用被端点拒绝。`loop` 与顶层 `model` 仍然互斥（ADR-0062 第 6 条）。
   - **列表是治理的开关。** 有列表的 AgentDef，循环须只经端点调用模型（第 6 条）。没有列表的按 ADR-0062 执行：自带模型、按步计价、评测不能换模型。业务线需要内核未接入的提供商时，先按[模型调用](../design/model-calls.md)的提供商准入在内核接入；接入之前这个 AgentDef 不声明列表。过渡期因此是显式的，从配置中可以数出还有多少循环在治理之外。
4. **经端点的调用照常计量。** 计为 `Kind="model"`，记在 Run 的用量范围（业务线、EndUser、AgentDef）下，在调用返回后计量（ADR-0019），计入金额配额。自报用量仍不记录：经端点的调用平台已经知道，不经端点的调用无法核实。
   - **按步单价保留**，价格表仍要求登记的每个循环有价格；只经端点调用模型的循环可以显式写 `per_step: 0`。不按 AgentDef 是否声明模型列表自动置 0：第 6 条只是登记要求，平台不能据此认定服务没有别的成本。
   - **配额在两处执行。** 每步之前照常检查（`callModel` 在解析外部循环之前检查），超出时 Run 挂起、配额恢复后继续。一步之内用完配额时，端点返回 429 与区别于提供商限流的错误码，这一步失败、计一次模型错误；下一步之前的检查随即让 Run 挂起，不会累积到 `MaxModelErrors`。外部服务不应在这一步内重试配额错误。
   - **缓存命中照常上报。** 端点上报的缓存命中计入用量。评测报告的 token 与"缓存命中"列读日志中 AssistantMessage 的用量，外部循环那一步没有模型用量；评测经端点的用量钩子（`extloop.Endpoint.OnUsage`）按 Session 把经端点的调用计入 Run（2026-11-25 更正：原文称"按用量合计、自然计入"，与评测的实现不符）。请求前缀是否稳定由外部服务的框架决定，"请求前缀保持稳定"的不变量对外部循环是建议，不是平台的保证。
5. **端点不做内容安全检查。** 外部服务收到的上下文已经过输入检查；模型的输出只经这一步的回答到达用户与日志，回答照旧在写日志之前检查（ADR-0021）。
6. **声明了模型列表的循环应只经端点调用模型。** 平台管不到外部服务自己的代码（ADR-0041），这一条是登记的要求，不是技术保证；`looptest` 扮演这个端点，检查服务把步令牌转给了模型调用。

## Considered Options

- **维持现状（自带模型、按步计价）**：最简单，治理缺口如上。
- **记录自报用量并计入配额**：数字与模型名都由外部服务填写，无法核实；自报的模型名进用量记录，而用量记录不随 Session 删除；也解决不了换模型与评测。
- **复用单次调用（ADR-0047）**：单次调用是声明式的提示词模板，输入是文字，没有多轮消息与工具定义，不适合 Agent 框架。
- **由平台代为调用模型**（外部服务回答"请用这些消息调用模型"）：等于把框架退回内置循环，失去外部循环的意义。
- **只做步令牌、不做模型端点**：解决身份问题，治理缺口仍在。
- **平台级 Ed25519 私钥签发步令牌**：外部服务可以确认令牌确由平台签发，但平台持有一把泄露即影响所有业务线的私钥（ADR-0014 正是为避免这一点而选了业务线签发）；见第 2 条。
- **每次模型调用核对 Attempt 是否当前**：省下至多一步的费用，代价是每次调用读一次日志；见第 2 条。

## Consequences

- 内核多一个对外端点，每个循环登记多一组 HMAC 密钥（轮换见第 2 条）；`loop.proto` 增加字段，AgentDef 的 `loop` 增加模型列表，`ProjectionVersion` 不受影响（令牌不写日志）。
- `looptest` 的假模型改为扮演这个端点，增加"转交步令牌"的检查；参考适配（ADR-0062 第 8 条）按端点配置模型，因此在本 ADR 实现之后做。
- 评测可以对真实的外部循环服务（或参考适配）运行并换模型，ADR-0062 Consequences 中"以回放式的假循环固定"可改为按需。
- 计量报表中外部循环的模型用量与内置循环同口径；"自报用量是否记录"的问题随之取消。

## 重审条件

- 外部服务普遍需要内核未接入的模型提供商，端点成为接入的主要障碍；
- 端点的延迟或可用性成为外部循环步时延的主要来源；
- 出现托管的三方开发者需要外部循环（ADR-0062 第 7 条的重审条件），令牌的信任范围须重新评估；
- 业务线需要区分"平台签发"与"持有共享密钥的一方签发"（第 2 条），改用平台的非对称密钥。
