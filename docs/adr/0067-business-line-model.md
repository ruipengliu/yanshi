# 业务线是内核之上的保护域：清单、定义命名空间与契约

> **方向已批准（2026-11-28），待定稿、未实现。** 设计见 [业务线模型](../design/business-line-model.md)（§2–§6）。实施前先回答下文"待回答的问题"；实现之前照旧按 [ADR-0060](0060-business-line-definition-access.md)、[ADR-0014](0014-business-line-signed-tokens.md) 与现有配置目录执行。

内核要承接多条业务线，但"业务线是什么"至今没有规范，只能从 xinli 的做法倒推：接入一条业务线的配置分散在 `businesslines/*.yaml`（`auth.BusinessLine`）、`mcp/*.yaml`（`internal/mcpcap`）、`-agents` / `-oneshots` 多目录与 `releases.yaml`、`-loops` 目录（`cmd/yanshi/serve.go`）；AgentDef 与 Oneshot 的名字是全局命名空间，归属只靠 `allow` 列表（ADR-0060），两条业务线不能各有一个同名定义并各自发布；业务线调用内核的约 46 个 HTTP 路由（`internal/httpapi`）请求与响应多为手写 JSON、没有机器可读的 schema，xinli 自己手写客户端（`apps/xinli/kernel`）；内核调用业务线的 MCP 扩展（`_meta`）只有文字描述（[旁听](../design/captures.md) §12），Persona 自行复刻（`persona/mcpserver`）。

## 提议的决定

1. **业务线是内核之上一个不受信任的保护域。** 主干参照微内核与能力安全：内核独占执行语义、来源推导、内容安全、审批、配额与物理删除；业务线只能经内核开放的接口与声明影响执行，权限只收紧不放大。Session 与 Run 内部沿用持久化执行的语义（ADR-0004、ADR-0062）；打包与导出借用应用清单的语义；actor 只作理解 Session 的辅助视角，不进规范（设计 §2）。
2. **业务代码不进入内核的提交路径。** 内核内部只接受业务线的声明（策略、白名单、定义）；业务线的代码只在边界上运行：提交输入之前、MCP 调用、外部循环的一步、上下文策略（ADR-0056）、消费出站流。不提供进程内钩子与沙箱化函数；嵌入式 WASM 纯函数留作远期选项（设计 §3）。
3. **一条业务线一个目录。** 目录中有一份清单（身份、策略、MCP 与外部循环登记、导出与引用、可选的专属 Worker 池）、本业务线的 `agents/` 与 `oneshots/`（各自的 `releases.yaml`）、`evals/`。价格表、分片表、步令牌密钥与单元出网白名单仍归单元运维，不进清单。清单配 JSON Schema 与离线校验命令，与启动校验共用代码。
4. **目录即归属，规范名 `<业务线>/<名>`。** 定义只能出现在所属业务线的目录中；业务线只能使用自己的定义、单元运维维护的共享定义与它引用的其他业务线导出（ADR-0069）。新写入日志的定义名用规范名；旧的无前缀名作为别名继续解析，历史日志照常重放。`allow` 列表在过渡期保留，之后由"目录即归属 + 引用"取代（修订 ADR-0060）。
5. **入向契约在 `proto/`。** 业务线调用内核的 HTTP 路由，其请求与响应补上 `proto/` 中的消息定义，沿用 ADR-0006 的工具链与 `buf breaking` 兼容检查；JSON 线上格式用 `protojson` 的 `UseProtoNames` 保持现有的 snake_case（事件接口已如此，`internal/httpapi/httpapi_events.go`），不改变线上格式。二进制体与 SSE 路由在契约文档中单独说明。由 proto 生成官方服务端 SDK（先 Go、后 Python；封装令牌刷新、幂等键、错误码与重试、出站流游标的恢复），xinli 迁移到同一 SDK。入向不另建一致性套件：它的行为由内核自己的 `authz_test.go`、e2e 与 `internal/sim` 保证。
6. **出向接口各配黑盒一致性套件。** 内核调用、业务线实现的接口：外部循环（已有 `internal/extloop/looptest`）、MCP 扩展、上下文策略、评测适配（ADR-0070）。MCP 扩展先用语言无关的 JSON Schema 冻结 `yanshi/*` 的 `_meta` 线上格式，再由各语言 SDK 封装类型，不以内核的 Go 包导出。
7. **仓库中有一条最小参考业务线。** 不用 Persona，只用外部循环与 MCP，覆盖全部接口，接入 `make check` 与 `internal/sim`；它是规范的可执行示例、出向套件的被测对象与新业务线的脚手架。

## 待回答的问题（定稿前须给出答案）

1. 业务线目录放在哪里（仓库内的 `apps/<业务线>/`，还是部署配置中的独立目录），以及与 `deploy/k8s` 的 overlay 怎样对应。
2. 规范名写入哪些事件字段，`State.Agent` 的投影是否同时变化（若变，递增 `session.ProjectionVersion`）。
3. 共享定义的维护与发布方式，以及业务线能否覆盖共享定义的版本。
4. 46 个路由按什么顺序补 proto（建议先出站流与生命周期相关的路由）。
5. 参考业务线的业务内容与放置位置。

## 必须验证

- 旧的无前缀定义名在历史日志重放、快照与灰度选择中行为不变。
- 补 proto 后，现有 xinli 客户端的请求与响应字节级兼容（对现有路由录制请求与响应作回归）。
- 依赖检查：参考业务线与 xinli 不 import `yanshi/internal/`。

## Considered Options

- **SaaS 应用平台（Slack、Shopify）作主干**：清单、权限与卸载语义好，但预设平台统一身份与 webhook 推送，与业务线自签令牌（ADR-0014）、出站流拉取（ADR-0046）不符；只借用其清单与导出语义。
- **Actor 作主干**：业务线是上百万 Session 的治理域，不是一个 actor；私有内存状态与任意消息，与事件日志真源、来源推导冲突。
- **入向契约用 OpenAPI 3.1**：生态成熟、能直接描述二进制体与 SSE；但与现有 `proto/` 契约是两套工具链与兼容检查，网页 SDK 已从 proto 生成。负责人选择 `proto/`（2026-11-28）。
- **维持现状、等第二条业务线**：ADR-0043 的 2026-11-14 修订明确，内核既有职责的完善不以第二条业务线落地为前提；规范由第一条业务线倒推，会把它的惯例写成通用规则。

## Consequences

- 新业务线按一个目录、一份 SDK、一组出向套件接入；xinli 的接入方式随之迁移，`apps/xinli/kernel` 的手写客户端被生成代码取代。
- 46 个路由补 proto 是主要工作量；线上格式不变，但每个路由要录制回归。
- 定义名从全局命名空间变为按业务线归属，涉及日志字段与灰度选择，必须保持历史重放。

## 重审条件

- 业务线超过数十条，或开放三方自助上架，GitOps 加评测门禁不够用（考虑控制面数据库）；
- 某个高频、零 I/O 的纯变换因进程外往返突破延迟目标（重审"业务代码不入核"，评估 WASM）；
- 补 proto 的路由出现无法用 `protojson` 保持兼容的线上格式；
- 第二条业务线接入时，清单字段或参考业务线无法覆盖它的接入需求。
