# 业务线经拉取式出站流获取事件

> **只在一条业务线（xinli）上验证过**（2026-11-14）：机制按通用设计，需求与使用目前都来自 xinli；第二条业务线接入时按重审条件复核（ADR-0043 的修订）。

业务线在没有在线客户端时仍须可靠发现回复、提问与审批，维护跨 Session 收件箱、转发渠道消息，并在服务端停机后继续消费。当前线程的 SSE 足以提供实时体验，但业务侧无法与内核日志原子提交接收记录；这才是出站流必须在内核提供的理由。领域事实是否接受由业务侧记录，不由 Run 完成推导。

## 决定

（设计见 [M7 内核补充](../design/m7-kernel-primitives.md) §6）

- GET /v1/outbox 使用服务令牌，按业务线、按 PostgreSQL 分片的游标长轮询，只返回平台登记的七种信封：run_completed、run_failed、question、approval_requested、background_settled、session_closed、session_deleted。
- **只含 ID 与运行元数据**，不含正文或调用参数；内容按 Session 与事件序号读取。出站流不成为新的内容存储。
- 普通信封在 `session.Store.commit` 统一派生，覆盖 pglog 的 Append 与 AppendAndEnqueue 两条路径，与事件同事务提交。删除信封在 `pglifecycle.Deletions.Mark` 写删除记录的同一事务产生，表示逻辑删除；没有 EndUser 与 Event seq，使用稳定独立信封 ID。
- 每行显式保存 xid8，读取在同一快照中只返回低于 xmin 的行，按 (xid8, id) 排序。版本化不透明游标含业务线、分片、流世代、过滤版本与位置；空结果返回安全进度。长轮询周期复查，不只依赖 NOTIFY。
- 至少一次投递，消费方按信封 ID 去重，持久保存游标与接收记录。普通行随 Session 删除；删除信封独立保留。淘汰以“安全水位及首次观察时间”检查点满 72 小时为准，分批清理完成才推进保留地板，不以插入时间或表内最小行推断过期。
- 游标过期明确报错。应用先取各分片安全起点 H，稳定枚举自己的账号及其 Session，按已存 seq 补读；未列出的已知 Session 须以删除信封或逐 ID 的 404 确认。最后从 H 追赶去重，H 过期则重来。不新增内核目录或删除枚举接口。

## Considered Options

- **每个 Session 一条 SSE**：现状，连接数随 Session 数增长。
- **消息队列（Kafka 等）**：新增基础设施组件，私有化部署多一个依赖（章程 §3 不重造、ADR-0001）。

## Consequences

- 新出站存储通过内存与 PG 共用的一致性套件，普通信封在 `app.SessionData` 登记；删除信封仅按出站保留地板淘汰。
- 长事务会拖住水位；监控水位滞后、最老事务、消费者延迟与保留空间，并配置事务超时约束。
- 内核保留 Connection 与 SSE；P4 产品经 BFF 代理 SSE，出站服务后台收件箱与渠道转发，不承担实时增量。

## P4 修订（2026-10-29，Q105、Q106）

依据[整体架构](../design/persona-architecture.md) §13 Q105、Q106，并按 Q117 补齐恢复分页、按 Q118 限定分片故障口径。适用范围收窄为以上七种通用运行信封；旁听的变化与删除闭环由业务线负责。提示也只用轮询与数据库通知，不增加外部回调投递。

现有 Session 列表增加按不可变 session_id 的恢复分页模式，包含已关闭 Session，默认最近输入排序不变。列表可能暂留逻辑删除项或创建失败的空索引，读取 404 可确认不可访问；“未列出”本身不能判删。恢复承诺是选定事件与当前可访问状态收敛，不保证补发全部历史通知。此前将当天归集归因于 Run 完成的描述由领域变化协议取代（Q99），业务接受与执行终态分别跟踪。

## 迁槽与游标（2026-11-22 补充，评审 A5）

来源：[架构评估评审](../review/2026-11-22-architecture-evaluation-review.md) §5 A5、§6 R7。整片搬迁（ADR-0051 §5.4）用物理复制，`xid8`、流世代、游标与地板原样保留，不涉及本节。本节只约束改变槽位表的停写迁槽；迁槽工具仍按 ADR-0051 §5.4 推迟，本节是它实现时必须遵守的契约。

**决定：迁槽即换代，游标不映射。**

1. **出站行不搬。** `xid8` 只在本库的事务号空间内有意义：带原位置写入目标分片，会落在目标的 `xmin` 之上或地板之下，导致跳读、漏读或被误清理。被迁槽位的出站行（普通信封与删除信封）在数据迁移校验通过后从源分片删除；留着会违反"随 Session 删除"（迁移后删除按新槽位路由到目标分片，源分片的残留行无人清理）。
2. **先追平再迁移。** 停入口写入与全部写入者之后、迁移数据之前，出站流保持可读，等各业务线消费方在受影响分片上读到空结果（没有新写入，安全水位不再前进）。这样停写前产生的信封（包括只有出站流才有 `reason` 与 `deletion_request_id` 的删除信封）都已送达。消费方故障而无法追平时，运维可以继续迁移，代价见第 4 条。
3. **受影响分片全部换代。** 迁移校验通过、切换槽位表之后、恢复准入之前，对每个源分片与目标分片执行换代（`RotateEpoch`：新的流世代与游标密钥，地板与检查点重置）；槽位未变的分片不换代，游标继续有效。旧游标在受影响分片上得到 `410 outbox_epoch_changed`，消费方走本 ADR 已有的游标过期恢复（取各分片安全起点 H，按 `/v1/outbox/shards` 的新槽位表枚举并补读，再从 H 追赶），不新增协议。目标分片也必须换代：否则消费方在该片停留在 Follow，迁入的 Session 不会被补读。"切换槽位表之后"指全部进程（包括只读的出站与会话读取接口）都已报告新的 `Identity()`：滚动部署未完成就换代时，仍按旧表回答 `/v1/outbox/shards` 的进程会给出新世代的 H 与旧槽位，消费方带着新游标进入 Follow，迁入的 Session 不再被补读（2026-11-23，Quint 模型的反例）。源分片因迁出而没有槽位、随之移出配置（合并）时同样换代，它的库在下线前仍在：回滚恢复原部署制品时槽位表摘要与移除前完全相同，没看到中间那张表的消费方（例如 xinli 当时停机）核对不出变化，只能靠世代不同让旧游标失效（2026-11-23，Quint 模型的反例）。
4. **恢复的承诺不变。** 与"恢复承诺是选定事件与当前可访问状态收敛，不保证补发全部历史通知"（P4 修订）一致：没有追平就迁移时，未送达的删除信封不再补发，消费方经逐 ID 的 404 确认删除，拿不到删除原因；未送达的普通信封由按 seq 补读覆盖。
5. **顺序固定**：停写 → 追平 → 迁移并校验（含删除源分片的出站行）→ 切换槽位表（全部进程报告新的 `Identity()`）→ 受影响分片换代 → 删除源分片上被迁 Session 的数据 → 恢复准入。回滚同样停写，回到旧槽位表后再次对受影响分片换代。
6. **源分片的 Session 数据删在切换完成之后、恢复准入之前**（2026-11-23，Quint 模型的反例）。提前到迁移时删除，按旧表路由的逐 ID 读取得到 404，xinli 恢复把它记为 Gone，此后不再补读该 Session；不删除，恢复准入后 Janitor 只按新槽位清理目标分片，源分片留下残留。

**不采用：**

- **游标映射**（迁移时把旧游标换算成目标分片的位置）：槽位合并或拆分时不是一对一；把源行以新 `xid8` 写入已有消费方的目标分片会造成重读与乱序，源与目标的 72 小时地板也无法对齐。
- **固定逻辑分区**（ADR-0051 评审 R7：每个分区整体落在一个物理分片，以分区为搬迁单位）：去掉 `xid8` 后的分区内序号在并发提交下会跳号漏读，仍要每分区的可见性屏障；消费契约、地板与检查点都要按分区重做。迁槽目前是罕见的运维事件，不值得为它改日常读取路径。

**迁槽工具实现时须一并完成**（现在不做）：

- 运维入口：换代目前只有存储层的 `RotateEpoch`（`internal/outbox/pgoutbox/stream.go`），没有命令行入口；
- 消费端：已补上（2026-11-23）。分片被移除或合并时（`/v1/outbox/shards` 列出全部配置分片、失联的也列出，不再列出即已移出槽位表），xinli 的发现循环停掉该片的恢复与出站循环，不再对 `404 outbox_unknown_shard` 重试，并把该片的恢复记录重置回 Heads；同一编号以后再加入时从新的 H 对账。只剩分片 0 时按单库消费，原各分片的记录同样重置（`delivery.Consumer.Retire`）。单库与各分片的轮次各自计数，只有单库的确认阶段读 Session 的 `SeenRound`，分片的轮次因此记 0：否则切到单库后，单库一轮的编号可能与某分片的轮次相同，确认阶段跳过迁移中被删除的 Session，它的删除再也得不到确认。迁出的 Session 由接收槽位的分片覆盖：它换代，或下面的摘要核对使它重新对账。xinli 停机期间被移除的分片，记录留在原阶段、不再被读取；同一编号再加入时，新建的库世代随机生成，旧游标得到 410；同一个库则靠第 3 条对它的换代，摘要核对不能代替：回滚到原部署制品时摘要与移除前相同。Quint 模型含合并（源分片没有槽位时移出配置）与回滚时以同一编号重新加入：重置被移除分片的进度不丢信封，移除后与重新加入后都能追平；被移除的源分片与目标分片都漏换代时，有摘要核对也会丢信封（摘要 ABA 变体）。`identity` 的核对：取 H 时记下槽位表摘要，每秒一次的发现循环看到摘要变化即把该分片的进度重置回 Heads（`delivery.Consumer.ReconcileIdentity`）。漏换代时，或滚动部署未完成就换代、恢复取到旧槽位时，它是第二道防线：部署完成后摘要统一，消费方按新槽位重新对账（Quint 模型中，有这道核对时漏换代、先换代后切表、部署未完成就换代三种错误下信封仍收齐；它不弥补源数据删早、残留或追平顺序的错误）；
- 验证：迁槽加双边换代的集成测试，以及在 `internal/sim` 中注入迁槽后检查"信封不丢、删除后不复活、源分片无残留"。步骤顺序已有 Quint 模型（[`docs/formal-verification/a5-slot-migration`](../formal-verification/a5-slot-migration/slot_migration.qnt)，在 `make verify` 中运行），工具实现时再补上实现轨迹与模型的对照。
