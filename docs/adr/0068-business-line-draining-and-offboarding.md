# 业务线的停用与卸载：可逆的排空，不可逆的清除

> **方向已批准（2026-11-28），待定稿、未实现。** 设计见 [业务线模型](../design/business-line-model.md) §8、§9。实施前先回答下文"待回答的问题"；实现之前，下线一条业务线须由运维逐个按 EndUser 删除，不得只删除配置。

现在业务线下线没有机制。删掉 `businesslines/<业务线>.yaml` 只会让它的令牌失效，数据不会随之清理：Janitor 的保留策略只遍历已配置的业务线（`internal/janitor/janitor.go` 中 `Retention` 的循环），配置删除后其 Session 不再按保留期清理，只有设了绝对删除期限的仍会被删；Memory、Grant、出站流、用量没有按业务线整体删除的操作。这与"存放 Session 数据的地方都必须能被删除"（ADR-0015）相悖。

## 提议的决定

1. **生命周期状态。** 业务线有状态 `active`、`draining`、`offboarding`、`purged`，写在清单中（ADR-0067）。`active ⇄ draining` 可逆；`draining → offboarding` 须显式确认，不可逆；`offboarding → purged` 由清理完成驱动。
2. **停用（draining）按操作检查，不靠拒绝令牌。** 令牌校验是无状态的（`internal/auth/auth.go`），分不清新旧令牌；拒绝服务令牌会堵死出站流的排空与删除查询，也拦不住无令牌的定时触发与不经业务线令牌中间件的步令牌（ADR-0063）。停用时拒绝：新 Session、新 Oneshot、新的入站跨业务线委托、定时触发与外部循环的新步；存量 Run 收尾；读接口、出站流、删除与用量查询保持可用；该业务线参与的跨业务线 Grant 立即失效。
3. **卸载（offboarding）写持久的业务线删除屏障。** 屏障存放在控制库（库 0），与 EndUser 删除屏障同理（[M7 内核原语](../design/m7-kernel-primitives.md) §12）；全部写入入口按"先写、后查"复查屏障并撤回迟到写入（同 `lifecycle.Recheck`）；同时撤销该业务线的公钥。
4. **Janitor 按业务线清理，不依赖保留策略配置。** 按分片分批删除该业务线的全部 Session（复用 `app.SessionData` 与委托子 Session 的删除），并清理按 EndUser 分片、主键含业务线的数据：Memory、Grant（含对方业务线持有的、涉及本业务线的授权）、档位、同意、Node 与 Inbox、推送登记。每个事务只涉及一个分片键（ADR-0028）；进度可查询、可恢复。
5. **用量匿名化保留，不物理删除。** 按 ADR-0019，用量在删除后仍须可核对：EndUser 改为匿名值，保留到 `-usage-retention` 期满。出站流的删除信封按出站保留规则淘汰（[M7 内核原语](../design/m7-kernel-primitives.md) §6）。
6. **清理完成才允许删除配置。** 全部清理完成后进入 `purged`；启动时发现有业务线在到达 `purged` 前被删除配置，拒绝启动。
7. **应急字段热加载。** 停用开关、配额、公钥追加、`allow` 收紧与 `releases.yaml` 一样以快照方式热加载（失败保留旧快照），不必滚动重启即可止损；定义文件、MCP 与外部循环登记、令牌密钥、价格表仍走滚动发布。
8. **合规紧急时停用期可以为 0**，但仍须两步确认：先进入 `draining`，再确认进入 `offboarding`。

## 待回答的问题（定稿前须给出答案）

1. 屏障与 EndUser 删除屏障是否共用一张表与一套复查代码；控制库不可用时写入入口的行为（失败即拒绝）。
2. 卸载的清理顺序（Session 与按 EndUser 的数据谁先），以及与 `lifecycle.Recheck` 的交互，需写进 Quint 规约并运行 `make verify`。
3. 停用期间存量的挂起 Run（等待审批、提问、设备结果）怎样收尾：等待超时、直接取消，还是保留到卸载。
4. 跨业务线委托（ADR-0069）中，被卸载业务线名下的子 Session 与调用方父 Session 的关系：子 Session 删除后父调用得到什么结果。
5. 停用状态的读取方（网关、Worker、Janitor 各自持有快照）不一致的窗口是否可接受。

## 必须验证

- `internal/sim` 的删除不变量覆盖业务线卸载：卸载完成后不存在该业务线的 Session 数据、Memory、Grant、Inbox；迟到写入被撤回。
- `make verify`：规约覆盖业务线屏障与复查顺序。
- 停用期间出站流可以排空，删除与用量查询可用。

## Considered Options

- **停用即拒绝该业务线的全部令牌**：实现简单，但堵死排空与删除查询，且拦不住定时触发与步令牌。
- **删除配置即视为下线，由保留策略兜底**：保留策略只遍历已配置的业务线，正是现在的漏洞。
- **卸载时物理删除用量**：违反 ADR-0019 的对账要求。
- **只提供运维脚本逐个 EndUser 删除**：没有屏障，删除期间的迟到写入会复活数据；也没有完成状态可查。

## Consequences

- 下线一条业务线是可查询进度、可恢复的过程，而不是删除一个文件。
- 写入入口多一次屏障复查（与 EndUser 屏障同一路径）。
- 应急字段可以在不重启的情况下止损。

## 重审条件

- 业务线卸载的清理量使 Janitor 的分批清理超出可接受时长（考虑整库或整分片下线）；
- 法规要求卸载时连同匿名化用量一并删除；
- 业务线需要"导出后卸载"的平台级数据导出能力。
