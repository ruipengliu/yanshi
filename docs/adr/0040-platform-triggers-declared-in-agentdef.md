# 平台按 AgentDef 的声明触发 Run

> **本 ADR 不实施**（2026-11-14）。它唯一的触发方式"流上静默"已由 ADR-0050（现整合进 [ADR-0052](./0052-attested-results-and-provenance.md)）取消：原文在业务线，静默由业务线判断后提交整理指令；按钟点的定时见 [ADR-0045](./0045-schedules-in-the-kernel.md)。代码中没有触发的实现。仍然有效的保证已迁入 ADR-0045：停放复用 ADR-0035 的机制；来源是平台、客户端不能伪造标记、写入闸门不把它当作依据、准入与配额照常。第 4 条中"工作类别为后台"没有实施，定时开启的 Run 按 ADR-0029 照常分类。

白天的整理由业务线服务端定时提交"整理交谈"（[旁听业务线 xinli](../design/xinli-captures.md) §2）。每条业务线都要自己写定时任务、自己判断有没有新内容；固定间隔的提交要么来得太晚，要么在没人说话时空转。平台本来就知道最后一次采集是什么时候写入的。

## 决定

AgentDef 可以在流上声明触发：有未读的采集、且最后一次写入后静默了 `quiet`，平台就开启一个 Run，输入是声明中的固定文字。

1. **只在空闲时触发。** Session 未关闭、没有活跃的 Run 时才判断；同一流上，最后一个 Capture 的序号没有前进就不再触发，Run 失败后不立刻重试。
2. **按写入时间算静默期。** 用服务端的写入时间，不用设备时钟。
3. **唤醒沿用后台调用的做法**（ADR-0035）：采集使流从"无未读"变为"有未读"时在同一事务中入队；Worker 空闲时停放到最早的截止时间，到期写入带触发标记的 `RunRequested`。
4. **来源是平台。** 触发的输入不是用户的话，写入闸门不把它当作依据；客户端提交的输入不能带触发标记。准入与配额照常，工作类别为后台。
5. **只有静默触发。** 按钟点的定时（每晚整理）仍由业务线提交：一天的边界与时区是业务线的概念。

这修改了 ADR-0037 中"跨 Session 编排都放在业务线"的范围：触发只在本 Session 内开启 Run，不跨 Session 写入，跨 Session 的编排仍在业务线。ADR-0036 中"Capture 不开启 Run"仍然成立：一批采集不开启 Run，开启的是声明中、按静默期合并后的一次整理。

## Considered Options

- **维持业务线定时提交**：内核不变，但每条业务线重复实现，且不知道何时真正有新内容。
- **每批采集都开启 Run**：ADR-0036 已否决，成本与语义都不成立。
- **按设备的说话时间算静默期**：与"进行中的交谈"的判断一致，但设备时钟不可信，断网后补交的旧批会立刻触发。
- **平台提供通用的定时调度**（cron）：功能更全，但要知道 EndUser 的时区与一天的边界，还要跨 Session 创建，越过了平台与业务线的边界。

## Consequences

- 每段交谈至多开启一次整理；没有新内容时不开启 Run，不调用模型。
- Worker 空闲时的分支多了一种截止时间；模拟测试须覆盖"同一序号至多触发一次"与崩溃前后不重复、不遗漏。
- 触发失败后要等新的采集或深夜的整理，白天的承诺可能晚到；这是有意的取舍，避免在配额或配置错误时反复消耗。
