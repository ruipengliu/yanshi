# 旁听原文在业务线，内核只采信结构化片段并由平台推导来源

旁听的内核规则分散在四条互相修订的 ADR 中：ADR-0036（只收文字、按说话人区分信任）、ADR-0037（按每日 Session 分级保留）、ADR-0039（来源由平台推导、按流登记）、ADR-0050（原文移到业务线）。后者修订前者，但前者的正文没有改：ADR-0036 仍写"读过 Capture 的 Run 一律经过注入判断""注入判断与高风险审批不依赖标签"，而现行实现并非如此，只在 ADR-0050 的补记中说明（[ADR 评审](../review/2026-11-14-adr-review.md) §2.2）。Agent 按正文行事，会把一条不成立的兜底当作不变量继续扩展信任。

本 ADR 把仍然有效的内核规则整合成一处，并如实写出现行的安全边界。它不改变任何既有语义；各条款的去向见文末附录的对照表。业务部分（每日工作 Session、归集到 Project）迁至 [xinli ADR-0001](../../apps/xinli/docs/adr/0001-daily-work-sessions-and-projects.md)。设计细节见 [旁听：attested 页与渲染器](../design/captures.md)。

## 决定

1. **只收文字。** 全天佩戴的录音外设经业务线的 HostApp 接入；音频、转写与声纹识别都在 yanshi 之外完成，yanshi 只见到转写后的文字与结构化的说话人。声纹是不属于任何 Session 的生物特征，Janitor 无法按 Session 删除它（ADR-0015），所以"只留文字、不留原声"由边界保证，而不是靠"转写完即删"。外设不是 Device，也不是 Node。非文字的采集，每一种另立 ADR。

2. **原文存放在业务线。** 业务线（xinli 中是 Persona 的库）保存原文，负责分页、时段、进行中判断、处理进度、纠错与擦除，保存变更集与推进处理进度在同一个本地事务中。内核不保存原文本体；内核日志中只有 Run 读过的页的副本（见第 6 条）。

3. **内核只采信同一业务线登记的结构化页。** MCP 登记 `attests_speakers: true` 的 Server（`internal/mcpcap`），只在与 Session 同一业务线时被采信。它返回**结构化的页**：片段的引用、说话人、说话时间、文字、可选的 `speaker_ref`，以及时段边界、是否进行中、下一页游标等元数据；**不返回给模型看的文字**。Worker 用内核的 `captures` 渲染器（`internal/capture`）把页渲染成文字与 `ContentBlock.capture`，并在 ToolResult 上记下平台写入的 attested 标记。
   - 写入限制在 service 中拒绝、在 `State.Apply` 中再校验一次（ADR-0039 的做法）：capture 块只能出现在带 attested 标记的 MCP 结果中，客户端提交的输入不能带 capture 块。旧日志中内置 `captures` 工具的结果仍可通过校验，只为重放保留（`internal/session/state_apply.go` 中 `hasCapture` 一处的注释）。
   - 页由平台渲染，结果中没有业务线写的文字。所以页头不会被算作外部内容而收紧来源，业务线写的文字也不会被洗成可信内容；模型看到的文字由同一个渲染器生成。
   - 渲染与分页依赖的平台参数（结果预算等）经 `_meta` 交给业务线。
   - `cite_captures` 只认 attested 结果中的片段，用于引用与说话人核对。

4. **来源由平台推导，映射固定且封闭。** 每段内容的来源（本人、他人、外部、平台、模型）是"事件 + 内容块"的纯函数（`session.Provenance`）。写入闸门、注入判断、`cite_captures` 与给模型看的标注都只用它，内容块上不存来源字段。旁听中唯一推导不出的是说话人，它是结构化字段，只能经第 3 条的 attested 结果写入。映射是：
   - 佩戴者（本人）的片段算用户原话（`FromUser`）；
   - 他人的片段合成一段，算他人发言（`FromOther`），与外部内容一样进入写入闸门与注入判断。

   业务线只提交证据字段，不能配置映射，也不能让内容被推导为平台来源。理由有两条：第一，映射直接决定 Memory 写入是否免审（`internal/session/provenance.go`、`internal/runtime/memgate.go` 的 `grounded`），交给配置会扩大授信；第二，旧事件若按当前配置解释，回放结果会随配置改变，违反 ADR-0004。**平台校验了结构，不代表说话人标签必然真实**：标签的正确性由业务线负责，标错的后果见第 8 条。

5. **写日志前审核。** attested 结果在写日志之前送内容安全检查（ADR-0021）。整页送检，被拦下时逐段复核，违规片段以占位写入；提供商故障时整个结果写为错误（fail closed）。第一版不缓存审核结果，重读即重审。

6. **不开启 Run，不自动进入上下文。** 旁听不是对 Agent 说的话，不开启 Run。Run 由明确的输入开启：用户的提问、业务线提交的整理指令，或平台的定时（ADR-0045）。旁听也不自动进入 Transcript，由 Agent 经业务线的工具按页读取：一天的转写可能超出上下文窗口，也会破坏请求前缀的稳定。

7. **保留与删除（内核部分）。**
   - **Retention 可以按 AgentDef 覆盖**（`lifecycle.Retention` 的 `agents`）：同一业务线中，短期保留的工作 Session 与长期保留的 Session 并存。未覆盖的 AgentDef 沿用业务线的 Retention。
   - **按 Retention 到期删除 Session 时，保留由它写入的 Memory**；EndUser 主动删除（删除对话、注销账号）时照旧一并删除。这修改了 [Memory 设计](../design/m4-memory-grant.md) §9 第 3 条：那一条的本意是尊重用户的删除意图，到期清理不是用户的意图。
   - **绝对删除期限。** 创建 Session 时可以给出 `delete_at`（只有服务令牌可以设，须晚于现在），到期以 `retention` 删除并保留 Memory。擦除后重建的工作 Session 继承原来的期限，重建与重读都不延长原文副本在内核日志中的寿命。Retention 是兜底。
   - **擦除即删除工作 Session。** 业务线删除一段原文时，在一个事务中删除原文、写墓碑、按依据级联派生对象，并记下"删除当天工作 Session"的待办；编排器之后幂等地中断并删除内核中的工作 Session，删除原因为 `erasure`，保留该 Session 写入的 Memory。内核提供删除进度的只读接口，以及按 Session 列出它们写入的有效 Memory 的只读查询，由 App 让用户决定是否删除这些 Memory。删除完成前，产品只承诺"删除中"。日志中的原文副本与派生副本随 Session 一起删除。

8. **现行的安全边界。** 以下是现状，不是目标；改变其中任何一项须修订本 ADR。
   - **误标的后果。** 被标为佩戴者的他人文字算用户原话：它可以为 `memory_save` 提供依据，使写入在含外部内容的 Session 中免审（`grounded`）。定时等本地写入的审批看整个 Session 是否 `tainted`，只有误标使整个 Session 都不含非用户原话时才会漏触发。
   - **注入判断不是兜底。** 注入判断（`decision.ToolResultInjection`）只检查他人与外部来源（`internal/runtime/worker_decisions.go` 的 `unjudged`），只在配置了 `-injection-check` 时运行，且目前只以影子模式记录、不阻断（ADR-0030）。误标为佩戴者的文字不会进入判断。即使注入判断改为阻断也覆盖不到误标：佩戴者对助手下指令是正常用法，判断佩戴者的话会大量误报。误标的风险由业务线的说话人识别质量承担，2026-11-20 书面接受为上线的残留风险（[上线检查清单](../launch-checklist.md)"说话人误标"）。
   - **不依赖标签的审批**，只有能力声明的高风险审批（`RequiresApproval`）；已经请求的审批须走完。
   - **Memory 写入闸门**看整个 Session 的来源：`scope: run` 只裁剪模型上下文，不裁剪闸门的判断。纠错后，旧文字在日志中仍可作为依据；要撤回旧依据，只能删除工作 Session。
   - ADR-0048 的"听过他人旁听的 Session 不能调用三方"同样由来源推导（**尚未实现**），误标的他人文字不会计入；三方出站的逐次审批是独立要求。

## 退役与待实现

- **已退役**：内核的 Capture 提交（`SubmitCaptures`）、内置 `captures` 的读取、`transcript` 流、读取位置、交付确认（ADR-0049）、Capture 正文存储与擦除事件（ADR-0044）、按流登记与 AgentDef 的 `streams`、流上的触发（ADR-0040）。
- **已删除**（2026-11-15）：原先仅为解码旧日志保留的 `CaptureAppended`、`ToolResult` 的 `capture_read` 与 `capture_ack` 及其消息，以及 `State.Apply` 对旧内置 `captures` 结果的接受。proto 保留编号与名称，投影版本递增为 26；旁听片段只能出现在 attested 结果中，退役之前的日志不再回放（[ADR 评审](../review/2026-11-14-adr-review.md) §8）。
- **保留、继续有效**：`captures` 渲染器（供 attested 结果使用）、定时（ADR-0045，不含 `window.stream`）、出站流的通用部分（ADR-0046）、单次调用、档位、重答、EndUser 删除屏障；`speaker_ref` 是结构化片段的字段。
- **尚未实现**：ADR-0048 中按来源判断"听过他人旁听"。

## Considered Options

- **原文留在内核**（原 ADR-0044）：平台担保原文保留期、有不可变的提交记录；代价是正文存储、统一展开器、擦除与修订事件、跨库信封等一整套原语，而且擦除仍不覆盖日志中的派生副本。已否决（原 ADR-0050）。
- **业务线返回渲染好的文字**：实现最省，但页头等业务线写的文字会被推导为外部内容，外部文字与他人的话共用一次调用，注入判断会重复或漏判；模型看到的文字也不再由平台保证逐字不变。已否决（原 ADR-0050）。
- **每个内容块存一个来源字段**：读取最直接，但字段可以由写入方自报，每个入口都要校验它没有被伪造；推导则天然只认平台写入的事件。已否决（原 ADR-0039）。
- **映射由业务线配置**：让业务线自定义"谁的话算用户原话"，便于第二类内容接入；但会扩大授信，并使回放依赖当前配置（第 4 条）。不采纳（[ADR 评审](../review/2026-11-14-adr-review.md) §2.2）。
- **所有旁听都算外部内容**：最安全，但从佩戴者原话中得出的偏好、承诺每条都要审批，产品不可用。已否决（原 ADR-0036）。
- **音频经网关中转、由 yanshi 转写**：能统一转写质量，但 yanshi 要承载全天音频并保管声纹，删除与合规边界都要扩大。已否决（原 ADR-0036）。
- **审核信任业务线自报"已审"**：省去重读的送检，但审核是写日志前的平台检查，不能以调用方的声明代替。已否决（原 ADR-0050）。

## Consequences

- 说话人标签的正确性由业务线负责，平台无法验证；标错的后果见第 8 条，目前没有平台层面的兜底。
- 容量：内核日志中仍有原文页的副本（每段读一次时，10 万 DAU 约 50 GB/天，保留 7 天），随工作 Session 删除。读取倍数大于一时，成本相应放大。
- 失去的：平台对原文保留期的担保与提交时刻的不可变记录。采集服务本来就经手音频与全部转写，Persona 本来就长期保存由他人发言派生的摘要，这份担保的实际增益有限。
- 删除的竞态：从业务库删除到内核 Session 删除之间，已经读到原文的 Run 仍可能写 Memory 或发出调用；墓碑只挡 Persona 的写入，Session 删除先不可见、后清理（ADR-0015）。
- 接口细节（业务日、引用编号、处理进度、级联与删除待办）见 [Persona 架构](../design/persona-architecture.md) §13 的 Q36–Q54。

## 重审条件

任一出现即重新评估：

- 出现第二类需要平台采信的结构化内容（不限于旁听）：评估"登记内容类型 + 受信适配器"的泛化。来源仍由平台推导，调用方仍只提交证据字段；在此之前不改内核中的命名与校验（[ADR 评审](../review/2026-11-14-adr-review.md) §4.1）。
- 某条业务线需要佩戴者与他人以外的说话人角色。
- 注入判断从影子模式改为阻断，或说话人误标在评测或线上被观察到造成越权写入：重写第 8 条。
- 内核日志中原文页副本的容量超出压测上限：把大的 ToolResult 正文外置到按 Session 删除的对象存储，另立 ADR。外置**不能**因此取消对工作 Session 的擦除，因为回复、调用参数与摘要中仍可能有派生副本（评审 §4.2）。
- 出现须在一个 Session 内部分删除的法定要求（与 ADR-0004、ADR-0015 一并重审）。
