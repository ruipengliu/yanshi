# 建会话以幂等键派生 Session ID

> **已定稿（2026-11-22），随本次提交实施。** 来源：[架构评估评审](../review/2026-11-22-architecture-evaluation-review.md) §5 A1。设计与流程细节见[建会话幂等](../design/session-create-idempotency.md)；本 ADR 只记录难以逆转的部分。

创建 Session 是内核唯一不能安全重试的写操作：回包丢失时，调用方既不知道 Session 是否已创建，也无法证明它不存在。xinli 为此维护创建意图与空孤儿的启发式扫描，且没有回包的意图只能永久保留（`apps/xinli/orchestrator/orphans.go`）。按 ADR-0043，这是内核既有职责的完善：任何经不可靠网络调用内核的端或服务端都会遇到，业务侧只能启发式地发现孤儿，做不到"恰好创建一次"。

## 决定

1. **幂等键确定性地派生 Session ID，不新增存储。** `POST /v1/sessions` 与 Connection 的 `CreateSession` 接受可选的 `idempotency_key`；带键时 Session ID 由 `HMAC-SHA256(secret, 业务线 ‖ EndUser ‖ 键)` 派生，经 `ids.SessionID` 带上槽位（ADR-0051）。日志上 `(session_id, seq)` 的唯一约束让第一条 `SessionCreated` 成为唯一的胜者，后到的读回已有 Session 并比对参数：一致返回同一个 ID，不一致返回 `conflict`。键不写入任何存储，日志与指标照常只记 Session ID（ADR-0015）。
2. **派生使用单元级密钥。** 键可能是取值空间小的业务编号；不带密钥的哈希会让拿到 Session ID 的人可以逐个猜键、确认"某用户有某业务对象的会话"。密钥经 `YANSHI_SESSION_KEY_SECRET` 配置，同一单元内调用 `service.Create` 的进程必须相同；未配置时带键的请求被拒绝，不退化为不幂等的创建。第一期不支持双密钥轮换，轮换后跨越轮换的重试会再创建一个 Session。
3. **删除后键永久消耗。** Session 删除记录永久保留，派生 ID 一旦被删除，以同一键重试得到 `not_found`，不复活 Session；需要新 Session 的（例如擦除后重建）换键。创建后复查 EndUser 屏障失败而撤回时，键同样被消耗（安全优先）。
4. **SDK 自动以同一键重试。** Go、网页与移动端 SDK 为每次创建生成键，断线后以同一键重试；"重试创建 Session 会再创建一个"的例外随之取消（ADR-0024、ADR-0026）。

## Considered Options

- **映射表 `(业务线, EndUser, 键) → Session ID`**：能支持按键查询与键过期，但它是新的 Session 数据存放处，需要分片登记、Janitor 删除、先写后查与一致性套件，且键本身可能是个人数据；换来的保证与派生 ID 相同。
- **不带密钥的哈希**：见第 2 条；只有规定键必须随机时才安全，内核无法检查。
- **客户端直接指定 Session ID**：把 ID 格式与槽位规则暴露给客户端，客户端还可以抢占 ID（ADR-0051）。
- **维持现状**：每条业务线都要重做一遍启发式孤儿清理。

## Consequences

- 带键的创建是"取得或创建"；重放返回 200，首次返回 201。
- 单元多了一项必须配置、不能随意轮换的密钥，列入上线检查清单。
- 参数一致的判定以首次请求为准：未指定版本的重放不比较版本，首次之后版本被撤回不影响重放。

## 重审条件

- 需要按键查询而不创建，或需要键过期后重新可用；
- 需要平滑轮换密钥（改为双密钥派生，见设计 Q2）；
- 线上观察到复查失败导致键被消耗（设计 Q3）。
