# Call 经网关中转，语音模型只通过 run_task 做事

全双工语音通话（Call）的音频经设备已有的 Connection 送到网关进程，由它连接端到端实时语音模型并双向转发。设备不直连模型厂商，也不另开 WebRTC 通道。实时语音模型只有一个工具 `run_task`：需要能力的工作交给 Session 的 AgentDef 作为后台 Run 执行，结果回注通话（落实 ADR-0005 的"派生、回注"）。

不选设备直连，原因有三：

- 厂商没有可下发给设备的短期凭证，直连就要把 API Key 交给设备。
- 转写、计量、派生 Run 都得靠设备上报，失去服务端的控制。
- 换厂商要改所有端。

厂商的 RTC 方案在抗弱网与回声消除上更好，但它多引入一个产品与 SDK，私有化部署（ADR-0001）更难。

不把 Agent 的全部能力直接交给语音模型，原因是审批、设备离线挂起、调用去重、Memory 写入闸门都已在 Run 中实现并经过模拟测试。语音模型直接调用能力，就要在 Call 里把这些重做一遍，而这条路径没有模拟测试的保护。

## Consequences

- 多一跳：网关与模型同机房时几十毫秒。网关进程按 20 ms 的节拍转发上行音频，并把网络抖动造成的积压限制在 300 ms 以内。
- Call 的状态只在中转进程中：进程退出时 Call 结束，设备重新发起即可。日志中没有结束记录的 Call 由下一个 Call 以 `replaced` 补上。
- 媒体不进日志，双方每句话的转写进日志（ADR-0005），并进入之后 Run 与文字对话的上下文。
- **内容安全的差异（ADR-0021）。** 转写在写日志之前检查，但播出的语音边生成边播放，无法先审后播。我们的检查在助手整句生成时（早于播完）进行，违规时中止剩余播放。在此之前播出的部分依赖厂商的严格审核。这一差异列入上线检查清单，须与合规确认。
- 通话中的审批仍在屏幕上完成：语音模型的转述不能作为用户的批准。
- 语音模型的 `run_task` 说明与系统指令是给模型看的文本，由 `evals/call-*.yaml` 评测（语音由语音合成产生）。
