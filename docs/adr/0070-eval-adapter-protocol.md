# 评测适配协议：评分进程与被测进程分开

> **方向已批准（2026-11-28），待定稿、未实现。** 设计见 [业务线模型](../design/business-line-model.md) §6、§10；方案来自 [调研：把 xinli 的评分移出 `internal/eval`](../review/2026-11-27-eval-xinli-decoupling-study.md) 方案 A。定稿后修订 [Persona 架构](../design/persona-architecture.md) §3.4 与 Q33（"夹具不提供 Check"）。实现之前照旧：xinli 的评分留在 `internal/eval`，夹具只提供 Seed、State 与操作。

xinli 的用例与基线已拆到 `apps/xinli/evals/`（[评测设计](../design/m4-eval.md) §2），但业务断言、夹具驱动与金标匹配仍在内核的 `internal/eval` 中（调研 §1 列出约 2,700 行触点）。原因是"被测方不做自己的裁判"：评分若由被测的业务进程完成，业务线可以给自己打高分。代价是内核认识了 xinli 的业务实体（交谈、项目、承诺），第二条业务线要有自己的业务断言就必须改内核。

## 提议的决定

1. **原则改写为"评分进程与被测进程分开"。** 业务线提供独立的评测适配进程（不是被测的业务服务），负责解析业务用例、驱动夹具、判定业务断言；内核掌控模型、时钟、评判调用（`-judge`）、运行与基线比较。
2. **协议是版本化的 JSON/HTTP**（调研 §2 方案 A）：就绪行 `{version, url}`；`DescribeCase`、`StartInstance`、`StartTrial`、`AdvanceTurn`、`Check`、`FinishTrial`。内核只执行限定在当前 trial 的动作：拨钟、提交输入、中断、旁听分页预览（复用 `internal/capture` 的校验与预算）、请求评判。
3. **`Check` 返回断言、指标与诊断**；套件声明指标方向，内核沿用报告的聚合与比较，基线文件格式不变。
4. **一致性套件。** 协议配黑盒套件，与其他出向接口一样（ADR-0067）；最小参考业务线（ADR-0067）提供第一个适配器。
5. **迁移按调研 §3 分阶段**，每阶段 `make check` 全绿、两份基线零差异；双路判定一致后才删除 `internal/eval` 中的 xinli 代码。

## 待回答的问题（定稿前须给出答案）

调研 §4 列出的问题，以及：

1. 业务断言由业务线维护后，评审门禁怎样防止业务线放宽自己的断言（断言改动是否须经内核评审）。
2. 评判（LLM judge）的提示由谁持有：留在内核，还是随业务断言一起归业务线。
3. 适配进程与被测业务服务之间是否允许共享代码（例如领域类型），以及怎样防止适配器读取被测进程的内部状态作弊。

## 必须验证

- 调研 §3 第 1 阶段的冻结口径：用两套历史报告锁住比较器，新旧判定读同一份冻结观察与原始评分响应，逐项一致。
- 最小参考业务线的适配器通过协议套件。

## Considered Options

- **方案 B：内核模块内的扩展包，静态注册**：迁移风险最低，但业务规则仍编入内核，第二条业务线要改内核；只适合作为过渡。
- **方案 C：业务评测二进制驱动公开的评测 SDK**：公开控制面宽，各业务驱动之间的超时、记账与跳过规则容易漂移。
- **维持现状**：每条业务线的业务断言都要进内核，与 ADR-0067 的"业务线是保护域"冲突。

## Consequences

- 内核不再包含业务实体的评分代码；第二条业务线提交自己的适配器、用例与基线即可。
- 断言的维护归业务线，裁判的独立性改由"进程分开、内核掌控模型与评判调用、断言改动经评审"保证。
- 迁移工作量约 2,500–3,500 行（调研 §2）。

## 重审条件

- 业务线出现放宽自身断言以通过基线的情况（重审断言的归属）；
- 跨进程协议的超时、重投与评分输入漂移导致评测结果不稳定；
- 评测需要内核尚未开放的动作（扩展协议前先评估是否应由业务线自己完成）。
