# 外部循环只做决定，动作都由平台执行

> **设计已认可，尚未实现**（2026-11-14 标注）：`internal/` 中没有外部循环的实现（[m5 设计](../design/m5-inputs-triggers-loops.md)的第 3 步待做）。本文中有两类内容，演进时区别对待：
> - **平台治理，不可替换**：对用户设备、Memory 与其他能力的影响都经平台执行的调用发生；回答写入日志后才生效；审批、写入闸门、能力白名单与内容安全不区分循环是内置的还是外部的。
> - **可替换的策略**：每一步做什么、上下文怎样组装。目前上下文仍由平台组装（第 1 条）；业务可替换的上下文策略与流式外部循环是已认可的方向，尚无设计（[ADR 评审](../review/2026-11-14-adr-review.md) §3.4）。
>
> 三处容易误读的地方：第一版**不流式**，客户端收到整条回复；**64 KiB 是不透明状态的上限**，不是每步都写满；平台的请求前缀缓存对外部循环不适用，外部服务自己调用模型时的缓存**由外部服务负责**。

Agent 循环写死在 Worker 中：AgentDef 只能调参数，表达不了确定性的步骤、分支、自定义的上下文或结束条件。章程原则 1 要求循环策略可替换。业务线要么把复杂流程塞进提示词，要么在平台之外另做一个 Agent，而后者绕开了审批、写入闸门、内容安全与按 Session 删除。

## 决定

AgentDef 可以用 `loop` 指定一个业务线登记的外部服务，由它决定每一步做什么：

1. **每步一问。** 内置循环中"调用模型"的那一步换成请求外部服务：平台照常组装上下文（含召回与压缩），外部服务返回回复与调用请求，平台照常执行调用。契约在 `proto/` 中定义，经 HTTP 以 JSON 传输。
2. **只做决定，不做事。** 对用户设备、Memory 与其他能力的影响都经平台执行的调用发生，审批、写入闸门、能力白名单与内容安全不区分循环是内置的还是外部的。
3. **回答写入日志后才生效。** 回放读日志、不再请求外部服务；同一步可能被请求两次，以写入日志的那次为准。外部服务的不透明状态（至多 64 KiB）随回复写入日志、下一步带回，随 Session 删除。
4. **只能用本业务线的循环**；用量按步计，外部服务自己调用的模型不经平台计量。

## Considered Options

- **整个 Run 交给外部 Agent**（A2A 式）：外部框架最自由，但它自带工具、自己执行，平台的检查管不到内部，结果只能当作外部内容。以后作为一种能力另行接入。
- **进程内插件**（Go 接口或钩子）：延迟最低，但业务代码进入内核的故障域与信任域；私有化部署时还要让业务线编译进二进制。
- **在 YAML 中加入工作流语法**：不需要外部服务，但 YAML 会变成半吊子编程语言，难写、难评测、难回放。
- **外部服务自己保存状态**：协议更小，但删除要另外处理，回放时也拿不回当时的状态。

## Consequences

- 每一步多一次往返，适合复杂流程，不适合闲聊；第一版不流式，客户端收到整条回复。
- 上下文（包括旁听中他人的话与设备的结果）会离开平台、到达业务线的服务，范围比 MCP 调用的参数大得多。业务线要承担保留与删除的义务，接入文档与登记中写明；外部地址只来自显式的登记（ADR-0001）。
- 前缀缓存与 token 计量对外部循环不适用；`max_turns`、配额与内容安全照常。

## 重审条件

（2026-11-14 补充）任一出现即重新评估：

- 业务线需要的上下文策略无法由平台的组装满足；
- 需要流式的外部循环（逐步推送草稿）；
- 开始实现本 ADR：届时核对上文的设计是否仍成立，并去掉"尚未实现"的标注。
