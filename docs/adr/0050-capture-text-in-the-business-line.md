# 旁听原文存放在业务线，内核只认可信登记的结构化片段

> **历史记录（2026-11-14）。** 本文的决定已整合进 [ADR-0052](0052-attested-results-and-provenance.md)，正文不再修改；后果中对 ADR-0036 的补记已成为 ADR-0052 第 8 条的正文。各条款的现状见 ADR-0052 附录的对照表。

M7 把旁听原文留在内核（ADR-0044），为部分删除、纠错、交付与跨库擦除补了一整套原语：正文存储、统一展开器、擦除与修订事件、读取 API、交付确认（ADR-0049）、出站流的擦除信封，以及流上的触发与定时窗口。[边界评审](../review/2026-10-27-capture-boundary-review.md)核实了两件事：

- 这些原语"只有平台能做"的理由，多数以"原文在内核"为前提：原文与派生对象分在内核与 Persona 两个库里，才需要出站流通知、72 小时对账、墓碑竞态与回执拼链。
- M7 的擦除只清片段正文，日志中模型回复、`file_changes` 参数里对被擦原话的概括与引用，要等当天 Session 删除才消失（约 7 天）。

而说话人的信任锚本来就在业务侧（ADR-0036 后果第 1 条：说话人标签由 yanshi 之外给出）。产品负责人确认原文保留期可以由业务线担保（[整体架构](../design/persona-architecture.md) §13 Q29）。

## 决定

（对照与评审记录见 [原文放在哪里：裁决记录](../review/2026-10-27-capture-placement-decision.md)）

**原文存放在业务线**（xinli 中是 Persona 的库，与交谈、承诺同库）。业务线负责原文的分页、时段、进行中判断与处理进度，保存变更集与推进处理进度在同一个本地事务中。内核只做下面几件事，它们都是"业务侧做了不安全"的：

1. **可信结构化片段。** MCP 登记新增 `attests_speakers: true`，只采信同一业务线的 Server（与 `acks` 同一写法）。这类 Server 在结果中返回**结构化的页**（片段的引用、说话人、说话时间、文字、可选的 `speaker_ref`，以及时段边界、是否进行中、下一页游标等页的元数据），**不返回给模型看的文字**。Worker 用内核现有的 `captures` 渲染器把页渲染成文字与 `ContentBlock.capture`，并在 ToolResult 上记下平台写入的 attested 标记；`State.Apply` 再校验：capture 块只能出现在内置 `captures` 或带 attested 标记的 MCP 结果中（ADR-0039 的"service 拒绝、Apply 再校验"）。
   - 因为页由平台渲染，结果里没有业务线写的文字：来源推导与内置 `captures` 等价（佩戴者片段 FromUser，他人片段合成一段 FromOther 进注入判断），不会因页头算作外部内容而收紧，也不会把业务线写的文字洗成可信内容。模型看到的文字由同一个渲染器生成，与现在逐字相同。
   - 结果预算等渲染与分页依赖的平台参数，经 `_meta` 交给业务线。
2. **写日志前审核。** attested 结果在写日志之前送内容安全检查：整页送检，被拦下时逐段复核，违规片段以占位写入；提供商故障时整个结果写为错误（fail closed，ADR-0021）。第一版不缓存审核结果，重读重审，先测成本。
3. **擦除即删除工作 Session。** 删除一段谈话时，业务线在一个事务中删除原文、写墓碑、按依据级联 Persona 的派生对象，并记下一条"删除当天工作 Session"的待办、停用旧的 Session；之后由编排器幂等地中断并删除内核中的工作 Session，删除原因为 Erasure（`erasure`）：保留该 Session 写入的 Memory。内核提供删除进度的只读接口；清理完成后（之后不会再有迟到的写入），编排器以当天用过的全部工作 Session 调用内核的只读查询，列出由它们写入的有效 Memory（依据可能落在被删范围内：同一天擦除两次时，第一个 Session 读过的原文也可能包含第二次擦除的范围），由 App 让用户决定。删除完成之前 App 只报告"删除中"。日志中的原文副本与派生副本随 Session 一起删除。
4. **绝对删除期限。** 创建 Session 时可以给出绝对的删除期限（`delete_at`，只有服务令牌可以设，须晚于现在），到期以 `retention` 删除并保留 Memory；擦除后重建的工作 Session 继承业务日原来的期限，重建与重读都不延长原文副本在内核日志中的寿命。Retention 是兜底。

**从 M7 删去**：Capture 正文存储与分区、统一展开器、Erasure 与 CaptureCorrection 事件（纠错是业务库中原文的修订）、Capture 读取 API、出站流的 `capture_erased`/`capture_corrected` 信封、`window.stream`、流上的触发、Stream 泛化及对声明流的 AgentDef 的限制。

**保留**：定时（ADR-0045，不含 `window.stream`；"流上静默满 2 小时"改由业务线判断后提交固定的整理指令，动态内容仍经工具读取）、出站流的通用部分（ADR-0046）、单次调用、档位、重答、EndUser 删除屏障。`speaker_ref` 成为结构化片段的字段。

**退役条件**：内核的 Capture 路径（`SubmitCaptures`、内置 `captures` 的读取、`transcript` 流、读取位置、交付确认）在 xinli 切换完成、且没有业务线声明流之后删除；`captures` 的渲染器保留，供 attested 结果使用。删除时 proto 字段保留编号，投影递增 `session.ProjectionVersion`。

## Considered Options

- **A：原文留在内核（现行 M7）**：平台担保原文保留期、有不可变的提交记录；代价是上面那一整套跨库一致性原语，且擦除仍不覆盖日志中的派生副本。
- **B：最小 Capture（保留提交与 `captures`，砍掉流泛化、交付确认与触发）**：只要产品要部分删除，正文存储、展开器、擦除与跨库信封都省不掉，成本下限与 A 相近。
- **C 的变体：业务线返回渲染好的文字**：实现最省，但页头等业务线写的文字在来源推导中算外部内容（纯佩戴者的页也要过依据比对），外部文字与他人的话共用一次调用，注入判断会重复或漏判；模型看到的文字也不再由平台保证逐字不变。
- **审核信任业务线自报"已审"**：省去重读的送检，但审核是写日志前的平台检查（ADR-0021），不能以调用方的声明代替。

## Consequences

- 修订：ADR-0036（存放位置；只收文字、说话人结构化、佩戴者的话算用户原话、他人的话算外部内容不变）、ADR-0037（原文保留期由业务线担保，内核担保自己的副本）、ADR-0039（结构化片段的写入方多了可信登记的 MCP 结果）、ADR-0040 第 2 步（流上的触发不做）、ADR-0045（去掉 `window.stream`）、ADR-0046（去掉擦除与修订信封）、ADR-0015 与 ADR-0021（新的删除原因、MCP 结果中的 attested 部分写日志前审核）。取代：ADR-0044、ADR-0049。
- 修订 ADR-0036 正文"读过 Capture 的 Run 一律经过注入判断"及后果第 1 条"注入判断与高风险审批不依赖标签"（2026-11-01 补记），二者与现行实现不符。来源按结构化说话人推导，误标为佩戴者的他人文字算用户原话：
  - 注入判断（`decision.ToolResultInjection`）只检查他人与外部来源（`internal/runtime/worker.go` 的 `unjudged`），且目前只以影子模式记录、不阻断。
  - 误标文字可以为 `memory_save` 提供用户原话依据，使其在含外部内容的 Session 中免审（`memgate.go` 的 `grounded`）；定时等本地写入的审批看整个 Session 是否 `tainted`，只在误标使整个 Session 都不含非用户原话时漏触发。
  - 首次触发审批的条件中，不依赖标签的只有能力声明的高风险审批（`RequiresApproval`）；已经请求的审批须走完。
  - ADR-0048 的"听过他人旁听"同样由来源推导（尚未实现），误标的他人文字不会计入；三方出站的逐次审批是独立要求。下面"安全"一条中的"只依赖来源推导，不受影响"指不受本次迁移影响，不是不受误标影响。

  业务侧的影响分析见 [转写评测](../design/xinli-transcription-eval.md) §5.3 的 T1（原在 ASR 选型文档 §7，2026-11-01 迁移）。
- 容量：内核日志中仍有原文页的副本（每段读一次时 10 万 DAU 约 50 GB/天，保留 7 天）。这是现在的一半（现在提交的原文与工具结果各一份），但重新引入了 Q15 想避免的逐 Session 删除的表膨胀；以 P4 压测为准，超标时把大的 ToolResult 正文外置到按 Session 删除的对象存储（工件机制的推广），另立 ADR。读取倍数大于一时成本相应放大。
- 安全：`scope: run` 只裁剪模型上下文，Memory 写入闸门看整个 Session 的来源；纠错后旧文字在日志中仍可作为依据，要撤回旧依据只能删除工作 Session。三方 Agent 的"听过他人旁听的 Session 不能调用三方"（ADR-0048）只依赖来源推导，不受影响。
- 失去的：平台对原文保留期的担保与提交时刻的不可变记录；说话人核对与原文保留由业务线负责。采集服务本来就经手音频与全部转写，Persona 本来就长期保存由他人发言派生的摘要，这份担保的实际增益有限。
- 删除的竞态：从业务库删除到内核 Session 删除之间，已经读到原文的 Run 仍可能写 Memory 或发出调用；墓碑只挡 Persona 的写入，Session 删除先不可见、后清理（ADR-0015），删除完成前产品只承诺"删除中"。
- 接口细节（业务日、引用编号、处理进度、级联与删除待办）见[整体架构](../design/persona-architecture.md) §13 的 Q36–Q54。
- 迁移：先做可信结构化片段、审核与 Apply 校验（来源推导、写入闸门的测试与 `internal/sim`），再把分页与处理进度迁入 Persona，以固定输入与内核现有的分页逐页差分；切换 xinli-day 时 `make eval` 的 `capture-*` 不得回归（工具名变为 `mcp_xinli__captures` 是唯一的模型可见差异，看缓存命中列）。
