# 跨业务线委托：调用对方导出的 Agent

> **方向已批准（2026-11-28），待定稿、未实现。** 设计见 [业务线模型](../design/business-line-model.md) §7。兑现 [M7 Agent 生态](../design/m7-agent-ecosystem.md) §4 与 Q25 的预留；定稿后取代 [ADR-0031](0031-delegation-as-routed-calls.md) 中"委托不跨业务线"的限制，ADR-0031 其余决定不变。实现之前照旧按 ADR-0031 执行：子 Session 沿用父 Session 的业务线（`internal/delegation/delegator.go`）。

业务线之间现在只有一种交互：经 Grant 读取对方的 Memory（ADR-0003、ADR-0064）。一条业务线的 Agent 无法请另一条业务线的 Agent 做事；业务侧之间要联动，只能由 A 持有 B 的令牌代 B 提交输入，两条业务线因此耦合，A 也能以 B 的身份写入。

## 提议的决定

1. **业务线之间只有两种交互，都经内核中转**：调用对方导出的 Agent（本 ADR），经 Grant 读取对方的 Memory（ADR-0003、ADR-0064）。异步联动（A 的结果触发 B 做事）用后台委托实现（ADR-0058），内核不另建业务事件订阅。
2. **不直接调用对方的工具。** A 的模型直接驱动 B 的 MCP 写入会绕过 B 的 AgentDef、写入闸门与审批策略；A 要 B 做事，只能请 B 的 Agent 去做。A 的服务令牌也不能以 B 的身份提交输入。
3. **导出与引用。** B 在清单（ADR-0067）中导出 Agent，声明暴露方式（给其他业务线委托、给三方经 A2A 调用）与能力上限；A 在清单中引用它，并在 AgentDef 白名单中列出 `agent:<业务线>/<名>`。导出与 A2A 入站共用一份 Agent 描述（Agent Card 由它生成），按暴露方式分别做加载校验：A2A 入站的约束不变（[M7 Agent 生态](../design/m7-agent-ecosystem.md) §3.2）。
4. **只在同一身份域内。** 两条业务线声明了相同的非空 `identity_domain`（ADR-0064）才走平台内委托；子 Session ID 按 EndUser 的槽位派生（ADR-0051），只有同一身份域才能保证父子是同一个人。不同身份域或不同单元一律视为三方，走 A2A 与 OAuth（ADR-0048）。
5. **授权是三道条件的合取**：B 导出、A 引用并列入白名单、EndUser 给过调用授权（Grant 新增 `kind: delegate`，撤销即时生效）。
6. **权限是交集**：子 Run 的能力 = B 的 AgentDef 白名单 ∩ B 导出时声明的能力上限 ∩ A 方各祖先的白名单 ∩ 用户授权；A 的 MCP 与 Memory 不透传给 B。
7. **双向都是外部内容。** B 收到的任务由 A 的模型写成，不是用户原话；A 拿到的结果来自 B。听过他人旁听的 Session 不能跨业务线委托（[M7 Agent 生态](../design/m7-agent-ecosystem.md) §5）。子 Run 的审批与提问在调用方的端上显示时标明来源业务线。
8. **计量与配额记在执行方 B**，同时记录调用方业务线（只记 ID，供对账）；B 可在导出中为每个调用方设置预算或速率上限。
9. **删除级联。** 子 Session 的删除期限不晚于父 Session；父 Session 删除时，Janitor 跨业务线删除子 Session 及其工件副本；EndUser 注销时按业务线清理并撤销双向 Grant；B 卸载时按 ADR-0068 处理。
10. **其余沿用委托**：路由调用、相邻委托并行与 `max_fanout`、工件复制交接（ADR-0055）、后台转交（ADR-0058）、追踪的 `link_trace_id`（ADR-0065）。对 A 而言，B 不可用就是一次失败或超时的调用结果。

## 待回答的问题（定稿前须给出答案）

1. 调用授权 Grant 的粒度（按被调业务线、按导出的 Agent，还是按能力）与用户界面上的呈现。
2. 子 Session 属于 B，但审批与提问的会话客户端连在 A 的端上：路由与鉴权怎样处理（Connection 的 Scope）。
3. 跨业务线子 Session 的删除期限与 A 的擦除（例如 xinli 删除当天的工作 Session）的时序。
4. B 导出的能力上限怎样表达，与 AgentDef 白名单的语法是否一致。
5. 计量中记录调用方业务线是否需要改动用量表（`usage_entries` 的字段），以及配额超限时 A 得到的错误。

## 必须验证

- `internal/sim` 覆盖跨业务线委托的删除级联与权限交集；`make verify` 覆盖跨业务线子 Session 的删除顺序。
- 未导出、未引用、未授权、不同身份域四种情况各被拒绝。
- 子 Run 的来源推导：B 收到的任务与 A 收到的结果都是外部内容。

## Considered Options

- **允许直接调用对方的 MCP 工具**：调用简单，但 A 的模型直接驱动 B 的写入，绕过 B 的策略。
- **内核提供跨业务线的事件订阅（A 的出站触发 B 的输入）**：后台委托已能承接异步联动；事件订阅需要新的来源规则与删除语义。
- **跨身份域也走平台内委托**：EndUser ID 可能撞号，父子不是同一个人。
- **调用方付费**：A 控制不了 B 的模型与轮数；以后有明确的代付需求再显式增加。

## Consequences

- 业务线可以组合：一条业务线的前台 Agent 可以把专门的工作交给另一条业务线的专员，权限只收紧。
- 跨业务线的删除级联使 Janitor 与删除不变量更复杂。
- A2A 入站与平台内导出共用描述，三方接入与业务线组合的声明一致。

## 重审条件

- 业务线之间需要不经 Agent 的直接数据或工具访问；
- 不同身份域的业务线之间需要平台内委托（需要账号关联映射，与 ADR-0064 一并重审）；
- 跨业务线委托的级联删除使 Janitor 的清理时长超出预算；
- 出现明确的调用方付费需求。
