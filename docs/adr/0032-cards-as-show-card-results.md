# 卡片是 show_card 的结果，卡片动作是一条输入

C 端对话需要比纯文本更丰富的呈现：图文混排的结果（日程、行程、对比）、可点选的后续操作、可填写的表单。这些要能在三个 SDK、多台设备上一致地出现，被模型理解，并且同其他交互一样经过校验、内容安全与去重（[卡片设计](../design/cards.md)）。

## 决定

1. **卡片是契约中的内容块。** `event.proto` 新增 `ContentBlock.card`（`Card`：标题、副标题、头图，正文元素为 Markdown、图片、键值、列表、字段，加按钮）与 `ContentBlock.card_action`。组件集合小而固定，由客户端自行渲染；Markdown 只渲染安全的子集。
2. **模型经内置工具 `show_card` 展示卡片。** 卡片是工具参数：与其他调用参数一样在写日志之前做内容安全检查（ADR-0021）。平台校验后把规范化的卡片作为调用结果写入日志；`session.Apply` 只接受 `show_card` 的、由 Worker 写入的结果中带卡片，用户输入与设备结果中的卡片一律拒绝。
3. **卡片不阻塞 Run。** 展示即返回；需要等用户选择才能继续的，仍用 `ask_user`（ADR-0025）。阻塞等待用户只有一条路径，挂起与恢复的语义不变。`ask_user` 的选项可以带配图，客户端以卡片样式渲染提问。
4. **卡片动作是一条输入。** 用户点按钮或点选列表项时，客户端提交带 `CardAction` 的输入：有进行中的 Run 时并入（Steer），否则开启新 Run；Run 正在等回答时作为回答。平台按日志中的那一版卡片核对动作与字段、填写动作的显示文字（客户端提交的被忽略），并以 `call_id` 与动作推导输入 ID：同一版卡片上的同一动作只生效一次，与点了几次、在几台设备上点无关。
5. **同一 `card_id` 再次展示即替换。** 卡片的每一版都留在日志中，客户端只显示最新版；动作带上 `call_id`，旧版本上的动作与新版本的互不混淆。
6. **图片只能是本 Session 的工件或内置图标。** 不允许外部地址：外部图片可以追踪用户，也不随 Session 删除（ADR-0015）。

## Considered Options

- **只用 Markdown**：图文混排可以做到，按钮、表单与回传动作做不到，"点了哪个"只能靠模型从文字里猜。
- **采用 Adaptive Cards、A2UI 等现成标准**：体量大、版本仍在变化，三个 SDK 都要跟进；契约在 `proto/` 中，自定义的小集合够用且可以向后兼容地扩展。
- **卡片作为 AssistantMessage 的一部分（模型直接输出结构化内容）**：模型的输出格式因提供商而异，校验失败时无处交还错误；作为工具调用，参数错误照常作为错误结果交还模型改正。
- **卡片动作作为单独的请求类型（如 Answer）**：动作的语义就是用户的一句话，只是带了结构；作为输入，插话、开新 Run、回答提问、内容安全、准入与配额都沿用已有路径。

## Consequences

- 卡片动作的核对要读卡片：客户端带上收到卡片的事件序号时读一条事件，否则扫描日志（罕见）。
- 卡片动作的去重沿用输入 ID 的去重窗口（最近 `session.MaxRecentInputs` 条输入）；更早的重复点击会再次生效。
- 内容安全提供商须检查卡片文字（作为调用参数）与卡片动作中填写的值（作为输入）。
- 模型看不到卡片本身：结果中另有一行说明（"已展示卡片 …"），卡片内容就是它自己写的参数，不再重复占用上下文。
