# 健康信息作为单独的 Memory 类别，按业务线的单独同意开启

Memory 增加 `health` 类别（过敏、饮食禁忌、慢性病与用药等）。业务线在配置中声明 `memory.health: true`，表示已在产品流程中取得用户对健康信息的单独同意；只有这样的业务线能写入该类别，召回与检索也只在开启时包含它。经 Grant 跨业务线读取时，还要求写入方业务线已开启。这修订了 ADR-0016 中"敏感个人信息不在任何类别中、平台拒绝写入"的约定。

原来的做法使助手在用户主动说出"我对花生过敏"时也不能记住，评测中观察到模型在指令与用户意图之间摇摆（3 次中有 1 次没有记住）。过敏这类信息关系到安全，记住它是用户期望的。我们没有选择对所有业务线默认开放：单独同意必须由业务线在自己的产品中取得，平台需要一个明确的声明，才能在出问题时说明哪条业务线承担了取得同意的责任。

## Consequences

- 健康信息是独立的类别：用户授权时能看懂"允许 B 读取你在 A 中的健康信息"，默认不会随其他类别一起授权。
- 关闭开关即停止使用（不召回、不检索），但不自动删除：删除仍由业务线经 API 完成，或随 Session、账号删除。
- 写入指令（`memory_save` 的描述）改为鼓励记住与安全相关的健康信息；修改它须经评测（`memory-health-recall`、`memory-save-intro`）。

## 修订（2026-11-19）：按 EndUser 的单独同意

ADR 评审第二轮。业务线开关表达不了"某个用户撤回同意"：业务线可以经 API 删除该用户的健康 Memory，却挡不住模型下次再用 `memory_save` 写进来——写入闸门与召回在内核，业务侧做不到（ADR-0043 的判据）。个人信息保护要求处理敏感个人信息前取得个人的单独同意，并允许撤回。

1. **按 EndUser 选择加入。** `memory.health: true` 只表示业务线有取得同意的流程；每个 EndUser 还须由业务线在用户同意后经 API 开启。未开启的用户，健康信息不写入、不召回、不检索；经 Grant 跨业务线读取时，要求写入方业务线对该用户已开启。不用"退出名单"：那会把"业务线开了开关"当成"所有用户都同意了"。
2. **存储与 API 沿用档位（Tier）。** 新表 `end_user_consents(business_line, end_user, kind, granted_at)`，分片键为 EndUser；`kind` 目前只有 `health`，为将来的敏感类别留位置。`PUT /v1/end_users/{id}/consents/health` 与 `DELETE`，只允许服务令牌；写入"先查、后复查"EndUser 删除屏障，注销账号时删除。读缓存 5 秒，开启与撤回跨进程至多 5 秒生效，**撤回在本进程立即失效缓存**。`granted_at` 同时是平台侧可出示的同意记录。
3. **撤回停止使用，删除由业务线决定。** `DELETE` 立即停止写入、召回、检索与 Grant 读取，默认不删除已有的健康 Memory（与关闭业务线开关一致，用户可能暂时撤回、之后重新同意）；`?purge=true` 一并删除该用户在本业务线的健康 Memory。
4. `-auth none` 的开发模式与评测照旧视为已开启（没有业务线服务端来开启）。

## 重审条件

（2026-11-14 补充）任一出现即重新评估：

- 出现健康之外的敏感类别需要按 EndUser 同意（`kind` 已留位置）；
- 第二条业务线需要健康之外的敏感类别；
- 评测（`memory-health-recall`、`memory-save-intro`）显示写入指令在新模型上不再可靠。
