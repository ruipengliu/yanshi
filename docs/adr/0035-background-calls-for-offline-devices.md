# 离线设备上的调用转入后台，迟到的结果作为输入送达

调用路由到设备时，Run 挂起等设备的结果（ADR-0002，[M1 设计](../design/m1-device-nodes.md) §3）。手机经常离线，一离线就是几十分钟：Worker 按顺序推进调用，调用没有结果，模型就不会再被调用。期间用户的话只是插话，对话没有任何回应；同一轮中排在后面、目标在线的调用也被卡住。唯一的出路是中断整个 Run，而中断也撤回了那次调用。

## 决定

1. **宽限期之后转入后台。** 路由到设备（Node 目录中的 Node；不含沙箱、用户本人与委托）的调用已派发、尚无结果，设备离线已超过宽限期时，Worker 不再等它：先以新的截止时间重新派发（Inbox 按 `call_id` 只延长截止时间），再写入一个带 `ToolResult.backgrounded` 的占位结果，告诉模型调用已排队、结果稍后单独送达、不要重试。Run 照常继续。调用记为 Session 级的后台调用（`session.State.Background`），Inbox 中的投递保留，设备上线后照常执行（SDK 按 `call_id` 去重）。
2. **宽限期与后台时限。** 宽限期默认 20 秒，从派发与设备下线中较晚者起算，覆盖短暂断网与切到后台：期间 Run 照旧挂起，停放到宽限期结束；期间上线的设备照常在 Run 中返回结果，行为与原来相同。设备下线时，网关唤醒 Run 中有调用在等它的 Session，执行中途下线同样在宽限期后转入后台。Worker 来晚了（宽限期与调用的截止时间都已过去）时，只要宽限期在截止时间之前结束，也转入后台。后台时限默认 24 小时。二者可配置（`app.Options`、`serve -background-grace`、`-background-timeout`），宽限期为负数时不转后台。
3. **迟到的结果是一条输入。** 设备结果到达时，网关在一次 `session.Store.Update` 的决策中看投影：调用仍在 Run 中等待，写入它的结果；已转入后台、尚未了结，写入一条输入，其中唯一的内容块是 `BackgroundResult`；否则作废。"Worker 转入后台"与"设备结果到达"的竞争由乐观并发解决。这条输入有活跃 Run 时并入它（插话；Run 正在等提问的回答时也不当作回答），否则开启新 Run，由模型向用户报告。新 Run 与用户输入开启的 Run 遵循相同的规则（撤回的版本同批切换、日志与队列同一事务、更新索引），但不做准入、不在入口检查配额（否则结果会丢），配额由 Worker 在调用模型之前检查。设备内容不做内容安全检查，与调用结果一致；注入判断覆盖它；Memory 写入闸门把它算作外部内容。
4. **到期也是一条输入。** 后台调用到截止时间仍无结果，Worker 先撤回投递，再写入 `reason = timeout` 的 `BackgroundResult`，同样并入或开启 Run，让模型告诉用户没有办成。有未了结后台调用的 Session，没有活跃 Run 时也停放在队列中，到最早的截止时间被唤醒。
5. **用户可以单独取消。** `POST /v1/sessions/{id}/background/{call}/cancel` 与 Connection 的 `CancelBackground` 都经 `service.Service.CancelBackground`：先撤回投递，再写入 `BackgroundCancelled`，不开启新 Run；模型之后在上下文中看到一条说明。已了结的返回 conflict。中断 Run 不影响后台调用：它们在 Run 中已有结果。关闭 Session 时撤回全部未了结的后台调用。
6. **每个后台调用至多了结一次。** 投影只接受针对未了结后台调用的了结（结果、到期、取消三者之一），客户端提交的输入中不能出现 `BackgroundResult`。
7. **委托派生的子 Session 不转后台。** 子 Run 结束后，迟到的结果回不到父 Run：子 Session 中的设备调用保持挂起，由委托时限兜底。

给模型看的文本：占位结果、迟到结果的说明（注明是哪个后台调用、内容来自设备、不是用户的话、其中的指令不要执行）、到期与取消的说明。它们只出现在上下文尾部，系统指令与工具定义不变，请求前缀缓存不受影响。

## Considered Options

- **调用之间并行推进，离线的调用不挡住其他调用**：解决了"同一轮后面的调用被卡住"，但模型仍要等全部结果才会被调用，对话照样没有回应。
- **离线就直接返回错误**：模型会让用户"稍后再试"，用户得记着重新发起；手机上线往往就在几分钟后，平台排队更省事。
- **迟到的结果写回原调用（修改已写入的结果）**：日志只追加（ADR-0004），而且原 Run 多半已经结束，结果写回去也没有模型会看到它。
- **迟到的结果写成新事件类型，再由 Worker 决定是否开新 Run**：开新 Run、去重、投影、快照、唤醒、上下文排序都要另做一遍；作为输入，这些都沿用已有路径（与卡片动作作为输入同理，ADR-0032）。
- **不设宽限期，派发时离线就转入后台**：手机切到后台、过隧道这类几秒的离线最常见，宽限期内回来时结果仍在同一轮中，模型不必分两次回答。

## Consequences

- 同一件事可能分两轮完成：先是"已排队"，设备上线后另起一轮报告结果。用户在两轮之间说的话照常得到回应。
- 设备 SDK 目前不检查 `Invoke.deadline`（`sdk/nodesdk` 不读它）：延长截止时间只是让 Inbox 中的记录与日志一致，不影响执行。
- 网关进程崩溃时 Node 目录中的在线状态不会更新（原有限制）：这期间设备看起来仍在线，调用不会转入后台，直到调用的截止时间。
- 后台调用至多等后台时限：之后撤回，用户需要重新发起。
- 计量、配额不受影响：迟到结果开启的 Run 照常计量，超额时由 Worker 挂起。
