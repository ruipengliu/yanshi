# 评审：xinli 与 persona agent 的整体架构

> 状态：评审意见与讨论记录（2026-10-27），不是设计，不改变任何不变量 · 术语以 [CONTEXT.md](../../CONTEXT.md) 为准 · 评审对象：[整体架构](../design/persona-architecture.md)、[M7 内核补充](../design/m7-kernel-primitives.md)、[M7 Agent 生态](../design/m7-agent-ecosystem.md)、ADR-0043–0048
>
> 方式：Codex（gpt-6-astra，推理强度 xhigh）在只读沙箱中独立评审（第一轮，不给 Claude 对设计弱点的判断）；第二轮把 Claude 的核实与取舍交给它逐条反驳。Codex 提出的代码级事实由 Claude 在代码中核实后才进入结论（§2）。最终取舍由 Claude 决定（§3），设计文档已按 §4 修订，并新增 ADR-0049。

## 0. 结论

- **底座成立，方向不变。** 三层划分、Memory 与 Persona 的分工、`speaker_ref` 不改变来源、档位放在内核，双方都同意；通用静默窗口留在内核（Codex 第二轮修正了自己第一轮的意见）。
- **原设计在可靠投递、删除闭环与三方授权上没有闭合**，已按评审修订：出站流按事务可见性水位发布；新增交付确认（ADR-0049）与 EndUser 删除屏障；擦除中断进行中的 Run、Persona 以墓碑拒绝迟到的提交；统一展开器；三方的出境规则改为结构性标记，承诺收窄。
- **落地顺序调整**：可靠通知、交付确认与删除闭环提前到 P1；P6 先做授权上下文与出境规则，再接协议。
- **修订后仍需警惕的风险**（Codex 第二轮）：擦除经迟到提交、旧派生文本或通知过期复活；确认的覆盖范围；三方标记跨压缩与委托的传递、撤销的出口屏障。§4 的修订针对这三条，验收写进 P1 与生态第 0 步。

## 1. 讨论记录

### 第一轮：问题（Codex 独立作答）

> 只读评审 docs/design/persona-architecture.md、m7-kernel-primitives.md、m7-agent-ecosystem.md 与 ADR-0043–0048：适配性与内核缺口是否找对；逐个原语对照不变量找竞态、确定性与删除语义漏洞；按 10 万 DAU、验证到 100 万找容量与稳定性瓶颈；三层隔离与抽象层级；三方生态的信任与合规；P0–P6 的顺序。结论附 file:line，区分事实与推断，按 P0/P1/P2 排序并给修改建议，给出最有把握的 3 个与最没把握的 1–2 个判断。

### 第一轮：Codex 的回答

**底座成立，设计方向基本正确，但可靠投递、删除闭环和三方授权尚未闭合，不能据此承诺生产可用或百万 DAU。** 七处缺口大体找对；还缺通用的授权上下文、业务交付确认和 EndUser 删除屏障。日终规则、会员权益应继续留在业务侧，内核只执行通用策略。

以下文档、代码行为是事实；失败时序是据此推断。全程只读，未修改文件、未运行测试。

1. **P0：Outbox 的游标会永久漏事件。**  
   [原语:157](../../docs/design/m7-kernel-primitives.md)采用 `bigserial`：事务 A 取得101未提交，B 的102先提交；消费者推进102后，A提交的101将被跳过，擦除通知也可能丢失。须采用提交有序的发布协议或可确认投递机制，不能靠增大轮询窗口。此外，72小时过期没有补偿协议，`session_deleted` 又会随 Session 清理。应独立保留删除信封，定义游标过期后的对账路径。

2. **P0：A2A 白名单不能保证授权范围和立即撤销。**  
   [生态:58](../../docs/design/m7-agent-ecosystem.md)采用长期 Session；但[自动召回:24](../../internal/runtime/recall.go)只识别 EndUser、BusinessLine，不识别三方及范围。撤销笔记权限后，旧工具结果、回答、摘要仍可被追问出来。须让 `client＋授权版本` 贯穿召回、对象查询、上下文和响应出口；初版可禁自动召回、限制 `scope: run`，撤销时取消在途 Run。

3. **P0：`origin` 只覆盖首条输入，遗漏插话。**  
   [生态:59](../../docs/design/m7-agent-ecosystem.md)只规定 `RunRequested`；若沿用 Submit，活跃 Run 的第二条三方输入会成为 `Steered`，其[现有来源判定:78](../../internal/session/provenance.go)仍可能认作用户原话。应覆盖所有输入入口及重答复制，或明确三方请求排队、不允许插话。

4. **P0：“他人原话不外流”的拦截方法不成立。**  
   [生态:82](../../docs/design/m7-agent-ecosystem.md)复用 `grounded`，但[实现:53](../../internal/runtime/memgate.go)只是号码检查和二元组重合率启发式。长参数夹短引文、拆分或编码都可能漏检；摘要也可能逐字引用原话。应采用带来源分类的结构化出境字段、受限模板，并隔离未经授权的上下文。出境同意必须独立于“只读”和工具审批豁免；现方案尚不能兑现所声明的合规保证。

5. **P0：擦除可能残留并复活派生内容。**  
   [总体:104](../../docs/design/persona-architecture.md)对部分依据删除仅标“依据不全”：依据 A/B 的摘要仍可能保留 A 的原话；擦除通知先到、旧 Run 的变更集后到，还会重新创建内容。须增加持久擦除标记、Lineage 反向索引和提交时来源版本校验；重算前禁止读取受影响内容，并覆盖变更集日志、向量及缓存。已有压缩摘要也不能继续生成被删知识。

6. **P1：正文引用与修订缺少统一读取视图。**  
   [原语:60](../../docs/design/m7-kernel-primitives.md)只改 Transcript，而[Provenance:111](../../internal/session/provenance.go)仍从工具结果取文字：改成纯引用后，模型看到原文，闸门和注入判断看到空文；直接读取“最新版本”又可能把旧投影与新正文混用。应统一按日志序号、修订版本解析，并使相关判断失效重算。擦除、修订确实会改变前缀，应明确为不变量例外并测缓存退化；不能仅称“仍然确定”。

7. **P1：分区删除的保留上界算错。**  
   [原语:54](../../docs/design/m7-kernel-primitives.md)按创建日＋3＋7天删除，却称到期后最多再留一天。当天关闭的 Session 第7天到期，正文可能留到第10—11天；不同业务线的保留期也不能共用固定截止。应按到期日或保留类别组织分区，明确策略变更、清理积压和物理删除完成的含义。

8. **P1：Persona 故障兜底与代码不符。**  
   [总体:231](../../docs/design/persona-architecture.md)称调用失败使 Run 失败、读取位置不前进。实际上[Worker:774](../../internal/runtime/worker.go)只记录工具错误；模型仍可正常结束，随后[State:979](../../internal/session/state.go)提交读取位置。因此“读页成功→交付失败→回复稍后重试”会跳过未保存内容。须增加交付确认或业务已接受范围账本，并支持重放对账。

9. **P1：定时与重答各缺一段持久语义。**  
   [定时:134](../../docs/design/m7-kernel-primitives.md)超额仅记指标，未定义如何持久消费该次到期；重启可能重做。执行、跳过及下次到期都应落事件，与开启 Run 原子提交。  
   [重答:224](../../docs/design/m7-kernel-primitives.md)只过滤旧 Run，挡不住[压缩摘要:41](../../internal/runtime/transcript.go)中的旧回答；须使相交摘要失效重建，并保留原输入来源。

10. **P1：Oneshot 无 Session，不代表没有删除义务。**  
    [原语:195](../../docs/design/m7-kernel-primitives.md)仍按 EndUser 计量，而[Meter:75](../../internal/usage/meter.go)仅有 SessionID 才复查删除。调用开始后注销、模型随后返回，会重新写入实名用量。需 EndUser 删除屏障和写后复查，档位的在途写入同样适用。档位本身放内核合理。

11. **P1：容量验收缺少峰值与关键放大项。**  
    按一分钟一批、8小时集中采集推算，10万/百万 DAU 为约1667/16667批每秒；设计的550/5500只是全天平均。[审核实现:95](../../internal/service/captures.go)在整批命中后逐段复核，并非总是每批一次。还需计入 Event 元数据、WAL、索引和备份。  
    [队列认领:107](../../internal/workqueue/pgqueue/pgqueue.go)按优先级扫描再过滤停放项，百万定时需到期索引或独立停放结构。[单次调用:198](../../docs/design/m7-kernel-primitives.md)与问答共享准入，也不能保证预览不挤占 Run：应设预览上限、全局提供商预算和后台保底。隔库方向合理，但当前[存储装配:76](../../internal/app/stores.go)仍是单 PG 池，分片路由及故障切换必须进入验收。

12. **P2：三层与扩展清单可用，边界表述需收紧。**  
    Memory 存本人陈述、Persona 存结构化世界的分工合理；`speaker_ref` 保持不透明且不改变来源，也无明显冲突。但[总体:68](../../docs/design/persona-architecture.md)“独立 module 自动阻止 internal 导入”并不普遍成立，须依赖检查落实。五步清单应补来源、删除、授权、幂等验收；托管经 Grant 可保留方向，尚不能直接沿用现有委托作为安全证明。

落地顺序应调整为：P0 保留边界迁移；**P1 同时定义跨层擦除与可靠通知契约**，不能等 P4 才补；P2加入交付确认、定时持久语义和百万停放压测；P3补 EndUser 删除屏障；P4验收断网补传、Persona故障、消费者落后和数据库切换；P6先完成授权上下文与出境约束，再接协议。原有“一天跑通”和评测无回归不足以证明这些保证。

最有把握的三点：**Outbox 乱序提交会漏投；Persona失败不保证游标停住；工具白名单无法覆盖召回和历史数据授权。** 最没把握的是实际容量上限及真实模型下的整理成本：缺少峰值分布、长期数据集和目标部署压测。

### 第二轮：Claude 的核实与取舍（交给 Codex 逐条反驳）

> 下面是设计作者（Claude）对你第一轮 12 条意见的核实与取舍。你提出的代码级事实已逐条在代码中核对，全部属实。请逐条反驳：同意的简短说明；不同意或认为修法不成立的，给出仓库内证据与更好的方案；他漏掉而你认为重要的补上；你第一轮中经他提醒应修正的也明确说出。只读，不改文件。中文，2000 字以内。最后给出你认为修订后仍然存在的最大风险（前 3 条）。
>
> ## Claude 的取舍
>
> 1. **Outbox 漏事件：接受。** 修法：每行记 `pg_current_xact_id()`（xid8），按 (xid8, id) 排序、游标为 (xid8, id)，只返回 `xid8 < pg_snapshot_xmin(pg_current_snapshot())` 的行。可见性地平线之下的事务都已结束，之后提交的行的 xid 必然 ≥ 地平线，所以游标单调不漏；代价是长事务会拖住地平线（内核事务都短）。删除类事件（`session_deleted`、`capture_erased`）的出站行不随 Session 删除，照常保留 72 小时（只含 ID）。游标过期返回明确错误，对账走 Session 索引（按更新时间列出 Session）后重读事件。
> 2. **A2A 授权范围：接受，但不做通用的 ABAC。** 对外开放的 AgentDef 加载时校验 `memory.recall: 0`、`context.scope: run`；`origin`（client + 授权版本）随 MCP 调用以请求头传给 Persona，由 Persona 按范围逐次检查；撤销时取消在途 Run 并删除该三方的 A2A Session。
> 3. **origin 遗漏插话：接受。** 修法：A2A 入口在有活跃 Run 时直接返回忙（A2A 任务状态），不产生 `Steered`；A2A Session 不允许重答。比给 `Steered` 也加 origin 改动面小。
> 4. **他人原话不外流：接受，改为结构性规则，并收窄承诺。** 不用 `grounded` 启发式。规则：上下文中含有他人旁听片段（来源 FromOther）的 Run，调用 `a2a__*` 一律拒绝（确定性，按来源）；Persona 对外接口不提供旁听原文（Persona 本身不存原文，`cite_captures` 不给文字）；`a2a__*` 的审批不能被 `no_approval` 放宽。文档改为承诺"旁听原文不外流"，Persona 摘要中的转述按用户授权的范围提供，残留风险（摘要逐字引用）写明，并在整理指令与 Persona 检查中约束。
> 5. **擦除复活：接受。** Persona 提交时拒绝引用已擦除片段的操作（`cite_captures` 已返回 `erased: true`）；依据部分被擦除的对象立即不可读、移出检索向量，重新整理后恢复或删除；Persona 维护依据的反向索引。内核侧：`CaptureErased` 若与已有压缩摘要覆盖的范围相交，投影使该压缩失效，Transcript 回退到事件历史并照常重新压缩。
> 6. **统一读取视图：接受。** Provenance 产出引用，文字由同一个展开器按日志前缀中可见的最新修订版本解析，Transcript、写入闸门、注入判断共用；擦除、修订列为"请求前缀稳定"的显式例外并测缓存。
> 7. **分区删除上界算错：接受。** 改为：到期时 Janitor 照常逐 Session 物理 `DELETE`（删除时刻精确），分区只用于回收空间：分区中的 Session 全部删除后整片删除，不依赖 vacuum。
> 8. **Persona 故障时读取位置照样推进：接受，这也是现有实现的缺陷。** 内核新增通用的交付确认：流声明 `ack: [能力名]`，`RunCompleted` 时读取位置只提交到"最后一次成功的 ack 调用之前读到的最后一页"；未声明 `ack` 的流行为不变。xinli-day 声明 `ack: [mcp_xinli__file_changes]`。放进 P1，先修现有缺陷。
> 9. **定时与重答：接受。** `ScheduleFired` 与 `RunRequested` 在同一次追加中写入；超额写 `ScheduleSkipped`；下次到期由投影计算。重答：被重做的 Run 开始之后发生过压缩则拒绝重答（不做摘要重建）；重答复制原输入的来源字段。
> 10. **Oneshot 与档位的删除屏障：接受。** EndUser 注销记录删除屏障，计量与档位写入"先写、后查"EndUser 屏障。
> 11. **容量：接受。** 改用峰值（集中 8 小时，约 1700 / 17000 批每秒）与审核逐段复核的放大；队列：长停放（超过数小时）移到独立的到期表，认领只扫可认领项，P2 以百万停放压测；单次调用设业务线并发上限与提供商预算分配；分片路由（ADR-0028 只定了键，`app.Postgres` 仍是单池）列为超过单分片容量前的前置条件，P4 验收包括分片路由、故障切换。
> 12. **module 边界：接受。** 新模块路径不以 `yanshi/` 为前缀（`persona`、`xinli`），Go 的 internal 规则才生效；`make check` 另加依赖检查。五步清单补来源、删除、授权、幂等的验收项。
>
> **不采纳的一处**：你建议"日终规则留在业务侧"。定时的 `window`（静默满 q 即执行、否则最晚时刻加抖动）是通用参数，具体值由业务线在创建时给出，内核不知道"一天"；保留在内核，理由是静默判断需要流的写入时间，业务侧拿不到。

### 第二轮：Codex 的回答

多数方向同意，但 **1、4、5、8 尚未闭合**。以下失败时序是依据代码作出的推断。

1. **Outbox：排序修法成立，补偿方案不成立。** 同一快照的 `xmin` 以下事务均已结束，该水位可以解决乱序提交。[PG说明](https://www.postgresql.org/docs/16/functions-info.html#FUNCTIONS-TXID-SNAPSHOT)。但长事务拖住水位时，不能把尚未发布的行按写入时间过期删除。更关键的是，Janitor会[删除日志及索引](../../internal/janitor/janitor.go)，72小时后扫描索引无法找回删除事件。需要可枚举的持久删除/擦除账本，信封包含范围、原因；仅存ID不能在日志消失后恢复含义。

2. **A2A授权：接受简化，不必做通用ABAC。** 仍须在同步响应、任务查询、订阅和推送出口检查授权版本：取消Run、删除Session挡不住已经读入内存的响应。另[ask_user](../../docs/design/m7-agent-ecosystem.md)会引入用户新回答，应明确告知三方身份与披露用途，Persona范围检查覆盖不到它。

3. **拒绝插话、禁止重答：接受。** 这是合理的小改法；限制须覆盖该类Session的所有入口，而非仅A2A适配器。

4. **出境规则：仍有绕过路径。** [压缩会裁掉History](../../internal/session/state.go)，[委托任务变成FromRelay](../../internal/session/provenance.go)。因此“读他人原话→压缩或委托→调用A2A”可能不再出现FromOther。应持久记录“接触过他人旁听”，并沿压缩、委托传递，不能只扫描当前上下文。既然接受摘要逐字引用风险，承诺应改成“不开放原文接口及内容块”，不能仍承诺绝对不外流。

5. **擦除：检查和重压缩都不足。** 引用核验发生在[远端调用之前](../../internal/mcpcap/mcpcap.go)：核验通过→Persona处理擦除→旧调用落库，仍会复活。必须保存擦除墓碑，并在变更集提交事务内检查；反向索引不能替代它。清除Compaction也不会恢复已裁剪History，须重新加载日志；而[旧回复和调用参数仍参与压缩](../../internal/runtime/compact.go)，可能再次生成被删内容。应使受影响派生消息失效，或隔离相关Run后从有效来源重建。

6. **统一展开器：接受，但要绑定判断版本。** 修订后不能继续复用仅按`call_id`缓存的旧注入判断；模型请求、闸门和判断应使用同一个日志前缀与正文版本。

7. **分区：可作过渡，不能称容量问题已解决。** 逐行DELETE仍有WAL、索引成本；一个长期保留Session会拖住整片回收。应隔离保留类别并限定分区寿命。此外，DELETE不立即移除MVCC旧版本；“精确删除”要区分API不可见与物理清理期限。[PG说明](https://www.postgresql.org/docs/16/routine-vacuuming.html#VACUUM-FOR-SPACE-RECOVERY)。

8. **交付确认：当前修法会继续丢数据。** 读A、B两页，只提交A成功，却确认到B；而当前[业务拒绝](../../internal/xinlimock/changes.go)也会以[MCP成功响应](../../internal/xinlimock/xinlimock.go)返回。必须使用结构化业务回执，绑定已持久化的页或范围、stream及版本，只推进连续完整确认的前缀；“成功调用过某能力”不是交付证明。

9. **定时与重答：接受。** 压缩后拒绝重答是有效收窄。下次到期应记录已解析的UTC值，明确夏令时规则，避免重放依赖升级后的时区数据库。

10. **EndUser删除屏障：接受。** 应按业务线隔离，并覆盖注销期间的新Session创建等入口，不能只保护计量和档位。

11. **容量：方向接受，验收还需补竞态与公平性。** 到期表与可认领队列之间必须原子迁移，覆盖同时唤醒、取消、删除。业务线并发上限仍挡不住预览挤占问答，需预览子限额和后台保底。

12. **module边界：接受。** 独立导入路径配合依赖检查，足以落实此边界。

我明确修正第一轮两点：**通用静默窗口可以留在内核**，此前建议整体放业务侧过强；也不应把当前读取游标契约本身直接认定为缺陷——缺陷是将“读过”解释为“业务已交付”。新增ack是契约增强，必须先定义确认范围。

顺序基本接受，但EndUser屏障应随首个相关持久化入口落地，不机械等P3。P1还应验收“擦除跨库竞态＋消费者离线超过72小时”。

**修订后最大风险前三条：**

1. 擦除仍可能通过迟到提交、旧派生文本或通知过期而复活。
2. ack缺少业务覆盖范围证明，仍可能静默跳过未交付内容。
3. 三方来源标记未跨压缩、委托保持，授权撤销也尚缺完整出口屏障。

## 2. 核实

Codex 的代码级陈述逐条在代码中核对，全部属实：

| 陈述 | 位置 |
|---|---|
| 召回只按 EndUser 与读取方业务线检索，不认三方与授权范围 | `internal/runtime/recall.go` 的 `recall` |
| 插话（`Steered`）除 `from_call` 外按用户原话推导来源 | `internal/session/provenance.go` |
| 来源推导直接读 `captures` 结果中片段的文字（改为只存引用后会读到空文） | `internal/session/provenance.go` 的 `resultPieces` |
| 委托派生的输入推导为转述（FromRelay） | `internal/session/provenance.go` |
| 工具调用失败只记为错误结果，模型可正常结束 Run，`RunCompleted` 随即提交读取位置 | `internal/runtime/worker.go`、`internal/session/state.go` |
| 模拟服务拒收变更集时仍返回成功的 MCP 响应，拒绝只写在文字中 | `internal/xinlimock/changes.go`、`internal/xinlimock/xinlimock.go` |
| 引用核对（`cite_captures`）发生在远端调用之前 | `internal/mcpcap/mcpcap.go` |
| 压缩裁掉投影中的 History | `internal/session/state.go` 的 `ContextCompacted` 分支 |
| 计量只在有 Session ID 时复查删除记录 | `internal/usage/meter.go` 的 `record` |
| 认领按优先级扫描、再过滤停放项 | `internal/workqueue/pgqueue/pgqueue.go` 的 `Claim` |
| 存储只有单个连接池，分片路由未实现 | `internal/app/stores.go` 的 `Postgres` |
| Janitor 删除日志与索引后，删除事件无从由它们找回 | `internal/janitor/janitor.go` |

Claude 另外核实：根模块路径是 `yanshi`（`go.mod`），新模块若用 `yanshi/persona` 之类的路径，Go 的 internal 规则不会阻止它 import `yanshi/internal/...`，原设计"编译器保证"的说法不成立。

## 3. 决定

### 3.1 接受

| # | 问题 | 修订 |
|---|---|---|
| 1 | 出站流按自增序号推进会永久漏掉晚提交的行；过期与删除后无法补偿 | 按 xid8 与快照 `xmin` 水位发布；删除信封（带范围）不随 Session 删除；游标过期时经删除记录与 Session 索引对账 |
| 2 | A2A 白名单管不到召回与历史 | 对外 AgentDef 校验 `recall: 0`、`scope: run`；`origin`（三方与授权版本）随 MCP 调用传给 Persona；出口检查授权版本；撤销时取消在途 Run、删除 Session；`ask_user` 标明三方 |
| 3 | `origin` 遗漏插话 | 这类 Session 有活跃 Run 时拒绝、不允许重答，在 service 中按 AgentDef 执行 |
| 4 | 文字重合拦截不住他人原话外流；压缩与委托会洗掉来源 | Session 级、只增不减、随委托传递的"听过他人旁听"标记，置位后不能调用三方；`a2a__*` 的审批不能被放宽；承诺收窄为"旁听原文不开放" |
| 5 | 擦除可能被迟到的提交复活；清除压缩不足以清除派生文本 | 擦除中断活跃 Run；声明流的 AgentDef 必须 `scope: run`；Persona 记墓碑、在提交事务内检查；部分依据的对象不可读并移出向量 |
| 6 | 正文改为引用后，闸门与判断看到空文 | 统一展开器按日志前缀解析，Transcript、闸门、判断共用；判断按版本缓存；擦除与修订列为前缀稳定的显式例外 |
| 7 | 分区删除的保留上界算错 | 删除仍逐 Session 精确执行，分区只回收空间；区分"行不存在"与"空间回收"；声明流的 AgentDef 必须有有限保留期 |
| 8 | 交出失败时读取位置照样推进 | 业务线结构化回执，读取位置只推进到连续确认的前缀（ADR-0049）；空时段交出空变更集 |
| 9 | 定时的跳过与重做没有持久语义；重答挡不住压缩摘要中的旧回答 | `ScheduleFired` 与 `RunRequested` 同一次追加，跳过写 `ScheduleSkipped`，UTC 写入事件、写明夏令时规则；重答在压缩之后拒绝、复制原输入的来源字段 |
| 10 | 单次调用与档位在注销期间可能写回实名数据 | EndUser 删除屏障，覆盖新建 Session、计量、档位、单次调用，随 P1 落地 |
| 11 | 容量按全天平均估算；停放扫描；预览挤占问答；分片路由未实现 | 按峰值（约 1700 / 17000 批每秒）与复核放大；远期定时进到期表、原子迁移；单次调用子限额与后台保底；分片路由列为 P4 前置 |
| 12 | 独立 module 不能自动阻止 import `internal/` | 模块路径用 `persona`、`xinli`；`make check` 做依赖检查；五步清单补来源、删除、授权、幂等四项验收 |

### 3.2 不采纳

- **日终规则整体留在业务侧**（Codex 第一轮）：不采纳，Codex 第二轮已撤回。定时的窗口参数由业务线给出，内核不知道"一天"；静默判断需要流的写入时间，业务侧拿不到。
