# 评审：xinli 与内核的划分，以及提升效果的发力点

> 状态：评审意见与讨论记录（2026-10-26），不是设计，不改变任何不变量 · 术语以 [CONTEXT.md](../../CONTEXT.md) 为准 · 关联：[旁听](../design/captures.md)、[旁听业务线 xinli](../design/captures-xinli.md)、[xinli 的建模](../design/captures-xinli-model.md)、[工作日评审](./2026-10-25-xinli-workday.md)、ADR-0022、ADR-0037、ADR-0040、ADR-0042
>
> 方式：Claude 先独立评估；再请 Codex（gpt-6-astra，推理强度 max）在只读沙箱中阅读仓库后独立作答（第一轮，不给 Claude 的结论，以免锚定）；第二轮把 Claude 的结论交给它逐条反驳。Codex 提出的代码级事实由 Claude 在代码中核实后才进入结论（§2）。最终取舍由 Claude 决定（§3）。

## 0. 结论

- **边界划得对。** 平台管运行、Capture、来源与引用、读取位置、审批与删除；xinli 管交谈语义、项目、承诺修订、期限与提醒。ADR-0042 整体改建模，平台只改了时段的命名与引用附上说话时间，proto 与 `session` 不动，是边界正确的直接证据。xinli 推动的内核原语（流、来源推导、读取位置、`context.scope: run`、按 AgentDef 的 Retention、Memory 历史、`cite_captures`）都是通用的。
- **内核有一处合规缺口**：Memory 的健康许可只看模型自报的类别（`internal/memory/service.go` 的 `Save`），他人的健康信息写成 `relationship` 就绕过了 ADR-0022（工作日评审 F3 中出现过）。先修（§4）。
- **效果的瓶颈不在执行语义，而在业务正确性与评测。** 小用例几乎全过、整日用例 0/6；xinli 的效果相当部分来自 `internal/xinlimock` 中的规则与回执（给模型看的文本），生产的业务线若另写一份，评测结论带不过去。
- **发力点按顺序**：真实的多日评测 → 业务线契约与一致性套件 → 按时段拆 Run 的实验 → 召回与归属、承诺语义与提醒 → 助手的查询工具（§3.3）。

## 1. 讨论记录

### 第一轮：问题（Codex 独立作答）

> 1. xinli 业务与内核的架构划分是否合理？哪些该在内核、哪些该在业务线，现在有没有放错位置的东西（双向都看）？
> 2. 后续要提升 xinli 的实际效果（每日整理、项目归集、承诺与提醒、助手问答），发力点应该在哪里？按优先级给出依据、预期收益、代价，以及放在内核还是业务线；也说明哪些方向不值得投入。
>
> 先读 AGENTS.md、CONTEXT.md、charter、captures*.md、ADR-0036/0037/0039–0042、agents/xinli-*.yaml、internal/xinlimock、internal/capture、internal/mcpcap/cite.go、internal/runtime/memgate.go、工作日评审 §0–§9、m4-eval §12、evals/capture-*.yaml、internal/eval。结论要有仓库内的证据，区分事实与推断；对评测数据保持怀疑；给出最有把握的 3 个判断与最没把握的 1–2 个。

### 第一轮：Codex 的回答

总体划分合理；下一阶段应主攻 xinli 的业务正确性与查询能力，内核补通用机制。本次只读、未复跑；数值均引用仓库记录。

架构事实：平台管运行、Capture、来源与引用、读取位置、审批和删除；xinli 管交谈语义、项目、承诺修订、期限与提醒。ADR-0042 已把语义切分移回业务；同仓库的 xinlimock 是开发适配，不等于污染内核。[ADR-0042](../../docs/adr/0042-xinli-entities-by-changeset.md:11)、[mock:1](../../internal/xinlimock/xinlimock.go:1)

双向问题：内核仍硬写“之后七天”来补模型日期能力，宜成为可替换展示策略，但不值得优先重构；反向缺口是通用静默触发仍靠业务定时补，Trigger及可替换Loop尚未实现。静默触发应进入平台，日界、项目编排及提醒策略仍属业务。[capture:199](../../internal/capture/capture.go:199)、[m5§11](../../docs/design/m5-inputs-triggers-loops.md:222)

另有安全缺口：Memory健康许可只检查模型填写的类别。我的判断是，防止改填类别绕过许可的通用校验应在平台，摘要禁健康则仍是xinli规则。[service:178](../../internal/memory/service.go:178)

建议按以下顺序投入，收益是推断，成本为相对估计：

1. **业务：承诺、归集与提醒闭环，成本中高。** §9仍有过时承诺；当前召回靠字符相似度，“核实”只核说话人。先分测候选召回与归属判断，补承诺对象、否定和转述判断，验证改期后的实际提醒及用户纠错；用真实多日留出数据衡量误报、漏报。收益是减少错归、漏改与无用提醒。[召回与核验](../../internal/xinlimock/xinlimock.go:348)
2. **业务：补助手查询，成本中。** 现有`recent_days`只读已汇总日期，`project_digest`只列项目未完成承诺；缺直接查询白天无项目承诺、完成历史的入口。增加按时间、状态、主题查询及修订依据，才能可靠回答“上次怎么改的”，比扩写提示词更有把握。[查询代码](../../internal/xinlimock/xinlimock.go:221)
3. **业务策略＋内核通用支持：减少已交付页的上下文，成本中高。** §9 workday用量约62→122万tokens。让后续整理依赖账本，单独设计可恢复的处理单元，保留回放与来源检查，验证重读、漏交及缓存代价。预期降低延迟和成本，再评估强模型；节省幅度尚无证据。[建模§9](../../docs/design/captures-xinli-model.md:161)
4. **内核：实现静默Trigger，成本中。** 减少空转、缩短改期到修订的等待；不会直接提高归集准确率。按ADR-0040实现，不扩成业务日程系统。[ADR-0040](../../docs/adr/0040-platform-triggers-declared-in-agentdef.md:11)

评测须降权：单人9200字剧本、自动审批、mock预置项目归集，未验证整理→问答→提醒全链。§9记录lite为0/6；健康失败含已拒调用，不能说已落库泄漏；第三方承诺修复只重跑小例。[评审§1、§3、§9](../../docs/review/2026-10-25-xinli-workday.md:275)、[mock:34](../../internal/xinlimock/xinlimock.go:34) 小例通过率还有采样噪声，曾保留较好的3/3基线，不能证明产品可用。[m4-eval§12](../../docs/design/m4-eval.md:283)

不值得优先做：平台语义切分（信号不足）、全面知识图谱（复杂度高）、直接换强模型（§9 GLM工作日43分钟、oneshot超时）。

**最有把握**：①总体边界正确；②说话人核验不等于承诺正确；③小例不能替代完整闭环。**最没把握**：改召回能解决多少归集错误，以及上下文减负的实际收益。

> ## Claude 的结论
>
> **总判断**：边界划得对，不用改；问题在于 xinli 的效果大部分来自"模拟"的业务线（internal/xinlimock），生产环境要另写一份，评测结论带不过去；评测本身也还不能可靠地判断效果。效果发力点几乎都在业务线与评测一侧，内核只需补几处小改动。
>
> **划分合理**
> - ADR-0042 整体改建模，平台只改了时段命名与引用附说话时间，proto 与 session 不动：边界对的最直接证据。
> - xinli 推动的内核原语（Stream、Provenance、读取位置、context.scope: run、按 AgentDef 的 Retention、Memory 历史、cite_captures）都是通用的；cite_captures 只证明可信元数据、不给原文，是对的内核职责。
> - 摘要经 MCP 拉取而不是推入（ADR-0037），信任边界对。
>
> **需要调整（按影响）**
> 1. 最有价值的逻辑放在"模拟"里：xinlimock 约 3000 行，含变更集检查、期限换算、健康兜底、rev 乐观并发、用户优先、宽容解析、回执与拒绝原因（changes.go:571、:648）。回执是给模型看的文本，评测验证的是"指令+回执"的组合；生产重写就失效。建议定位为参考实现并交出契约，或仿 eventlogtest 写工具契约的一致性套件，并让评测能指向外部 MCP Server（现只能进程内，runner.go:299）。
> 2. 内核工具链写死 xinli：XinliSetup/XinliExpect（suite.go:60、:97）、judgeCoverage、serve -xinli-mock、/v1/debug/xinli*。一条业务线时可接受，第二条到来前抽成通用 fixture 接口（Seed/State/Check）。
> 3. 业务术语混进平台词汇：CONTEXT.md 的 Project/Exchange/Changeset/Revision/Commitment/Awareness，ADR-0042 在平台 ADR 序列中；exchange_gap（agentdef.go:56、event.proto:375）现在控制的是 Span。建议业务线单独文档与术语区，YAML 加 span_gap 别名，proto 只补注释。
> 4. 健康信息写入 file_* 的拦截在 mock（changes.go:208），而章程把合规定为基座能力；可考虑平台对 MCP 调用参数做 ADR-0030 式只收紧的判断（开放问题）。
>
> **效果发力点（按优先级）**
> 1. 先修好评测：小用例 96/96、workday 0/6。数据只一天剧本约 9200 字、说话人标签全对、无识别错误；项目召回用字符二元组（xinlimock.go:371），纯度不达标部分在测 mock 召回器；噪声大（3/3 与 9/12）。补几天带金标注的数据，注入识别与说话人错误，指标改为分项：承诺精确/召回、修订正确率、提醒精确率。
> 2. 一个 Run 只整理一个时段，借此用上更强模型：GLM 评分 5.0 vs lite 2.67，GLM 只因延迟 43 分钟被否；tokens 62 万→122 万源于一个 Run 顺序处理全天、上下文累积。不用改内核：captures 一页至多一个时段、读取位置在 RunCompleted 提交、scope: run，已支持"读一个时段→交出→结束"；当天整理只剩 day_ledger+file_day。不选"丢弃已交出的页"，因为破坏前缀缓存不变量。细节：ADR-0040 "同一位置只触发一次"，拆 Run 后不会自动连续触发，需业务线循环提交或扩展触发。拆完重跑 lite 与 GLM 矩阵再定模型。
> 3. 项目归集（纯度 6/6 不达标，最大缺口）：mock 先用嵌入召回、候选附最近交谈标题；再看是否把归属最终判定移到当天整理（全天视野）；unsure 使用率单独作指标。
> 4. 承诺精确率即提醒质量（36–42 条/天仍偏多）：规则交给业务线（无期限不提醒、当天已过期不提醒）；平台实现"引用文字的核对"（captures.md §12）；必要时 ADR-0030 只收紧的承诺判断。
>
> **不建议**：继续往 xinli-day 指令打补丁（57 行，补丁造成过回归：回执提示使第三方承诺误记 5/6；F6/F7 在强模型下消失）；更多内核改动（压缩、核对、注入防护在真实一天里站得住，瓶颈不在执行语义）。

## 2. 核实

Codex 的代码级陈述逐条在代码中核对：

| 陈述 | 结果 |
|---|---|
| Memory 的健康许可只检查自报的类别 | 属实：`Save` 只在 `r.Category == Health` 时检查业务线是否开启；同一内容写成 `relationship` 不受限制。工作日评审 F3：母亲的血压在 `no_health` 的业务线里以 `relationship` 写入，只多一次审批 |
| 助手缺少直接查询承诺的入口 | 属实：`project_digest` 只列本项目未完成的承诺，`recent_days` 没有参数、只列已汇总日期的交谈；归属 `none` 的承诺、完成与改期的历史都查不到 |
| 评测已经通过 HTTP MCP 调用 mock | 属实：`xinlimock.Start` 监听本机端口并以 `mcpcap.Server{URL: ...}` 登记；绑死在 mock 上的是 Seed、State 与断言（`internal/eval/runner.go` 的 `setup.xinli`、`checkXinli`） |
| 注入判断默认关闭，开启也只是影子模式 | 属实：`serve -injection-check` 默认 off，`DecisionMade` 都是 `shadow`（[判断](../design/m6-decisions.md) §8）。工作日里挡住他人指令的是模型本身与不含高风险能力的白名单，不是注入判断 |

## 3. 决定

### 3.1 接受 Codex 的

1. **Memory 健康许可按内容判断**（Claude 第一轮漏了）：内核的合规缺口，立即修（§4）。
2. **助手的查询工具**（Claude 第一轮漏了）：按时间、状态、对方、主题查询承诺并附修订依据；补工具，而不是靠换模型。
3. **修正"生产要另写一份"**：应复用领域核心（变更集、账本、期限换算、回执），mock 只是其内存存储；评测接真实服务只缺 Seed/State 的契约。
4. **修正"注入防护站得住"**：没有验证过，见 §2。
5. **按时段拆 Run 是实验，不是结论**：GLM 不只是慢（过时承诺 1/2、纯度不达标 2/2），tokens 翻倍也没做消融。实验须处理续页、被拒后重交、无进展退出；当天整理仍要交对账的变更集。
6. **反对的是无依据地堆提示词，不是改规格与回执**：第三方承诺那次修改是有效的反例。
7. **96/96 与 0/6 来自不同版本、用例与断言**：只说明小用例不能预测整日效果，不是回归率。

### 3.2 不采纳或下调的

- **把"之后七天"的日期列表改为可替换的展示策略**（Codex 第一轮）：不采纳。它是通用的、经评测验证（`capture-relative-date` 1/3 → 6/6），改造没有收益。
- **平台检查 MCP 调用参数中的健康信息**（Claude 第一轮）：撤回。摘要不写健康信息是 xinli 的政策；平台的缺口是 §3.1 第 1 条。
- **下调**：平台触发（不提升准确率，业务线可以提交）、`exchange_gap` 改名（captures.md §5 已写明只管分页）、内核层面的"丢弃已交出的页"（破坏前缀缓存不变量）。若拆 Run 的实验成功，ADR-0040 的"同一位置只触发一次"需要扩展，作为依赖记下。

### 3.3 发力点（按顺序）

| # | 做什么 | 在哪一侧 | 验收 |
|---|---|---|---|
| 1 | 多天、带转写噪声与说话人错误的金标数据，覆盖整理 → 归集 → 提醒 → 问答 → 用户纠错；分项指标：承诺精确率与召回率、修订正确率、提醒精确率 | 评测 | 指标可复现、噪声可估计（多次运行的方差） |

第 1、2 项的先后：评测可信之前迭代方向都是噪声，所以评测在前；生产的业务线一旦开工，契约须先于它的实现，届时两者对调。

## 4. 落地：Memory 健康许可按内容认定（2026-10-26）

实现见 [Memory 设计](../design/m4-memory-grant.md) §2 与 [M0](../design/m0-core-primitives.md) §4：

- `internal/memory/health.go`：健康信息用词。内容中出现时不论关于谁都只能写入 `health`：业务线未开启一律拒绝（并告诉模型不要换个类别或说法），开启的要求改用 `health`。
- `memory.Service.Check`：`Save` 中不依赖存储、没有副作用的检查；新增的 `capability.Checker` 让 Worker 在审批与写入闸门之前调用它，注定被拒绝的写入不再先请求审批。
- 同一件健康信息之前以别的类别记下的，改写为 `health` 时不按重复吞掉：新的写入、旧的失效。

改动经 Codex 对抗式审阅（同一模型与推理强度），它的 6 条全部采纳：去重吞掉改写（P1）、用词误伤职业（"心理咨询师""药物研发""复查合同"）与漏判（"降压药""乳糖不耐受""透析""收缩压"）、注定被拒的写入先审批、评测会空过（补正向断言与开启健康信息的对照用例）、两处拒绝提示不一致。runtime 单元测试与模拟测试的注入（`internal/sim/memprecheck.go`，覆盖统计 `MemoryPrechecked`）由 Codex 编写、Claude 审阅；去掉 Worker 中的预检后两者都失败。

评测（各 3 次）：新增 `memory-health-family`、`memory-health-family-disabled`、`capture-health-other-person` 均 3/3，已加入基线；`memory-health-recall`、`capture-health-*`、`capture-memory-*`、`memory-gate-user-stated`、`memory-save-intro`、`call-remember-allergy` 与基线相同。第一次运行 `memory-*` 时 `memory-refuse-id-number`（先回复"记下来了"再被证件号规则拒绝）与 `memory-recall-new-session`（改用 `ask_user` 反问）各 2/3，两者的日志中都没有触发健康规则，属于已记录的波动。

未做：不回溯已有的记忆（上线前没有存量数据）；换个说法的健康信息（"母亲身体不太好"）仍只靠写入指令，模型层的判断按 ADR-0030 留待留出集。
