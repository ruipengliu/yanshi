# 评审：现有 ADR 是否阻碍架构发展

> 状态：评审意见（2026-11-14，基于 `0d83d2d`），不是设计，不改变任何不变量 · 术语以 [CONTEXT.md](../../CONTEXT.md) 为准 · 关联：[章程](../charter.md)、[docs/adr](../adr/)、[部署](../design/deployment.md)、[Persona 架构](../design/persona-architecture.md)
>
> **执行情况**：负责人于 2026-11-14 全部批准；第一批（§9 第 1–14 项）已于同日执行，现状见 [ADR 索引](../adr/README.md)。第二批的五项已写成 ADR（ADR-0054–0057、Persona ADR-0002），2026-11-15 全部批准方向，其中 ADR-0054 已实现；第三批保留。§8 的第 1 项（Memory 写入闸门的文字覆盖）已于 2026-11-15 修复。
>
> 本文只给出发现与建议处置。每一项须经负责人逐条批准（§9）后，再新增、修订或整合 ADR；代码改动另立任务，走 `make check`、`make sim`，涉及给模型看的文本时加 `make eval`。本文综合了两份评审：一份由本会话完成（含与 Codex 的两轮讨论，附录 A），另一份由负责人提供（附录 B）。

## 0. 结论

核心不变量没有阻碍发展，应当保留：Event 日志是唯一事实源、契约在 `proto/`、沙箱内无受信组件、按键分片、三层分离。主要问题有四类。

1. **失效的正文仍在指导开发。** 0036、0039、0040、0007、0028 的正文与现行实现或其他 ADR 矛盾，只靠别处的补记或状态行说明。本项目主要由 Agent 开发，Agent 按正文行事，这比任何一条"过硬"的决定代价都大。
2. **业务规则写进了内核编号。** 内核 ADR 中有 7 条与旁听或 xinli 相关（0036、0037、0039、0042、0044、0049、0050），第二条业务线接入时，它要先读懂 xinli 才知道哪些约束属于内核。
3. **"当前的能力边界"写得像永久规则。** 0031 的串行委托与纯文字交接、0041 的外部循环（尚未实现）、0051 的旧数据不可迁出，都是阶段性限制，正文却没有标明。另外，51 条中只有 0007、0010、0021、0039、0048、0050 写了何时重新评估。没有重审条件的规则只会被绕开，不会被推翻。
4. **有两处可用性与性能问题，需要新增决定。**
   - 内容安全服务不可用时，长 Run 会失败（§3.1）。
   - Persona 每次全量装载用户的数据（§3.2）。

另有一处安全缺陷，与 ADR 文字相关，须在上线前修复（§2.1）。

落地顺序：先做第一批的文档修订（§2）；新增决定中优先设计审核故障恢复与 Persona 按需读取（§3）；委托、外部循环与存量迁移随后推进；§4 的问题保留，暂不批准替代方案。

## 1. 方法与前提

**基准。** 以[章程](../charter.md)的 G1–G9、设计原则与 §8 成功标准为方向；同时检查内部问题：ADR 之间的矛盾、取代链断裂、正文与代码不符、缺少重审条件。

**负责人已确定的前提。**
- 私有化部署（ADR-0001）仍是硬约束。
- 第二条业务线会到来，形态未知。
- 系统尚未上线（[上线检查清单](../launch-checklist.md)除委托一项外均未完成），没有真实用户的日志需要兼容。
- 多个 EndUser 共享一个 Session（群聊、家庭共享）不在路线图上。

**三条原则**（两份评审一致）：
- 不把性能优化变成替换事实源；
- 不把能力扩展变成放宽权限；
- 不把未来方向写成当前承诺。凡是"方向已认可、尚未实现"的内容，正文必须这样标明。

**分级标准：推翻代价 × 被依赖程度。** 一级是推翻即重写，二级是结构性约束，三级是局部决定、推翻代价低。

## 2. 第一批：现在即可修订的表述与权威关系

### 2.1 Memory 写入闸门对多数文字失效（0023，安全缺陷）

[ADR-0023](../adr/0023-memory-write-gate.md) 规定：Session 中出现过外部内容时，要写入的内容如果在用户原话中"字符二元组覆盖不足一半"，就须用户批准。实现中，`bigrams` 只收汉字（U+4E00–U+9FFF）、ASCII 小写字母与数字（`internal/runtime/memgate.go:85-88`）。`grounded` 在内容的二元组为空时直接返回"有依据"（`memgate.go:71`）。

**后果。** 日文假名、韩文、西里尔字母、带变音的拉丁字母、汉字扩展区组成的内容，只要不含邮箱、链接与号码，在含外部内容的 Session 中写入 Memory 时一律免审。这正是 0023 要防的记忆投毒。

**建议。**
- 代码：二元组为空时按"无依据"处理，失败保守；覆盖 Unicode 字母与数字类别；补测试。加入上线检查清单。
- ADR：追加修订，写明匹配算法可以替换，但必须失败保守。重审条件：多语言业务线接入，或评测中闸门的误报、漏报越过阈值。

### 2.2 旁听相关的 ADR 互相修订，正文与实现不符（0036、0037、0039、0050）

- [0036](../adr/0036-captures-are-text-only.md) 正文写"读过 Capture 的 Run 一律经过注入判断"，后果写"注入判断与高风险审批不依赖标签"。[0050:43-47](../adr/0050-capture-text-in-the-business-line.md) 补记说这两句与现行实现不符：注入判断只检查他人与外部来源，且目前只以影子模式记录；误标为佩戴者的他人文字，可以为 `memory_save` 提供依据从而免审。但 0036 的正文没有改，只在状态行指向 0050。
- [0039](../adr/0039-captures-by-stream-provenance-derived.md) 仍规定"采集按流区分""读取位置是结构化的"，0050 已删除整套流与读取位置。但 0039 的"来源由平台推导"仍是现行原则。
- [0037](../adr/0037-tiered-retention-by-daily-capture-sessions.md) 混合了两种东西：内核机制（Retention 按 AgentDef 覆盖）与 xinli 的业务模式（每天一个旁听 Session，每晚归集到 Project）。0050 又加了绝对删除期限 `delete_at`。
- 退役已基本完成：`agents/*.yaml` 中已无 `streams:` 或 `captures: true`，[CONTEXT.md:130](../../CONTEXT.md) 写明旧 `CaptureAppended` 只为解码日志保留。但它仍在 `proto/yanshi/v1/event.proto:532` 与 `internal/session/state.go` 中。

**阻碍。** 读 0036 的 Agent 会以为"标签错了也有注入判断兜底"，并在此基础上扩展信任。错误的安全说明会被当作不变量继续强化，这是本次评审中代价最大的误导。

**建议：写一条新 ADR 整合 0036、0039、0050 与 0037 的内核部分，并取代它们。** 不能一刀切地废止，因为其中仍有有效的来源与安全原则。新 ADR 须满足：
- **附一张逐条对照表**：0036、0037、0039、0050 的每一条决定与后果，标为"沿用 / 修订 / 失效"，并写明去向。旧 ADR 页首指向这张表，不能只写"见 0050"。
- **来源由平台推导，映射固定且封闭。** 调用方只能提交证据字段（结构化说话人等），最终的 `Provenance` 由平台推导：本人的话算用户原话，他人的话算外部内容。业务线不能配置映射，也不能把内容映射为平台来源。这个映射直接决定 Memory 写入是否免审（`internal/session/provenance.go:126`）；按当前配置解释旧事件，还会改变回放结果。平台校验了结构，不代表说话人标签必然真实；新 ADR 要把这一点写明。
- **如实写出现行的安全边界**：误标的后果、注入判断目前只在影子模式、哪些审批不依赖标签。这些内容取自 0050 的补记，在新 ADR 中作为正文。
- **写入 Retention 的内核部分**：按 AgentDef 覆盖、`delete_at`、0050 的擦除契约与"保留 Memory"的约定，一项都不能漏。
- **不借整合之机泛化或改名。** 内核现有的渲染、写日志前审核与写入校验保持原样。是否把它泛化为"登记内容类型 + 受信适配器"，留到出现第二类具体内容时再验证（§4.1）；那时不要求第二条业务线已经上线。

0037 的业务部分迁为 xinli 的业务 ADR（§6.1）。

### 2.3 "一条业务线一个单元"与跨业务线共享 Memory 冲突（部署设计、0051、章程 G4）

- [deployment.md:11](../design/deployment.md)："一条业务线一个单元（cell）……一个 Session 只属于一个单元，入口按业务线路由，不做跨单元双活。"
- [0051:41](../adr/0051-shard-slots-and-id-location.md)："同一 EndUser 的跨业务线 Memory / Grant 在同一库。"
- 章程 G4 与 [0003](../adr/0003-memory-owned-by-business-line-shared-by-grant.md)：经用户 Grant，Memory 可以跨业务线共享。

三者同时成立时，跨业务线的召回与 Grant 就是跨单元操作，而部署设计没有跨单元路径。现在只有一条业务线，问题还没暴露；第二条业务线接入当天就会暴露。

**建议（需批准）。** 修订部署设计：单元是"一组共享 EndUser 身份与 Memory 的业务线"，默认所有业务线在同一个单元；只有不与其他业务线共享 EndUser 的业务线（例如私有化客户的独立部署），才单独成为一个单元。在 0051 中写明这一适用范围。按业务线拆单元仍可作为扩容手段，代价是这些业务线之间不能共享 Memory，这一点写进重审条件。

### 2.4 生产沙箱的决定悬空（0010）

[0010](../adr/0010-k8s-gvisor-for-production-sandboxes.md) 自标暂缓，并写着"须一并决定：云厂商沙箱只用于公有云部署……还是修订 ADR-0001"（`0010:11`）。可是 [deployment.md:47](../design/deployment.md) 已经把 gVisor RuntimeClass 当作定论，[上线检查清单:14](../launch-checklist.md) 又写"选定云厂商服务或自托管隔离方案"。三处说法不一致。

**建议：写一条新 ADR 取代 0010，只决定 0010 自己留下的那个分叉，隔离技术仍然待定。**
- 自托管隔离是基线。理由是私有化为硬约束，0010 提出的"修订 ADR-0001"一支因此不成立。
- gVisor、Kata、Firecracker 中选哪一个仍然待定，依据有四项：安全边界、客户 IDC 能否部署（内核版本、嵌套虚拟化）、运维成本、压测结果。压测不能单独决定。
- 云厂商沙箱只作为公有云部署时可选的 Provider，按 0001 的规则显式列出、可以配置关闭。
- 选型之前，`deployment.md:47` 与上线检查清单第 14 行都不得把任何一种隔离技术写成定论。

### 2.5 0040 已经失效，却仍被引用

[0040](../adr/0040-platform-triggers-declared-in-agentdef.md) 唯一的触发方式是"流上静默"，已被 0050 取消；按钟点的定时由 [0045](../adr/0045-schedules-in-the-kernel.md) 负责。代码中没有触发的实现。[xinli-model.md](../design/xinli-model.md) 第 118、135、192 行仍把 0040 当作现行或待实现的机制。

**建议。** 先把 0040 中仍然有效的保证迁入现行决定，再把 0040 整体标为被 0045 与 0050 取代：
- "来源是平台、客户端不能伪造标记"：0045 已经写明（`0045:15`）。
- "唤醒沿用后台调用的停放"：0045 第 15 行写的是"复用后台调用与触发的停放（ADR-0035、ADR-0040）"，依赖了 0040。须改为只引用 0035，或者在 0045 中自己写清楚。
- 同时修正 `xinli-model.md` 的三处引用。

### 2.6 通话的媒体通道被两条 ADR 锁死（0024、0027、0005）

章程 §10 写着"弱网下的 Opus / RTC 待评估"。真正禁止另开媒体通道的是 [0027:7](../adr/0027-call-relayed-through-the-gateway.md)："设备不直连模型厂商，也不另开 WebRTC 通道。"[0024](../adr/0024-one-connection-per-host-app.md) 又规定一个 HostApp 只有一条 Connection。只修订其中一条，就会产生新的矛盾。

**建议。**
- 0024 与 0027 一起修订："一条 Connection"只约束控制面与事件流；Call 的实时媒体可以另开通道，鉴权与生命周期从这条 Connection 派生。这只是放开口子，不设计 RTC。在另立 ADR 设计之前，现有实现照旧遵循现有决定，修订本身不带来替换能力。
- 0005 与 0027 中"语音模型只经 `run_task` 做事"的决定保留：它保证了通话中做的事都经过写日志、审批与内容安全（0004、0021）。补写重审条件，以下任一出现即重审：
  - 实时模型能在不绕过写日志、审批与内容安全的前提下直接发起 Capability 调用；
  - `run_task` 回注的延迟成为评测上可测量的主要瓶颈；
  - 弱网下的通话质量达不到上线要求。
- 0013（直接拉取）与 0026（共享 Go 核心）同样标明是现行的技术选择，并补写重审条件（§5）。

### 2.7 分片：进度描述互相矛盾，阶段缺口没有标明（0028、0051）

- [0028:39](../adr/0028-shard-keys.md) 写"现在不分片"，`0028:21` 写"多库装配另行完成"；[0051:7](../adr/0051-shard-slots-and-id-location.md) 写"实现包含按键多库装配、有界遍历、部分可服务"。
- 0051 §5 写明只支持新建单元，或全部槽位留在库 0 的既有单元；把旧数据迁离库 0 不在支持范围，扩容要停写迁移（`0051:78-81`、`0051:139`）。

**建议。**
- 直接修正 0028 中过时的进度描述，注明日期。
- 0051 分三层写：当前支持的范围、对未来迁移的约束、已经验证过的能力。"旧数据不能迁出库 0"标为阶段缺口，不写成设计结论。保留的内容：固定的 ID 格式、真实归属校验、唯一定位与事务保证。
- 0028 与 0051 都补写重审条件，以下任一出现即重审：
  - 出现需要原子地跨两个 EndUser 的产品需求；
  - 停写迁移所需的时间超出停机预算；
  - 出现热点槽位。
- 上线前评估是否删除旧格式 ID 的兼容（库 0 回退、兼容清单），与删除 `CaptureAppended` 解码兼容按同一原则处理（§8）。
  - 如果删除，旧数据迁出的缺口随之消失，只剩按 0051 §5.4 实现停写迁移工具。
  - 如果保留，就需要 §3.5 的存量迁移 ADR。

### 2.8 0007 的后果已过时

[0007:19](../adr/0007-postgresql-as-storage-baseline.md) 写"实时增量（LiveBus）仍是进程内的……跨进程增量分发留待引入消息总线时解决"。[0013](../adr/0013-live-deltas-pulled-from-executing-process.md) 已经用 `AttemptStarted.live_endpoint` 直接拉取的方式解决，并且明确拒绝了消息总线。**建议**直接修正这一条后果，注明日期，并指向 0013。

### 2.9 0043 的泛化判据需要澄清

[0043:21](../adr/0043-kernel-persona-app-layers.md) 规定：内核只在"第二条业务线也需要，且业务侧做不到或做了不安全"时修改。这句话有两种读法，代价都不小：
- 读得太严，内核已有职责的正确性与可靠性修复（如 §2.1、§3.1）也要等第二条业务线；
- 读得太松，Agent 会凭想象中的"第二条业务线"往内核里扩充东西。

0045、0046、0047 正是为通用而设计的机制，需求却全部来自 xinli。

**建议：0043 追加修订，核心表述如下。**

> 业务实体与产品规则默认留在业务层。内核既有职责的完善不以第二条业务线实际落地为前提，但必须说明跨业务适用性、现有接口不足，以及业务侧实现的正确性或安全成本。

保留：业务实体不进内核、模块依赖方向、独立故障域。

0045、0046、0047 在索引中标为"只在一条业务线上验证过"，以下任一出现即逐条复核：第二条业务线接入；xinli 出现超出现有语义的新需求。

### 2.10 0042 的"人不建模"是初期范围，不是结论

[0042:33](../adr/0042-xinli-entities-by-changeset.md) 写"人不建模：语音识别只能区分不同的人，不能指出是谁"。新设计已经规划了人物与组织的实体。

**建议。** 0042 迁到 xinli 的 ADR 目录时一并修订（§6.1）：
- "人不建模"改为初期范围，人物与组织实体允许在 Persona 中演进，并标明尚未完成。
- 保留：依据、版本冲突检查、来源重交时的取代语义，以及"识别出说话人不等于证明了人物身份"。

### 2.11 委托与外部循环：把阶段性边界标为阶段性（0031、0041）

- [0031](../adr/0031-delegation-as-routed-calls.md) 的后果中写有"同一个父 Run 同时未完成的委托至多一个"与"父子之间只传文字"。这是当前的能力边界，但读起来像永久规则。
- [0041](../adr/0041-external-loops-decide-platform-acts.md) 的状态是 accepted，而代码中没有外部循环的实现（`internal/` 下没有对应的包）。正文也没有说清楚三件事：步骤是否流式、64 KiB 的状态上限是上限还是常态、模型缓存由谁负责。

**建议。**
- 0031 把串行与纯文字交接单列为当前能力边界，注明有界并行与授权工件交接是演进方向（§3.3）。保留：权限交集、幂等派生、取消与删除的传播。
- 0041 区分平台治理与可替换的策略：动作由平台执行、决定写入日志后才生效，这两条是治理，不可替换。同时写清上面三件事，并标明"设计已认可，尚未实现"（§3.4）。

### 2.12 已取代的 ADR 保留历史

0044 与 0049 保持"已被取代"的状态，不删除文件。它们在 CONTEXT.md、章程与设计文档中的残留引用要核对一遍：现行文档引用它们时，必须同时写明已被取代。

## 3. 第二批：新增决定的提案

这一批会改变执行、存储或信任的语义，各自先写成提案，编号在落盘时分配。提案的正文只写"方向已认可"，不写成"已经支持"。

### 3.1 审核基础设施故障时可恢复地等待（修订 0021 的失败方式）

[0021:7](../adr/0021-moderation-before-the-log-fail-closed.md) 写明："内容安全服务不可用时一律不放行……输出重试直到 Run 因持续出错而失败。"小时级的 Run（G3）会因为审核服务一次较长的故障而失败，这违反了章程 §8 的"故障透明"。

**方向。** 区分三种情况：内容违规而拒绝、依赖的服务故障、输入未被接受。输出审核遇到服务故障时，Run 挂起等待恢复，不消耗普通的错误预算，也不因此失败。待审的正文仍然不得进入正式日志。
- **最小方案**：记录一个不含正文的等待状态，恢复后重新生成并重新审核。
- 如果要保存待审结果以免重做，必须另行定义隔离存储、期限、授权与删除，不能把它悄悄放进正式事件。

**必须验证：** 恢复、取消、删除、超时；不重复计量；有副作用的调用不重放。

### 3.2 Persona 按需读取与增量物化（修订 0042 的装载方式）

Persona 的 PG 存储按 `business_line` 与 `end_user` 读出每张账本表的全部行（`persona/store/pgstore/rows.go:530`），每次操作都是全量装载。数据随时间增长，成本也随之增长。原因在存储实现的选择，变更集作为事实源本身并不要求这样做。

**方向。** 保留有效变更集的事实语义，允许查询投影、局部加载与增量更新。不把变更集降为审计日志。

**必须验证：** 来源取代的顺序、`rev`、擦除后的重算、处理进度与业务写入在同一事务中提交，结果与现有领域逻辑一致。

### 3.3 有界并行委托与工件交接（扩展 0031）

**方向。** 定义并发上限、结果的提交、部分失败、审批与取消。工件通过显式复制或授权交接，不默认整个委托树共享。不预先规定"全部返回后才唤醒"：结果的持久化、队列的唤醒、模型何时继续执行是三个不同的决定，分别定义。

**必须验证：** 重复回写、乱序完成、父子删除的竞争、权限与工件的生命周期。委托不得扩大权限（m5-multi-agent）。

### 3.4 可替换的上下文策略与流式外部循环（扩展 0041）

**方向。** 上下文策略由业务决定，平台校验来源与权限。流式草稿与最终提交分开。明确状态的版本、用量的可信度与缓存由谁负责。

**必须验证：** 回放、重试、状态恢复、请求前缀保持稳定（AGENTS.md 不变量），以及策略无法扩大权限。

### 3.5 存量分片迁移（视 §2.7 的决定而定）

只有保留旧格式 ID 兼容时才需要。先支持有维护窗口的迁移，解决旧 ID 与迁移后新派生对象的定位与回滚，不预先决定双写。

**必须验证：** 唯一的写入权、日志与队列一致、删除屏障、出站流的连续性、恢复写入。

**顺序：** 3.1 与 3.2 优先；3.3、3.4、3.5 随后。

## 4. 第三批：保留问题，暂不批准替代方案

### 4.1 0050 的可信内容泛化

可以评估"登记内容类型 + 受信适配器"，但最终的 `Provenance` 仍由平台推导，调用方只能提交证据字段。在出现第二类具体内容来验证这个抽象之前，不以泛化为由移除现有的渲染、审核与写入校验，也不改内核中的命名。现有的渲染器是面向旁听结构化页的，但没有绑定 xinli 这个名称，因此"其他业务无法复用"的说法过重。

### 4.2 大 ToolResult 外置

0050:50 已写明这是容量问题，触发时另立 ADR。外置要定义不可变引用、审核、回放读取与 Session 删除的一致性。**外置不能因此取消对工作 Session 的擦除**：回复、调用参数与摘要中仍可能有派生副本，删除派生副本是另一项设计。

### 4.3 0035：委托派生的子 Session 不转后台

[0035:17](../adr/0035-background-calls-for-offline-devices.md) 的限制有正确性上的理由：子 Run 结束后，迟到的结果没有完整的归属路径。先保留这条限制。只有在定义了异步委托的完成、迟到结果、取消与删除语义之后，才能解除。

### 4.4 账号合并与在线迁槽

合并登录身份不一定改变稳定的 EndUser。真正把两个 EndUser 合并，会牵涉 Memory、Grant、设备、配额与删除屏障，改路由或双写解决不了，也不能据此立即废除带槽位的 ID。出现这类需求时，按 §2.7 的重审条件处理。

### 4.5 0021 对内部步骤的审核豁免

不能凭"内部"二字整体豁免。先列出检查点矩阵：每一类内容是否展示、是否写日志、是否外发、是否被执行、是否进入后续上下文。之后再评估策略。

## 6. ADR 的管理规则

### 6.1 按层存放

`persona/`、`apps/<业务线>/` 各自建立 `docs/adr` 目录，业务 ADR 不再进入内核编号。
- 0042 迁到 xinli 的 ADR 目录并按 §2.10 修订，原位置留一行指向新位置。
- 0037 的业务部分（每日旁听 Session、归集到 Project）迁为 xinli 的业务 ADR；内核部分并入 §2.2 的新 ADR。
- 涉及内核契约的留在内核。

### 6.2 修订方式

- **纠正事实**（进度、已过时的后果描述）：直接修改正文，注明日期。例如 0007:19、0028:21、0028:39。
- **标明边界**（当前能力边界、尚未实现、现行技术选择）：直接在正文中标明，注明日期。例如 0013、0026、0031、0041、0051。
- **架构改变**：写新 ADR，与旧 ADR 双向链接。
- **部分失效**：页首（状态行之下）逐条列出哪些有效、哪些已修订、哪些失效，以及现行规则在哪里。不能只在文末补记，也不能只写"见某某 ADR"。Agent 从头读正文时，必须先看到这条提示。
- **正文与现行规则矛盾时**：用整合后的新 ADR 取代，并附逐条对照表，例如 0036 + 0039 + 0050。
- **取代之前**：先把被取代 ADR 中仍然有效的保证迁入现行决定，例如 0040 → 0045。

### 6.3 索引

新建 `docs/adr/README.md`。表的列为：编号、标题、状态（accepted / 已修订 / 被取代 / 暂缓 / 不实施）、实施状态（已实现 / 部分实现 / 未实现）、所属层、分级、重审条件摘要、取代关系、是否"只在一条业务线上验证过"。AGENTS.md 的"先读"部分指向这份索引。
