# 评审：内核架构评估（2026-11-21）

> 状态：待裁决（2026-11-22）· 评审对象：[内核架构评估：业务支撑灵活性与边界清晰度诊断](../architecture/architecture-evaluation.html)（2026-11-21，提交 23e4dd0）· 依据：[章程](../charter.md) v0.2、[ADR 索引](../adr/README.md)、`docs/design/*.md` 与 2026-11-22 的代码 · 术语以 [CONTEXT.md](../../CONTEXT.md) 为准

评估文档回答两个问题：内核能否不改基座就支撑多条业务线；内核与业务线的边界是否清晰。它给出的结论是“下层原语正交，上层边界双向越界”，并据此提出 B1–B6 六个问题和 R1–R12 四阶段路线图。

本文逐条把它的断言对照代码与现行文档，结论是：

- **事实大多属实**：被点名的文件、行号与机制基本都在，但有十余处细节需要纠正（§3），其中几处影响定级。
- **框架有偏差**：文档点名的“缺陷”大多已写入 ADR 或设计文档，有明确的推迟理由与重审条件；评估没有引用这些条件，也没有按 ADR-0043 的改内核判据衡量，因此把“有意推迟”定成了“边界失守”，P0 定级偏高（§2）。
- **两项建议与现行不变量冲突**：Run 内折叠（R4）与 capture 渲染下放（R5）分别与请求前缀稳定、平台渲染可信页相矛盾，而评估在 §4 正把前者列为优势（§4）。
- **有六项值得单独立项**（§5），其中建会话幂等与 Guard 取令牌顺序在现行文档中没有取舍说明。

建议：不整体采纳路线图与定级；把评估当作第二条业务线接入时的复核清单，与 ADR 索引的重审条件对照使用；§5 的条目单独立项。

## 1. 方法

- 按评估的 B1–B6 与首屏数字拆成 34 条断言，分三组核对：租户、幂等与调度；领域语义下沉；Outbox、规模与数字。
- 每条对照代码（`internal/`、`proto/`、`cmd/yanshi/`），并查 `docs/adr/`、`docs/design/`、`docs/launch-checklist.md`、`docs/review/` 中是否已有决定、理由与重审条件。数字追到原始出处（设计文档或提交）。
- 没有运行测试或评测；没有核对卡片表单控件的种类数与 `worker.go` 的循环实现细节。

## 2. 框架：有意推迟被定为缺陷

`apps/` 下只有 xinli 一条业务线。ADR-0043 的判据是“第二条业务线也会需要，且业务侧做不到或做了不安全”；在第二条业务线接入之前，“它也会需要”只是待验证的假设，据此泛化内核要在 ADR 中写明依据与撤回方式（2026-11-14 修订）。评估点名的条目几乎都已有对应记载：

| 评估的指控 | 现行记载 |
|---|---|
| AgentDef、Release 无业务线归属（B1） | `docs/design/m4-agent-rollout.md:9` 把“按业务线配置不同的发布（AgentDef 本身不分业务线）”列为不做；单元是共享 EndUser 的一组业务线，默认全在同一单元（`docs/design/deployment.md:11-13`） |
| MCP Server 名全局唯一（B1） | `docs/design/deployment.md:14` 已列为现有限制，同名须分属不同单元 |
| 队列同优先级全局 FIFO，无业务线公平调度（B1） | ADR-0029 第 24 行列为未做，用池隔离替代（`pgqueue.go:132` 的池可限定业务线）；重审条件“静态的业务线与优先级不够用” |
| 模型准入只在单进程，各提供商共用参数（B6） | `docs/design/model-calls.md:53,55` 已写明与改进方向 |
| QueueAdmission 默认关闭、各网关扫全分片（B6） | ADR-0029 第 40 行：阈值依据线上分布确定；`docs/review/2026-10-11-codex-discussion.md` D 点：规模到了再做 |
| `WEARER` / `OTHER`、`speaker_ref` 写进 proto（B2） | ADR-0052 重审条件：“第二类可信结构化内容”“说话人角色扩展”，在此之前不改内核中的命名与校验 |
| 记忆类别、health 同意项、中文健康词表（B2） | ADR-0022 重审条件“健康之外的敏感类别”（`consent.Kind` 已留位置）；ADR-0023 重审条件“多语言业务线” |
| 卡片组件集封闭（B2） | ADR-0032 重审条件“固定组件集外的需求超过两次” |
| 循环与上下文锁死在 runtime（B3） | ADR-0041、ADR-0056 已定稿、未实现；ADR-0056 Q1：A 期等业务线提出需要时实施，B 期等 0041 开始实现时实施 |
| MCP 无用户级 OAuth（B5） | ADR-0017 重审条件；`docs/design/m5-mcp.md:98` 已写好将来的登记方式与删除流程 |
| AgentDef 等需改文件重启（B5） | ADR-0020 重审条件“需业务方自助发布”；`releases.yaml` 每 10 秒热加载（`cmd/yanshi/serve.go:519,524`） |
| Outbox 绑定物理分片，无迁槽（B4） | ADR-0046 标为“单线”；ADR-0051 第 128 行明确推迟迁槽工具并给出触发条件；`docs/launch-checklist.md:39` |
| 网关通知无归属路由（B6） | ADR-0051 第 139 行、`docs/design/deployment.md:164` 列为不做 |
| 沙箱无预热池（B6） | ADR-0053：冷启动 p95 远低于 3 秒，预热池不是上线前提；重审条件“目标集群冷启动 p95 超过 3 秒”“apiserver 成为 exec 瓶颈” |

所以评估实际在主张“现在就提前触发这些重审”。这可以成立，但要逐条说明为什么不等触发条件出现，以及假设不成立时怎样撤回；评估没有做这一步。部分建议还要推翻现行决定：例如 R1 以 `(business_line, name)` 为 AgentDef 的复合键，与 `m4-agent-rollout.md` 的“AgentDef 本身不分业务线”相反，须先写 ADR，评估没有提到。

定级同样受影响。B1 被定为 P0“安全与多租户阻断”，前提是同一单元内的业务线互不信任；现行文档没有这一要求，而现有的隔离层评估也没有计入（§3 第 1 条）。

## 3. 事实勘误

| # | 评估位置 | 评估写法 | 实际 |
|---|---|---|---|
| 1 | 首屏、B1 | “0 租户隔离”，业务线 A 可越权调用业务线 B | 已有的隔离：令牌只能用于本业务线（`httpapi.go:270-287`）；MCP 工具按 Session 的业务线过滤（`capability/catalog.go:191`）；Oneshot 有业务线并发层；委托的子 Session 继承父的业务线与 EndUser（`delegation/delegator.go:121`）。确实没有的是：AgentDef 目录不按业务线过滤（`service.go:100-128` 只调 `Agents.Resolve`；`agent:*` 经 `delegator.go:464-481` 列出全部 Agent）。后果是可以使用别的业务线的指令与能力声明，数据、配额与 MCP 工具仍在本业务线内 |
| 2 | B1 | Oneshot 并发槽键是 `"name:"+d.Name`，跨业务线争抢 | 键分 `total`、`business_line:<bl>`、`name:<name>` 三层（`oneshot/service.go:119-123`，`docs/design/model-calls.md:30`）；只有声明名一层跨业务线共享 |
| 3 | B1 | RPS 先于优先级抢令牌 | 顺序属实（`model/guard.go:206-212` 先 `rate.wait` 再 `gate.acquire`），但并发门按类别排队，低优先级不会插到高优先级前面。准确的说法是：RPS 层不区分类别，令牌在排队前即被消耗 |
| 4 | B4 | 改槽位表后全部游标报 403/410 作废 | 游标只含业务线、分片、epoch、过滤版本与位置（`outbox/stream.go:61-69`），不含槽位表；410 来自 epoch 轮换或低于保留地板，403 是游标与请求的业务线或分片不符（`httpapi/outbox.go:64-75`）。游标失效后的恢复流程已设计并实现（`docs/design/m7-kernel-primitives.md` §6.5，`apps/xinli/recovery`）。设计中缺的是重分片之后游标怎样映射 |
| 5 | §4 S1 | 内存只保留最近 4 个完整 Run | `KeepRuns = 2`，至多 3 个（`session/state.go:235,384`） |
| 6 | 首屏 | 问答 TTFT p99 53 ms | 出自 `scripts/bench-ttft.sh`，假模型首字固定 50 ms（`docs/design/m2-scale-test.md:183`），衡量的是内核约 3 ms 的开销，不是真实模型的首字延迟 |
| 7 | §4 S6 | 长 Run 缓存命中 40% → 70% | 只是 `long-run-ledger` 一个用例（`docs/design/m2-long-runs.md:207`）；`compaction-recall` 为 60% → 72%，`multi-turn-memory-chat` 约 33% |
| 8 | 首屏、S3 | 2200+ 差分模拟种子 | 是一次 `make sim` 记录的合计：2000 内存 + 100 PG + 100 双库（`docs/design/day-acceptance.md:210`）；`make check` 默认只跑 3 个双库种子 |
| 9 | 首屏、S4 | 1→4 进程扩展、10 GB 搬迁停写 573 ms | 数字有出处（`m2-scale-test.md:68,78,99`、`deployment.md:318-321`），但都在开发环境（Mac mini 同机容器）测得；目标环境验收未完成（`launch-checklist.md:41`），评估未注明 |
| 10 | B2 | 身份证正则与 Asia/Shanghai 时区在 `health.go` | 在 `memory/service.go:76,137`；时区是默认值，可经 `Service.Location` 覆盖 |
| 11 | B2 | `cite.go` 递归扫描任意参数中的 `#57.3` | 只对登记了 `cite_captures: true` 的同业务线 MCP 启用（`docs/design/captures.md:36`） |
| 12 | B2、§2 表第 4 行 | 业务的 MCP 写工具无法接入写闸门，没有保护 | 未声明只读的 MCP 工具默认需要审批（ADR-0017）。缺的是更细的“受外部内容影响时才要求审批”，目前只有 `memory_save` 有（`runtime/memgate.go:28,110`） |
| 13 | B2 | `speaker_ref` 是“声纹引用” | 它是业务线填入的不透明实体 ID，内核只校验语法，来源推导不看它（ADR-0052） |
| 14 | B3 | AgentDef 的 context 只能调窗口大小与压缩比例 | 还有 `scope: run`（`agentdef/agentdef.go:79-100`） |
| 15 | B6 | 大 ToolResult 过期靠逐行 DELETE | `events` 没有过期清理路径，只有按 Session 删除（`eventlog/pglog/pglog.go:192`）；“全文内嵌、无分区、无自动外置”属实 |

## 4. 与现行不变量冲突的建议

**R4 的“长 Run 内已消费工具结果的声明式折叠”。** ADR-0056 Q3、Q4 有意规定策略每个 Run 只调用一次、Run 内上下文只在尾部追加、当前 Run 总是保留，理由是 Run 内的请求前缀保持稳定（AGENTS.md“请求前缀保持稳定”）。在 Run 内折叠会让此后每一步的前缀缓存失效，而评估在 §4 S6 正把前缀缓存列为核心优势。B3 引用 ADR-0056 第 49-50 行，把这一定稿当作缺口，却没有讨论它的理由。要做，须先满足 ADR-0056 的重审条件“需要 Run 内调整”，并用评测报告的缓存命中列证明代价可以接受。现有的手段是 `MaxToolResult` 截断（只作用于模型视图）与压缩。

**R5 的“把 internal/capture 的渲染下放回业务侧 MCP”。** ADR-0052 的安全边界是平台渲染可信页、写日志前审核：业务侧给出的文字不能作为来源推导的依据。中文星期、“之后七天”日期头与 5 分钟交谈间隔（`capture/page.go:20` 的 `DefaultExchangeGap`）这类渲染参数可以改为可配置；把渲染整体交给业务线，则是拆掉旁听的信任边界，不只是“泛化”。说话人角色的扩展已是 ADR-0052 的重审条件，届时须同时修订来源推导。

## 5. 值得采纳的部分

下列条目或在现行文档中没有取舍说明，或属于 ADR-0043 修订所说的“内核既有职责的完善”，不必等第二条业务线接入。

| # | 条目 | 现状 | 为什么值得做 | 下一步 |
|---|---|---|---|---|
| A1 | 建会话幂等 | 创建 Session 不接受幂等键（`httpapi.go:371-408`、`node.proto:182-186`）；`docs/` 中没有找到取舍说明 | 输入早有 `input_id` 去重，建会话却没有，客户端重试会产生孤儿 Session，业务线须自建映射表与回收 | 设计 `external_key` 的唯一范围（业务线 + EndUser）与存放位置；须登记分片键并接入删除路径（`app.SessionData`），按 m2-session-lifecycle 的要求处理 |
| A2 | 输入去重窗口 | `MaxRecentInputs = 64`（`session/state.go:468-470`），注释的前提是“重提通常在几秒内” | 业务线的异步编排在超时后重提，可能晚于窗口，前提不成立；委托已有不受窗口限制的例外（`State.Delegated`） | 与 A1 一起评估：持久去重表或延长窗口，注意投影有界与 `ProjectionVersion` |
| A3 | Guard 取令牌顺序 | `guard.go:206-212` 先取 RPS 令牌再进并发门排队；RPS 层不区分类别 | 令牌在排队前被消耗；RPS 紧张时交互类与后台类同等竞争，与 ADR-0029 的分类意图不一致；没有文档说明这一顺序 | 局部修改，改动 `model-calls.md` 的准入一节；需 `make sim` 与 TTFT 压测对照 |
| A4 | AgentDef 的业务线归属 | 代码中 AgentDef 不分业务线，`m4-agent-rollout.md:9` 也这样写；但 `deployment.md:11` 写“Token、配额、AgentDef……都以 BusinessLine 为单位” | 两份设计文档互相矛盾；MCP 工具按业务线过滤而 AgentDef 目录（含 `agent:*`）不过滤，口径不一 | 先裁决单元内业务线之间的信任假设并写入 `deployment.md`；若要求隔离，按 ADR 流程修订 m4-agent-rollout |
| A5 | Outbox 重分片后的游标 | 游标绑定物理分片与 xid8；整片搬迁能保住游标，改槽位表时的游标处理未设计（ADR-0051 §5.4 只要求校验出站水位） | 对外契约每多一个消费方就更难改；同库长事务拖住所有业务线的水位，ADR-0046 已承认，对策只是监控与事务超时 | 第二条业务线接入 Outbox 之前，在 ADR-0046 补写重分片的游标映射或换代方案；不必先实现迁槽工具 |
| A6 | 大 ToolResult 全文存入 events | `MaxToolResult` 只截断模型视图，日志存全文；`events` 无分区 | `docs/review/2026-10-11-codex-discussion.md:66` 提过“大结果工件化”，一直没有形成决定 | 按字节压测后决定是否外置为所属 Session 的工件；须保持重放、续传与删除语义 |

R3（真实审核提供商、推送与唤醒、链路追踪、目标集群验收）与 `docs/launch-checklist.md` 的阻断项重合，定为 P0 没有问题，按清单推进即可，不需要另立。
