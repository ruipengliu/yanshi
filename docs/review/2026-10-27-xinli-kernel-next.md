# 评审：xinli 与内核的下一步

> 状态：评审意见与讨论记录（2026-10-27），不是设计，不改变任何不变量 · 术语以 [CONTEXT.md](../../CONTEXT.md) 为准 · 承接：[架构评审](./2026-10-26-xinli-architecture.md) §3.3、[按完整时段拆 Run 的实验](./2026-10-26-xinli-span-runs.md)
>
> 方式：Claude 先读评审与基线形成判断；Codex（gpt-6-astra，推理强度 xhigh）在只读沙箱中独立作答（第一轮，不给 Claude 的结论）；第二轮把 Claude 的结论交给它逐条反驳。Codex 提出的代码级事实由 Claude 在代码中核实后才进入结论。没有重跑评测，数值均来自 `evals/baselines/default.json`。

## 0. 结论

- **划分仍然对。** 没有发现 xinli 的实体逻辑放在 runtime / service 中；耦合只在评测装配的 Seed / State / 断言路径。两个月内不大改运行时、不换模型、不重提拆 Run。
- **效果的短板在维护与使用已抽出的承诺。** 多日用例的抽取分项尚可，失败集中在助手问答与白天修订；整日、多日四个用例仍为 0/3。
- **两处新发现的缺陷**（静态推导，已在代码核实，未复现）：变更集重交时承诺按数组位置继承 ID（§2.1）；Capture 一页的字符上限与 `max_tool_result` 的配套只写在注释（§2.2）。
- **产品决定（用户，2026-10-27）**：近期不对真实用户开放，先打磨效果，真实内容安全接入随之后移；**涉及健康的事可以记成承诺**（§3.3）。

## 1. 现状的证据

| 用例 | 结果 | 主要失败 |
|---|---|---|
| `capture-multiday` | 0/3 | turn 6 "应办承诺"、turn 7 "改期时间线"评分 2（各 3/3）；turn 4 用户纠错找不到对应的未完成承诺（3/3） |
| `capture-multiday-noisy` | 0/3 | turn 6 3/3、turn 7 2/3；turn 2 修订正确率 .278 ± .048（末轮 .879） |
| `capture-workday` | 0/3 | 碎片率、纯度、`P-0004` 归属；`file_day` 的调用参数含"失眠"（3/3） |
| `capture-workday-oneshot` | 0/3 | 碎片率、纯度、过时承诺 |

多日末轮的提醒精确率只有 .69–.76；四天加问答的整个场景用 1.88M / 1.96M tokens，一个工作日 1.54M，缓存命中 51%–59%。

## 2. 核实的事实与纠正

1. **重交时的承诺身份。** `xinlimock` 的 `commit` 沿用"同一位置"的承诺 ID（`internal/xinlimock/changes.go` 的 `commit`）。已接受的变更集用同一个 source 重交、创建项换了顺序时，之后按 ID 重放的修订与用户修改会落到另一条承诺上。没有找到触发它的日志，频率未知。
2. **Capture 页与截断。** `capture.MaxChars = 6000` 按 rune 计，模型估算按字节计；日期头、页首页尾不在字符预算里；`max_tool_result` 缺省为 `Window/8`。超出时 Transcript 截掉尾段，Run 完成后读取位置仍越过整页。`xinli-day` 设为 8000，目前未触发。
3. **健康信息（纠正 Claude）。** `file_day` 已经拒收含健康用词的总览与觉察（`internal/xinlimock/xinlimock.go` 的 `fileDay`）；`no_call_args` 不看工具是否接受，基线说明的是**模型试图提交**，不是被收下。承诺的内容、对方、期限说明与修订原因没有健康检查。
4. **用户纠错（纠正 Claude）。** `xinli_edit` 在找不到对应的未完成承诺时失败，此时还没有调用编辑（`internal/eval/runner.go`）；编辑接口本身存在。根因是漏抽、错关或合并，现有汇总不能区分；评测诊断中压缩机、油烟机的承诺经常漏记，是最强线索。
5. **逐轮指标（纠正两方）。** 末轮掩盖了白天修订的低谷；但未匹配的金标在修订统计前被跳过，分母随轮次变化，不能断言"同一条白天改错、日终修好"。
6. **缓存。** 系统指令固定、召回在 Run 的位置、工具按名称排序，没有发现每次请求变化的前缀；可疑点只有 MCP 工具缓存的定时刷新失败时会略去该 Server（`internal/mcpcap/mcpcap.go`），基线中没有它被触发的证据。
7. **SDK 离线补交**：Codex 撤回优先级。SDK 已按同一 ID 重试，持久缓冲由 HostApp 负责；中期验证超过 512 批、丢 ACK、重启与关闭交错的契约即可。

## 3. 决定

### 3.1 xinli（按顺序）

| # | 做什么 | 验收 |
|---|---|---|
| 1 | 助手按责任方、状态、时间、对方、主题查询承诺，单条附修订历史（当前值、说话时间、记录时间、用户修改） | 预置正确账本的确定性查询测试；`capture-multiday*` turn 6–7 |
| 2 | 逐轮的抽取、修订、去重与纠错保持；预置正确承诺的编辑用例，把"没有可编辑对象"与"编辑后被覆盖"分开 | 逐轮、逐实体断言；提醒精确率；拒收次数 |
| 3 | 承诺身份：先复现，再加保守护栏（对应不上就拒收并返回旧对应，不按下标猜） | 换序、增删创建项、之后有引用、用户锁定的确定性测试 |
| 4 | 健康：承诺可以记下涉及健康的事；摘要、觉察、决定、风险、项目名与总览不变 | 健康承诺的新用例；`capture-health-*`、`capture-workday` 原断言 |
| 5 | 语义金标：承诺的内容、对象与责任方；逐轮门槛 | 内容写错而引用正确的反例被判错 |

### 3.2 内核（按顺序）

| # | 做什么 | 验收 |
|---|---|---|
| 1 | Capture 页的预算护栏：加载 AgentDef 时校验，返回前按实际渲染结果检查，超出即失败、不附读取位置；不改投影语义 | Unicode、页首尾、边界预算；相关 sim |
| 2 | 评测报告：预期指标缺失、有效样本不足、完成与中断的成本分开 | 缺指标、部分完成、超时的报告与比较测试 |
| 3 | 按请求分解缓存命中（首调、后续、Run 切换、工具变化），定位后再改组装；限时 | 固定请求回放、同模型冷暖对照 |
| 4 | Capture 负载的容量与存储验证 | 扩展 M2 压测 |
| 5 | 真实内容安全接入：开放真实用户之前完成，现在后移 | [上线清单](../launch-checklist.md) |

### 3.3 健康信息记成承诺

用户决定：涉及健康的事可以记成承诺（陪家人复查、取药、预约体检），提醒照常。承诺写要做的事本身（谁、做什么、何时、对谁），不写病情、诊断与推断；交谈的标题与摘要、觉察、决定、风险、项目名、当天总览仍不写健康信息，Memory 的 ADR-0022 不变。需要同步改 [xinli 设计](../design/xinli-captures.md) §3 与 `xinli-day` 的指令，并加评测。

### 3.4 不采纳

- 把 Memory 的健康词表直接换给 xinli：两者取舍不同（Memory 求少误伤）。可共享检测实现，词表与处置分别配置。
- 切碎超长的首段 Capture：入口已限 2000 字，切碎会牵涉 `seq.index` 的引用与游标。

## 4. 第一周

内核 §3.2 第 1、2 项；xinli §3.1 第 3、4、5 项。第二周做 §3.1 第 1、2 项，再按轮次跑 `capture-workday*`、`capture-multiday*`，并限时做 §3.2 第 3 项。开发交给 Codex（gpt-6-astra，推理强度 medium），Claude 负责拆分、架构与审阅。
