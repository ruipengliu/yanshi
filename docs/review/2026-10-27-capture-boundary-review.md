# 评审：Capture 与流该不该在内核

> 状态：评审意见（2026-10-27），不是设计，不改变任何不变量；**已裁决为方案 C**（[ADR-0050](../adr/0050-capture-text-in-the-business-line.md)、[裁决记录](./2026-10-27-capture-placement-decision.md)），§3.3、§3.4 中关于 C 的擦除的两处陈述已在裁决记录 §4 更正 · 术语以 [CONTEXT.md](../../CONTEXT.md) 为准 · 对象：[xinli 与 persona agent 的整体架构](../design/persona-architecture.md)、[M7 内核补充](../design/m7-kernel-primitives.md)、[旁听](../design/captures.md)，ADR-0036、ADR-0037、ADR-0039、ADR-0040、ADR-0043、ADR-0045、ADR-0049 · 承接：[persona 架构评审](./2026-10-27-persona-architecture-review.md) · 图示与容量复算：[Persona 分层方案](./2026-10-27-persona-plan.html)

> 方式：Claude 复核一份先行意见（三层方向、职责变化、当前实现、业务耦合、Capture 的必要性、更薄的替代、外置原文与删除、Stream 泛化），在代码与文档中逐条核实后给出裁决。只读代码与文档，没有运行测试或评测。下文的【事实】可在所引位置核对，【推断】由事实推出，【假设】尚未验证。

## 0. 结论

- **先行意见大体成立**，以下四处推得更远或做了修正。
- **来源语义并不是 Capture 独有的。** 说话人的信任锚本来就在业务侧，可登记为可信的业务 MCP Server 返回结构化片段，得到同样的来源推导，不扩大信任面（§2）。
- **M7 的多数新增原语是"原文在内核"的推论**，不是独立需求；它们"只有平台能做"的理由以原文在内核为前提（§2）。
- **M7 的擦除只清片段正文**，同一日志中的派生副本仍可读到当天 Session 删除；外置原文后可改用"删除当天 Session"，更彻底也更简单（§3）。
- **"最小 Capture"不比现行方案便宜多少**：只要产品要部分删除，正文存储、展开器、擦除与跨库信封都省不掉（§3）。
- **建议**：P1 动工之前，用一次小的验证在"现行 M7"与"业务存储 + MCP + 安全扩展"之间做出裁决并写 ADR；暂停 Stream 泛化。EndUser 删除屏障与定时（不含 `window.stream`）不受影响，照常推进（§5）。

## 1. 用户的三个问题

### 1.1 xinli 能否作为普通 BusinessLine 接入；Persona 是否改变了划分

- 【事实】接入面是通用的：AgentDef、能力白名单、远程 MCP（[`mcpcap.go`](../../internal/mcpcap/mcpcap.go) 的 `transport` 注入身份头）、服务令牌。核心执行路径中没有 xinli 分支。
- 【事实】开发耦合：[`cmd/yanshi/serve.go`](../../cmd/yanshi/serve.go) import `internal/xinlimock`，其中的 `xinliBusiness` 经进程内接口直接调用 `service`；[`internal/httpapi/debug.go`](../../internal/httpapi/debug.go) 提供 `/v1/debug/xinli*`；`internal/eval/` 有 7 个文件直接 import 它。
- 【事实】不太显眼的一类：给整理模型的提示文字写在内核。[`internal/capture/capture.go`](../../internal/capture/capture.go) 的 `dayHeader` 列出"之后七天的日期与星期"，理由是"模型自己推算星期常错一天"，这是 xinli 整理的提示工程，不是平台语义；`exchange_gap` 的字段名也是"沿用"下来的。
- 划分确实改变了，而且不只 Schedule：ADR-0045 推翻 ADR-0040 第 5 条（后者拒绝 cron 的理由正是"越过平台与业务线的边界"）；擦除改写 ADR-0037"只按整个 Session 删除"的前提；Outbox、Oneshot、Tier 是新增的内核职责。各项是否成立见 §2。
- Persona 是可选的业务侧服务，这一点成立：内核设计中的回执、出站流消费方都是通用接口；没有 Persona 的业务线照常使用 `relationship`。

### 1.2 当前实现是否遵循此前的接入规范

同意先行意见：是开发与评测用的模拟，不是生产接入。补充两点：

- 【事实】mock 的跨 Session 编排经进程内 `Business` 接口调用 `service`，没有走 HTTP 加服务令牌，授权矩阵从未在 xinli 的真实调用形态下被测到。
- 【事实】内核调 mock 的 MCP 登记没有配置凭证 headers。

### 1.3 Capture 与流是否必须是内核原语

见 §2–§4。

## 2. 哪些必须在内核

两条关键事实：

- 【事实】服务令牌提交的输入，在来源推导中就是 `FromUser`：[`provenance.go`](../../internal/session/provenance.go) 中 `RunRequested` 的输入除转述外一律算本人的话。
- 【事实】说话人标签由 yanshi 之外给出，内核无法验证（ADR-0036 后果第 1 条）。

【推断】所以"佩戴者原话可以作为 Memory 依据"这份信任，锚点始终在业务侧。若由**登记中声明可信**的业务 MCP Server 在结果中返回结构化片段（复用 `ContentBlock.capture`；只采信同一业务线、登记为 `attests_speakers: true` 的 Server，写法与 `acks: true` 相同），平台照旧按说话人字段推导来源，信任面不扩大：业务线现在以服务令牌就能写入 `FromUser` 的内容。写入闸门（[`memgate.go`](../../internal/runtime/memgate.go) 的 `userText`）、"只把他人的话交给注入判断"、[M7 Agent 生态](../design/m7-agent-ecosystem.md) 的"听过他人旁听的 Session 不能调用三方"都只依赖 `Provenance`，不依赖原文存放在哪里。

| 能力 | 裁决 | 依据 |
|---|---|---|
| 来源推导、写入闸门、注入判断 | 必须在内核（已有） | 内核要认识**结构化说话人**，不必**保存原文** |
| 写日志前的内容审核 | 必须由内核执行或强制 | 【事实】MCP 结果现在不单独审核（[内容安全](../design/m4-moderation.md) "调用结果暂不单独检查"）；外置方案必须补上 |
| 定时（Agent 创建、文字由模型写） | 必须在内核 | 独立成立：模型写的到期文字经服务令牌提交就成了 `FromUser`。`window.stream` 部分依赖 Capture |
| EndUser 删除屏障 | 必须在内核 | 修的是现有入口的缺陷，与 Capture 无关 |
| 档位 | 成立 | 触发、定时开启的 Run 没有用户令牌 |
| 单次调用 | 成立，理由是治理而非做不到 | 计量、审核、评测 |
| 重答 | 机制只能在内核 | 【假设】第二条业务线需要，尚未证明 |
| 出站流 | 通用部分成立（`run_completed`、`question` 等） | `capture_erased`、`capture_corrected` 是 Capture 的推论 |
| 原文存储、分页与时段、进行中判断、读取位置、交付确认、`cite_captures`、读取 API、触发、`window.stream`、擦除与修订 | 业务侧能做，只是在内核里更顺手 | 下段 |

最后一行的理由是循环的。【事实】[persona 架构评审](./2026-10-27-persona-architecture-review.md) 的"不采纳"一节写"静默判断需要流的写入时间，业务侧拿不到"；ADR-0049 写"只有平台能决定位置"。【推断】这两句只在原文与读取位置都在内核时成立。原文在业务侧时，业务侧自有写入时间；它可以在保存变更集的同一事务中记下已处理的范围，"读过不等于已保存"从结构上就不存在，也就不需要回执拼链（[`session/ack.go`](../../internal/session/ack.go)、`Run.CapturePages`）。同理，`cite_captures` 是为了让拿不到原文的业务线核对说话人；原文在业务侧时它自己就能核对。

## 3. 整体复杂度

三个方案：

- **A**：现行 M7。
- **B**：最小 Capture。保留提交、日志与 `captures` 工具，砍掉 Stream 泛化、交付确认与触发。
- **C**：业务存储 + MCP + 安全扩展。

### 3.1 B 并不便宜

【推断】只要产品要"删除 10:15–10:40"这样的部分删除，原文在 Session 日志中，就仍需要 M7 §2–§4 的全套：正文存储、展开器、擦除事件、修订、读取 API，以及跨库擦除的出站流信封与 Persona 墓碑。B 只省掉交付确认与触发，成本的大头不变。部分删除这一项需求决定了 B 的成本下限。

### 3.2 M7 的擦除有缺口

【事实】[M7](../design/m7-kernel-primitives.md) §3 只清空 `capture_segments` 的正文、中断活跃 Run，并依靠 `scope: run` 保证之后的**上下文**看不到被擦除的内容；它没有处理**日志**中的派生副本。【推断，可能性高】模型回复与 `file_changes` 参数中对被擦原话的概括与引用，仍可经 `events` 接口、出站流"按需读事件"读到，直到当天 Session 删除。"原文立即删除"只对片段正文成立。

### 3.3 C 的组成

内核只做四件事：

1. 可信登记的结构化片段进入来源推导（`resultPieces` 加一处登记校验，`Apply` 再校验一次）。
2. 这类结果写日志前审核，复用"整批送检、违规再逐段复核"的策略；或由契约规定业务侧在入库时审核。
3. 擦除：业务库删除原文并写墓碑（与 Persona 同库，一个本地事务），再删除当天的内核 Session。Session 不再是原文的唯一载体，可以随删随建；日志中的派生副本一并删除，比 A 更彻底。
4. 新增一种删除原因：保留 Memory，并列出受影响的 Memory 交给用户决定（类似 `lifecycle.ReasonRetention`）。这改了删除语义，需要 ADR。

业务侧接手：原文表（10 万 DAU 约 50 GB/天，保留 7 天）、分页与时段逻辑（`internal/capture` 约 950 行，迁入 Persona，本来就是领域逻辑）、处理进度、审核调用。

### 3.4 比较

【推断】C 的整体复杂度更低，主要不在行数，而在于**少了一整个跨库一致性面**：A 的原文在内核、派生对象在 Persona，才需要出站流的删除信封、72 小时对账、墓碑与迟到提交的竞态分析（[persona 架构评审](./2026-10-27-persona-architecture-review.md) 第 5 条）。C 中两者同库，这些退化为本地事务。

| | A（现行 M7） | B（最小 Capture） | C（业务存储 + MCP） |
|---|---|---|---|
| 内核新增 | 正文存储、展开器、擦除、修订、读取 API、交付确认、触发、`window.stream`、出站流的擦除信封、声明流的 AgentDef 限制 | A 去掉交付确认与触发 | 可信片段、结果审核、一种删除原因 |
| 跨库一致性 | 出站流信封、对账、墓碑竞态 | 同 A | 业务库本地事务 |
| 擦除覆盖日志中的派生副本 | 否（§3.2） | 否 | 是（删除当天 Session） |
| 原文保留期由谁担保 | 平台 | 平台 | 业务线（平台只担保自己的副本） |

## 4. 各方案改变什么

**产品体验**

- C 与 A 能做同样的功能。实况预览直接读业务库，不需要内核的读取 API；单次调用的"旁听引用范围"输入随之去掉，只收文字。
- 整理的读取也依赖 Persona 可用；【事实】写入本来就依赖它（[整体架构](../design/persona-architecture.md) §8）。
- C 的擦除粒度更粗：当天的工作日志整个重建，可能触发一次重新整理。

**安全保证**

- 说话人信任：两者的锚点相同（§2）。
- 内容审核：A 在提交时审核一次；C 须明确由内核在结果写日志前审核（重读会重复送检，【假设】10 万 DAU 下成本可接受，未测），或由契约交给业务侧。
- 可审计性：C 失去"提交时刻的不可变记录"，说话人核对改由业务线自己做，平台不再能独立复核。
- 三方：C 下"听过他人旁听的 Session 不能调用三方"照常成立，它只依赖来源推导。

**删除语义**

- 【事实】ADR-0037 明确拒绝过"由业务线服务端按时删除"，理由是平台无从保证。选 C 等于放弃平台对原文保留期的担保，内核只担保自己的副本（受 Retention 约束）。
- 【推断】这份担保的实际价值有限：采集服务本来就经手音频与全部转写，Persona 也长期保存由他人发言派生的摘要。
- 【假设】合规与产品方接受"原文保留期由业务线担保"，需要确认。
- 部分擦除：A 只清片段正文（§3.2）；C 删除当天 Session，连派生副本一起清除，但 Memory 的处理要新的删除原因。

## 5. Stream 泛化与下一步

**暂停 Stream 泛化。** 【事实】代码层面的泛化很薄：[`session/stream.go`](../../internal/session/stream.go) 是只有 `transcript` 一项的 map；声明流的两个 AgentDef 中 `console-capture` 是调试用的。成本在设计层面：M7 把流当作挂载点，挂上了回执、定时窗口、触发，以及"声明流就必须有限 Retention、`close_after_open` 与 `scope: run`"。【事实】后者是 A 的擦除正确性所依赖的前提（M7 §3），不是平台本身需要的约束；C 下可以全部去掉。

- 在裁决 A 与 C 之前：不新增流种类，不实现 `window.stream` 与流上的触发，不加强对声明流的 AgentDef 的限制。
- 来源推导的集中化（ADR-0039 第 1 条）独立有价值，保留。
- 选 C 时，分页、处理进度与交付确认移回业务侧；交付确认已合入（`3e60717`），删除它是净减代码。

**P1 动工之前的验证。** P1（正文存储、擦除、交付确认、出站流）几乎全是 Capture 决定的推论，也是成本最高的一段：

1. 实现可信结构化片段进入来源推导，用 `memgate_test`、`provenance_test` 证明佩戴者原话可免审批、他人片段仍使上下文含外部内容。
2. 让业务侧的 mock 输出与 `captures` 完全相同的文本，跑 `make eval` 的 `capture-*`，与基线比较。
3. 写一页删除语义对照：A 与 C 在"删一段、删一天、注销、到期"四种操作下各删到哪里、由谁担保。

这三步的结论加上合规方对"原文保留期由业务侧担保"的意见，足以写一条 ADR 裁决 A 与 C。
