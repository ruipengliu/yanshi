# xinli 按完整时段拆 Run 的实验

> 2026-10-26 · 发力点：[架构评审](./2026-10-26-xinli-architecture.md) §3.3 第 3 项 · 机制：[评测](../design/m4-eval.md) §14

**决定：保留实验入口，维持默认流程。** lite 可以减少 13%–44% 的 tokens，但多日提醒精确率等指标回归；GLM 完整工作日样本的 tokens 增加约 8%、耗时增加约 80%，修订正确率也回归。下一步按原排序处理契约，或在当前参考服务中分开评测召回、归属、承诺修订与重复提醒。

## 1. 问题与方法

原 `xinli-day` 在一个 Run 内逐页读取、逐时段交出，前面的原话、召回与回执会持续进入之后的模型请求。实验让一个 Run 只整理一个完整 Span，时段之间靠平台的读取位置与业务线的变更集衔接；日终另开 Run 读取账本并对账。它不依赖改写 Transcript、删掉旧工具结果或改平台触发。

对照使用原来的 `capture-workday*` 与 `capture-multiday*`，不复制或放宽断言。各 Run 的用量、耗时和工具调用计入同一个原轮次，金标只在原轮次结束时计算。实验检查读取位置与业务线接受的完整范围一致；续页、拒收后重交、无进展退出都由确定性测试约束。默认 AgentDef 与原用例基线保持原来的流程。

## 2. 成本来源

先分析金标评测的原日志 `eval-results/20261026-164217`，每个用例各 3 次。`scripts/xinli-cost.py` 从同一份 Event 日志分解输入、输出、压缩、各工具与拒收次数，并核对总用量。

原报告没有保存精确的每段历史 token 数；「相对首调增长」是每个 Run 后续调用输入超出该 Run 首次调用的部分，包含新读取的旁听、召回与回执，不能全归为可避免的重复历史。缓存命中同时报告，不能把 token 的下降直接当作同比例的费用下降。耗时是报告记录的整次运行时间，包含评分模型。

| 用例 | 总 tokens | 模型调用 | 工具调用 | 相对首调增长 | 压缩用量 | file_changes／拒收 | 缓存命中 |
|---|---|---|---|---|---|---|---|
| workday | 1,541,438 | 78.7 | 80.0 | 1,030,628（67%） | 0 | 32.3／12.0 | 51% |
| workday-oneshot | 1,108,529 | 67.7 | 69.0 | 534,063（48%） | 136,113（12%） | 26.3／8.0 | 35% |
| multiday | 1,880,336 | 139.3 | 137.7 | 1,001,599（53%） | 0 | 49.3／8.7 | 59% |
| multiday-noisy | 1,964,550 | 140.7 | 138.7 | 1,074,523（55%） | 0 | 52.7／10.0 | 56% |

这先排除了「主要是压缩贵」：除了 oneshot，其余没有压缩；oneshot 的压缩也只占总量约 12%。增长的上下文与反复交出都应测：workday 的变更集调用约 37% 被拒，拆 Run 未必减少这种重交。拆 Run 还会增加首次请求与结束回复，可能降低缓存命中，因此不能仅从平均上下文长度推断收益。

## 3. 探索轮：日终输入的歧义

第一轮日终仍提交「整理今天」，其余实验规则与正式轮相同（`eval-results/20261026-182250`，各 3 次）。它同时对应原指令的「先读完全天」与追加规则的「只读账本」，出现一次日终重新读了 19 页旁听：仅日终就用了 718,370 输入 tokens。正式轮改用专用输入「只按账本整理今天」，业务线仍认定为日终；这是为排除同名流程的混淆，没有放宽验收。

| 用例 | 总 tokens | 相比原流程 | 耗时 | 最后金标有效次数 | 碎片率 |
|---|---|---|---|---|---|
| workday | 1,176,019 | -24% | 732.8s | 2/3 | 1.85（原 1.69） |
| workday-oneshot | 841,776 | -24% | 569.8s | 2/3 | 2.20（原 1.80） |

两项碎片率都触发回归。缺金标的两次分别是日终重读、以及模型读到 `#340.0` 却只以 `source.to: #339.0` 交出（漏了最后的寒暄句），没有覆盖完整时段的回执。表中成本含这两次失败，不能据此声称稳定节省。workday 平均 18 个 Span Run 用 829,561 tokens，日终用 346,458；拆 Run 后仍有约 12 次变更集拒收，说明它没有自动解决重交。

## 4. 正式对照与决定

正式轮使用专用日终输入、严格的新 Changeset 范围检查。原流程的 lite 对照是 §2 的金标基线；GLM 对照单独以当前数据建立临时基线。所有组都以默认并发 4、各 3 次运行，保留原轮次、上下文窗口、断言与金标。下表中的耗时包含评分。

输入都经评测的普通提交路径；本轮没有测真实后台触发、线上并发负载与吞吐。耗时只能用于这个评测负载的对照，不能据此推断生产调度的收益。

模拟业务线仍使用真实时钟登记交出的日期，旁听中的期限按原话的说话时间核对；本轮没有同时修改每个 EndUser 的模拟时钟。数据中的主题标注与金标也沿用原版本，相关局限见 §5 与评测设计 §13。

| 模型／用例 | 原 tokens | 拆 Run | 变化 | 原耗时 → 拆 Run | 缓存命中 | 最后金标有效次数 |
|---|---|---|---|---|---|---|
| lite／workday | 1,541,438 | 860,210 | -44.2% | 1003.0s → 544.2s | 51% → 66% | 3/3 |
| lite／workday-oneshot | 1,108,529 | 957,859 | -13.6% | 802.7s → 664.4s | 35% → 58% | 2/3 |
| lite／multiday | 1,880,336 | 1,635,568 | -13.0% | 817.0s → 870.9s | 59% → 70% | 3/3 |
| lite／multiday-noisy | 1,964,550 | 1,569,157 | -20.1% | 1204.8s → 817.9s | 56% → 67% | 3/3 |

工作日正式报告：`eval-results/20261026-184237`。workday 的 3 次都完成 18 个时段与独立日终，完整范围回执均通过，日终没有调用 `captures`；平均时段部分用 779,982 tokens，日终用 80,228。oneshot 中有一次在修订与引用错误、压缩后调用 `captures{after:"new",all:true}` 作空探测，返回「已读完」，实际没有重读原文；预先声明的日终策略不允许此调用，因此仍按失败处理，最后金标只剩 2 次。其平均时段部分用 813,328 tokens，日终用 144,531，压缩仍占 30,347。

workday 的「相对首调增长」从 1,030,628 降至 193,916（-81%），但模型调用从 78.7 增至 97.7：多出来的 Run 结束回复、每次重新取得上下文与召回都要付成本；工具调用只由 80.0 增至 84.3。变更集拒收仍有 11.3 次（原 12.0 次），拆 Run 的主要收益是限制上下文增长，尚未解决重交。

|---|---|---|---|---|---|---|
| lite／workday 原流程 | .96 | .80 | .83 | .92 | .62 | 1.69 |
| lite／workday 拆 Run | .98 | .67 | .72 | .88 | .61 | 1.83 |
| lite／oneshot 原流程 | .86 | .73 | .61 | .91 | .62 | 1.80 |
| lite／oneshot 拆 Run | .94 | .60 | .33 | .89 | .61 | 1.90 |
| lite／multiday 原流程 | .89 | .89 | .33 | .76 | .70 | 2.44 |
| lite／multiday 拆 Run | .96 | .76 | .72 | .60 | .75 | 2.89 |
| lite／multiday-noisy 原流程 | .91 | .88 | 1.00 | .69 | .72 | 2.28 |
| lite／multiday-noisy 拆 Run | .93 | .86 | .67 | .67 | .75 | 2.78 |

工作日两个用例仍都是 0/3。workday 的碎片率触发回归（1.69 → 1.83），oneshot 的评分均值由 4.0 降至 3.5 触发回归；已有的过多承诺与归属问题仍在。表中质量是计算出最后金标的运行的均值，不能把少了一次的 oneshot 视为稳定提高召回；完整均值、标准差和各轮指标见原报告。

多日正式报告：`eval-results/20261026-190241`。6 次都完整处理 4 天与两轮助手问答，每次 38 个 Span、4 个日终与 2 个助手 Run，完整回执与日终不读旁听的检查都通过，最后金标都是 N=3。干净版按时段用 1,391,400 tokens，日终用 189,850；带噪声版分别为 1,337,843、188,516，两版都没有压缩。变更集拒收由原来的 8.7／10.0 次升至 18.7／17.3 次。干净版少用 13% tokens，却多耗时约 7%，进一步说明调用与重交的成本不能只由上下文大小预测。

干净版「相对首调增长」从 1,001,599 降至 255,050（-75%），但模型调用从 139.3 增至 204.7（+47%），工具调用由 137.7 增至 170.0。上下文确实缩小，新增的结束回复、召回与反复交出抵消了相当一部分收益。

多日两版仍为 0/3：干净版最后的提醒精确率由 .76 降至 .60，触发回归；带噪声版触发了 turn 3 的提醒精确率与修订正确率、turn 4 的修订正确率、最后的原位修订，以及评分均值 2.5 → 2.0 的回归。助手问答仍约 2 分，另外有用户改动时找不到账本中未完成承诺的断言失败。当前证据不支持以拆 Run 改善质量。

### GLM 原流程对照

模型为 `ark/glm-5-3-flash-260828`，报告 `eval-results/20261026-193133`，整组耗时 1 小时 19 分。workday 的三次都完整结束，0/3，平均 946,878 tokens、2528.4s、58 次模型调用、76.7 次工具调用、5.3 次变更集拒收，缓存命中 90%。输出用量达 108,921 tokens，明显高于 lite 原流程的 28,112；较少调用并不等于更快。

GLM oneshot 三次中两次到 40 分钟后中断，一次正常结束，只有 1 次计算出最后金标（召回 .74）。报告平均 551,085 tokens、2319.3s、7 次压缩，包含两个未完成样本的部分用量；不能把它当作处理完整天的成本基准。新的超时统计已用原日志核对总量，避免重现旧报告超时后记零用量的问题。

### GLM 拆 Run

先按实际完整处理全天的样本分组，耗时从日志的首个 `RunRequested` 到最后一个 `RunCompleted`，两组使用同一口径，不含末尾评分：

| 流程 | 完整 workday 样本数 | 每次 tokens | 日志耗时 |
|---|---|---|---|
| GLM 原流程 | 3 | 946,878 | 2444.55s |
| GLM 拆 Run | 2 | 1,018,500 | 4397.24s |

完整样本中，拆 Run 的 tokens 反而约增加 7.6%，耗时增加 79.9%。两份完整拆 Run 样本分别为 1,201,655 tokens／5063.66s 与 835,344／3730.82s，均处理 18 个时段与日终、没有日终旁听读取；原流程三份分别为 1,013,684／2266.13s、838,851／2328.60s、988,100／2738.93s。样本数不大，这些数值是观测比较，不是生产吞吐预测。

这两份完整样本平均 96 次模型调用（原 58 次），输出用量平均 212,212 tokens（原 108,921），接近翻倍。相对首调的输入增长从 516,927 降至 240,235，但新增的调用与输出抵消了收益；仅把每次上下文缩小，不能保证整天用量更低。

拆 Run 的另一次 workday 在第 13 个时段后被额外来源检查停止：同一 Run 先接受 `#367.0–#383.0`，又接受了不同 from 的 `#372.0–#382.0`。它用了 674,174 tokens，却没有完成全天，不能放入上表的完成收益比较。首个 oneshot 则在 40 分钟中断，9 个时段完成、第 10 个中断，未进入日终。

报告为 `eval-results/20261026-205141`，整组耗时 1 小时 34 分。workday 仍为 0/3，完整范围检查失败的那次未计算最后金标，因此 N=2；修订正确率由 .73 降至 .60，触发回归。报告的 group 均值为 903,724 tokens／4053.4s，混入了提前停止的样本，不能代替上表的完整样本比较。缓存命中仍约 91%（原 90%），观察不到缓存命中退化，但不足以抵消新增调用与输出成本。其他末轮均值如下：

| GLM workday 流程 | 精确率 | 召回 | 修订正确率 | 原位修订 | 提醒精确率 | 纯度 | 碎片率 |
|---|---|---|---|---|---|---|---|
| 原流程（N=3） | .95 | .94 | .73 | 1.00 | .88 | .71 | 1.77 |
| 拆 Run（N=2） | .94 | .95 | .60 | 1.00 | .90 | .70 | 1.91 |

GLM 拆 Run 的 oneshot 三次都在 40 分钟中断，均未处理完整天；其平均 387,418 tokens 全是部分用量，最后金标 N=0，也没有评分。自动报告把原流程唯一完成样本的评分 3.0 与此处的 0 比较而列为回归；这里的 0 表示没有评分样本，不能解释为实际答卷得零分。这个统计局限不影响三次均未完成的事实，也不能用部分 tokens 的下降作为收益。

### 决定

这一版不替换默认流程，也不据此切换模型。lite 的上下文增长确实下降，但多日提醒精确率显著变差；GLM 的完整工作日样本更费 tokens、更慢，深夜一次整理也没有改善完成率。默认 AgentDef 与原用例基线保留，实验以显式开关留下，便于后续在召回、实体修订、回执与查询契约改善后重测。

专用小用例 `capture-span-runs` 最终也按事实建立基线（`eval-results/20261026-222707`）：0/3，三次日终都把两段交谈合成一条，其中一次留下两条未完成承诺。它的金标精确率与召回率仍全为 1，说明承诺匹配不能替代交谈与修订断言；修订正确率为 .67 ± .58，提醒精确率 .83 ± .29。没有为得到通过结果放宽“两段交谈保留”的断言。

## 5. 已核对的失误与下一项

以下是日志中可核实的链条，不能仅凭三个样本把原因全部归于 Run 边界。S、R 分别按单份日志中 Session、Run 首次出现的顺序编号。

| 样例 | 证据 | 指向的问题 |
|---|---|---|
| 多日第 2 次，`boards` 已完成却仍提醒 | 周二下午 S2/R18、seq150 的 `find_related` 查询使用「门店整改／分色砧板」与对方「方经理」，返回没有相关未完成承诺，之后没有关闭砧板承诺；原流程同次 S2/R3、seq123 查询含「城西店食安整改」、对方为「城西店店长」，召回 C-0015 并在 seq126 关闭。 | 查询与称呼不同导致召回结果不同；误把佩戴者的称呼当作对方是可见错误。 |
| 多日第 3 次，`ptm` 候选可见仍新建 | S3/R21、seq71 已召回原家长会承诺 C-0001；seq83 把关闭写进 revise 被拒，seq86 重交删掉该操作、另建 C-0033；晚上只关闭 C-0001，重复条仍提醒。 | 实体复用与拒收后修正失败；原流程第 2 次也有家长会重复。 |
| 多日第 2 次，`cost-sheet` 重复后修复没交上 | 周二、周三分别新建 C-0027、C-0033，周四只关闭后者；日终 R42、seq216 关闭初始 C-0003 时引用了不存在的 `#2.2`，最终 seq222 接受的变更集已删去该关闭。原流程同次 seq157 用有效的 `#2.0` 关闭了它。 | 跨天重复加上引用错误后的漏交；原流程第 1、3 次也有成本表重复，不能称为拆 Run 独有。 |
| 工作日第 2 次，按当前 topic 标注发生碎片 | R13、seq500 已新建 P-0102「老陈保留与职业发展沟通」；R15、seq607 的候选中没有 P-0102，seq610 又建 P-0104「排班引擎重构」，并关联另两个项目。 | 未返回旧项目是事实，但技术重构可能是独立的新主题，不能断言新建项目错误；较粗的 topic 不能替代这层语义判断。 |
| 工作日第 1 次，老陈交谈误挂绿源 | R15、seq604 同一交谈同时归入老陈职业谈话与绿源超市；原流程同次 seq563 只归入老陈职业发展。 | 归属判断错误，不能都归咎于候选没召回。 |

继续遵循架构评审 §3.3 的排序：生产业务线开工时，先做第 2 项的共享核心与契约。在当前仍只有内存参考服务的范围内，下一项是把候选召回与归属判断分开测，并检查同一事项的承诺修订与重复提醒（第 4 项）。这里只是按当前 lite 的失误定位方向；GLM 的工作日结果另列，不用它替代尚未测过的多日质量。平台层面的删旧页或触发扩展不是这些日志直接支持的修复。

碎片率触发回归并不表示每个新增项目都错。候选召回需要单独的语义标注，才能区分漏召回、合法新项目与实际错归；更直接的错归证据是把职业谈话挂到无关的绿源项目，提醒侧则有已完成事项仍提醒的明确错误。

成本表那次的 `#2.2` 在 seq216 之前没有出现过，四个旁听 Session 的 Event 2 也都只有 `#2.0`；当时账本给 C-0003 的引用是 `#15.0`，因此不是照搬旧 Session 引用，生成原因未知。另一个独立问题是 `commitmentLine` 展示旧承诺时不附引用所属 Session，确有歧义，后续工具契约应处理；它不能直接解释这一次的不存在编号。

## 6. 实现与验证

实验入口为 `xinli_span_runs: true` 与 CLI `-xinli-span-runs`，只派生评测中的 AgentDef。确定性测试覆盖跨页、拒收重交、缺完整回执、无进展、超读、空与进行中时段、换 Agent，以及超时中断后保留用量；同时修复评测窗口覆盖丢失 Scope 的问题。runtime、session、service 与默认 AgentDef 均未改动。

最终 `dev fmt`、完整 `dev check` 全绿（源码摘要 `5d8c2c8541dc2691`，其后只补本文统计说明）：包括 Go race、模拟测试、PG／S3／Docker、e2e、Web SDK 与文档检查。所有正式报告都经成本脚本逐日志核对总用量。默认基线只新增 `capture-span-runs` 的真实结果，原有条目逐项比对无变更；实验大用例的回归没有写入默认基线。
