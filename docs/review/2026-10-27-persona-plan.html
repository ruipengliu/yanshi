§1

结论速览

架构 D1 D8

三层方向成立。内核的接入面（AgentDef、白名单、MCP、服务令牌）是通用的，Persona 是可选的业务服务。现有耦合在启动入口、调试接口和评测里，执行路径中没有 xinli 分支。

设计复杂度 D2 D3 D10

M7 计划给内核加的原语里，左侧 9 项及其派生都以"原文在内核"为前提。原文改放业务侧（方案 C），这些多数可以不做。这是最大的一处待裁决。

数据关系 D6 D7

三处存储各按 Session、EndUser、(业务线, EndUser) 分片，跨层只靠 ID 关联。有两处关系没有定义：注销的跨层顺序，以及项目与 xinli-project Session 的映射归谁保存。

关键流程 D3

一天的整理、删除一段谈话、定时执行、实况预览都已写成流程。方案 A 下删除一段谈话要经出站流跨库通知，而且日志里的派生副本不在擦除范围内。

容量 D4 D5 D11 D12

文档只估了存储与写入，没有估模型 token。按评测复算，10 万 DAU 每天约 1.2–6 千亿 token，这是最大的瓶颈和成本项，远超存储。

扩容范式 D9

内核按单元、分片、角色池扩，Persona 按 (业务线, EndUser) 分片。键规则已经在执行，但 PostgreSQL 分片路由还没实现，它是 100 万 DAU 的前置条件。

ID 如何把三处数据串起来

  • end_user：三层共用的人的标识，由业务线签发令牌时给出。账号到 EndUser 的映射在应用层。
  • session_id + #seq.idx：原话的唯一引用。当天 Session 7 天后删除，Persona 里的这些引用按设计悬空，只保留引用与"超过保留期"的说明。
  • 变更集来源键：(旁听 Session, source.from) 或 (旁听 Session, day)。按它去重、重交时整体取代，Run 重试与接管时因此幂等。
  • speaker_ref：采集服务比对声纹后填入 Capture 的 Persona 实体 ID。内核不解析它，只透传到给模型的文本与 cite_captures。
  • 出站行：(session_id, seq) 指向事件。消费方按它去重，需要内容时回读事件。
  • 项目：每个项目一个 xinli-project Session。mock 把映射存在 Persona 侧的项目记录里；生产时归谁保存，设计没写（D7）。
分片键核对：Capture 的事件与片段在同一个 Session 键里，同一事务写入；注销按 EndUser 键写屏障，跨 Session 的清除由 Janitor 离线完成；Persona 的一个变更集只涉及一个 (业务线, EndUser)。三处都满足"一个事务一个键"（ADR-0028）。

§6

关键流程

6.1 一天的整理（目标形态）

  1. 设计应用层以服务令牌建当天的 xinli-day Session。现状由控制台或评测创建。
  2. P2定时：当地 18:00 到次日 04:30 的窗口，流上静默满 2 小时即执行，否则 04:00–04:30 之间随机执行。现状由业务线到点提交。
  3. 设计HostApp 把音频分片交给采集服务；识别、说话人区分、声纹比对都在应用层，内核只收文字。
  4. 已实现SubmitCaptures：一批至多 200 段，按 capture_id 去重。
  5. 已实现整批送内容安全审核，违规时逐段复核、只留占位；提供商不可用时拒绝（fail closed）。写入后不开启 Run。
  6. P2流上静默满 quiet，平台开启 Run，输入是 AgentDef 声明的固定文字，来源是平台。现状由业务线提交"整理交谈"。
  7. 已实现captures{after:"new"} 从已提交的读取位置读一个时段，进行中的时段先不读。
  8. 已实现每段交谈召回候选项目与相关的未完成承诺。
  9. 已实现每个时段交出一个变更集；平台附上被引用原话的说话人，业务线据此核对承诺人。
  10. 已实现保存成功时附回执；拒收时不附，并在文字中写明原因让模型改正后重交。
  11. 已实现ack: true 的流只把读取位置推进到回执连续覆盖的页尾。
  12. P2到期写入 ScheduleFired 与带定时标记的 RunRequested，同一次追加。
  13. 已实现day_ledger、当天整理的变更集、file_day。
  14. P1编排器按分片拉取出站流，只拿到 ID。现状由 mock 在 file_day 时于进程内直接触发。
  15. mock为当天涉及的项目建或复用 xinli-project Session，提交"整理 <日期>"。

6.2 删除一段谈话（方案 A）

  1. 引用范围在同一 Session 内，含两端；按 erase_id 去重。Session 已关闭也可以擦除。
  2. 擦除与中断在同一次决策中写入。依据：声明了流的 AgentDef 都是 scope: run，之后的 Run 看不到旧回复与压缩摘要。
  3. 被中断的 Run 已交给 Persona 的内容，由第 8 步的级联处理。
  4. 展开器按日志前缀判断：前缀里有覆盖它的擦除事件，就一律返回占位，即使存储还没清空。
  5. 返回本 Session 写入、依据可能落在范围内的 Memory，由 App 询问用户；内核不自动删除。
  6. BFF 立即隐藏相关对象，盖住出站流的消费延迟。
  7. 擦除信封保留 72 小时，不随 Session 删除；消费者离线更久时走删除对账接口。
  8. 编排器把擦除转告 Persona。
  9. 墓碑与级联在 Persona 内同一事务完成；之后引用这段的变更集被拒收，迟到的提交不会复活内容。

7.2 复算：模型 token 复算

依据评测基线 capture-workday：一个工作日约 9 小时、465 段、31,124 字。原流程用了 1,541,438 token、80 次工具调用，缓存命中 51%；按时段拆 Run 的实验用了 1,176,019 token，但碎片率回归，未采纳。

每字 token 1,176,019 / 31,124 ≈ 38 · 1,541,438 / 31,124 ≈ 50 每人每天 3.1 万字 × 38–50 ≈ 1.2–1.5 M （评测的旁听密度） 12 万字 × 38–50 ≈ 4.5–6.0 M （文档假设的"十几万字"，按线性外推） 10 万 DAU 1.2–6.0 × 10¹¹ token/天 ≈ 全天平均 1.4–6.9 M token/秒 100 万 DAU × 10 实况预览 假设峰值 10% 用户在前台、每分钟一次、输入约 5–8k token 10 万 DAU：约 170 次/秒 ≈ 0.8–1.4 M token/秒（只在峰值时段）

线性外推是乐观的一侧：单个 Run 内上下文逐页累积，原流程略超线性；触发把一天切成许多短 Run 后接近线性。缓存命中的部分更便宜，但仍占提供商的吞吐配额。这一项比存储高好几个数量级，是容量和成本的主项。

7.4 瓶颈排序

  1. 1高模型 token 的吞吐与费用后台整理最大，其次是实况预览，再次是问答。缓解手段：按时段拆 Run（−24%，但指标回归）、把已交出的页移出上下文（建模 §9，未做）、降低 37% 的拒收重交、把 find_related 并进 file_changes、白天整理改用更小的模型。
  2. 2高语音识别（应用层）峰值的流式识别路数，约等于同时佩戴且在说话的人数。它在内核之外，却决定采集链路的容量；文档没有量化。
  3. 3中内容安全提供商每批一次，10 万 DAU 峰值 330–1,700 次/秒，100 万 DAU 再乘 10。失败即拒绝，提供商故障时采集停在 HostApp 的本地缓冲。
  4. 4中→高内核 PostgreSQL 单库app.Postgres 现在是单个连接池，分片路由未实现（M7 §13 列为 P4 前置）。片段写入与逐 Session 删除的 WAL 未压测。10 万 DAU 为中，100 万为高。
  5. 5中停放定时与队列认领pgqueue.Claim 先扫描、再过滤停放项，百万级的长停放会拖慢认领；设计用独立的到期表规避。
  6. 6中通知扇出每个网关进程监听全部分片，分片归属路由未实现（deployment §8），单元内进程数受通知投递上限约束。
  7. 7低Persona写入每秒几十次；检索总按单个用户过滤。独立库、按 EndUser 分片已经足够。

设计

避免瓶颈的规则

  • 在线路径按键访问，一条 SQL、一个事务只涉及一个键；新表先在 pg.Tables 登记分片键（ADR-0028）。
  • 跨层消息只带 ID，按 ID 幂等：capture_id、输入 ID、变更集来源键、出站行的 (session, seq)。
  • 后台工作走后台类别与准入，交互优先；当天整理按各人作息加抖动分散。
  • 模型并发按提供商账号上限全局分配；单次调用有子限额，后台保有最低份额。
  • 大对象不进事件日志：工件只放引用；原文进正文存储（A）或留在业务侧（C）。
  • 每一项容量结论都要有压测支撑：P1 的片段写入与逐 Session 删除，P2 的百万停放，P3 子限额下的首字延迟。
§9

待讨论

每条写了当前倾向，以及什么证据能定下来。

D1
内核与业务的边界是否按 ADR-0043 的判据执行

倾向：定时、单次调用、档位、出站流的通用部分、EndUser 删除屏障通过判据；Capture 相关的多数项不通过（§3 表）。

D2
原文放哪里：方案 A 还是 C

倾向 C，前提是合规回答"原文保留期能否由业务线担保"。P1 动工前先做三步验证：可信片段进入来源推导、业务侧 mock 跑 capture-* 对齐基线、写一页四种删除操作的语义对照。

D3
擦除的完整性

方案 A 不覆盖日志里的派生副本（模型回复、调用参数），它们留到当天 Session 删除。是接受，并把隐私说明改成"约 7 天内删除"，还是补上"删除并重建当天 Session"？

D4
每人每天的 token 预算

需要一个目标值，以及用哪个评测指标约束它；还要定下愿意用多少整理延迟换成本。

D5
旁听密度

文档按十几万字，评测一天 3.1 万字，差约 4 倍，存储与 token 估算都随之放大。需要真实佩戴数据。

D6
注销的跨层顺序

内核有 EndUser 删除屏障，但 Persona 与应用层何时删、谁先谁后、Persona 怎样得知，设计没写。出站流只有 session_deleted，没有 EndUser 级的信封。

D7
项目与 xinli-project Session 的映射归谁

Persona（像 mock 那样）还是应用层的编排器？它决定删除某个项目时由谁删除那个 Session。

D8
Persona 的租户隔离

Persona 信任内核注入的业务线与 EndUser 请求头，前提是每条业务线的 MCP 登记有独立凭证，且 Persona 校验头与凭证一致。mock 未配置凭证。

D9
PostgreSQL 分片路由的时间点

10 万 DAU 是否已经需要？在压测给出单库上限之前不定。

D10
是否暂停 Stream 泛化与流上的触发

倾向暂停，直到 D2 定下来。来源推导的集中化独立有价值，保留。

D11
实况预览的成本

前台每分钟一次单次调用，峰值约 1 M token/秒的量级。可以考虑改为有新旁听时才调用，或者在端侧做。

D12
内容安全失败即拒绝对采集的影响

提供商故障时，HostApp 需要缓冲多久、多大？需要一个数字，写进接入文档。
