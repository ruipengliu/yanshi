PoC #1 实验报告：lifecycle.Recheck 删除屏障形式化验证

对照 落地方案（PoC #1），在不改动任何 Go 生产代码的前提下，我们在 docs/formal-verification/poc1-lifecycle-recheck/ 与 internal/sim/lifecycle_trace_test.go 落地了首个形式化闭环实验： 包含 Quint 形式规约、Apalache SMT 符号模型检验、两项协议变异测试（防空洞证明）与 Go 真实存储 Trace Validation 回放。

实验总结论

1. 零 Docker 闭环全绿跑通：run.sh 串行跑完“静态类型检查 + 内置单元测试 + 2000 样本模拟 + 12 步 Apalache SMT 符号检验 + 两项变异检出 + Go -race 轨迹导出 + Quint 回放检验”共耗时 56.78 秒；若日常内循环仅跑 Quint 模拟与 Trace 回放，耗时仅 ~4.3 秒。

3. Trace Validation 当场抓出“模型与代码偏差”：首轮回放即在 164ms 内报出 ordWithdraw 抽象偏差，证实 Trace Validation 能有效堵住“规约与实现两张皮”。

01

实验架构、建模范围与显式假设边界

PoC #1 聚焦 internal/lifecycle/lifecycle.go（Recheck / KeepsMemory）、 internal/janitor/janitor.go（Janitor.delete 六阶段与崩溃接管）、 internal/memory/service.go（Save 写后复查）与 internal/presence/presence.go（Put 写后撤回），形成如下闭环交付物：

已证明的 5 条核心安全不变量

allInvariants
  • invCompletedHasTombstone：清理完成（completed）前必然已写入删除记录。
  • invNoOrdinaryDataAfterComplete：清理完成且在途 Recheck 收敛后，普通存储、日志（hasLog）与索引（hasIndex）绝无残留。
  • invNoMemoryOnHardDelete：普通硬删除（end_user）完成后，memories 同样绝无残留。
  • invNoLateMemorySurvived：retention / erasure 虽保留既有 Memory，但删除标记之后发生的迟到写入（memAfterDel）绝不残留。
  • invPreMemoryPreserved：retention / erasure 下，删除前已确认完成的既有 Memory 绝不会被误删。

显式模型假设与协议边界（诚实声明）

TCB 边界
  • 活写入方收敛假设：对应代码中 lifecycle.Recheck 内 withdraw(context.WithoutCancel(ctx)) 的保障——模型假设写入存储后若进程未永久断电，会继续执行复查与撤回。
  • 极限崩溃窗口边界：若外部写入方在 Janitor sweep2（第二遍清扫）结束之后落盘数据，并在执行 Recheck 之前进程自身发生硬崩溃（未执行撤回），则单次进程内 Recheck 无法拦截；该风险在生产中由接口层前置检查、service.Delete 先写删除记录以及租约/上下文隔离把窗口压至极窄。
  • 抽象粒度：PoC #1 抽取“普通 SessionData”与“KeepOnRetention Memory”两类代表存储并叠加多阶段 Janitor 崩溃；未涵盖多节点设备离线 Inbox 与级联子 Session（留待后续扩展）。

变异测试实测：自动构造最短 9 步反例（防空洞证明）

为了证明 allInvariants 并非“永真假命题”，我们在 lifecycle_recheck_mutant.qnt 中构造了两个常见工程误改，Apalache SMT 与 quint run（32ms / 16ms）均立即命中致命竞态：

变异 #1：先查后写（mutant_check_then_write）

3,814 ms 捕获

把普通写入方改成直观但错误的“先检查未删除 → 再写入落盘且不做 Recheck”。Apalache 在 State 9 精确构造出导致僵尸数据残留的 9 步调度序列： 

[State 0] init (tombstone="none", data=Set())
[State 1] ordCheckBeforeWrite("d1") -> ordPC["d1"]="checked_ok"
[State 2] markDeleted("end_user")   -> tombstone="end_user"
[State 3..7] Janitor 完成 interrupt -> sweep1 -> delete_log -> sweep2 -> delete_index
[State 8] ordWriteWithoutRecheck("d1") -> data=Set("d1"), ordPC["d1"]="done"
[State 9] janitorComplete -> completed=true, hasLog=false, hasIndex=false, data=Set("d1")
[violation] invNoOrdinaryDataAfterComplete 失败：删除完成但 data 残留 "d1"！

变异 #2：erasure 跳过 Recheck（mutant_erasure_skips_recheck）

3,747 ms 捕获

模拟工程师误以为 KeepOnRetention 代表在 erasure 模式下不需要复查 Recheck（与 ADR-0050 第 5.2 节规定直接冲突）。Apalache 在 State 9 构造出迟到记忆污染： 

[State 0] init (tombstone="none", memories=Set())
[State 1] markDeleted("erasure")   -> tombstone="erasure"
[State 2] janitorClaim             -> janitorStage="interrupt"
[State 3] memWrite("m1")           -> memories=Set("m1"), memAfterDel=Set("m1")
[State 4..5] Janitor 推进至 delete_log
[State 6] memRecheckBuggy("m1")    -> 因 tombstone=="erasure" 错误跳过撤回, pc="done"
[State 7..8] Janitor 跳过 KeepOnRetention memories 完成 sweep2 -> delete_index
[State 9] janitorComplete          -> completed=true, memories=Set("m1") ∩ memAfterDel ≠ ∅
[violation] invNoLateMemorySurvived 失败：擦除后写入的新 Memory 逃逸留存！

Go 真实实现 Trace Validation 与真实收获

在 internal/sim/lifecycle_trace_test.go 中，我们没有写死任何 mock 逻辑，而是直接装配了真实的 app.Memory + app.NewCore + service.Service + presence.Service + memory.Service + janitor.Janitor（仅利用其已有的 BeforeStage 测试钩子观测内部清理阶段与注入崩溃），运行以下 4 条场景并逐帧导回 Quint 校验：

Go 真实场景名 真实 Go 调用链与并发交错 校验结果
traceHardDeleteWithLateWrites 写 presence(d1)、memory(m1) → Service.Delete("end_user") → 迟到 presence.Put(d2) 与 Memory.Save(m2) 经真实 Recheck 撤回 → Janitor.Step 全程完成 Go + Quint 同构通过
traceErasureKeepsPreWithdrawsLate 写 d1、m1 → Service.Delete("erasure") → 迟到 Memory.Save(m2) 被真实 Recheck 撤回并返回 ErrNotFound → Janitor 完成后 m1 留存且 d1/m2/log/index 全清 Go + Quint 同构通过
traceRetentionJanitorCrashRecovery 写 d1、m1 → Service.Delete("retention") → Janitor 在 "log" 阶段被 cancel() 中断模拟崩溃 → 时钟推进越过租约后新 Janitor 接管重跑完成 Go + Quint 同构通过
traceJanitorCrashAfterLogDeleteAndLateWrite 写 d1 → 硬删 → Janitor 删完日志、进入第二遍 "sweep" 前崩溃 → 崩溃窗口内注入迟到 presence.Put(d2) → 新 Janitor 重扫完成清理 Go + Quint 同构通过
工程实证亮点：Trace Validation 如何在 164ms 内抓出“规约假设偏差”

在初次把 Go 真实轨迹导回 Quint 执行 quint test generated/trace_replay_test.qnt 时，测试在 164ms 内立刻在第 54 行报错： Error [QNT508]: Assertion failed — assert(data == Set())（预期在延迟写入 d2 被撤回后 data 清空，但模型仍留有 d1）。

回查 internal/presence/presence.go 第 78–80 行发现：lifecycle_recheck.qnt 最初想当然地假设所有普通存储的 withdraw 回调都是按单条 ID 删除（data.exclude(Set(id))）；但真实代码中，presence.Service.Put 的撤回回调直接调用了 s.Store.DeleteSession(ctx, e.SessionID)——即一旦复查发现删除记录，整条会话的在场记录全部清空！ 我们在规约中同步修正 ordWithdraw 语义后，全部 7 项测试与 12 步 Apalache 符号检验重新全绿通过。这直接证明了“Trace Validation 把代码真实语义反向钉死在形式模型上”的独特价值。

经验沉淀与推进 PoC #2 建议

PoC #1 核心工程结论

可行性已证实
  • 工具链完全可行：Quint 0.33 + Rust evaluator（50ms 级随机探索）+ Apalache SMT（数十秒级符号穷举）在 macOS 本机运行流畅，且零 Docker 依赖。
  • 与现有 internal/sim 高度互补：无需改动生产代码即可通过测试钩子实现 Trace 导出对齐。
  • CI 注意点：仓库已有门禁 scripts/docrefs/main.go 会扫描 docs/ 下所有 Markdown 链接，需保持忽略 node_modules（已在本次实验顺带修补）。

下一步推进 PoC #2 的具体调整

Run / Worker 状态机
  • 将 Trace 导出接入随机高覆盖种子：PoC #1 先用了 4 条定向情景轨迹；进入 PoC #2（session.State + Worker.Step）时，直接从 internal/sim 精选 20–50 个高覆盖随机种子把 v1.Event 序列导出为标准 ITF / Quint trace 批量回放。
  • 把时间拆进分级门禁：日常开发内循环用 quint test + quint run + Go PBT/Trace 回放（控制在不超 15 秒）；较重的 Apalache SMT 符号检验放进按需命令或合并前检查，从而真正解决高频反馈耗时痛点。
