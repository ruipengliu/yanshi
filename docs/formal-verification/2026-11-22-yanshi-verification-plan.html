yanshi 形式化验证落地方案与 Rust 迁移评估

基于业界形式化验证调研（见 2026-11-22-industry-survey.html）与 yanshi 现有代码基线（约 8.7 万行 Go 源码 + 5.7 万行测试、纯函数事件投影与 internal/sim 确定性仿真框架）， 回答三个工程决策问题：① 能否直接落地形式化验证；② 是否应将项目转成 Rust；③ 新方案如何同时缓解 make check / make sim 耗时过长并提升完备性。

核心结论

1. 无需重写语言，可直接落地：yanshi 已具备“纯函数投影 + 确定性单步 + 仿真底座”的极佳基因，最适合走 Quint 符号模型检验 + Event 日志 Trace Validation + Go rapid 属性测试 + 分层门禁路线。
2. 不建议全量迁 Rust：Rust 在代码级静态验证上确有先天优势，但 yanshi 90% 的高危缺陷来自分布式协议时序与跨存储竞态，换 Rust 无法自动消除这类问题，且 14.4 万行 Go 与 gomobile 生态重写 ROI 极低。
3. 提速与完备性兼得的机制：把“证明协议本身没错”与“证明代码按协议写”解耦——将开发与 AI 迭代期反馈从分钟级压至 15–30 秒（无 Docker/PG），同时把协议验证从“随机抽样”提升至“SMT 数学穷举”；PG 差分与全量 -race/集成测试则按门禁分层后移。

01

现状诊断：为什么 make check / make sim 耗时很长？

对照 Makefile、internal/sim/sim_test.go 与 internal/sim/pg_test.go，当前验证慢并非因为某一处性能劣化，而是因为三类性质完全不同的验证成本被捆绑在同一个高频反馈路径里：

耗时来源 当前实现现状 本质成本原因 形式化方案能否提速/替代？
1. 海量内存随机种子 make sim 跑 sim.seeds=2000（叠加 Faults / LongRuns / NoFault / Attested 共 6000+ 个 World）；make check 也默认跑 300 种子 以算力换概率完备性：要撞出多因子极端交错，靠盲摇大量随机种子，后段边际收益急剧递减 可提速且完备性反超
Quint + Apalache 在 5–30 秒内穷举协议状态空间，覆盖深度远超 2000 种子；内存 sim 仅需少量高覆盖种子做 Trace Validation
2. PG 与双库分片差分 sim.pgseeds=100、sim.shardseeds=100，受数据库连接数限制最多 8 并发 / 4 对并发，占 make sim 耗时的六成以上 真实 PostgreSQL 往返 I/O、schema 初始化、事务隔离级别与 SQL 语义等价校验 不可替代 · 可分层降频
形式规约替代不了真实数据库语义；但开发内循环零 PG 依赖，本地快速门禁缩至极小覆盖集，全量 100 种子移至合入前/夜间 CI
3. 全仓 -race 与容器/SDK 联调 make check 串行起 deps-up、web、day-bin、三模块 -race、Docker 沙箱、S3 与双分片短日测 数据竞争检测开销（放大数倍）、容器/对象存储与跨语言 SDK 真实联调 不可替代 · 避免高频误触
通过 Tier 0 过滤协议与逻辑错误，避免“改一行状态机逻辑也要先等全套容器联调”
yanshi 天然适合形式化验证的三个架构基因

与一般业务后端不同，yanshi 已经把最难建模的副作用与确定性内核隔离开： ① internal/session/state.go 是纯函数事件投影，任何非法状态迁移在 Apply 立即报错； ② internal/runtime/worker.go 的 Worker.Step 使用注入的虚拟时钟与 ID 生成器，天然是离散状态迁移系统； ③ internal/sim/sim.go 已具备单 goroutine 确定性回放与覆盖统计（Stats），导出标准执行轨迹（Trace）几乎零成本。

02

语言选型评估：转成 Rust 是否更有利形式化验证？

业界 AI 形式化验证的主战场确实集中在 Rust（详见 调研报告）：Rust 凭借所有权与借用检查器砍掉了形式化验证里最痛的指针别名与分离逻辑难题，并拥有 Kani → Verus → Aeneas/Lean 4 完整梯队。但具体落到 yanshi 项目，必须区分“代码级静态证明上限”与“项目整体 ROI 与真实风险结构”：

转 Rust 的明确收益（理论上限更高）

代码级证明友好
  • 对 session.Apply、provenance、memgate、委托能力交集等纯函数逻辑，可直接跑 Kani 查 panic/越界/不变量，或用 Verus / Lean 4 做全量数学证明。
  • Rust 带数据的 enum 取代 Go 的 Protobuf oneof + 接口断言，编译期强制穷尽分支，减少空指针与漏处理。
  • 无 GC 与极小运行时，便于未来下探到机器码级安全验证。

为什么全量迁 Rust 得不偿失（核心否决项）

风险错配 · 成本过高
  • 核心风险错配（决定性因素）：yanshi 不是密码学库、不是 C 内存解析器，而是分布式编排与状态管理基础设施。90% 的致命缺陷在多 Worker 接管、lifecycle.Recheck 删除竞态、Outbox/分片一致性、后台超时交错——这些是协议层问题，换 Rust 依然必须靠 Quint/TLA+ 与 DST，Kani/Verus 证明不了跨库事务与网络分区。
  • 迁移与翻译 Bug 成本巨大：现有 14.4 万行 Go、51 个 internal/ 包、pgx/minio/mcp-go 生态以及 sdk/mobile 的 gomobile（macOS / iOS / Android）绑定。全量重写短期会引入远超收益的语义漂移风险。
  • Go 架构已绕开主要短板：纯函数投影与单步确定性已经把 Go 最难验证的“隐式并发共享状态”压到极小范围。
折中原则：Go 主干 + 仅在强安全纯计算边界局部评估 Rust

95%+ 的分布式运行时与编排留在 Go，主攻 Quint 协议验证 + Trace Validation + 强化版 sim + 属性测试。 仅当未来出现两类明确诉求时，才考虑把极小块（2%–5%）抽成独立 Rust crate 并用 Kani/Verus 证明： ① 自研不可信输入解析器、沙箱强隔离控制面底层或自定义密码学组件； ② 需要把 sdk/nodesdk 的去重/幂等状态机做到 iOS / Android / Web(WASM) 三端共享一份经形式验证的核心实现。

03

目标架构：解耦“协议完备性”与“实现一致性”

新方案的核心思想是把原本由 make sim 单点硬扛的两件事拆开，并利用 yanshi 现成的 v1.Event 日志流建立自动化对齐桥梁：

Layer A · 协议层完备性

Quint 形式规约 + Apalache 符号模型检验

  • 选用 Quint（TLA+ 现代化继任者，类 TypeScript 语法 + 静态类型），相比原生 TLA+ 对工程师与 LLM 都更易读写，且支持直接仿真、类型检查与 Apalache（底层 Z3 SMT）符号模型检验。
  • 规约聚焦最小核心协议（每份 100–300 行），不照搬业务细节，从而在 5–30 秒内完成有界/归纳穷举。
Layer B · 实现对齐与安全属性

零侵入 Trace Validation + Go rapid 属性测试

  • Trace Validation：复用 internal/session 的 Event 序列与 internal/sim 的确定性 World，在测试侧将执行轨迹序列化为标准 ITF JSON，喂给 Quint Trace Validator 逐帧比对状态转移。只要 Go 代码出现任何规约未允许的迁移、漏写事件或非法重排，立即报出精确帧号。
  • 属性与模糊测试：在纯逻辑安全边界（provenance.go、memgate.go、delegation.go）引入 pgregory.net/rapid 与 go test -fuzz，把自然语言安全要求变成可自动收缩反例的数学不变量。
04

分层门禁体系与防 AI 作弊（Spec Gaming）治理

为了在不削弱任何生产质量底线的前提下解决“每次改代码都要等很久”的痛点，将验证拆分为三级门禁，并同步引入防 AI 规约作弊规则：

门禁层级 命令入口 目标耗时 外部依赖 验证内容与定位
Tier 0
开发 & Agent 内循环		 make verify
新增		 15–30 秒 零依赖
（无 Docker / PG）		 Quint 模型检验（协议完备）+ 20 种子 Trace Validation（实现对齐）+ session / runtime / lifecycle / delegation 单测与 rapid PBT。每次 AI 改完内核逻辑必跑。
Tier 1
本地提交前快速闸门		 make check-fast
（或精简 check）		 1–2 分钟 Docker PG / S3 / Node 完整 lint（含 docrefs / buf）+ 单元测试 -race + 精简 PG 差分（如 pgseeds=5）+ TestDayShort。
Tier 2
合入前 / 夜间深度验证		 make check + make sim + 变异测试 5–15 分钟 完整环境 保留完整 2000 种子 + 100 PG/分片差分 + 全量沙箱/SDK 联调 + 定期规约变异测试，作为最终合并与发布红线。
防 Spec Gaming 治理（锁定可信计算基 TCB）

当编码智能体面对失败的验证器时，天然倾向于“修改规约/放宽断言”以骗取绿灯。为此建立两条硬约束：
1. TCB 权限隔离：将 specs/*.qnt、核心属性测试文件及 internal/sim 不变量断言列为受保护的 TCB——在 AGENTS.md 与 Code Review 规范中明确：实现任务的编码智能体不得擅自修改或弱化 TCB 文件；确需变更规约必须单独提交、人工审计。
2. 规约变异测试（Mutation Testing）：针对关键不变量准备若干已知的“坏补丁”（例如故意把 lifecycle.Recheck 改成“先查后写”、或把 memgate 的 NFKC 去掉），在 Tier 2 / 实验阶段确认 Quint 与属性测试必然失败，杜绝“空洞证明（Vacuous Proofs）”。

05

三期 PoC 渐进落地路线

不追求一步到位覆盖全仓，按“状态空间最小 → 业务价值最高 → 安全边界最硬”分三期推进，每期均有独立可量化的验收标准，实验过程与数据持续沉淀至 docs/formal-verification/：

  1. PoC #1 lifecycle.Recheck 删除屏障与 Janitor 物理删除协议（ADR-0015）
    推荐首个实验 · 1–2 天

    选择理由：状态空间极小（Session 删除记录、写入入口“先写后查”、Janitor 多存储清理与任意步崩溃重启），但并发竞态最隐蔽——任何一条路径顺序颠倒或漏查都会导致删除完成后残留“僵尸数据”，直接触碰隐私删除红线。

    核心不变量：一旦 Session 物理删除完成，任何已登记存储中绝不存在该 Session 的残留数据；写入与删除并发交错时绝不出现“漏删”。
    交付物：lifecycle_recheck.qnt（~120 行）+ 从 internal/sim/lifecycle.go 导出 ITF 轨迹跑通首次 Trace Validation。
    验收标准：故意把一处实现改为“先查后写”，Quint 与 Trace Validation 须在 < 20 秒内自动给出最短反例路径。
  2. PoC #2 session.State 与 Worker.Step 核心执行状态机
    最高核心价值 · 3–5 天

    选择理由：internal/session/state_apply.go 与 internal/runtime/worker.go 是整个分布式运行时的心脏，涵盖 RunStatus 迁移、Attempt 崩溃接管（Takeover）、Call 审批/派发/转后台（ADR-0035/0058）与重答（Redo）并发冲突，也是 AI 改动最频繁的高危区域。

    核心不变量：同一 Session 任意时刻至多一个活跃 Run；非终态 Run 在故障恢复后不丢失、不双活；Call 审批/结果/后台转入严格保序且去重。
    交付物：核心状态机 Quint 规约 + sim Event 流 ITF 导出器 + Makefile 新增 make verify（Tier 0 门禁）。
    验收标准：精选 20–50 个高覆盖 sim 种子 100% 通过 Trace Validation；全流程总耗时控制在 30 秒内且无需 Docker。
  3. PoC #3 安全边界硬闸门：Provenance、memgate、委托交集与三方隔离
    安全合规防线 · 2–3 天

    选择理由：记忆投毒防护（ADR-0023）、来源推导（ADR-0039/0052）、委托权限不放大（ADR-0031/0060）与听过他人旁听的 Session 禁调三方 Agent（ADR-0048）属于绝对安全红线，单靠固定手写样例难以防住 Unicode 变体、嵌套委托或边界输入绕过。

    核心不变量：写入闸门严格单调（只收紧不放宽）；FromOther 一旦进入上下文则三方调用必被拒；子 Run 能力集严格满足 Cap(child) ⊆ Cap(self) ∩ ⋂ Cap(ancestors)。
    交付物：基于 pgregory.net/rapid 的属性测试套件 + go test -fuzz 入口 + 面向关键安全函数的变异测试脚本。
    验收标准：全部属性测试运行 < 3 秒纳入 make verify；安全逻辑关键变异体击杀率达到 100%。
