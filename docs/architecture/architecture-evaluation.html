§1

核心评估结论：下层原语高度正交，上层边界存在“双向越界”

核心诊断结论：yanshi 内核的下层执行与存储原语（Event 唯一事实源、Attempt fencing、单事务原子唤醒、统一 Capability 路由、1024 槽预分片、物理删除闭环）设计极度克制且坚固，完全具备世界级 Agent 运行时的骨架；但内核与业务线交界的上层接入契约与治理切面存在显著的“双向越界”——既把首条业务线的领域规则硬编码进了内核，又把内核底层的物理分片拓扑与幂等补偿负担甩给了业务线。若不在第二条业务线大规模接入前完成边界收敛，将直接引发每次新增业务场景都要改内核 `proto`、多业务线共池相互饥饿/越权、以及内核分片无法在线扩容三大系统级扩展性瓶颈。

下层执行底座：边界清晰、无需推翻 核心资产

内核严守“只管可靠执行、来源推导、审批拦截与按主键物理删除，不建模具体业务实体”。无状态 Worker.Step + 单二进制五角色裁剪 + 14 套一致性套件与三方差分模拟（make sim），使标准对话、工具调用、端云协同与长任务场景可开箱即用。

对应：m0-core-primitives · m1-device-nodes · m2-sandbox · ADR-0004/0028/0051

越界方向一：业务语义下沉污染内核 假通用·真耦合

可穿戴录音的二元角色（SPEAKER_WEARER / OTHER）、声纹引用 speaker_ref、中文“之后七天”相对日期头、6 个固定记忆分类、纯中文健康词表与唯一 health 同意项、封闭 5 类卡片元素被硬编码进内核 proto 与状态机 Apply；同时循环与上下文组装仍锁死在内核 runtime 中未插件化。

代码实证：event.proto · internal/capture · internal/memory · internal/card · worker.go

越界方向二：物理拓扑上浮与租户原语缺位 抽象泄漏·缺位

Outbox 直接向业务线暴露内核 PG 物理分片号 shard=N 与本地事务号 xid8，反向锁死内核在线重分片；AgentDef / Release / Oneshot 无业务线命名空间（可跨业务线越权创建与委托），MCP 同名全局冲突；缺建会话幂等键、缺持久输入去重、缺跨业务线公平调度。

代码实证：httpapi/outbox.go · agentdef · oneshot · mcpcap · pgqueue · model/guard.go
§2

内核 vs 业务线职责边界清晰度诊断

健康的平台架构应当满足“策略与领域语义向上归业务线，租户隔离、幂等原语与物理拓扑封装向下归内核”。下图与对照表展示了当前代码在八个关键切面上的实际边界偏离：

边界切面 理想架构边界（内核 vs 业务线） 当前内核实现偏离（代码现状） 引发的系统扩展性风险
1. 租户命名空间 内核按 BusinessLine 隔离一切定义与发布；业务线在自有命名空间内独立命名、灰度、撤回。 AgentDef、releases.yaml、Oneshot 全局无 BusinessLine 字段与访问校验；mcpcap 强制全局唯一名称。 高危 业务线 A 可直接调用业务线 B 的 Agent/Oneshot；同名 MCP 迫使拆单元从而阻断跨线 Memory 共享。
2. 循环与上下文 内核守住权限、审核、日志确定性与缓存度量；业务线按场景插拔循环控制与上下文裁剪策略。 ADR-0041 与 ADR-0056 均未实现；步进循环、上下文拼接与工具列表全量暴露写死在 runtime/worker.go。 严重 SOP 流程型或重度工具调用型业务无法定制上下文，要么 Token 暴涨，要么绕开内核另建运行时。
3. 可信内容与来源 内核定义通用信任等级（本人 / 外部个体 / 外部系统 / 平台）与验签机制；业务线提供结构化数据并映射标准角色。 event.proto 写死可穿戴录音 CaptureSegment（WEARER/OTHER、speaker_ref），internal/capture 硬写中文七天头与 5 分钟间隔。 中度 会议系统（多发言人）、企业 IM、医患问诊、邮件工单等第二类可信内容接入时必须改动内核 proto 与投影。
4. 记忆与合规闸门 内核提供可声明类别的存储、跨线 Grant 引擎与通用“外部污染写审批”算子；业务线声明敏感类别与需保护工具。 硬编码 6 个记忆类别、纯中文健康词表、中国身份证正则、单一 health Consent；memgate 仅保护内置 memory_save。 中度 金融/儿童/企业机密类业务无法扩展 Consent 与 Memory 类别；业务自有 MCP 写工具无法复用内核防注入写闸门。
5. 结构化交互卡片 内核负责卡片生命周期、版本替换与动作按钮去重；业务线可扩展自定义卡片类型与校验 Schema。 internal/card 硬编码 5 种元素、6 种表单控件与 23 个图标，无任何扩展载荷字段，且仅允许内置 show_card 产出。 中度 电商商品卡、航班选座卡、图表交互卡等富 UI 需求超过两次即触发 ADR-0032 重审并被迫频繁改内核契约。
6. 服务端事件消费 内核提供基于逻辑分区（如虚拟桶）的稳定流游标，隐藏底层数据库拓扑；业务线无感按游标拉取或收 Webhook。 GET /v1/outbox?shard=N 直接暴露物理 PG 分片号与 0..1023 槽位表，游标硬绑单台 PG 本地 xid8 与行号；全业务线共用 xmin 水位。 高危 内核未来扩分片或拆热点槽将致全体业务线游标作废停写；任一租户慢事务会卡死同分片所有业务线出站流。
7. 会话与输入幂等 内核提供会话外部幂等键（external_key）、轻量业务标签过滤与持久输入幂等保证；业务线直接声明式调用。 创建 Session 无幂等键、无 labels；input_id 仅保留最近 64 条（仅给内部委托留了永久幂等例外）。 中度 每条需要异步编排的业务线都被迫自建映射表、孤儿回收器，并在超时后全量拉取内核 Event 日志重扫对账。
8. 多租户资源调度 内核在工作队列、模型并发/RPS 与数据库池上按业务线做公平隔离与配额预留；业务线互不干扰。 pgqueue.Claim 同优先级按全局 FIFO 认领；model.Guard 单进程限流且完全不感知 BusinessLine，RPS 先于优先级抢令牌。 高危 典型“吵闹邻居”隐患：单一业务线批量任务或流量洪峰会直接饿死同集群其他业务线的实时交互问答。

§4

当前内核的六大核心优势（演进中必须守住的基石）

在指出边界问题之前必须明确：yanshi 内核在分布式执行语义、安全防线与可验证性上的工程质量远超常规 Agent 框架，以下六项核心设计无需推翻：

S1 · 事件溯源 + Fencing + 单事务原子唤醒

  • 正确性与活性解耦：WorkQueue 租约过期即可接管，新 Worker 递增 Attempt 号并经 (session_id, seq) 唯一索引乐观并发写日志，从根源杜绝分布式脑裂乱写。
  • 恒定投影开销：每 200 事件写带 ProjectionVersion=27 的快照，内存仅保留最近 4 个完整 Run，无论会话持续多久，每次状态校验开销恒定。
  • 零窗口原子提交：CommitAndWake 在单条 SQL 事务内完成写 Event、队列唤醒与写 Outbox 信封，每 Run SQL 从 83 条降至 34.1 条。

S2 · 统一 Capability 执行网络与幂等账本

  • 跨端云一致抽象：手机/电脑本地工具、K8s gVisor 沙箱、远程/本地桥接 MCP、向用户提问 ask_user 与子 Agent 委托共享同一套派发、挂起与超时转后台语义。
  • 先落盘后执行：内核侧先写 ToolCallStarted、端与沙箱侧经 nodesdk.Executor 按 call_id 落盘账本去重，崩溃后非幂等调用明确报 outcome unknown 绝不重放副作用。
  • 权限严格收敛：子 Agent 委托白名单自动取祖先交集，工件经显式复制交接（ADR-0055），绝不因多级编排放大权限。

S3 · 确定性单步 Worker 与三方差分模拟体系

  • 同步单步可注入：Worker.Step 无内部隐式并发，时间与 ID 全经接口注入，可在任意两步间精确注入崩溃、断网、限流与乱序。
  • 单一对象图装配：app.NewCore 统一支撑生产 serve、模拟 sim、评测 eval，2200+ 种子在单库内存、双库内存与双库真实 PG 间做状态指纹差分验证，极度适合 AI Agent 持续安全迭代。

S4 · 模块化单体多角色裁剪与低成本预分片

  • 不按领域拆微服务：单二进制按扩缩维度与权限拆为 gateway / worker / worker-bg / sandbox / janitor 五角色，既保留本地一条命令零依赖启动，又避免跨服务分布式事务损耗。
  • ID 内嵌槽位：持久 ID 编码 0..1023 槽位，在线请求一次定位唯一分片，预分 8 片配合流复制整片搬迁（10GB 停写仅 573ms），单分片故障不影响健康分片继续服务。

S5 · 纯函数来源推导与物理删除闭环

  • 不可伪造的 Provenance：不信写入方自报标签，由事件类型与结构纯函数推导来源，驱动高危审批与防记忆投毒闸门。
  • 可证明的遗忘权：所有含 Session 数据的存储强制在 app.SessionData 登记，写入入口执行“先写后查删除屏障”（lifecycle.Recheck），日志与指标只记 ID 不落个人内容（ADR-0015）。

S6 · 前缀缓存一等公民与快慢分离调度

  • 成本杠杆内建：静态系统指令、动态上下文置入 Run 位置、工具字典序固定、压缩摘要复用主请求前缀，实测长 Run 缓存命中率从 40% 提升至 70%。
  • 交互体验受保护：通话走低延迟流、重活交后台 run_task；长任务达阈值自动 Handoff 至后台池，配合 Oneshot 子限额守住即时问答低延迟。
§5

导致后续扩展性不足的六大内核问题（代码级剖析）

聚焦 internal/ 与 proto/ 源码，我们将阻碍多业务线灵活接入与大规模水平扩展的根因归纳为六大结构性问题：

B1多租户命名空间与访问控制缺位，且缺乏跨业务线公平调度
P0 安全与多租户阻断 租户隔离 吵闹邻居
内核代码实证 • AgentDef / Release 无租户归属：internal/agentdef/agentdef.go:22-44 中 Def 无 BusinessLine 字段；service.Create（service.go:114-128）不校验业务线权限，业务线 A 的令牌可直接创建并运行业务线 B 的 AgentDef；若开启 agent:* 通配委托，delegation/delegator.go:464-481 会把全内核所有业务线的 Agent 暴露给模型！releases.yaml 的灰度哈希与撤回同样全局耦合（release.go:69-81）。
• Oneshot 与 MCP 全局冲突：oneshot.Registry 无业务线隔离，且并发槽锁 "name:"+d.Name 跨业务线争抢（oneshot/service.go:119-123）；mcpcap.LoadDir（mcpcap.go:67-81）强制 Server.Name 全局唯一，两条业务线注册同名 MCP 即报错，拆单元又会丧失跨业务线 Memory 共享。
• 队列与模型准入无业务线公平性：pgqueue.go:126 同优先级按全局 ord 纯 FIFO 认领；model/guard.go:106-132 的并发池与 RPS 桶完全不区分 BusinessLine，且 rate.wait 在优先级排队前抢令牌。
对系统扩展性的制约 1) 多业务线无法安全共池：在补齐租户作用域前，同一单元内业务线之间存在定义泄漏、误撤回、命名冲突与越权调用风险。
2) 跨业务线雪崩传染（Noisy Neighbor）：业务线 A 突发大促流量或批量定时任务，会瞬间排满全局 FIFO 队列并耗尽共享模型并发额度，导致同单元业务线 B、C 的实时对话全面卡死。

§7

防止边界再次侵蚀的六条内核准入标尺

为避免后续接入第二、第三条业务线时再次发生“把业务特例写进内核”或“把内核拓扑漏给业务”，建议将以下六条判据固化为内核 PR 与新 ADR 评审的硬性门禁：

1. 领域名词零准入测试（Noun Test） 凡是出现在 proto/ 与 internal/ 中的类型、枚举、提示词与配置字段，若含特定硬件形态（如“佩戴者”）、特定行业分类、特定自然语言词表或日历口语规则，一律判定为业务语义越界，必须抽象为声明式配置或退回业务线 MCP。
2. 租户复合键强制测试（Tenant Key Test） 内核中任何新增的注册表、发布灰度、限流桶、调度池或缓存键，只要不是显式声明的全局系统原语，第一维作用域必须是 BusinessLine，严禁再引入跨业务线共享裸名。
3. 物理拓扑零暴露测试（Topology Opacity Test） 公开 HTTP/WS API、SDK 与游标载荷绝不允许暴露底层数据库实例编号、PG xid、表名或物理节点地址；外部契约只能绑定稳定的逻辑 ID 或逻辑虚拟桶，确保内核可随时独立重分片。
4. 治理不可绕过、策略可替换（Mechanism vs Policy） 凡涉及“能不能做、谁说的、审没审、删没删”（白名单交集、Provenance 纯函数推导、写前审核、SessionData 删除）必须留在内核强执行；凡涉及“给模型看哪几段、分几步想、展示什么行业卡片”必须通过受控契约开放给业务线插拔。
5. 外部动作完备幂等测试（Client Idempotency Test） 内核暴露给业务线或客户端的每一个会产生状态变更的写操作（建会话、发输入、点卡片、创定时），都必须在内核侧提供覆盖重试生命周期的确定性幂等保证，绝不迫使调用方拉取全量事件日志自建对账。
6. 单进程可跑与差分模拟不退化（Sim & Single-Binary Test） 任何多租户隔离、逻辑流路由或全局配额协调改造，必须同时提供零外部依赖的单进程实现，并通过 14 套存储一致性套件、`make sim` 双库差分测试与 `make eval` 前缀缓存命中核验。
