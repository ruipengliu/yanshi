# 10 开放问题与演进

> 本章回答：哪些地方还没做、做了一半、或有争议；上线前必须完成什么；下一阶段按什么顺序推进；评审者应当重点审视哪里。

本章是本套文档中唯一不以"已实现"为主的一章。凡是前面章节标 🟡 或 ⚪ 的，都在这里汇总。

## 10.1 现状的边界

### 规模

延展性评审（2026-10-11）的结论：**架构可以延展到亿级月活，扩展接缝基本都在，正确性不依赖单点；但按现状直接承载不行。** 两道硬天花板：

| 天花板 | 为什么 | 对策与状态 |
|---|---|---|
| 单个 PostgreSQL 主库 | 写入上限通常 1–3 万事务/秒；亿级月活峰值约 4.5 万条 Event/秒 | 分片键已是契约（§7.3）；分片层未做 |
| 每个进程 LISTEN 全部通知频道 | 每条 Event 要投递给全部监听进程；100 个网关即 450 万条通知/秒 | 频道已按分片命名；**Session 按通知分片归属到少数网关**未做，需要客户端按 Session 路由到归属进程，与部署形态一起做 |

容量测算（1 亿月活：2 千万日活、每人每天 3 个 Run、峰值 4 倍）：约 3 千 Run/秒、45k Event/秒、100 万并发长连接、约 100 个网关进程。现状上限在数百万日活量级。

### 功能缺口

| 领域 | 缺口 | 影响 |
|---|---|---|
| 推送 | 提醒与设备离线唤醒都是日志桩 | 用户没在看时收不到提醒；离线设备不会被唤醒执行调用（上线后由厂商通道补上） |
| 沙箱 | 只有 Docker 实现；生产 Provider 待选型（§4.6） | 不能上生产 |
| 内容安全 | 提供商为关键词模拟；暂存策略未定 | 不能上生产 |
| Call | Go 与移动端 SDK 没有通话接口；语音审批；Opus 与弱网；跨连接续接；视频 | 只有网页能通话 |
| 委托 | 扇出实际至多 1；父子不共享工件；注册中心与 A2A 未做 | 并行委托与跨业务线协作不可用 |
| 判断 | 注入检测只在影子模式；小模型路径未接真实端点；工具折叠、Call 快速判断、交付前一致性未做 | 判断层目前只有规则层产生实际效果 |
| 移动端 | Android aar 未构建、未在真机验证 | iOS 已实测 |
| 部署 | Kustomize 清单未在集群上验证；PostgreSQL 高可用未演练；容量矩阵未测 | 生产形态未闭环 |
| 治理 | Submit 准入默认关闭（阈值待线上指标）；模型准入单进程 | 洪峰下交互延迟无保护 |

## 10.2 上线前必须完成

对真实 EndUser 开放之前逐项完成，完成时注明日期与依据：

- [ ] **内容安全接入真实提供商**：实现文本、图片、音频的检查，按提供商错误语义区分"违规"与"不可用"；确认流式草稿是否满足监管要求，必要时实现流式检查；评估外部来源（MCP、网页）的调用结果是否单独检查；配置故障域独立的备用提供商；决定全部不可用时是否允许暂存输出。上线配置中模拟提供商的指标必须为 0。
- [ ] **价格表填入合同价**：当前为占位值。
- [ ] **生产沙箱**：选定云厂商服务或自托管隔离方案后实现 Provider；若选云厂商，决定是否修订私有化约束。
- [ ] **业务线配置**：密钥、保留策略、配额按约定填写。
- [ ] **健康信息的单独同意**：开启健康类 Memory 的业务线须能出示同意记录。
- [ ] **Call 的语音输出审核**：与合规确认"助手整句生成时检查、违规时中止剩余播放、之前部分依赖厂商严格审核"可接受；不可接受时改为按句缓冲、检查后再下发。
- [ ] **实时语音模型的价格与用量**：按合同价填写；评估每个会话首轮约 5K token 内置输入对短通话成本的影响。
- [ ] **评测基线**：上线所用的 AgentDef 版本与模型通过评测，基线随代码提交。
- [x] **委托的阻断项**（2026-10-11 完成）：委托输入绕过 Memory 写入闸门、子 Session 可被复活。
- [ ] **生产部署形态**：PostgreSQL 主 + 同步备、故障切换不丢 Event 且 seq 不倒退、旧主隔离；SQL 经事务池、LISTEN 与迁移锁直连；就绪探针；迁移以独立任务运行；排空超时小于编排系统的终止宽限期；沙箱控制器独立节点池与 gVisor；模型并发与速率按账号上限除以进程数；通知分片数一致；生产不带 `-faults` 与 `-insecure-remote`；部署清单含网络策略（出网只允许模型、内容安全、推送三类）；配置分发与按 Run 的链路追踪；容量矩阵与准入阈值在目标环境实测后填入。

建议确认：推送接入真实通道；Android 绑定实测；SDK 分发（npm、xcframework、aar 的仓库与版本约定）；监控告警覆盖（内容安全错误、用量记录错误、发布配置重载错误、Run 失败率按版本、模型重试、准入等待、握手拒绝）。

## 10.3 下一阶段清单

延展性评审与两位评审者（Claude 与 Codex）三轮讨论后形成的清单，按"先正确性、再空闲负载、再准入、最后分片"排序；每项的验收以 `make check`、`make sim` 全绿为底线。

| # | 项 | 状态 | 验收标准 |
|---|---|---|---|
| 1 | 原子唤醒与错误分类 | ✅ 完成 | 所有提交窗口崩溃后 Run 无须新输入即可恢复；临时的目录或存储故障不使 Run 终态 |
| 2 | 有界投影 | ✅ 完成 | 历史扩大十倍时活跃推进成本不线性增长；全量重放与快照 + 尾部等价 |
| 3 | 通知与共享 feed | 🟡 部分 | 取消逐等待者轮询 ✅、共享 feed ✅；**Session 归属到少数网关、小事件内联 NOTIFY** ⚪——验收：每个通知分片的监听进程数不随进程总数增长 |
| 4 | 容量基线 | ⚪ | 在目标环境压测长 Session、空闲连接、在场、Janitor 积压、Call、NOTIFY 负载内联；产出每分片的 QPS、WAL、连接、通知队列与带宽预算；据此定准入阈值 |
| 5 | 准入与调度 | ✅ 基本完成 | 模型排队总时限与 `Retry-After` ✅；长任务按服务量、恢复名额 ✅；Submit 准入 ✅（默认关闭，阈值待定） |
| 6 | 内容安全容灾 | 🟡 | 故障切换 ✅；暂存与重试检查须先与合规确认 |
| 7 | PostgreSQL 高可用演练 | ⚪ | 故障切换不丢已确认 Event、seq 不倒退；连接与 LISTEN 在约定 RTO 内恢复 |
| 8 | 分片验证 | 🟡 | 队列契约改为分片内有序 ✅；分片层、2 → 4 分片迁移期间旧路由、旧租约、并发删除无反例 ⚪ |

### 代码结构

评审结论：**不需要大改**。包边界清楚、接口放在消费方、12 套一致性套件、Step 模型都是对的。值得做的三处：

| 项 | 状态 | 说明 |
|---|---|---|
| 装配集中化 | ✅ | 存储与核心对象图都由唯一入口构造（§7.1） |
| Session 数据登记制 | ✅ | 登记列表、统一的写后复查、删除不变量对列表自动检查（§6.7） |
| Worker 的模型回合改成固定顺序的阶段 | ⚪ | 当前一次模型调用串着配额、目录、压缩、审核、计量、增量、提醒七种横切逻辑（§3.7）；等下一个横切需求到来时做；验收：新增一种横切策略不改 Worker 本体，模拟日志逐字节不变 |

明确**不要做**的：拆微服务、引入依赖注入框架、把 Step 改成异步流水线——它们会破坏"单进程可运行"与"确定性模拟"两条原则，收益为零。

### 架构评审待办（2026-10）

两轮架构评审已合并的项：装配入口、决策-提交循环统一、内容安全请求的构造集中。待做的项（均为整理，不改变语义）：Call 与调用的命名区分进一步收紧（给 session 中表示调用的类型加上种类字段）；serve 中的策略装配移入装配选项；增量的形状统一；模型引用类型化；模型错误分类器；模型调用的信封结构；投影的 reducer 拆分；提交入口的命名统一；委托规则的集中。

## 10.4 待决架构问题

| 问题 | 现状 | 需要什么才能定 |
|---|---|---|
| 沙箱隔离方案 | 自托管（gVisor / Firecracker / Kata）还是云厂商沙箱服务；与私有化约束的关系 | 目标部署环境与合规要求 |
| 私有化下的模型接入 | 火山私有化方案与开源模型自托管推理服务的统一网关抽象 | 第一个私有化客户的环境 |
| 判断层的小模型 | 自托管小开源模型读 logits 做校准分类；中文注入样本几乎为零 | 影子模式一到两周的数据；自建中文留出集 |
| 通知分片的归属路由 | Session 固定到少数网关、客户端按 Session 路由 | 与部署形态一起设计 |
| 子 Session 的 Memory 写入归属 | 已决定子 Session 一律视为受外部内容影响；归属按 EndUser 不变 | 是否需要更细的策略待评测 |
| 注册中心的形态 | 本地目录还是服务；`description` 字段怎样评测 | 多业务线接入后的实际需求 |
| Call 的弱网 | PCM 经 WebSocket 约 640 kbps 双向；Opus / RTC 待评估 | 真机弱网实测 |
| 全局模型准入 | 单进程准入；弹性扩容时需共享令牌服务 | 部署形态与提供商账号结构 |

## 10.5 评审者应当重点审视的地方

基于以上，建议评审聚焦：

1. **三个根决策是否成立**（§9.2）：私有化、日志是事实源、设备即节点。它们推出了其余全部；若有疑义，优先在这里。
2. **安全默认是否有漏洞**：§6.6 的"权限只能收缩"表是否完备；委托、Call 转述、界面上下文三处外部内容的处理是否一致。
3. **删除是否真的删干净**：§6.7 的登记制与"先写后查"是否覆盖了所有存放 Session 数据的地方；设备端账本的清除是否可接受。
4. **两道天花板的拆除路径**是否清晰（§10.1）：分片键契约与通知分片归属是否足以让后续工作不推翻设计。
5. **内容安全的两处"先展示后检查"**（§6.2）是否能过合规。
6. **评测的代表性**：47 个用例对当前模型偏容易，首要作用是发现退化；是否需要更难的用例、更多中文注入样本。
7. **代价是否被低估**：每个设备调用一次挂起与恢复（§2.11）、压缩对缓存命中的损失（§3.4）、内容安全加在每次模型调用上的延迟（§6.2）。

## 10.6 演进路线

```mermaid
flowchart LR
    NOW["现在<br/>单元内多进程 · 单库<br/>数百万日活量级"] --> P1["阶段 1：上线闭环<br/>真实内容安全 · 推送 · 生产沙箱<br/>PG 高可用演练 · 清单上集群"]

    P2 --> P3["阶段 3：分片<br/>分片层 · 槽位迁移<br/>每分片独立 LISTEN"]
    P3 --> P4["阶段 4：生态<br/>注册中心 · A2A<br/>判断层驱动审批 · 工具折叠"]
```

每个阶段都不推翻前面的设计：接口不变，实现在接口后面换；一致性套件与差分模拟是每次换实现的安全网；评测是每次改效果的裁判。
