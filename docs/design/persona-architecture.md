# xinli 与 persona agent 的整体架构

心力球是以录音为入口的个人助手：记录、回忆、跟进事务、反思成长。本文回答三个问题：现在的 yanshi 能不能承载它；不能承载的部分补在哪一层；以后它演进成更完整的 persona agent、接入三方 Agent 时，扩展的范式是什么。

## 0. 结论

- **yanshi 的执行内核能承载 xinli，不需要推倒。** Session、Run、Event、可信结构化片段、来源推导、写入闸门、Retention、委托、评测与模拟测试，正是一个长期运行的个人 Agent 需要的底座。
- **缺的是两块。** 一是内核的几处原语（§2.3），都是"第二条业务线也会需要、且业务侧做不到或做了不安全"的；二是更大的一块：生产的业务后端完全没有，目前只有 `persona/` 的内存实现与 `apps/xinli` 的开发进程。
- **分三层**（ADR-0043）：yanshi 内核只管 Agent 怎样可靠、安全地运行；Persona 层管关于一个人的结构化知识；xinli 应用层管产品（账号、设备、识别、渠道、推送、编排）。Persona 与应用层只经公开契约使用内核，内核不认识它们。
- **扩展范式**：新功能默认只改 Persona 与应用层（§9）；内核只在满足判据时改，并写 ADR。

## 1. 适配性评估

下表保留最初评估的功能落位；P0–P3 的实现状态及 P4 范围以 §11、§13 为准。

| 功能 | 现在的 yanshi | 落在哪里 |
|---|---|---|
| 全时记 | Persona 保存原文、分页与处理进度，`xinli-day` 整理；内核渲染与审核可信页 | 持久存储在 P4a；识别在应用层（§4.1），交谈与重点在 Persona |
| 实况预览 | 只能开 Run，每次刷新都写日志 | 内核新增**单次调用**（Oneshot，ADR-0047） |
| 随口记 | 输入、`/transcriptions` | 内核已有；笔记在 Persona |
| 内容纠错与词库 | Event 只追加，原文不能改 | 原文存放在业务线，原文的纠错是业务库中的修订（ADR-0050）；摘要与知识的纠错是 Persona 中用户的变更集；词库在 Persona，识别热词在应用层 |
| 个人记忆（人、组织、概念、事件） | Memory 是扁平陈述，每人每业务线至多 500 条，不建模"人"（ADR-0042） | Persona 的实体与时间线（§3） |
| 智能问答（引用、历史、重生成、收藏） | 助手 Session、Memory 召回、卡片 | 内核新增**重答**（Redo）；线程即 Session，收藏在应用层，引用来自 Persona 的依据（§3.4） |
| 项目跟踪、待办 | `xinli-project`、承诺账本（mock） | Persona |
| 定时提醒与执行 | 按钟点的定时由业务线以服务令牌提交，内容在投影里算"用户原话" | 内核新增**定时**（Schedule，ADR-0045） |
| 未来录音关注、心力优先、周期洞察 | 无 | Persona 的关注项与目标；由定时开启的 Run（§5） |
| 个性化理解 | Memory（本人） | 内核 Memory 只存本人；画像在 Persona（§3.3） |
| 账号、设备、权益、声纹 | 无 | 应用层；会员分档的配额由内核执行（**档位** Tier） |
| 多渠道 | 只有按 Session 的 SSE | 内核新增**出站流**（Outbox，ADR-0046）；渠道适配在应用层 |
| 外部 AI 授权 | 无 | Persona 对外的 MCP（[M7 Agent 生态](./m7-agent-ecosystem.md) §3） |
| 数据控制（部分记录删除） | 只能按整个 Session 删除，`captures` 的工具结果里还有原文副本 | 原文存放在业务线：业务库删除原文、按依据级联删除派生数据，再删除当天的工作 Session（删除原因 Erasure，ADR-0050） |
| 运营与版本分发 | 用量、指标（只含 ID） | 应用层 |

## 2. 三层

### 2.1 拓扑

```
 HostApp（手机）── 领夹 ─ 蓝牙（真实硬件在外部接入阶段）
   │ 采集上传                 │ 输入、审批、回答、事件流（经 BFF，应用登录态）
   ▼                          ▼
┌──────────────── xinli 应用层（apps/xinli）────────────────────────────┐
│ 采集识别  账号·设备·声纹·权益  渠道适配(微信/飞书/TeamTalk)  推送  编排器  BFF  运营 │
└──┬─────────────┬──────────────────────┬───────────────┬──────────────┘
   │ 服务令牌：     │ 出站流（拉取）          │ 查询与用户改动   │ 单次调用
   │ 输入、        │                        ▼               │
   │ 定时、Session  │        ┌──── Persona 层（persona/）────┐ │
   │               │        │ 实体·时间线·交谈·承诺·项目·笔记 │ │
   │               │        │ 有效变更集 + 直接事实 + 原文 + 检索 │ │
   │               │        │ MCP 工具（内核调用）· 查询 API   │ │
   │               │        │ 对外 MCP（OAuth，三方只读）     │ │
   │               │        └──────────▲────────────────────┘ │
   ▼               ▼                   │ MCP（可信登记；身份 _meta、attests_speakers）
┌──────────────────────── yanshi 内核 ─────────────────────────────────┐
│ Session·Run·Event  触发·定时  来源·写入闸门·内容安全  Memory·Grant      │
│ 能力路由(设备/沙箱/MCP/A2A/委托)  可信片段·删除期限      出站流  单次调用  配额·档位 │
└──────────────────────────────────────────────────────────────────────┘
```

### 2.2 职责与边界

| 层 | 管什么 | 不管什么 | 数据 |
|---|---|---|---|
| yanshi 内核 | Agent 怎样运行：执行语义、来源与信任、内容安全、配额、删除、能力路由、评测 | 任何业务实体（交谈、承诺、项目、人）；一天从哪里开始 | 事件日志（含已读可信页副本）、Memory、用量；按 Session 或 EndUser 分片 |
| Persona 层 | 关于一个人的结构化知识：实体、时间线、交谈、承诺、项目、笔记、关注项、目标、画像、词库；变更集的检查与回执 | 账号、设备、渠道、推送；Agent 的执行 | 独立的 PostgreSQL，按 (BusinessLine, EndUser) 分片；有效变更集与直接事实是它的事实源（§3.2） |
| xinli 应用层 | 产品：采集识别、账号设备声纹、权益、渠道、推送、跨 Session 编排、App 的 BFF、运营 | 知识的语义（交给 Persona）；Agent 的执行（交给内核） | 账号、设备、权益、渠道映射、收藏、编排任务与收件箱 |

依赖方向只有一个：应用层 → Persona → 内核的公开契约（`proto/`、`gen/`、`sdk/`、HTTP API、MCP）。`persona/` 与 `apps/xinli/` 是独立的 Go module，模块路径不以 `yanshi/` 开头（`persona`、`xinli`），Go 的 internal 规则才会拒绝它们 import `yanshi/internal/...`；`make check` 另做依赖检查；内核不 import 它们（ADR-0043）。

Persona 按业务线分租户，数据归业务线（ADR-0003 的延伸）：第二个 persona 类产品用同一套 Persona 服务，数据互不可见；跨业务线读取以后经 Grant 扩展（[M7 Agent 生态](./m7-agent-ecosystem.md) §4）。

### 2.3 内核补的原语

| 原语 | 为什么在内核（§9 的判据） | 设计 |
|---|---|---|
| 可信结构化片段（`attests_speakers`） | 原文存放在业务线（ADR-0050），说话人的来源推导只能由平台渲染与标记；业务线写的文字会被洗成可信内容 | ADR-0050 第 1 条 |
| 写日志前审核 attested 结果 | 审核是写日志前的平台检查，不能以业务线自报代替（ADR-0021） | ADR-0050 第 2 条 |
| 擦除即删除工作 Session、绝对删除期限 | 日志中的原文与派生副本只有删除 Session 才会消失；重建的 Session 不能延长原文副本的寿命 | ADR-0050 第 3、4 条 |
| EndUser 删除屏障 | 注销期间按 EndUser 的写入可能复活数据 | [M7](./m7-kernel-primitives.md) §12 |
| 定时（Schedule） | 业务侧提交的输入在投影中是"用户原话"，会把模型写的或外部来的文字洗成可信内容 | [M7](./m7-kernel-primitives.md) §5（不含 `window.stream`），ADR-0045 |
| 出站流（Outbox） | 无在线客户端时可靠发现回复、提问与审批，支持跨 Session 收件箱、渠道转发与停机后续消费；业务侧无法与内核日志原子提交 | [M7](./m7-kernel-primitives.md) §6，ADR-0046 |
| 单次调用（Oneshot） | 业务侧直连模型会绕过计量、配额、内容安全与换模型的评测（章程 G9） | [M7](./m7-kernel-primitives.md) §7，ADR-0047 |
| 档位（Tier） | 配额由内核执行，触发与定时开启的 Run 没有用户令牌，档位只能存在内核 | [M7](./m7-kernel-primitives.md) §8 |
| 重答（Redo） | 只有平台能让 Transcript 略去被重做的 Run | [M7](./m7-kernel-primitives.md) §9 |
| 说话人引用（`speaker_ref`） | 契约字段，只能在 `proto/` 中加 | [M7](./m7-kernel-primitives.md) §10 |

加上三方 Agent 的 A2A 出站和入站（ADR-0048）。原先列出的 Capture 正文存储、擦除、原文修订（ADR-0044）、交付确认（ADR-0049）与流上的触发（ADR-0040 第 2 步）由 ADR-0050 取代：原文存放在业务线，分页、处理进度与纠错由 Persona 负责；交付确认与内核 Capture 提交、读取路径已在 P1 删除。

## 3. Persona 层

### 3.1 术语

Persona 层术语见 [persona/CONTEXT.md](../../persona/CONTEXT.md)，内核的 `CONTEXT.md` 只保留内核术语。Exchange、Changeset、Revision、Commitment、Project、Awareness 沿用原有定义，已迁入 Persona 术语表；以下新增术语也在其中定义。Span 是平台的分页单位，留在内核。

- **Entity（实体）**：Persona 中有稳定 ID 的一个人、组织、概念或事件，带别名。承诺的对方、交谈的参与者、项目的相关方都引用实体。
- **Note（笔记）**：EndUser 经随口记口述的内容，是本人的话，整理后保存。
- **Watch（关注项）**：EndUser 事先指定的、之后的旁听中要特别留意的内容（"下周和供应商开会时留意交期"）。整理时随候选一起召回，命中后在交谈中标出。
- **Goal（目标）**：EndUser 明确说过的重要目标，心力优先据此对照近期投入。
- **Lexicon（词库）**：EndUser 的专有词汇（人名、项目名、术语），供识别热词与整理使用。
- **Lineage（依据）**：派生对象所依据的引用（`#seq.index`、交谈 ID、笔记 ID）。

### 3.2 数据模型与存储

- **事实模型**（Q92）：有效变更集按稳定顺序叠加得到交谈、承诺等当前状态；同一来源重交整体取代，保留原叠加位置，不能按新变更集 ID 排到末尾。项目、日总览、周回顾等保存直接事实，不是全面不可变事件溯源。用户改动仍记为带作者与依据的变更集，`rev` 做乐观并发。事实、物化、依据索引与处理进度同事务提交。
- **存储**（Q93、Q112）：独立的 PostgreSQL（与内核不共用库，故障域分开），自有迁移、角色与连接配置；按 (BusinessLine, EndUser) 即 owner 分片，一个事务只涉及一个键。原文按 owner、业务日、批次独立存储并按批惰性读取；其余账本（变更集、交谈、承诺、项目、日总览、周回顾、墓碑、删除待办、处理进度）每类一表，键列加 JSONB，每事务整体装载非原文账本。领域规则继续共用一份。
- **原文事务接缝**（Q112）：提供引用查找、相邻片段、范围迭代、时段尾检查、追加与擦除；整日检查可流式遍历。Update 锁住同一 owner，账本与原文一次提交；View 中两者来自同一快照。原文读取沿用当前事务连接，读取器不逃逸事务寿命，读错误上抛、不解释成引用不存在；克隆与 JSON 快照剥离原文载荷。事务内不调用内核、模型或外部服务。
- **检索**（Q94）：P4 在已装载账本上运行共享字符二元组算法，保持现有召回语义；不做 PG 倒排索引、中文分词或 pgvector。中文全文、向量检索及嵌入经单次调用的接入后置，以成本与效果实测决定。
- **依据**：每个派生对象记录 Lineage，并维护反向索引（引用 → 对象）。两处用它：问答的来源引用直接给出依据；擦除的级联删除。
- **旁听原文与处理进度**（ADR-0050，§13 Q37–Q39）：原文按 (BusinessLine, EndUser, 业务日) 保存，引用为 `<批次>.<段号>`、永不复用；`captures` 工具返回结构化的页，由内核渲染、审核。处理进度在接受范围变更集的同一事务中推进，只越过被完整覆盖的时段，取代内核的交付回执。可信页读取仍在 Update 中登记已读位置，不能改成纯 View。
- **擦除**（ADR-0050，§13 Q46–Q49、Q52）：一个事务中删除原文、去掉依据与擦除范围相交的变更集并重新叠加、处理进度退回到最早受影响的时段之前、停用当天的工作 Session、记下删除待办；被擦除的编号不复用，引用它的承诺、修订与交谈端点一律拒收。删除待办由编排器幂等执行（§4.5）。
- **期限与原文版本**（Q95、Q96、Q98）：首次接收固定业务日时区，期限为次日当地 00:00 再加七个当地日历日，保存 UTC；补传、账号改时区、工作 Session 重建均不延长。首次上传已过期的历史日也拒收。到期立即拒绝原文访问、补传及旧工作 Session 的整理写入；后台清原文与读页状态，保留账本、历史绑定及不含正文的不可复用标记。自然到期与主动删一天分开，长期账本查询和用户修改仍允许。追加、擦除、自然到期改变 capture_revision，P4 不做原位修订。

### 3.3 与内核 Memory 的分工

| | 内核 Memory | Persona |
|---|---|---|
| 存什么 | 关于 EndUser **本人**的陈述：profile、preference、interest、plan、health | 关于 EndUser 的**世界**：他人、组织、事件、交谈、承诺、项目、笔记、画像 |
| 怎么进上下文 | 每个 Run 开始时自动召回（记为 Event） | Agent 按需调用工具拉取；结果是外部内容 |
| 跨业务线 | 经 Grant 按类别共享（ADR-0003） | 按业务线隔离；三方经 OAuth 范围授权 |
| 写入保护 | 写入闸门（ADR-0023）、健康许可（ADR-0022） | 变更集检查、用户优先、三方写入只进"待确认" |

xinli 的 AgentDef 不再把他人的信息写成 Memory 的 `relationship`：人在 Persona 中只记一处。这是接入 Persona 的业务线的约定，由 AgentDef 的指令与白名单落实；内核的 `relationship` 类别不变，没有 Persona 的业务线照常使用（北极星场景 A 用它识别"同事"）。Persona 的知识不自动注入，请求前缀保持稳定，信任边界也不变（工具结果按外部内容对待）。画像是推断，与觉察一样不写入 Memory。

### 3.4 接口

| 接口 | 谁调用 | 说明 |
|---|---|---|
| MCP 工具 | 内核（Agent 的调用） | 现有的 `find_related`、`file_changes`、`day_ledger`、`file_day`、`day_summary`、`set_status`、`update_commitments`、`list_commitments`、`commitment_history` 等，加上 `save_note`、`entity`、`search`、`watch`、`goals`；只读的在登记中声明只读，交出结果的以 `no_approval` 放宽（ADR-0017），登记开启 `cite_captures` |
| 查询与改动 API | 应用层的 BFF | App 的项目、待办、笔记、实体页面；用户的改动记为作者为用户的变更集 |
| 对外 MCP（OAuth） | 三方 AI | 只读加提议写入，不含旁听原文（[M7 Agent 生态](./m7-agent-ecosystem.md) §3） |
| 评测夹具契约 | `internal/eval` | HTTP 上的 Seed、State 与用户、业务线的操作（确认归属、改承诺、绑定 Session 等）；评测通过独立进程接入，同一套用例可指向内存实现或生产实现。评分逻辑留在 `internal/eval`，夹具不提供 Check：被测方不做自己的裁判 |

领域核心（变更集检查、期限换算、核对、回执文字）只有一份，生产与评测共用，只是存储不同。回执是给模型看的文本，属于被测行为（[架构评审](../review/2026-10-26-xinli-architecture.md) §3.1）。

## 4. xinli 应用层

### 4.1 采集与识别

- ADR-0050 后文字批次直接交给 Persona，内核没有 Capture 提交接口。P4 只实现认证后的有序文字采集、持久发送端与识别适配契约；识别只有确定性 fake，真实领夹、ASR 与声纹在外部接入阶段（Q108）。
- **一条有序采集会话**（Q97）：发送端持久保存序号、capture_id、业务日、时区、内容与确认状态，丢响应或重启复用原 ID，顺序补传。服务端暂存缺口，按序正式追加成功后才确认接受并返回引用，不重排已分配引用；多设备合流、任意迟到插入后置。
- **采集世代与删除**（Q114）：缺口正文放在 Persona 原文暂存区，与业务日、采集世代同 owner 事务管理。擦除或删一天推进世代、清除旧世代未提交正文并拒收旧请求；到期与注销清全部缓冲正文。客户端收到明确的重新同步状态，不得自动将旧请求换新世代重交；去重元数据不夹带正文。
- 识别片段可带 `speaker_ref`（Persona 实体 ID，[M7](./m7-kernel-primitives.md) §10）；来源只看佩戴者或他人，被认出的他人仍是他人。fake 覆盖延迟、失败与说话人错误，不证明真实识别准确率。
- **音频默认不保留**，真实接入后只在识别完成前缓存，故障时由 HostApp 缓冲；若以后保留，须另定与业务日一致的删除闭环。
- 真实转写链路（前端处理、语音检测、识别、说话人与佩戴者判定、后处理）的设计见 [xinli 的声音转写方案](./xinli-transcription.md)，评测方法与评分表见其配套文档。

### 4.2 账号、设备、声纹与权益

P4 使用测试身份提供方，但真实保存账号、时区、安装实例、设备绑定、偏好、权益及版本，并实现登录态、刷新与撤销（Q103、Q119）。产品数据只经 BFF，客户端不持有可绕行的内核用户或服务令牌；内核 API 与 Persona MCP 不直接向产品客户端开放。BFF 按用途拒绝用户向日、周、项目内部 Session 提交输入、创建定时等绕过编排的操作。

BFF 查询覆盖问答线程、项目、承诺与修订历史、日周总览、原文、任务与权益，逐次校验 owner、分页与删除状态。问答线程按话题创建；操作覆盖输入、中断、卡片动作、回答与审批、重答、定时、用户修改、擦除及注销进度。SSE 保留 seq 续传与登录态撤销；卡片透传 call_id，重答提交 input_id 与 expected_run_id，最终资格由内核判断；删除完成前只报告“删除中”。笔记领域、工具与页面留 P5（Q107）。

生产提供 serve、迁移与共享装配，Persona、BFF、编排角色可拆开，也可合在开发进程；生产不挂夹具与开发路由。MCP 服务凭据须匹配元数据中的业务线，内核客户端按业务线刷新令牌（TokenSource），不信任外部自报身份。

权益变化生成持久任务，以服务令牌同步内核 Tier；App 只能读有效档位，未知档位是配置错误（Q120）。注销先封禁应用入口，建立 Persona owner 屏障，再持久推进内核及逐库清理；保留必要的“注销中”恢复状态，全部完成才报告完成。补传、后台任务与旧 Tier 同步不得复活账号，重注册生成新 EndUser ID（Q104）。领夹不建模成内核 Device/Node；真实声纹注册与短信后置。
### 4.3 渠道

P4 先做中立渠道契约、账号映射、入站消息 ID 去重与确定性 fake；真实微信、飞书、TeamTalk 接入后置（Q108）。适配器是 `apps/` 下可复用的渠道模块：入站以服务令牌提交到 EndUser 的问答线程；出站消费出站流中的回复。渠道账号到 EndUser 的映射由 xinli 保存。卡片、提问降级为"文字 + 深链"；**审批一律回到 App 完成**，第三方渠道不能批准。

### 4.4 推送

- **业务事实提醒**（承诺到期、设备状态、权益）：应用读 Persona 或账号数据建立持久通知任务，不经模型。发送前复查承诺版本、状态与偏好；改期、完成或删除取消旧提醒（Q120）。
- **Agent 生成的内容**（回复、提问、审批、定时结果）：从内核出站流可靠发现，再按 ID 取当前可访问内容。接收记录与游标同事务保存，之后建任务；去重、重试与退避持久化，已删除或过时内容不发送。
- 内核 Notification 与应用推送必须明确唯一发送归属，同一审批或 Run 结束只由一条路径实际发送。B6 选择 xinli 应用独占实际发送，产品客户端只持 BFF 凭据、应用不登记内核推送设备；现有登记须先撤销，实施边界见 [M7 §6 的 B6 实现](./m7-kernel-primitives.md)。推送载荷只含种类、ID 与深链，正文按权限现取。P4 使用确定性 fake，APNs/FCM 后置（Q108）；不以 fake 验收真实送达。

### 4.5 编排器

Persona 的领域变化驱动业务后续；内核出站只承担运行事件（Q99）。Session 内通用触发与定时由内核执行，业务日与跨 Session 策略在应用层。

| 来源 | 编排器做什么 |
|---|---|
| Persona 接受 `file_day` 的领域变化 | 为涉及的项目创建或复用 `xinli-project` Session，提交“整理 <日期>” |
| Persona 接受 `file_week` 的领域变化 | 为本周有新交谈的项目提交“重写现状”；空结果也是接受，同命令重复交付不重复建任务，合法重交生成新事实版本（Q115） |
| Persona 的删除待办（Q49） | 中断并删除当天工作 Session，等清理完成后查候选 Memory；过去的日子在原期限内重建并整理（Q53） |
| 内核出站流 | 更新所跟踪 Run 的执行状态，把回复、提问、审批交给应用收件箱、渠道或推送 |

**领域变化与任务**：Persona 接受事实时，在同一 owner 事务持久记录稳定事实 ID 与版本，不保存 Agent 调用策略；应用持久接收后才确认。编排任务按（来源事实版本、操作、目标）去重，保存 owner、输入 ID、状态、租约代数、重试时间、次数与提交凭据（receipt）。短事务认领，事务外调用内核，再按租约代数和业务对象世代条件提交结果；失败持久退避，启动与周期扫描恢复。旧持有者不能覆盖新绑定（Q99–Q101）。

**提交与创建恢复**：后台 Session 单在途，提交前持久保存命令与 receipt；结果未知时，分页完整补读所需事件中的 `input_id`，确认前不推进、不盲重发，读失败不能当作未提交。内核最近 64 条去重不是永久幂等。创建先持久化意图，允许有界的空孤儿 Session，以 CAS 绑定并清理；绑定成功前不得提交内容（Q100、Q101）。

**命令资格与迟到隔离**：内部工作 Session 仅编排器写入，先登记命令类型，命令确认终态前不切换；生产日、周、项目写工具在事务内校验当前绑定。正常且写调用结果明确时可复用 Session；无法排除旧远端写入时，下一命令前退役旧 Session、创建并 CAS 换绑，保留历史绑定、继承原删除期限。取消 context 或租约过期不代表旧 MCP 写入已隔离（Q102、Q113）。

**自动调度**：应用按固定业务日时区、原文与处理进度安排白天静默整理、日终与每周回顾；日终沿用当地 18:00 后静默满 2 小时或次日 04:00–04:30 的规则，抖动由 owner/date 稳定派生或持久保存。进度未前进时退避；业务完成由进度与接受事实共同判定，不能用 Run 终态代替，故障不延长原文期限（Q116）。A10 的自动白天输入明确使用“整理今天”，静默 5 分钟；自动周回顾为周日 23:00–23:30，具体默认值、稳定抖动、5 次上限与评测开关见 [xinli-captures](./xinli-captures.md) §2 的 A10 自动调度默认值。周回顾后的项目重写是编排顺序：当前项目重写读取项目、交谈与承诺，不读取周回顾产出；仍须等 `file_week` 接受后安排（Q115）。

内核不新增跨 Session 写入（ADR-0037 不变）。出站恢复与应用账号枚举见 [M7](./m7-kernel-primitives.md) §6，Q105、Q106、Q117、Q118。

## 6. 关键流程

### 6.1 一天

1. 采集服务把当天的旁听提交给 Persona（按业务日保存，ADR-0050）。需要整理时，编排器为业务日创建或复用当天的 `xinli-day` Session（带当天的绝对删除期限）并绑定。
2. 说完一段话、静默满 5 分钟后，A10 自动入口提交"整理今天"，并完成日总览；原有手动/评测入口仍可提交"整理交谈"。Run 经 `mcp_xinli__captures` 读平台渲染、审核过的页，逐时段交出变更集，Persona 在同一事务中推进处理进度。
3. 傍晚之后业务线判断静默满 2 小时、或到 04:00–04:30 时，提交"整理今天"（固定指令，由业务线判断时机，ADR-0050；不用内核定时，Q55）：读完余下的时段、当天整理、`file_day`。
4. Persona 接受 `file_day` 时同事务记录领域变化，编排器据其事实版本归集到各项目；Run 完成只用于执行跟踪（Q99）。
5. 应用层关闭当天的 Session；到删除期限时内核删除工作 Session（日志中的原文副本），Persona 按固定的业务日 UTC 期限自然到期并清理原文（Q95、Q96）；交谈、承诺与 Memory 保留。

B7 的跨进程驱动位于 `internal/day`，运行入口为 `make day`、`make day-short` 与 `make day-ark`；三库、共用业务时钟、生产保护、逐阶段断言、前三类故障与 Mac mini 验收记录见 [单库完整一天验收](./day-acceptance.md)。完整场景默认不进入 `make check`，数据库切换演练留在 C6。

### 6.2 删除一段谈话

（ADR-0050；§13 Q46–Q53）

1. 用户在 App 中选中 10:15–10:40 删除，BFF 换算成当天的引用范围，调用 Persona 的擦除。
2. Persona 在一个事务中：删除这段原文；去掉依据与它相交的变更集（`source` 相交、`refs` 落在其中、以及依赖被去掉的交谈的合并与修订）并重新叠加交谈与承诺；处理进度退回到最早受影响的时段之前；删除当天总览；停用当天的工作 Session；记下删除待办。之后旧 Session 的调用、引用被擦除编号的提交都被拒收。以被去掉的交谈为依据的项目变更集一并去掉；周回顾、项目现状文字与内核项目 Session 日志中已读到的摘要不级联（与 ADR-0037 的"删一天"一致）。
3. 编排器执行删除待办：中断当天工作 Session 中进行中的 Run，以 `erasure` 删除它（保留 Memory）；等内核清理完成，用当天用过的全部工作 Session 查出它们写入的有效 Memory，存进待办，App 让用户决定是否删除。待办完成前 App 只显示"删除中"。
4. 之后的整理用到时才重建工作 Session，继承当天原来的删除期限；被擦除的若是过去的日子，编排器重建后提交一次"整理今天"，重新整理剩下的原话与当天总览。

### 6.3 定时执行

用户在问答中说"每周五下午五点给我一份本周项目周报"：Agent 调用 `schedule` 在本线程创建定时；每周五到期时，内核以平台来源开启 Run，输入是创建时写下的文字；Run 用 Persona 的查询工具生成周报；出站流交给推送服务。用户说"取消周报"时，Agent 列出并取消。

## 7. 容量与性能

以下保留早期量级估算（每人每天约 8 小时旁听、十几万字），不是已验证的用户规模承诺。P4 以固定负载实测与报告验收（Q111、Q123，取代 Q2 的 P4 验收口径）：

| 项 | 10 万 | 100 万 | 处理 |
|---|---|---|---|
| Capture 正文 | 约 50 GB/天，7 天约 350 GB | 约 500 GB/天，约 3.5 TB | 原文在业务库，由业务线按保留期删除；内核日志中只有读过的页的副本，随工作 Session 删除（ADR-0050 后果中的容量一条） |
| Persona 原文批次写入（峰值） | 全天平均约 550 批/秒，旁听集中在 8 小时，峰值约 1700 | 平均约 5500，峰值约 17000 | 按 (BusinessLine, EndUser) 分片；同 owner 事务保存批次、原文版本与进度元数据，不是内核 Event 写入；内核只存已读可信页副本 |
| 内容安全 | attested 结果每读一页一次（第一版不缓存），整页被拦下时逐段复核（ADR-0050） | 随读页与逐段复核次数增长 | 外部提供商的容量按峰值与复核放大采购 |
| 整理 Run | 每人每天几十次（应用调度）＋1 次当天整理 | 同比 | 后台工作类别；准入让交互优先；当天整理按各人作息分散 |
| 停放的定时 | 每人若干个长期定时 | 百万级 | 远期的到期放独立的到期表，认领只扫可认领项；P2 压测 |
| Persona 写入 | 每人每天约几十个变更集 | 同比 | 独立 PG，按 (BusinessLine, EndUser) 分片 |
| 实况预览 | P4 手动调用，自动刷新后置 | 同比 | 单次调用有并发子限额与提供商预算上限，后台保有最低份额 |
| 出站流 | 每个 Run 一两条 | 同比 | 按分片的游标，只含 ID |

内核日志仍保存可信页的原文副本，随工作 Session 删除；旧“工具结果只存引用”的方案已由 ADR-0050 取代。P4 固定一年账本与八天原文工作集，写明可复现的数据配方，记录追加、分页、重交、擦除、WAL、内核出站查询与双库分摊，以及 p50/p99、账本和原文装载量、SQL 数、峰值内存。不设性能硬阈值；语义正确与普通事务不全量装载原文的断言必须通过。全账本按需查询等进一步优化由成本报告决定（Q93、Q111、Q123）。
### Persona 大工作集成本（A14）

本节落实 Q93、Q111、Q123 与 Q124 的 A14 行，只覆盖 Persona 的单 owner、单库事务。内核出站与双库分摊留给相应后续步骤。本测试不设延迟、吞吐、WAL 或内存的性能硬阈值，也不据此承诺用户规模；领域正确性和普通事务惰性装载的断言必须通过。

**固定数据配方**（实现常量在 `persona/store/costtest/fixture_test.go`）：

| 项 | 数量与规则 |
|---|---|
| owner、种子、时钟 | 一个 `(a14, fixed-owner)`；局部 PRNG 种子 `140123`；固定 `2026-10-29 20:00:00 UTC` |
| 一年账本 | 365 个连续日历业务日（包含周末），2025-10-30 至 2026-10-29；每日 1 个总览、15 个交谈、5 个承诺；合计 365 / 5475 / 1825 |

`capture-workday` 的 morning、midday、evening 剧本合计约 465 段、9175 字（all 文件是同一合集），`xinli-captures` 描述约一分钟提交一批，现有剧本不足以直接推导连续满负荷。因此这里采用任务约定的 1200 × 3 × 40 固定满负荷配方，明显高于稀疏剧本，不把它称为实际用户采集量。全部生成经 `Store.Update` 内的 `AppendCaptures`、`FileChanges`、`FileDay`、`FileWeek`、`SetStatus`、`Erase`、`CompleteDeletionTask`、`ExpireCaptures` 等领域命令；不直接写表、不导入 Book 快照、不使用绕过工具校验的 Seed。

**测量与断言**：`TestLargeWorkingSetCost` 默认跳过，只有 `PERSONA_BENCH=1` 才运行；默认 N=200，可由 `PERSONA_BENCH_N` 改变。显式开启后缺少 PG 配置会失败，不能把仅有内存的结果当作完整报告。内存、PG 串行执行相同配方，各轮重建同一个 owner，并校验完整 Book JSON 的 SHA-256、账本数量、修订、已完成删除待办及八天原文数量跨轮、跨实现一致。造数和重建可能很慢，独立打印准备时间；不计入操作样本，每项都执行 N 次真实操作，擦除和到期不会变成第二次起的幂等空操作。生成和校验已预热数据，结果不是冷缓存或并发负载。

每轮依次执行：中段读页、末尾读页、追加三段、`day_ledger`、`list_commitments`、`find_related`、普通 `file_changes`（一交谈、一承诺）、同来源重交、擦除该来源的一段、清理最早仍存原文的一天。重交前另准备一个后续来源，用于验证取代保留原位置。所有轮次各操作的起始条件相同；后面的操作包含本轮之前的有限变化，例如追加之后当天有 3603 段。读页与 MCP 一样走 Update；三个查询走 View。测领域与存储路径，不含 HTTP/MCP 编解码、内核、模型或外部服务。

| 指标 | 口径 |
|---|---|
| 延迟 | Store 调用开始至返回（含装载、领域执行、写回和提交/回滚）；p50/p99 用 nearest-rank；外部准备和持久化结果断言不计入 |
| 账本字节/事务 | PG 在 `loadRows` 累计实际收到的 JSONB payload 字节，含物化交谈/承诺，不含协议及键列；内存复用入口 Clone 的 JSON 字节，提交时第二次 Clone 不重复算装载。两者形状不同，不能把差值当压缩率 |
| 原文片段/事务 | 存储读取点计数，重复读取重复计数；PG 含每次扫描预取的 128 段，即使领域提前结束；内存计交出的片段/批次副本，不把共享目录和既有驻留正文算成重新装载；目录遍历和复制的成本仍在延迟、堆与分配量中 |
| SQL/事务 | 专属 pgx 池的 QueryTracer 计 Query/Exec 调用，含 BEGIN/COMMIT/ROLLBACK，含参数化执行；协议 prepare 不另计。监测用另一池，准备/验证/WAL 查询不计；内存为 0 |
| Go 堆 | 每次操作前 GC，读取起点、终点并每 1 ms 采样 HeapAlloc，取所有样本最高观测值及相对起点最大增量；同时报告 TotalAlloc 差的 p50。是进程 Go 堆，含内存存储驻留配方，不是 RSS/PG 内存，也不是不会漏峰的精确最大值；探针会影响耗时 |
| WAL | 追加、来源重交、擦除分别读取操作前后 `pg_current_wal_lsn()`，以 `pg_wal_lsn_diff` 求字节，输出每操作 p50/p99。这是整个 PG 实例的 WAL，不能按 schema 隔离；运行时停止其他写负载，并记录 checkpoint/full-page-write 的影响，不把数字视为纯业务 payload |

读页固定 `all=true`、limit=200、MaxChars=20000、gap=10 分钟；中段 `after=600.2~1.0` 返回 200 段，尾页 `after=1190.2~1.0` 返回 30 段且 Done。每个事务的装载量与 SQL 都记录，报告汇总 p50 / max。必须通过的装载断言为：读页 ≤512 段、追加 ≤16 段、三个列表/召回查询为 0 段，且有界类操作均小于八天总量的 1/10；这些是防全量原文装载的结构性检查，不是耗时门槛。读页抽查引用、正文与结束标记，追加查持久化内容和版本；查询检查命中及 open 总数；变更集查实体数量，重交查位置与承诺身份；擦除查依赖账本撤销、相邻片段保留、删除待办和版本；自然到期查账本 SHA 不变、绑定保留、访问拒绝及版本增长，PG 另查原文物理行已清空。

**读法**：普通读页、追加与三个查询的原文读取有界（≤256 段；查询为 0），惰性断言成立。成本的大头是 Q93 的**整体装载非原文账本**：一年账本在 PG 上每个事务读入约 7.4 MB JSONB（23–96 条 SQL），只读查询 p50 约 185–225 ms，写事务约 400–460 ms；内存实现约 50–115 ms。`file_changes`、来源重交与擦除另会扫描当天原文（3608–7209 段）。这为 Q93 推迟的"账本按需有界查询"提供了实测依据：一年用户的单次工具调用已达数百毫秒，列为 P4 之后的优化项（例如交谈与承诺按日期/状态分页装载、物化查询读表），不在 P4 内实施。

## 8. 稳定性与故障域

| 故障 | 影响 | 兜底 |
|---|---|---|
| 采集服务或识别提供商不可用 | 新的旁听暂停进入 | HostApp 本地缓冲，恢复后以同一 `capture_id` 重交 |
| 内容安全不可用 | 输入被拒绝、可信页读取返回错误（fail closed） | 原文在 Persona，恢复后重读；保留期限不延长 |
| Persona 不可用或拒收 | 交出失败；模型可能仍正常结束 Run | 未接受的不推进处理进度；已接受的领域变化持久保留，恢复后继续；到期未处理完形成明确状态 |
| 编排器落后或崩溃 | 归集、渠道回复延迟 | 领域变化、删除待办、编排任务与出站接收均持久化；恢复扫描，出站过期按 Q106 对账 |
| 内核分片故障 | 该分片的数据及依赖它的汇总 | 健康分片独立读写、队列认领、出站消费继续；相关汇总有界失败且不把缺失数据当零，就绪与入口允许部分可服务（Q118） |
| 模型提供商限流 | 后台整理排队 | 准入让交互优先；单次调用独立限流 |

故障域按层分开：Persona 与内核不共用数据库，应用层的任何组件故障都不影响内核写日志。

## 9. 扩展范式

新功能按这个清单做，默认不改内核：

1. **Persona**：新的实体类型或变更集操作，及其检查与回执；
2. **工具**：Persona 的 MCP 工具，声明是否只读；
3. **AgentDef**：新增或修改，写明能力白名单；
4. **编排**：区分领域事实接受与运行事件，选择领域变化、应用调度或内核触发、定时、出站流；
5. **评测**：用例，以及 Persona 夹具的一致性测试。

每一步的验收都要回答四个问题：新内容的**来源**是什么（本人、他人、外部、平台）；它存在哪里、怎样随 Session、EndUser 或擦除**删除**；三方能否读到、经哪项**授权**；重试与重交是否**幂等**。

**改内核的判据**：第二条业务线也会需要，**并且**业务侧做不到或做了不安全。满足时写 ADR，在 [M7](./m7-kernel-primitives.md) 这类设计中记录理由。本次新增的每一处都按这条判据记录（§2.3）。

persona agent 的演进按同一范式（ADR-0043）：

- **一个前台、几个专员。** 用户面对前台（问答线程），它直接使用 Persona 的工具；重的活（报告生成、项目深度回顾）经委托交给专员（ADR-0031），子 Run 的能力不超出前台的白名单。后台整理不归前台调度，仍由触发、定时与编排器开启。
- 演进就是给前台加工具、加专员，接入三方 Agent（[M7 Agent 生态](./m7-agent-ecosystem.md)），内核不变。

- A11 的生产入口、角色、两库迁移、MCP 凭据轮换与内核 TokenSource 配置见 [xinli 部署](./xinli-deployment.md)；账号与产品 BFF 仍按 A12/B1 接入。

P4c 的固定槽位按真实路由键选择：内核区分 Session 与 EndUser（后者不加 BusinessLine），Persona 按 (BusinessLine, EndUser)；同 Session 的工件、调用随 Session 槽位，外部指定 Node ID 等入口也须携带真实键。新 ID 携带所属键的槽位，旧 ID 默认兼容库 0；迁移搬走旧数据须同步提供兼容映射，不能仍无条件落 0。槽位只决定去哪查，授权仍核对真实归属。只支持新单元或明确的停写迁移，不做在线迁槽、再平衡、网关通知归属；涉及格式的具体决定由 C1 的 ADR 固定（Q109、Q110）。

## 12. 不在这一版

- **跨业务线共享 Persona**：先按业务线隔离；第二个 persona 类产品出现时，按 Grant 的方式扩展。
- **端侧识别**：先用云端识别；端侧按章程 §3 的"规则 → 经典 ML → 小模型"另行评估。
- **音频保留与回放**：默认不保留（§4.1）。
- **采集的非文字种类**（照片、位置）：每一种另立 ADR（ADR-0036）。
