# 输入、触发与外部循环

> 状态：已确认（2026-10-25）；第 1 步已实现，第 2、3 步待做 · 依赖：[M0 核心原语](./m0-core-primitives.md)、[旁听与 Project](./captures.md)、[旁听按交谈整理](./captures-by-exchange.md)、[旁听白天逐段整理](./captures-daytime.md)、[Memory 与 Grant](./m4-memory-grant.md)、[模型调用](./model-calls.md) · ADR-0039、ADR-0040、ADR-0041 · 术语：`CONTEXT.md` 的 Provenance、Stream、Trigger、Loop

目标是内核只做一次：以后加一种新的采集内容或一种新的业务玩法，不再改内核；Agent 怎么想、怎么做也不受 YAML 的限制。本文把现在为旁听写进内核的部分收成四个通用原语（来源、流、触发、循环），所有写进日志的内容都经过同一个检查点。

## 1. 要解决的问题

旁听是第一种"不是对 Agent 说的输入"。为了接入它，内核增加了一批专用代码，其中一部分是通用机制，一部分其实是旁听整理的业务规则：

1. **每个入口各写一遍检查。** 用户输入（`service.SubmitWithID`）、旁听（`service.SubmitCaptures`）、通话转写（`service.AppendTranscript`）各自实现了校验、去重、内容安全、准入与配额，内容安全就有三种写法（`moderateInput`、`moderateCaptures`、直接调用 `moderation.Check`）。再加一种输入，又要复制一遍。
2. **信任规则分散。** "这段内容是谁说的、能不能作为写入 Memory 的依据、要不要做注入判断"分散在 `userText`、`tainted`、`unjudged`、`otherSpeech`、`hasUIContext`、`deviceResult` 等函数中，各自按事件类型判断。每种新输入都要逐个函数补上，漏一处就是一个信任缺口。
3. **旁听的业务规则留在内核。** 交谈间隔写死为 5 分钟（capture 包中的常量）；接着读的位置靠正则从给模型看的工具结果文字中找回，措辞一改就可能读不到；AgentDef 的开关是专用的 `captures: true`。
4. **接着读要扫描整个日志。** 找读取位置时每次都从头读出当天的全部日志。白天每 15 分钟整理一次，一天就是几十次全量扫描，日志越到晚上越大。
5. **何时整理只能由业务线定时提交。** 每条业务线都要自己写定时任务，自己判断有没有新内容（[旁听白天逐段整理](./captures-daytime.md) §5）。
6. **Agent 循环写死。** 循环固定在 `Worker.advance`：召回 → 判断 → 调用模型 → 执行调用 → 重复。YAML 只能调参数，表达不了确定性的步骤、分支、自定义的上下文或结束条件。章程原则 1 要求"Agent 循环策略……是可替换插件"，还没有做到。

## 2. 概要

```
来源方：用户、设备、HostApp（旁听）、通话、业务线服务端
      │
      ▼
 统一检查点：拒绝平台专属内容 → 去重 → 规范化 → 内容安全 → 准入与配额 → Store.Update
      │                                                    ▲
      ▼                                                    │
 Event 日志 ── 流：采集按种类追加，结构化的读取位置          │
      │                                                    │
      ▼                                                    │
 触发：AgentDef 声明的条件满足时，Worker 写入一条输入、开启 Run │
      │                                                    │
      ▼                                                    │
 循环：内置（AgentDef + 模型）或外部（业务线服务）给出回复与调用 ─┘
 来源：每段内容由谁产生，由平台从事件推导；闸门、判断都只看它
```

| 原语 | 做什么 | 取代 |
|---|---|---|
| 来源（§3） | 每段内容由谁产生、是否对 Agent 说，由平台从事件推导，写入闸门与注入判断只看它 | 分散的 `userText`、`unjudged` 等判断 |
| 统一检查点（§4） | 所有写进日志的入口按同一顺序检查；Agent 的输出走同一套规则 | 各入口各写一遍 |
| 流（§5） | 采集按种类追加；读取位置由平台记录在投影中；分段参数来自 AgentDef | `captures: true`、正则找位置、写死的间隔 |
| 触发（§6） | AgentDef 声明"什么情况下开启 Run"，平台按静默期合并后开启 | 业务线的定时提交 |
| 循环（§7） | Agent 的"大脑"可替换：内置的模型循环，或业务线的外部服务 | 写死的 `Worker.advance` |

分三步落地（§11），每一步单独可交付：第 1 步是收拢，模型看到的文本不变；第 2 步加触发；第 3 步加外部循环。不保留对之前实现的兼容（§11）。

## 3. 来源（Provenance）

**定义。** 来源说明一段内容由谁产生、是不是对 Agent 说的：

| 来源 | 举例 | 写入 Memory 的依据 | 注入判断 |
|---|---|---|---|
| 本人 | 用户的输入、对提问的回答、通话中用户说的话、旁听中佩戴者的话 | 可以 | 否 |
| 他人 | 旁听中他人的话 | 不可以：上下文含外部内容 | 是 |
| 外部 | 设备、沙箱、MCP、委托的调用结果，界面上下文，后台调用迟到的结果 | 不可以：上下文含外部内容 | 是 |
| 平台 | 平台写的说明（分页提示、拦截占位）、触发写入的输入（§6）、卡片 | 不可以，但不算外部内容 | 否 |
| 模型 | Agent 的回复与调用（含外部循环给出的，§7） | — | — |

依据与判断的规则与现在相同（[Memory 设计](./m4-memory-grant.md)、ADR-0023、ADR-0030、ADR-0036），这里只是把它们集中到一处。

**由平台推导，不由写入方填写。** 来源是"事件 + 内容块"的纯函数，放在 session 包中，例如：`RunRequested` 中不带触发标记的内容 → 本人；名称含 `__` 的调用的结果 → 外部；`captures` 结果中的旁听片段 → 按 `speaker` 字段分为本人或他人。不在每个内容块上存一个来源字段：存储的字段就可以由写入方自报，这正是要防的。唯一推导不出、需要写入的是旁听的说话人，现在已经是结构化字段（`CaptureSegment.speaker`），且只能由 `captures` 的结果写入（`session.CheckCapture` 与 `Apply` 校验）。

**谁用它。** 写入闸门（依据与外部内容）、注入判断（哪些结果待判断、交给判断的是哪些文字）、`cite_captures` 附上的说话人、给模型看的标注（`model.CaptureText` 中的 `[佩戴者]`、`[他人 other-1]`）。新增一种输入时，只在推导函数里登记它的来源，闸门与判断自动适用。

**第 1 步的验收。** 规则不变，只是集中：给模型看的文本不变，闸门与判断的单元测试原样通过，`make eval` 与基线一致。

## 4. 统一检查点

所有写进日志的入口按同一顺序做同一组检查，每个入口声明自己用哪几步：

| 入口 | 拒绝平台专属内容 | 去重 | 规范化 | 内容安全 | 准入与配额 | 写入后 |
|---|---|---|---|---|---|---|
| 用户输入（含卡片动作） | ✓ | `input_id` | 媒体、设备标注 | 整条 | 新 Run 时 | 开启 Run、插话或回答提问 |
| 采集（`SubmitCaptures`） | ✓ | `capture_id` | — | 整批，违规时逐段 | — | 只追加；有触发时可能唤醒（§6） |
| 通话转写 | — | — | — | 整条 | — | 只追加 |
| 设备结果、回答、审批 | 已有的校验 | `call_id` | — | 照旧 | — | 唤醒 Session |
| 触发（Worker 写入，§6） | — | 位置 | — | 不需要：内容是 AgentDef 中的固定文字 | 新 Run 时 | 开启 Run |

- **"平台专属内容"** 是只能由平台写入的内容块与字段：`background_result`、`capture`、卡片，以及本文新增的触发标记（§6）与读取位置（§5）。客户端提交中带有它们一律拒绝，`Apply` 再校验一次。
- **实现方式。** service 中的一组共用步骤，按上表组合，不是一个通吃的函数；它们最后都经 `session.Store.Update` 决定并追加，"先校验、再乐观并发追加"不变。
- **输出走同一套规则。** 模型或外部循环（§7）的回复，在写日志之前做内容安全检查（已有，ADR-0021）；调用按能力白名单与审批执行；`memory_save` 经过写入闸门，闸门按来源（§3）判断。检查点不区分输出来自哪种循环。
- **热路径上不加步骤。** 合并的是重复的代码，不是新增的检查：一批采集仍是一次内容安全调用加一次追加。

## 5. 流（Stream）

**Capture 按流区分。** Capture 仍是"采集到的、不是对 Agent 说的内容"，增加它属于哪个流的标记。旁听转写是 `transcript` 流，也是第一版唯一的流。`CaptureAppended` 增加必填的 `stream` 字段，`session.CheckCapture` 拒绝空值与未登记的流；提交接口（HTTP、Connection、三个 SDK）同样必须给出流名。

**流的种类由平台登记。** 种类决定：片段的校验、内容安全的送检方式、来源的推导（§3）、给模型看的格式。登记表让第二个种类不必再改闸门与工具。照片、位置这类非文字的种类，每一种都要另立 ADR：ADR-0036 只收文字，理由是删除边界与内容安全，需要逐种重新论证。

**AgentDef：`streams` 取代 `captures: true`。**

```yaml
streams:
  - name: transcript
    exchange_gap: 5m        # 交谈间隔，默认 5 分钟
    trigger:                # 可选，见 §6
      quiet: 5m
      input: 整理交谈
```

`captures: true` 删除。AgentDef 改为严格解析，未知的键报错：否则留着旧写法的 AgentDef 会被静默当作不接收任何流。`service.SubmitCaptures` 改为检查 AgentDef 是否声明了这个流。

**结构化的读取位置。** 现在的接着读（`after: "new"`）靠正则解析工具结果中给模型看的文字，而且每次扫描整个日志。改为：

- `captures` 的结果（`ToolResult`）新增平台写入的读取位置：流名，与读到的位置（与页尾给模型看的 `after` 相同）。它只能出现在 `captures` 的结果中，`Apply` 校验，与旁听片段相同。
- 投影：Run 进行中读到的位置记在 Run 上；`RunCompleted` 时提交为这个流已读到的位置。失败的 Run 不推进位置，与现在的语义相同（[旁听白天逐段整理](./captures-daytime.md) §4）。
- `after: "new"` 直接读投影，不再读日志；原来扫描日志、解析页尾文字的代码一并删除。快照随之多几个字段，递增 `session.ProjectionVersion`。
- `after` 只接受位置字符串（`"57.3"`、`"57.3~50.0"`）与 `"new"`，删除第一版的整数形式。

**分段参数来自 AgentDef。** `exchange_gap`（默认 `agentdef.DefaultExchangeGap`，5 分钟）取代写死的常量。交谈 ID 由切分决定，同一个 Session 中途换了间隔，业务线按交谈 ID 去重就会出错，所以一个 Session 第一次读取时使用的间隔随读取位置记下，之后沿用它。AgentDef 改了间隔，从新的 Session 起生效（旁听 Session 每天一个）。

**给模型看的提示文字**（分页、"还在进行"、拦截占位）仍由平台生成，属于平台来源；多语言等有了第二种语言的业务线再做。

## 6. 触发（Trigger）

**声明。** 流上的 `trigger` 表示：这个流有了未读的采集、且最后一次写入之后静默了 `quiet`，平台就开启一个 Run，输入是 `input` 的文字。`xinli-day` 用它取代业务线白天的定时提交；深夜的"整理今天"仍由业务线提交（§12）。

**语义：**

- **何时开启。** 同时满足：Session 未关闭；没有活跃的 Run；这个流有未读的采集（最后一次 Capture 晚于上次触发时的位置）；距最后一次写入（服务端的写入时间，不是设备时钟）已过 `quiet`。有活跃 Run 时等它结束再判断。
- **同一位置只触发一次。** 触发写入的 `RunRequested` 带触发标记：流名，以及触发时最后一个 Capture 的序号。投影记下每个流上次触发到的序号，序号没有前进就不再触发。所以 Run 失败后不会立刻重试、反复消耗配额：等有了新的采集，或业务线深夜整理时一并处理。输入 ID 由流名与序号派生，两个 Worker 同时判断也只生效一次。
- **与"进行中的交谈"一致。** 触发时距最后一次写入已过 `quiet`，而说话时间早于写入时间，所以 `captures` 看到的最后一段交谈也已结束，不会被当作"还在进行"跳过（[旁听白天逐段整理](./captures-daytime.md) §4）。批的间隔会让实际等待比 `quiet` 多出至多一个批的间隔。
- **来源是平台。** 触发的输入是 AgentDef 中的固定文字，不是用户的话：写入闸门不把它当作依据，也不需要内容安全检查。客户端提交的输入不能带触发标记（§4）。
- **准入与配额照常。** 超额时这一次不开启（记一条指标），等下一次条件满足；不为触发放宽配额。工作类别为后台（`workqueue.Background`），不挤占用户正在等待的交互。
- **ADR-0036 仍然成立。** 一批采集不开启 Run；开启 Run 的是 AgentDef 声明的、按静默期合并后的一次整理，一段交谈不论提交了多少批，至多一次。

**唤醒：沿用后台调用的做法。** 到期的后台调用就是"空闲时停放到截止时间，到期时写一条输入、开启 Run"（ADR-0035，`Worker.Step` 中的 `dueBackground` 与 `NextBackgroundDeadline`）。触发走同一条路径：

1. **写入时。** 这一批采集使流从"无未读"变为"有未读"时，`Decision.Wake` 为 true，在同一事务中入队；之后的写入不再入队。每段交谈只入队一次，而不是每批一次。
2. **Worker 认领、没有活跃 Run 时。** 有到期的触发就写入 `RunRequested`，随后照常推进；没有到期的，停放到最早的截止时间，与后台调用的截止时间取较早者。
3. **醒来时又有了新的写入。** 截止时间随最后写入时间后移，再停放一次。持续说话期间，每过一个 `quiet` 醒来一次。
4. **Run 结束时。** 原来是移出队列；有未读的采集时改为停放到触发的截止时间。

时间取自 `clock.Clock`，判断在 `Worker.Step` 的同步路径里，`internal/sim` 可以在任意两步之间注入故障。

**业务线仍可以手动提交"整理交谈"。** 它与触发读的是同一个读取位置（`after: "new"`），不会重复交出。

## 7. 外部循环（Loop）

**声明。** AgentDef 的 `loop` 指定由谁决定每一步做什么，不写时就是现在的内置循环：

```yaml
loop:
  server: xinli-loop        # loops/*.yaml 中的登记
model: ark/doubao-seed-2-1-lite-260915:minimal  # 仍然必填：压缩摘要用它（或 context.summary_model）
```

登记与远程 MCP 相同（`mcpcap.Server`）：`name`、`business_line`、`url`、`headers`（`${VAR}` 从环境变量注入）、`timeout`。只有同一业务线的 Session 能用这个循环，否则 Run 以配置错误失败。

**每一步一问。** 内置循环中"调用模型"的那一步，换成调用业务线的服务；其余步骤不变。平台照常组装上下文（含召回与压缩）、照常执行调用。契约在 proto 中定义（拟新增 loop.proto），经 HTTP 以 JSON 传输：

```proto
message LoopStepRequest {
  string session_id = 1;
  string run_id = 2;
  uint32 attempt = 3;
  uint32 turn = 4;
  string end_user = 5;
  AgentRef agent = 6;
  string system = 7;                  // AgentDef 的指令
  repeated LoopMessage messages = 8;  // 与模型请求相同的上下文视图（经压缩）
  repeated ToolSpec tools = 9;        // 本 Run 可用的工具，按名称排序
  bytes state = 10;                   // 上一步返回的 state；Run 的第一步为空
}

message LoopStepResponse {
  repeated ContentBlock content = 1;  // 回复
  repeated ToolCall tool_calls = 2;   // 为空表示 Run 完成
  bytes state = 3;                    // 至多 64 KiB，随 AssistantMessage 写入日志，下一步原样带回
}
```

**语义：**

- **循环只做决定，不做事。** 它只返回回复与调用请求；对用户设备、Memory 与其他能力的一切影响，都经平台执行的调用发生，审批、写入闸门、能力白名单照常生效。外部服务在自己的系统里做什么，平台管不到，这与业务线的 MCP Server 相同（ADR-0017）。
- **确定性。** 返回的结果作为 `AssistantMessage` 写入日志，回放读日志，不再调用外部服务，`Worker.Step` 的确定性不变。
- **重复请求。** Worker 在写入之前崩溃时，同一步（`run_id`、`attempt`、`turn`）会再请求一次，两次的回答可以不同，以写入日志的那次为准。外部服务按这三个字段做幂等即可，不必保证每次回答相同。
- **状态。** `state` 是外部服务给自己的不透明数据，存在日志里、随 Session 删除，外部服务因此可以不保存状态。它不进入模型上下文，也不出现在客户端的事件流中。
- **失败与时限。** 按模型调用的规则处理（[模型调用](./model-calls.md)）：暂时性失败本步重试，连续失败由 `StepErrorBudget` 使 Run 失败；第一版不流式，不存在"已输出增量后重试"的问题。
- **内容安全与计量。** 回复在写日志之前检查，与模型输出相同。用量按"步"计，不按 token 折价：外部服务自己调用的模型不经平台计量。`max_turns` 照常限制步数。
- **数据离开平台。** 请求带着完整的上下文，包括旁听中他人的话与设备的结果，会到达业务线的服务。MCP 调用只带参数，外部循环看到的范围大得多：业务线要承担保留与删除的义务，不应保存超出 `state` 的副本。这一点写进接入文档，由业务线在登记时确认。外部地址只来自显式的登记，私有化部署时可以不登记（ADR-0001）。
- **不变的部分。** 前缀缓存不适用（外部服务自己负责）；实时增量第一版没有，客户端收到的是整条回复。

**为什么是"每步一问"，而不是把整个 Run 交出去。** 把整个 Run 交给外部（A2A 式），外部 Agent 自带工具、自己执行，平台的审批、写入闸门、内容安全与删除都管不到它的内部，平台只能把最终结果当作外部内容。每步一问让外部服务只决定"下一步做什么"，而所有动作仍经过统一检查点（§4）。代价是每一步往返一次，延迟比内置循环高，适合复杂流程，不适合闲聊。A2A 作为另一种能力，以后另行设计（§12）。

## 8. 容量与成本

以一个 EndUser 一天十几万字、说话时间约 8 小时估算：

| 项 | 每人每天 | 10 万人 |
|---|---|---|
| 转写原文（中文每字 3 字节） | 约 0.5 MB | 约 50 GB/天，保留 7 天约 350 GB |
| 整理时工具结果中的副本 | 约 0.5 MB | 同上 |
| 写入（每分钟一批） | 约 480 次 | 平均约 550 次/秒 |
| 内容安全 | 每批一次 | 同写入 |
| 触发的入队 | 每段交谈一次 | — |
| 触发的唤醒 | 每段交谈约"时长 ÷ quiet + 1"次 | — |
| 接着读找位置 | 读投影，O(1)（现在：每次读整个日志） | — |

- 写入次数主要由批的间隔决定。建议 HostApp 用语音活动检测去掉静音，每 1–5 分钟或每次停顿提交一批，写入与内容安全调用都随之下降。这是给 HostApp 的建议，内核不变。
- 数据按 Session 分片（ADR-0028），写入可以水平扩展；存储由分级保留兜底（ADR-0037）。
- 工具结果不复制原文、只存引用，可再省约一半存储，但改动了回放读取的内容，不在这一版（§12）。

## 9. 不变量核对

| 不变量 | 本设计中 |
|---|---|
| Event 日志是唯一事实源 | 读取位置、触发到的序号、外部循环的 `state` 都在日志中，投影只是从日志推导 |
| `Worker.Step` 是确定性的单步 | 触发按 `clock.Clock` 判断，外部循环的回答写入日志后才生效 |
| 请求前缀稳定 | 内置循环的请求组装不变；`streams` 与 `trigger` 不改变系统指令与工具定义 |
| 内容安全在写日志之前、失败即拒绝 | 统一检查点与外部循环的回复照常检查 |
| 写入闸门只收紧不放宽 | 规则不变、只是集中；触发的输入不是依据；外部循环的 `memory_save` 照常过闸门 |
| 按 Session 删除 | 没有新的存储；`state` 与读取位置随 Session 删除 |
| 外部写入后唤醒用 `Decision.Wake` | 采集使流变为"有未读"时置 Wake，与输入同一事务 |

## 10. 测试与评测

- **第 1 步。** 来源推导函数的表格测试覆盖每种事件与内容块；闸门与判断的现有测试原样通过；读取位置：投影在 `RunCompleted` 时提交、失败的 Run 不推进；`after: "new"` 不读日志（计数读取次数）；空的或未登记的流名被拒绝；AgentDef 中的未知键报错。`make eval` 的 `capture-*` 与 `memory-*` 用例与基线一致。
- **第 2 步。** `internal/sim` 新增触发的不变量：同一序号至多触发一次；有活跃 Run 时不触发；关闭后不触发；Worker 在写入 `RunRequested` 前后崩溃都不重复、不遗漏。加入覆盖统计。评测 `capture-daytime` 增加触发版本（评测用的 AgentDef 把 `quiet` 设为几秒）。控制台场景（`scenarios.js`）增加一段：提交采集、等待静默、看到触发的 Run。
- **第 3 步。** 模拟测试中的脚本化外部循环：超时、错误、重复请求、`state` 往返；回放不再请求外部服务。评测用模拟的外部循环服务跑通一个 xinli 用例，结果与内置循环可比；`make check` 中的 e2e 走一次真实的 HTTP。

## 11. 实施顺序

| 步 | 内容 | 验收 |
|---|---|---|
| 1. 收拢（模型看到的文本不变） | 来源推导函数，闸门与判断改用它；统一检查点的共用步骤；必填的 `stream`（契约、service、三个 SDK、控制台）；结构化的读取位置与投影，删除扫描日志的接着读；`exchange_gap` 来自 AgentDef；`streams` 取代 `captures: true`，AgentDef 严格解析 | `make check`、`make sim` 全绿；`make eval` 与基线一致 |
| 2. 触发 | `trigger` 声明；`RunRequested` 的触发标记与投影；Worker 空闲时的触发判断与停放；`xinli-day` 改用触发；业务线不再需要白天的定时提交 | 同上，加上 §10 的模拟测试与评测 |
| 3. 外部循环 | loop.proto 与 `make gen`；`loops/*.yaml` 登记；Worker 中模型调用一步的替换；计量单位"步"；接入文档 | 同上，加上 §10 的模拟测试、评测与 e2e |

第 1 步不依赖后两步是否通过，可以先做。

**不保留兼容。** 之前的实现不再支持：

- `captures: true`、`after` 的整数形式、不带流名的提交，都直接报错；
- 不读升级前写下的日志：`stream` 为空的 `CaptureAppended` 被 `Apply` 拒绝，含有它的 Session 无法加载。Mac mini 上的开发数据库要在部署第 1 步之前清空（届时先确认再做）；评测每次新建 Session，不受影响；
- 投影快照随 `session.ProjectionVersion` 作废。

契约仍只做 `buf breaking` 能通过的修改：删除的字段保留编号与名称（`reserved`）。日志与线上传输都是 protobuf 字节（ADR-0006），复用编号会让旧字节被误读成新字段；保留编号没有成本。

## 12. 不在这一版

- **定时触发**（如每晚 23:30 整理）：一天从哪里开始、EndUser 在哪个时区，是业务线的概念；旁听 Session 也由业务线按天创建。深夜的"整理今天"仍由业务线提交。
- **非文字的采集**（照片、位置）：每一种另立 ADR（§5）。
- **A2A**：把整个外部 Agent 作为一种能力接入，结果是外部内容（§7）。
- **在沙箱中运行的循环**：业务线上传循环代码、在沙箱中运行（ADR-0008：沙箱只运行不可信代码），业务线不必自己部署服务。等生产沙箱选型（ADR-0010）之后再做。
- **外部循环的流式增量、使用平台的模型代理**：先看接入方是否需要。
- **工具结果只存引用**（§8）：需要单独评估回放与评测。
- **采集移出 Event 日志、单独存储**：等单表写入真成瓶颈；它要另外接入删除、Janitor 与模拟测试的删除不变量。

## 13. 待确认的决定

| 决定 | 建议 | 没有选的 |
|---|---|---|
| 采集如何泛化 | `CaptureAppended` 加必填的 `stream`，种类由平台登记 | 换一个新名字的通用事件（不必兼容，但只是改名，代码与文档的改动面更大）；不泛化（第二种采集再改一遍内核） |
| 来源的表示 | 由平台从事件推导；只有说话人作为字段写入 | 每个内容块存一个来源字段（写入方可以自报，要处处校验） |
| 白天谁触发整理 | 平台按 AgentDef 的声明触发（改 [旁听白天逐段整理](./captures-daytime.md) §7 的第一条决定，ADR-0040） | 维持业务线定时提交 |
| 静默期按什么时间算 | 服务端的写入时间 | 设备给出的说话时间（设备时钟不可信，补交的旧批会立刻触发） |
| 触发的 Run 失败后 | 同一位置只触发一次，等新的采集或深夜整理 | 退避重试（失败多半是配额或配置问题，重试只会反复消耗） |
| 外部循环的形态 | 每步一问，平台执行全部调用（ADR-0041） | 整个 Run 交给外部（平台的检查管不到）；进程内插件（业务代码进入内核的故障域与信任域） |
| 外部循环的状态 | 不透明的 `state` 写入日志 | 由业务线自己保存（要另外处理删除，回放时也拿不回当时的状态） |
