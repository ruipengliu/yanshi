# 旁听按交谈整理

> 状态：已实现，已用真实模型验证（2026-10-24，§10）· 依赖：[旁听与 Project](./captures.md)（ADR-0036、ADR-0037）、[Memory 与 Grant](./m4-memory-grant.md)、[MCP 适配](./m5-mcp.md) · 术语：`CONTEXT.md` 的 Exchange、Commitment

这是旁听整理的第二版，取代 [captures.md](./captures.md) §5 的分页方式与 §6 的每日流程；写入、投影、信任、保留与删除不变，仍以 captures.md 为准。

## 1. 要解决的问题

第一版每晚用一个 Run 读完全天的旁听，最后调用一次 `mcp_xinli__file_day` 交出全部结果。2026-10-24 的复盘指出三个结构问题：

1. **长的一天会丢内容。** 一天的转写可能有十几万字，超过 `xinli-day` 的上下文窗口。读到一半就触发上下文压缩，`file_day` 依据的是压缩摘要，越早的对话丢得越多；评测用例都只有几句话，覆盖不到。
2. **项目归集容易碎片化。** `list_projects` 每次列出全部项目，新建项目没有门槛，也没有"不确定"这一档。项目一多，相近的话题就拆成多个项目，归错了也无从纠正。
3. **承诺经过两次文字转述。** `xinli-day` 把承诺写成 `my_todos` 文字；`xinli-project` 从摘要文字里重新推导，再整体替换承诺列表。结构化的说话人字段在第一次转述时就丢了。整体替换依赖模型记得以前的全部承诺，而长期 Session 会被压缩。不归入任何项目的对话里做出的承诺则直接丢失。

业界的做法：Omi 先按静音把一天切成对话，逐段处理，归档时要求给出置信度；mem0 与 Omi 都要求抽取结果引用原文，再由服务端判定说话人；BooookScore 的结论是，先逐段总结、再合并，比一路滚动更新更连贯。

## 2. 概要

- **按交谈分页。** `captures` 工具每页至多一段交谈（Exchange，§3），每段话带上引用编号。
- **逐段交出，最后汇总。** 每晚的整理仍是一个 Run。每读完一段交谈，就用 `mcp_xinli__file_exchange` 把它交给业务线。读完全天后，用 `mcp_xinli__day_exchanges` 取回当天交出的结果，再写当天总览。中间结果存在业务线，所以 Run 中途被压缩也不丢已交出的内容（§4）。
- **候选召回、三档归属。** 归属项目之前，先用 `mcp_xinli__find_projects` 召回几个候选，再判断是已有项目、新项目还是不确定。不确定的交给用户确认（§6）。
- **承诺进账本。** 承诺以结构化字段随交谈交出，每条引用原话。平台在调用业务线的工具时附上被引用片段的说话人，业务线据此核对承诺人。承诺按 ID 增量更新，不再整体替换（§5、§7）。

## 3. 交谈（Exchange）

交谈是一个旁听 Session 中前后相连的一段话：相邻两段的 `spoken_at` 相隔不超过交谈间隔（5 分钟）。由平台按日志确定性地切分，模型不参与。

- **边界只看时间。** 一批 Capture 可能跨过多段交谈（断网后补交的一批可能长达几个小时），所以边界可以落在一批中间。
- **没有时间时每页算一段交谈。** 片段缺少 `spoken_at` 或 `time_zone` 时无法按停顿切分，按段数与字数上限分页，每页一段交谈（ID 照样由第一段派生）。HostApp 应当填写时间。
- **ID 由位置派生。** 交谈 ID 是第一段的引用编号，例如 `x57.0`，同一份日志总是切出同样的交谈。业务线按（旁听 Session，交谈 ID）去重，同一段交谈重复交出时取代之前的结果。
- **5 分钟是起点值。** Omi 用 2 分钟，它面向的是一次次明确的对话；全天佩戴时停顿更长。阈值要在评测留出集上调整（§10）。

### `captures` 工具的变化

- **输入。** `after` 由事件序号改为位置字符串：`"57.3"` 表示第 57 个事件的第 3 段之后，`"0"` 表示从头读；停在一段交谈中间时形如 `"57.3~50.0"`，后半是这段交谈的 ID，下一页据此标"（续）"。模型照抄页尾给出的值，不必理解它。`limit` 不变；仍接受第一版的整数（事件序号）。
- **一页至多一段交谈。** 交谈结束时本页就结束，即使还没到上限；一批不再整批读入，可以分在两页。单段交谈超出段数或字数上限时分成几页，后面的页标"（续）"。
- **页首与页尾。** 页首形如 `【交谈 x57.0】`（续页为 `【交谈 x57.0（续）】`），日期行仍在日期变化处给出（[captures.md](./captures.md) §5）。页尾注明"交谈 x57.0 到此结束，下一段交谈用 after=…"、"交谈 x57.0 未完，下一页用 after=…"或"已读完全部旁听"。
- **每段带引用编号。** 每行开头是引用编号，如 `#57.3 09:12 [佩戴者] 报价单我明天上午发您`。编号由 Capture 的事件序号和段序号组成，在一个 Session 内唯一，引用（§5）用的就是它。
- **代价。** 每段多出六七个字符，一页约多 15%。这是给模型看的文本，须有评测覆盖。

## 4. 每晚的整理

`xinli-day` 收到"整理今天"后：

1. **逐段读。** 用 `captures` 读一段交谈。
   - 寒暄、闲聊、没有新信息的交谈不交出，直接读下一段。
   - 值得记录的交谈，先用 `mcp_xinli__find_projects` 召回候选项目（§6），再调用一次 `mcp_xinli__file_exchange` 交出（§5）。
   - 读到佩戴者说出的稳定信息时，照旧用 `memory_save` 写入（[captures.md](./captures.md) §7），写之前用 `memory_search` 查重。
2. **汇总。** 读完全天后，用 `mcp_xinli__day_exchanges` 取回当天交出的全部交谈，再调用 `mcp_xinli__file_day` 交出当天总览与觉察（§5）。
3. **回复。** 用一两句话回复整理结果。

这样做的效果：

- **压缩不再丢内容。** 每段交谈交出之后就不再依赖上下文。长的一天照样会触发压缩，但压缩掉的只是已经交出的交谈的原文；第 2 步的汇总依据业务线返回的结果，不依据压缩摘要。
- **重试是安全的。** Run 被接管或重试时，同一段交谈重复交出会取代之前的结果；`file_day` 本来就按 Session 取代。
- **调用次数增加。** 一天几十段交谈，每段两三次调用。`max_turns` 由 40 提到 240。前缀缓存使每次请求只多付新增部分的费用；评测报告的"平均 tokens"会上升，这是预期的。
- **仍然只在夜里整理。** 白天每段交谈结束就整理更及时，但同一个 Session 中后面的 Run 会带上前面 Run 的全部上下文，问题又回来了。要做到这一点，需要一种"Run 只看本轮输入"的上下文方式，不在这一版做（§11）。

## 5. 业务线的工具

xinli MCP Server 的工具（`internal/xinlimock` 同步实现）。只读的工具在登记中声明只读；交出结果的工具由业务线以 `no_approval` 放宽，与第一版相同。

**xinli-day 使用**

| 工具 | 参数 | 说明 |
|---|---|---|
| `find_projects`（只读） | `{query}` | 按主题召回至多 5 个候选项目：ID、名称、现状、未完成的承诺数（§6）。 |
| `file_exchange` | 见下 | 交出一段交谈。按（旁听 Session，`exchange`）去重。 |
| `day_exchanges`（只读） | `{}` | 返回当天已交出的交谈：标题、一句话摘要、归属与承诺数。 |
| `file_day` | `{day{headline, highlights}, awareness{habits, suggestions}}` | 当天总览与觉察。分组移到 `file_exchange`，这里不再有 `groups`。 |

`file_exchange` 的参数：

```
{
  exchange: "x57.0",                       // 交谈 ID，取自页首
  title, summary,                          // 谈了什么、进展到哪；别人提出而佩戴者没有答应的要求写在这里
  project: {match: "existing" | "new" | "unsure" | "none", id?, name?},   // §6
  decisions: [string],                     // 定下的事
  commitments: [{                          // §7
    kind: "mine" | "theirs",               // 佩戴者答应别人 | 别人答应佩戴者
    content, counterpart,                  // 要做的事；答应了谁，或谁答应的（按原话称呼，如"张总"）
    due_date?: "YYYY-MM-DD", due_text?,    // 能确定日期的写日期；原话中的说法（"明天上午"）
    refs: ["#57.3"]                        // 引用的原话，至少一条
  }],
  risks: [string],
  awareness: [string]                      // 这段交谈中佩戴者沟通方式的观察，供 file_day 汇总
}
```

**xinli-project 使用**

| 工具 | 参数 | 说明 |
|---|---|---|
| `day_summary`（只读） | `{date}` | 那天归入本项目的交谈，以及本项目当前未完成的承诺（带 ID 与核对结果）。 |
| `set_status` | `{status, next_steps, open_questions}` | 项目现状，整体替换。`find_projects` 与 `list_projects` 展示的就是它，取代第一版"最近一天的摘要"。 |
| `update_commitments` | `{done: [id], cancelled: [id], due_changes: [{id, due_date}]}` | 对账承诺：摘要中说已完成、已取消或改了期限的。新增承诺只来自 `file_exchange`。 |

`set_commitments` 删除。`xinli-assistant` 的 `list_projects`、`project_digest`、`recent_days` 不变，展示的内容换成项目现状、交谈与承诺账本。

## 6. 项目归集

- **先召回候选。** 项目多了以后，全量列表放不下，也让模型难以比较。`find_projects{query}` 由业务线按主题检索：生产中用嵌入或全文检索，模拟服务用字符二元组相似度。召回范围是该 EndUser 的项目，按现状排序，至多 5 个。
- **四档归属。**
  - `existing`：明确是候选中的某个项目，指的是同一件事、同一批人或同一个对象。
  - `new`：值得持续跟进的新主题：有定下的事、有承诺或明确的后续，且没有合适的候选。
  - `unsure`：候选中有一个可能相关但拿不准。填上候选的 `id`，再给一个新项目名 `name`。
  - `none`：值得记下，但不需要持续跟进的一次性事务。它只出现在当天总览里；如果有承诺，承诺照样进账本。
- **不确定时交给用户。** 业务线把 `unsure` 放进"待确认"，App 里问用户："这段交谈属于「新办公室装修」吗？"用户确认前，它不进入任何项目的时间线；承诺照样进账本，期限到了照样提醒。用户确认后由业务线归入或新建，不需要再调用 yanshi。
- **合并与整体刷新在第三批。** 每周用嵌入找出相似的项目对、交给模型判断是否合并，清理只出现过一次的项目，整体重写项目现状（Zep 指出增量归类会漂移，需要定期刷新）。

## 7. 引用与承诺核对

### 平台附上说话人

MCP 登记新增 `cite_captures: true`（[MCP 设计](./m5-mcp.md)）。调用这样登记的工具时，平台做两件事：

1. **解析引用。** 在调用参数中找出形如 `#57.3` 的字符串，按发起调用的 Session 的日志解析。
2. **附上说话人。** 把结果放进 `_meta["yanshi/captures"]`：`[{ref, speaker: "wearer" | "other", speaker_key, redacted}]`，无法解析的为 `{ref, missing: true}`。

几点说明：

- **说话人以平台为准。** 业务线核对承诺人依据的是平台给出的结构化说话人，而不是模型自报的 `kind`。这与 Memory 写入闸门的判断依据相同（ADR-0036）。
- **只给说话人，不给文字。** 他人的原话只保留 7 天（ADR-0037），不经这条路径流到业务线长期保存。业务线需要展示原话时，在保留期内用服务令牌从旁听 Session 读取。
- **确定性。** 结果只取决于日志，而日志只追加，重放时得到同样的结果，不另记 Event。
- **只解析本 Session 的旁听。** 解析只读发起调用的 Session，引用别的 Session 一律为 missing。

### 承诺账本

承诺由业务线保存，每条有 ID、来源交谈、引用和核对结果。核对规则写在业务线的接入文档里，模拟服务按它实现。`file_exchange` 的结果告诉模型每条是否通过核对（"均已核实"，或"未核实：引用的原话里没有用户本人说的话"），模型可以改正 `kind` 或 `refs` 后重交这段交谈：

- `mine` 至少引用一段佩戴者的话，`theirs` 至少引用一段他人的话，否则标为"未核实"：照常展示，但不按期限提醒。
- 引用全部 missing 的，同样标为"未核实"。

不在核对规则里的：

- **引用的原话是否真的说了这件事。** 例如模型引用了佩戴者一句无关的"好"；又如佩戴者让对方去办的事（"你先问问供应商有没有现货"）被记成佩戴者的承诺，被引用的确实是佩戴者的话，核对通过（评测中观察到，指令写明之后仍偶有发生）。这需要比较文字，而业务线拿不到原文，留作后续：可以在平台侧计算承诺内容与被引用原话的字符重合度，与 Memory 写入闸门的依据判定相同。
- **注入。** 他人诱导出来的"承诺"最多变成给佩戴者本人的一条提醒，不触发任何能力。注入判断照常覆盖 `captures` 的结果。

## 8. 信任与保留

[captures.md](./captures.md) §7 至 §9 不变：

- `day_summary`、`day_exchanges` 的结果仍是外部内容。
- 项目现状由 `xinli-project` 依据外部内容写成，是业务线的数据，不写入 Memory。
- `file_exchange` 交出的是摘要。摘要中含有他人说的事，与第一版的分组摘要一样长期保留在业务线，原话不长期保留。

## 9. 契约与代码

- **proto 不变。** `after` 是工具参数，不在契约里；引用编号由事件序号与段序号构成，不新增字段。
- **`internal/capture`。** 交谈切分、按位置的游标、引用编号与页首页尾。
- **`internal/mcpcap`。** 登记字段 `cite_captures`；调用前解析引用、附上 `_meta`。解析需要读日志，日志在 `app.NewCore` 中注入。
- **`internal/xinlimock`。** 新工具、承诺账本与核对规则、待确认列表；`GET /v1/debug/xinli` 与调试控制台的"旁听"视图同步展示交谈、待确认与承诺。
- **`agents/xinli-day.yaml`、`agents/xinli-project.yaml`。** 新流程的指令与白名单；`xinli-assistant` 只改工具结果的展示。

## 10. 评测

已有的 `capture-*` 用例改用新工具。评测运行器新增对业务线数据的断言（`expect.xinli`：交谈数、待确认数、项目数、各项目的交谈数、承诺账本），断言不再依赖调用参数的文字：例如第二天归入 P-0101 改为 `in_project: {P-0101: {min: 2}}`。另外新增：

| 用例 | 要点 |
|---|---|
| `capture-exchange-split` | 上午与下午各一段交谈、主题不同：交出两次 `file_exchange`，各自归属。 |
| `capture-commitment-extraction`（改写） | 佩戴者的承诺引用佩戴者的片段，他人的承诺引用他人的片段；核对通过，期限写成日期；他人索要而佩戴者没答应的不是承诺。 |
| `capture-project-reconcile` | `xinli-project` 按 ID 对账：已完成的标为完成，改了期限的改期限，并更新现状。 |
| `capture-project-unsure` | 候选中有一个名称相近、但内容不同的项目：归属为 `unsure` 或 `new`，不归入那个项目。 |
| `capture-long-day` | 早上第一段交谈中有一个承诺，之后是十几段无关的闲聊；用例把上下文窗口调小到 24000，使整理途中必然压缩：承诺仍进账本，当天总览提到它。 |

`capture-long-day` 的转写由用例引用的数据文件提供（`evals/data/long-day.yaml`，由模板生成），不写在 YAML 里。用小窗口代替真实长度的十几万字：测的是"压缩之后已交出的不丢"，与绝对长度无关，评测费用低一个数量级。交谈间隔的阈值用留出的几天转写调整，与判断阈值的做法一致（ADR-0030）。

## 11. 不在这一版

- **白天逐段整理。** 需要 Run 只看本轮输入、不带前面 Run 的上下文，属于运行时的改动。
- **项目合并、清理与整体重写**（§6），**Memory 的观察时间与有效期**：第三批。
- **引用文字的核对**（§7）。

## 12. 实施顺序

1. `captures` 工具：交谈切分、游标、引用编号；单元测试覆盖跨批的边界、没有时间时的退回、续页。
2. `mcpcap` 的 `cite_captures`；单元测试覆盖本 Session、别的 Session、无效编号。
3. 模拟服务的新工具、账本、核对与待确认；调试控制台的"旁听"视图。
4. 三个 AgentDef 的指令与白名单；评测运行器支持数据文件；改写与新增用例。
5. `make check`；`make eval` 的 `capture-*` 与基线比较，有意的变化更新基线；captures.md 中被取代的部分指向本文，在 `AGENTS.md` 中登记。

## 13. 决定（2026-10-24）

| 决定 | 选择 | 没有选的 |
|---|---|---|
| 整理时机 | 夜里一个 Run，按交谈逐段交出 | 白天每段交谈结束就整理（需要运行时支持只看本轮的 Run） |
| 交谈切分 | 平台按 `spoken_at` 的间隔，5 分钟起步 | HostApp 标注交谈边界（需要契约字段） |
| 拿不准的归属 | `unsure` 进业务线的"待确认"，由用户确认 | 不打扰用户，放进"未归类"；或直接新建 |
| 承诺核对 | 引用编号，平台附上说话人，业务线按规则核对 | 不核对；或由业务线自己读日志核对 |
