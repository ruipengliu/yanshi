# M6 判断：规则、小模型与 LLM 的分层（草案）

> 实施前须：在 CONTEXT.md 中定稿 Decision 一词；ADR-0030 转为 accepted；`internal/model` 支持 logprobs；`internal/sim` 注入判断失败故障。

## 1. 要解决的问题

harness 里有大量"给定状态、有限合法选项"的判断：暴露哪些工具、调用结果里有没有注入、这句话是闲聊还是任务、该不该追加审批。现在它们要么是固定规则，要么混在一次完整的 LLM 调用里。本设计规定判断分几层、每层能做什么、以及引入小模型（System 1）时必须遵守的约束。

判断不是新能力：它只缩小候选、追加约束或触发默认路径，从不替模型做最终决定，也从不放宽安全要求。

## 2. 分层

按章程非目标的阶梯，云端判断同样逐级选用，上一层够用就不上下一层：

| 层 | 适用 | 性质 |
|---|---|---|
| 规则 | 有明确属性可依据的判断 | 确定、可重放、零成本；写在代码里，由模拟测试覆盖 |
| 经典 ML / 统计 | 有自有数据、特征稳定的判断 | 确定（同输入同输出），可离线训练与评测 |
| 小模型（System 1） | 需要理解自然语言、但只需在有限选项中选一个 | 不确定；一次前向传播输出选项概率，带置信度；须按 ADR-0030 记为 Event |
| LLM（System 2） | 需要推理或生成 | 不确定；现有的模型调用 |

## 3. 判断点清单

按"收益 × 可行性"排序。证据来自调研 §3.2 的独立评测（英文为主，中文证据几乎为零，须自建中文用例）。

| 判断点 | 层 | 作用 | 证据与约束 |
|---|---|---|---|
| 设备歧义消解（同类设备多台） | 规则 + 用户 | 按"UIContext 的来源设备 → 最近在前台的设备 → `ask_user`"的固定顺序；属性来自 Presence 与推送设备的 `LastActive` | 无需模型；属性进工具描述时注意前缀稳定（在线状态不进描述，M1 §5） |
| 交互与后台分类 | 规则 | 已实现：按已提交的模型调用次数（ADR-0029） | System 1 做"快答 vs 长任务"路由在评测中是随机水平，不替换 |
| 调用结果中的提示注入 | 小模型 | 对每条 `ToolResult` 打分；高分时在上下文加隔离标记，或让后续高风险 Capability 强制 Approval。只收紧 | 最强（AUC 0.97–0.98）；第一步影子模式 |
| 工具折叠（top-k 暴露） | 小模型 | 从几十上百个 `设备__能力`、MCP 工具中选出候选暴露给模型；置信度低时全量暴露 | 工具选择 Jev 84.5% 与 LLM 83.0% 相当；同时缩短前缀；须用评测的"缓存命中"列确认无退化 |
| 交付前事实一致性 | 小模型 | 发送类 Capability 审批前检查拟发送内容是否有上下文依据；不一致时让 LLM 自检 | AUC 0.95；只追加检查 |
| Call 中的快速判断 | 小模型（自训） | 这句话是闲聊、追问进度、插话还是要派生 Run；是否打断播报 | 延迟预算百毫秒级最契合；中文数据需自建 |
| 审批辅助 | 小模型 | 对"声明只读但看起来有副作用"的调用追加审批 | AUC 0.77–0.86；永不免除审批 |
| 委托给哪个 Agent | LLM | 规划判断，不是分类（[多 Agent 委托](./m5-multi-agent.md) §7） | 零样本小模型无证据；先积累评测数据 |
| Memory 召回相关性、PII、模型路由、作为唯一的内容安全闸门 | 不用 | | 评测不可用或合规不允许 |

## 4. 约束（摘自调研 §3.4，实施时逐条核对）

1. **私有化（ADR-0001）。** 托管 API 形态的 System 1 不可用于客户 IDC。路线是自托管小开源模型，读取选项标签首 token 的 logits 做校准分类；不训练也能先做原型，LoRA 留给效果不够时。TokenHub 不返回 logprobs（2026-10-10 实测），须自托管推理端点；`internal/model` 需加 logprobs 支持。
2. **判断是 Event（ADR-0030）。** 影响后续执行的判断先写日志再行动，重放读日志而不重新调用；`internal/sim` 注入"判断调用失败或超时"。
3. **失败即保守。** 判断不可用时退回默认路径：全量暴露工具、按原规则审批、不加隔离标记以外的任何放宽。
4. **只收紧不放宽。** 判断可以追加审批、追加标记、缩小候选，不能免除审批、不能替代合规审核、不能跳过写日志前的检查。
5. **个人数据（ADR-0015）。** 判断的输入含用户内容，只放在可按 Session 删除的地方；日志与指标只记 ID 与分数分桶。
6. **计量（ADR-0019）。** 每次判断都是一次计量的模型调用；评估节省时计入全部组件成本。
7. **评测纪律。** 阈值只在留出集上确定；报告调用率与留出集漏检率，而非准确率；测选项顺序扰动；按判断点在 `evals/` 分组建中文用例。
8. **前缀稳定。** 判断改变工具列表时，列表仍按名称排序，且同一 Run 内的候选集只能单调扩大，不在尾部之外改动上下文。

## 5. 组件

- `internal/decision`：`Decider` 接口（输入：状态文本 + 类型化问题；输出：各选项概率、置信度），实现有 `rules`（确定）、`logits`（自托管小模型）、`llm`（退回 System 2）、`fake`（模拟测试）。
- Event：`DecisionMade{run_id, attempt, kind, options, chosen, confidence, model}`，不含状态文本原文。
- Worker 在对应 Step 内同步调用 `Decider`，结果与由它推导的事件同批提交；失败走默认路径并计数。
- 指标：`yanshi_decisions_total{kind, outcome}`（applied / fallback / error）、`yanshi_decision_duration_seconds{kind}`。

## 6. 落地顺序

1. **规则先行**：设备属性（最近在前台、来源设备）进入歧义消解顺序与 UIContext；评测用例 `device-pick-recent`、`device-pick-ui-context`。零风险。
2. **影子模式试点注入检测**：自托管小模型给每条 `ToolResult` 打分，记为 `DecisionMade` 但不影响执行；用 `prompt-injection-file` 加一批中文样本离线评测；一到两周后看分布与延迟，再决定是否驱动强制 Approval。这一步顺带做出 logprobs、判断 Event、故障注入三件基础设施。
3. **工具折叠**：复用同一小模型做 top-k 暴露；评测报告的"缓存命中"与通过率不得回归。
4. Call 中的快速判断、交付前一致性检查：有中文数据后再做。
