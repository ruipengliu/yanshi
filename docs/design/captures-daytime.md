# 旁听白天逐段整理

> 状态：已实现（2026-10-25）；评测结果见 [m4-eval.md](./m4-eval.md) §12· 依赖：[旁听按交谈整理](./captures-by-exchange.md)、[长 Run 与上下文压缩](./m2-long-runs.md)（`runtime.Transcript`）

## 1. 要解决的问题

每晚整理一次，白天答应的事要到深夜才进承诺账本，当天的提醒来不及；用户白天在 App 里问"刚才我答应了张总什么"，助手也查不到。

直接在白天多跑几次整理不行：同一个旁听 Session 中，后面的 Run 会带上前面所有 Run 的上下文（`runtime.Transcript` 把整个 Session 的历史交给模型），到了下午，每次整理都背着上午读过的全部旁听，第二版刚解决的问题（[旁听按交谈整理](./captures-by-exchange.md) §1）又回来了。

## 2. 概要

| 改动 | 内容 |
|---|---|
| 只看本轮的 Run | AgentDef 新增 `context.scope: run`：模型上下文只含当前 Run 的输入、输出与调用结果，不含之前的 Run（§3） |
| 接着读 | `captures` 的 `after` 新增 `"new"`：从本 Session 之前已完成的 Run 读到的位置之后接着读（§4） |
| 进行中的交谈先不读 | 最后一段距现在不到交谈间隔的交谈可能还没结束，白天整理时跳过，下次再读（§4） |
| 两种输入 | 业务线白天定时提交"整理交谈"，只交出已经结束的交谈；深夜的"整理今天"交出余下的全部交谈，再写当天总览（§5） |

## 3. 只看本轮的 Run（`context.scope: run`）

- **上下文。** Transcript 只保留当前 Run 的事件：它的输入（`RunRequested`）及之后的插话、模型输出与调用结果。系统指令、工具定义与召回照旧。之前的 Run 不进入上下文。
- **压缩。** 只有当前 Run 内发生的压缩摘要进入上下文；之前的 Run 的摘要不进入。压缩的时机按只看本轮的上下文估算。
- **写入闸门与注入判断不变。** 它们按整个 Session 的历史判断是否有外部内容，比只看本轮更严，只收紧不放宽（ADR-0023）。
- **适用范围。** 每次输入彼此独立、靠外部状态衔接的 Agent：`xinli-day`（衔接靠业务线保存的交谈与 `captures` 的读取位置）。对话类 Agent 不用它。
- **默认值。** 不写时为 `session`，即现在的行为。
- **请求前缀。** 系统指令与工具定义不变；每个 Run 从头开始，Run 内照旧只在尾部追加，前缀缓存的命中方式不变。

## 4. `captures` 接着读

**`after: "new"`。** 从本 Session 之前已完成（`completed`）的 Run 中，`captures` 最后一页读到的位置之后接着读。

- 位置由平台记录（ADR-0039）：`captures` 读到旁听的每一页，Worker 在结果中写入读取位置（`ToolResult.capture_read`，模型看不到）；Run 完成时投影把本 Run 最后一页的位置提交到 `State.Captures`。接着读直接读投影，不扫描日志，也不解析给模型看的文字。没有读到任何旁听的页（"还在进行"、"已读完"）不带位置。
- 只认已完成的 Run：Run 读了一段交谈、还没交出就失败了，下一次会重新读到它，同一段交谈重复交出时取代之前的结果（[旁听按交谈整理](./captures-by-exchange.md) §3）。
- 模型不需要记住位置，也不依赖之前 Run 的上下文。

**进行中的交谈。** 读到日志末尾、而最后一段距现在不到交谈间隔（5 分钟）的交谈可能还在继续：`captures` 不返回它，只注明"交谈 x… 还在进行，稍后再整理"，读取位置也就不前进。这一条不只对 `"new"` 生效：白天整理时模型可能照抄页尾的位置接着读，同样不能读到进行中的交谈。`all: true` 时照常返回（深夜的整理、调试控制台读刚写下的旁听）。

- **"现在"取自平台的时钟。** 结果写入日志后，重放时使用记录下来的结果，与其他调用一样。

## 5. 每日流程

1. **白天。** 业务线服务端定时（如每 15 分钟，或 HostApp 报告停顿之后）向当天的旁听 Session 提交"整理交谈"。Run 用 `captures{after: "new"}` 一段段读已经结束的交谈，照第二版的做法交出（`find_projects`、`file_exchange`、`memory_save`），读到"已读完"或"还在进行"为止。没有新的交谈时，读一次就结束。
2. **深夜。** 业务线提交"整理今天"。Run 用 `captures{after: "new", all: true}` 读完余下的交谈并交出，再用 `day_exchanges` 取回全天交出的交谈，写当天总览与觉察（`file_day`）。
3. **归集与承诺不变。** 每段交谈一交出就进入承诺账本，业务线可以当天提醒；归集仍在 `file_day` 之后进行。

### 成本

- 白天每次整理都从头开始，模型只看到新的交谈，不再重复读已经交出的内容。
- 没有新交谈时，一次整理只有一次 `captures` 调用与一次回复。
- 业务线可以按 Session 的旁听数判断有没有新内容（`State.Captures` 的计数），没有新的旁听就不提交。

## 6. 评测与测试

- **`runtime` 单元测试。** `scope: run` 的 Transcript 不含之前的 Run，含当前 Run 内的插话与调用结果；之前 Run 的压缩摘要不进入，当前 Run 的进入；调用与结果的配对完整。
- **`capture` 与 `session` 单元测试。** `"new"` 从投影中已提交的位置接着读；失败的 Run 不提交位置；进行中的交谈被跳过、不带位置，`all: true` 时返回。
- **模拟测试。** 版本 2 的 AgentDef 改为 `scope: run`，同一批 Session 在两个版本之间切换，接受相同的不变量检查（调用配对完整、确定性回放、请求不超过窗口）。它发现了一个问题：模拟测试的窗口（3060）只比工具定义多几百 tokens，`captures` 的说明变长之后，"一次带两个调用的输出加上结果"压缩后仍放不下（调用与结果不能拆开压缩）。`captures` 的说明已压短，窗口调到 3200。
- **评测 `capture-daytime`。** 同一个 Session 三轮：
  - 第一轮：上午一段已结束的交谈和一段刚开始的交谈，"整理交谈"只交出前者；
  - 第二轮：再次"整理交谈"，不重复交出，也不读进行中的那段；
  - 第三轮："整理今天"交出余下的那段并写总览。

  评测运行器的旁听时间支持相对于运行时刻的 `now-Nm`。

## 7. 决定（2026-10-24）

第一条（白天谁触发）已由 ADR-0040 改为平台按 AgentDef 的声明触发，见 [输入、触发与外部循环](./m5-inputs-triggers-loops.md) §6；实现之前仍由业务线定时提交。

| 决定 | 选择 | 没有选的 |
|---|---|---|
| 白天谁触发 | 业务线定时提交"整理交谈"（编排在业务线，ADR-0037） | 平台在旁听写入、发现上一段交谈结束时自动开启 Run（改 ADR-0036 中"Capture 不开启 Run"） |
| 只看本轮的方式 | AgentDef 的 `context.scope: run` | 每段交谈一个独立的 Session（删除"某天"要删很多 Session，旁听也要分开写） |
| 进行中的交谈 | 最后一段过去 5 分钟才整理 | 立即整理，交谈继续后重交（同一交谈的结果会被反复取代） |
