# 卡片

> 状态：已实现（2026-10-11）· 依赖：[多端双工通道](./m3-duplex-channel.md)、[端侧 SDK](./m3-client-sdks.md)、[工件](./m2-artifacts.md) · 契约：[`event.proto`](../../proto/yanshi/v1/event.proto) `Card`、`CardAction` · ADR-0032

## 1. 目的

C 端对话里，很多结果用文字说不清楚，或者说清楚了也不好操作。例如：

- 订好的闹钟：时间、重复、设备，下面带"再加一个""取消"；
- 一段行程：路线、预计时间、天气；
- 几个候选的对比：图片、价格、评分，点一个继续；
- 一张简单的表单：确认前改一下时间、选一下重复方式。

卡片是 Agent 展示这类内容的方式。它要满足下面几点：

- 在三个 SDK、多台设备上一致地出现；
- 被模型理解；
- 和其他交互一样经过校验、内容安全检查与去重。

## 2. 卡片（`Card`）

| 部分 | 说明 |
|---|---|
| `card_id` | Session 内标识一张卡片。模型可以指定；省略时由调用 ID 生成。同一 ID 再次展示时替换前一版 |
| `call_id` | 展示这一版卡片的 `show_card` 调用 |
| `title`、`subtitle`、`image` | 标题必填；头图是 `artifact://<id>` 或 `icon:<名称>` |
| `body` | 至多 20 个元素：`markdown`、`image`、`facts`（键值）、`list`（条目可点选）、`field`（text / number / date / time / select / toggle） |
| `buttons` | 至多 6 个，`style` 为 primary / default / danger |

图片只能是本 Session 的工件或内置图标（`card.Icons`）。外部地址可以用来追踪用户，也不随 Session 删除，所以不允许。

Markdown 由客户端只渲染安全的子集：不执行 HTML，链接只允许 `https:` 与 `artifact://`。

## 3. 展示：`show_card`

`show_card` 是进程内的内置能力，在 AgentDef 白名单中写 `show_card`。模型以 JSON 给出卡片，`body` 的元素以 `type` 区分。平台的处理分三步：

1. 校验参数：上限、ID 格式、图片归属、select 的初始值必须是选项之一。不合法时把错误交还模型改正。
2. 校验通过后，把规范化的 `Card` 与一行说明（"已展示卡片 alarm（闹钟 07:00）"）作为调用结果写入日志。
3. 客户端从事件流里的结果读出卡片并渲染（`Cards` / `CardOf`）。

还有三点需要注意：

- **内容安全。** 卡片文字是调用参数，与回复文本一起在写日志之前检查（ADR-0021）。
- **只能由平台写入。** `session.Apply` 只接受 `show_card` 的、由 Worker 写入的结果中带卡片。设备结果、用户输入中的卡片都被拒绝。
- **不阻塞。** 展示即返回，Run 继续。必须等用户回答才能继续时用 `ask_user`，它的选项可以带 `image`，客户端以卡片样式渲染提问。

模型看不到卡片本身，只看到那一行说明。卡片的内容就是模型自己写的参数，重复放进上下文只会占用窗口。

## 4. 动作：`CardAction`

用户在卡片上点按钮或点选列表项时，客户端提交一条输入，其中带一个 `CardAction`：

- `card_id`、`call_id`、`action`；
- `values`：卡片上字段的填写值；
- `seq`：收到这一版卡片的事件序号。

SDK 的方法分别是 `submitCardAction`（网页）、`SubmitCardAction`（Go 与移动端）。

`service.submit` 在其他检查之前先处理卡片动作：

1. **按日志中的那一版卡片核对。** 有 `seq` 时只读那一条事件，否则扫描日志。动作必须是卡片上的按钮或可点选的列表项。字段只能是卡片声明过的，值要符合字段类型；按按钮时必填字段要填。
2. **填写显示文字。** `label` 取自卡片，客户端提交的值被忽略。模型看到的是"[卡片动作] 用户在卡片 alarm 上选择了「好的」（动作 ok），填写：repeat=工作日"。
3. **推导输入 ID**：由 `call_id` 与动作推导。同一版卡片上的同一动作只生效一次，与点了几次、在几台设备上点无关；重复点击返回 `duplicate`。
4. **之后与普通输入相同。** 有进行中的 Run 时并入它；Run 正在等回答时作为回答；否则开启新 Run。内容安全检查覆盖填写的值，准入与配额也照常检查。

## 5. 客户端

- **渲染**：调试控制台的 `static/console/cards.js` 是参考实现，与 DOM 无关的部分（收集卡片、组装动作）在 SDK 中。
- **替换**：同一 `card_id` 只显示最新版。旧版本仍在日志里，回看历史时可以展开。
- **点过的动作**：动作提交后，客户端把该版卡片的按钮显示为已选。其他设备从事件流里看到这条输入（`Steered` 或 `RunRequested` 中的 `CardAction`）后同样更新。
- **`ask_user` 的提问**以卡片样式渲染：问题是标题，选项是可点选的列表项（带说明与配图），字段与"提交"按钮在下方。回答走 `answer`，不是卡片动作。

## 6. 验证

| 层 | 覆盖 |
|---|---|
| 单元测试 | `internal/card`：参数校验、动作核对、输入 ID；`internal/service`：核对、标签、去重、并入或开新 Run；`session.Apply` 拒绝伪造的卡片 |
| 模拟测试 | 模型随机展示卡片（含不合法的参数、替换同一 ID），客户端随机点按钮、连点两次（`Cards`、`CardActions`、`CardDuplicates`） |
| 控制台场景 | "卡片"：展示、替换、点按钮、两台设备连点只生效一次 |
| 评测 | `card-*`：结构化结果用卡片展示、卡片动作驱动后续操作、需要等待时用 `ask_user` 而不是卡片 |
