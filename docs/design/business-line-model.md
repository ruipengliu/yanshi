# 业务线模型：内核承接业务线的规范

> 状态：**草稿**（2026-11-28），Claude 起草，经 Gemini（gemini-4-neon-xhigh）独立方案与对照评审两轮整合，方向已由负责人批准、未定稿、未实现 · [ADR-0067](../adr/0067-business-line-model.md)（保护域、清单、命名空间与契约）、[ADR-0068](../adr/0068-business-line-draining-and-offboarding.md)（停用与卸载）、[ADR-0069](../adr/0069-cross-line-delegation.md)（跨业务线委托）、[ADR-0070](../adr/0070-eval-adapter-protocol.md)（评测适配协议），均为"方向，待定稿" · 依赖：[Persona 架构](./persona-architecture.md)（ADR-0043）、[鉴权](./auth.md)（ADR-0014）、[M7 内核原语](./m7-kernel-primitives.md)、[M7 Agent 生态](./m7-agent-ecosystem.md)（ADR-0048）、[输入、触发与外部循环](./m5-inputs-triggers-loops.md)（ADR-0062）、[委托](./m5-multi-agent.md)（ADR-0031、ADR-0058）、[Session 生命周期](./m2-session-lifecycle.md)（ADR-0015）、[部署](./deployment.md)

## 0. 结论

内核要承接多条业务线，就要由内核给出"业务线是什么"的规范，而不是由第一条业务线（xinli）的实际做法倒推。本文的定义：

- **业务线是内核之上的一个不受信任的保护域**：内核独占执行语义、来源推导、内容安全、审批、配额与物理删除；业务线只能通过内核开放的接口与声明影响执行，权限只收紧、不放大（§2）。
- **一条业务线 = 一份清单 + 业务侧服务**：清单在一个目录里声明身份、策略、自有的定义与对外导出；业务侧服务（BFF、领域存储、MCP 能力、外部循环、出站消费）运行在内核进程之外（§4）。
- **三个流程的边界**：输入在内核外处理、经统一检查点进入内核；推理由内核运行声明式循环，或由业务线的外部循环决策、内核执行动作；输出在内核审核写日志后，由业务侧消费出站流处理（§5）。业务代码不进入内核的提交路径（§3）。
- **业务线之间只有两种交互**：调用对方导出的 Agent（跨业务线委托），经 Grant 读取对方的 Memory。不直接调用对方的工具（§7）。
- **生命周期是一等概念**：接入、升级、停用（可逆的排空）、卸载（不可逆、清除数据）（§8）。

## 1. 目标与要求

目标：把分布式 personal agent 系统中复杂的部分沉淀在内核——分布式任务（持久化、排队、重试、接管、幂等）、端到端交互（多端连接、审批与提问、增量、送达）、数据处理（来源与信任、内容安全、删除、配额）——让业务线只关注业务数据流与推理链路，轻量、灵活、快速迭代。

要求：

1. 内核主动提出明确的业务线规范，机制清晰、尽量灵活。
2. 抽象在业务线这一层成立，不以 xinli 为模板；xinli 是第一个使用者。
3. 不等第二条业务线出现再设计：规范是内核既有职责的完善（ADR-0043 的 2026-11-14 修订，见 §10）。
4. 覆盖三个基本流程：输入处理、推理计算、输出处理。
5. 业务线之间的交互（调用、数据共享）纳入规范。

## 2. 参考模型

评判标准：① 内核不变量不放松（AGENTS.md"不变量"）；② 同一单元内互不信任的业务线彼此隔离；③ 三个流程上的灵活性（业务线可用任意语言与框架）；④ 跨业务线组合时权限单调收紧；⑤ 私有化部署时单进程仍能运行，`internal/sim` 仍能验证。

| 模式 | 能对上的 | 对不上的 | 在本模型中管哪一层 |
|---|---|---|---|
| 微内核 + 能力安全 | 内核执行不可绕过的闸门，业务在"用户态"；能力白名单取交集、委托不扩大权限（ADR-0031、ADR-0060） | 本身不涉及打包与发布 | **主干**：保护域、闸门、跨业务线的权限 |
| 持久化执行（Temporal 一类） | Run 对应工作流执行，工具调用对应带幂等的 activity，输入对应 signal，外部循环的步令牌对应 task token | 要求业务方写确定性的工作流代码；LLM 推理本身不确定；没有来源与信任模型 | Session / Run 的执行语义（内核内部，已有） |
| 应用清单与导出组件（Android） | 清单声明组件与权限，组件显式导出才可被其他应用调用，卸载时清除数据 | Slack、Shopify 一类 SaaS 平台预设平台统一身份与 webhook 推送，与业务线自签令牌（ADR-0014）、出站流拉取（ADR-0046）不符，只借清单与导出语义 | 打包、导出、生命周期 |
| 端口与适配器 | 业务线的输入、输出处理就是边界上的适配器 | 只描述边界形状 | 三个流程的边界 |
| Actor / 虚拟 actor | Session 有身份、信箱、单写者 | 业务线是上百万 Session 的治理域，不是一个 actor；actor 的私有内存状态与任意消息，与"状态只来自事件日志"、来源推导冲突；Akka 默认最多一次投递 | 只作理解 Session 的辅助视角，不进规范 |
| 事件驱动与流处理 | 出站消费、渠道投递 | 没有长期 Session、审批、挂起 | 业务侧适配器的实现方式，不进规范 |

## 3. 硬边界：业务代码不进入内核的提交路径

内核内部只接受业务线的**声明**（策略、白名单、定义）。业务线的**代码**只在边界上运行：提交输入之前、工具回调（MCP）、外部循环的一步、上下文策略（ADR-0056，可选）、消费出站流时。原因：

- `Worker.Step` 是确定性的单步，`internal/sim` 依赖它在任意两步之间注入故障；
- 来源由平台从事件推导（ADR-0052）：业务代码一旦能改写输入或输出，就能把外部内容洗成"用户原话"；
- 故障域：业务代码的崩溃、泄漏、慢调用不能变成内核的故障。

被否决的入核形式：

| 形式 | 结论 | 理由 |
|---|---|---|
| 进程内钩子（Go 插件、回调） | 否决 | 打破隔离与故障域，锁定 Go |
| 沙箱化函数（复用云端沙箱） | 否决 | 沙箱无网络（ADR-0008、ADR-0053），访问不了业务库与 API；冷启动慢；沙箱只运行不可信的模型代码 |
| 嵌入式 WASM 纯函数 | 暂不做，留作远期选项 | 能隔离、计步、确定，但无 I/O，覆盖不了多数业务；只有实测某个高频、零 I/O 的纯变换因网络往返突破延迟目标时再立项，其输出仍须经内核审核与来源推导 |

进程外调用的往返（内网毫秒级）相对模型推理（百毫秒到秒级）可以忽略。

## 4. 一条业务线的组成

### 4.1 清单

一条业务线一个目录，收拢目前分散在 `businesslines/*.yaml`（`auth.BusinessLine`）、`mcp/*.yaml`（`internal/mcpcap`）、`-agents` / `-oneshots` 多目录与各自的 `releases.yaml`、`-loops` 目录（`cmd/yanshi/serve.go` 的参数定义）中的配置。示意布局（名称待定）：

```
lines/<业务线>/
  manifest.yaml      身份、策略、MCP 与外部循环登记、导出
  agents/            本业务线的 AgentDef 与 releases.yaml
  oneshots/          本业务线的 Oneshot 与 releases.yaml
  evals/             用例与基线
```

`manifest.yaml` 的内容：

| 部分 | 字段（示意） | 现状对应 |
|---|---|---|
| 身份 | 名称、公钥、`identity_domain`、生命周期状态 | `auth.BusinessLine` 的 `keys`、`identity_domain`（ADR-0064） |
| 策略 | 保留期、健康类同意开关、档位与配额、Oneshot 并发上限 | `auth.BusinessLine` 的 `memory`、`oneshots`；保留策略；`internal/usage` 的档位 |
| 能力登记 | MCP Server、外部循环服务、可选的上下文策略服务 | `internal/mcpcap` 的登记、`-loops` |
| 导出 | 对其他业务线开放的 Agent 及其暴露方式（§7.5） | A2A 入站的 `a2a_inbound`（[M7 Agent 生态](./m7-agent-ecosystem.md) §3.2） |
| 引用 | 本业务线使用的其他业务线导出（§7） | 无 |
| 执行资源 | 可选的专属 Worker 池 | `-worker-business-lines` |

单元级的配置不进清单，仍由运维独占：价格表、分片表、步令牌密钥、单元的 MCP 出网白名单。

清单配 JSON Schema 与离线校验命令（与现有的启动校验共用代码），在 CI 中运行。

### 4.2 定义的归属与命名

现在 AgentDef 与 Oneshot 的名字是全局命名空间，归属只靠业务线配置的 `allow`（ADR-0060），两条业务线不能各有一个 `assistant`，也不能各自独立发布与撤回同名定义。改为：

- **目录即归属**：定义只能出现在所属业务线的目录里；业务线只能使用自己的定义、显式共享的定义（`shared/`，由单元运维维护）与它引用的其他业务线导出。
- **规范名 `<业务线>/<名>`**：新写入日志的 `SessionCreated.agent` 等字段用规范名；旧的无前缀名作为别名继续解析，历史日志照常重放（ADR-0004）。
- `allow` 列表在过渡期保留，之后由"目录即归属 + 引用"取代。

### 4.3 内核侧的运行态

内核按清单装配每条业务线的一组状态，全部在 `app.NewCore` 中构造：令牌校验、按业务线隔离的定义、MCP 与外部循环登记、配额与同意闸门、出站流过滤、可选的专属 Worker 池。这些都是参数化的通用机制，不含业务代码。

### 4.4 业务侧的运行态

运行在业务线自己的进程中、语言不限：BFF 与短令牌签发（ADR-0014）、领域存储（Persona 是一种可选范式，不是必需）、MCP 能力服务、可选的外部循环与上下文策略服务、出站流的消费与投递、跨 Session 的编排。

## 5. 三个流程

| 流程 | 业务线做什么（内核外） | 内核做什么 | 边界 |
|---|---|---|---|
| **输入处理** | 渠道与采集适配、识别（语音、图片、webhook）、按删除粒度划分 Session（[生命周期](./m2-session-lifecycle.md) §3.1）、以幂等键与 `input_id` 提交 | 统一检查点（`internal/service/checkpoint.go`）：验签、拒绝只能由平台写入的字段、去重、输入审核（ADR-0021）、准入与配额、来源推导、日志与队列同事务提交并唤醒；定时与触发（ADR-0045）；输入状态查询（ADR-0066） | 提交 Input 的那一刻 |
| **推理计算** | 选择推理方式并提供：声明式的 AgentDef、外部循环服务、MCP 工具、可选的上下文策略 | 三级推理：**单次调用**（Oneshot，无 Session，ADR-0047）、**内置循环**（AgentDef 的 `model`，前缀缓存最好）、**外部循环**（AgentDef 的 `loop`，外部只决策、内核执行动作并写日志，ADR-0062；外部服务的模型调用经步令牌回到内核模型端点，ADR-0063）。工具、设备、沙箱、委托、`ask_user` 一律经内核路由，审批、重投递、审核统一处理 | 外部循环的一步、MCP 调用、上下文策略调用 |
| **输出处理** | 消费出站流或事件流，投递到渠道、推送；跨 Session 编排；在 MCP 调用中完成领域事务 | 写日志前的输出审核（ADR-0021）、卡片校验（ADR-0032）、Memory 写入闸门与条件审批（ADR-0023、ADR-0061）、增量推送、与日志同事务写出站信封（ADR-0046） | 出站流的游标 |

上下文策略（ADR-0056 A 期，已定稿、未实现）是内置循环与外部循环之间的中间档：保留内置循环的低延迟与前缀缓存，同时让业务线按 Run 选择上下文材料。它列为推理端口的可选扩展点，按 ADR-0056 的重审条件实施。

## 6. 契约

按调用方向分两类，治理方式不同：

**业务线调用内核（入向）**：建 Session、提交输入、定时、回答与审批、输入状态、出站流、Memory 与 Grant、EndUser 删除、单次调用、用量与配额等，目前是 `internal/httpapi` 中约 46 个服务令牌路由，请求与响应多为手写 JSON，没有机器可读的 schema；xinli 用手写客户端 `apps/xinli/kernel`。

- 请求与响应补上 `proto/` 中的消息定义（2026-11-28 负责人决定，§12 第 1 项），沿用 ADR-0006 的工具链与 `buf breaking`；JSON 线上格式用 `protojson` 的 `UseProtoNames` 保持现有的 snake_case，二进制体与 SSE 路由在契约文档中单独说明。由 proto 生成官方服务端 SDK（先 Go、后 Python；封装令牌刷新、幂等键、错误码与重试、出站流游标的恢复），xinli 迁移到同一 SDK。
- 不另建入向的一致性套件：入向行为由内核自己的 `authz_test.go`、e2e 与 `internal/sim` 保证，再建一套属于重复。

**内核调用业务线（出向）**：外部循环、MCP、上下文策略、评测夹具。这些由业务线实现、内核消费，**每一种都配黑盒一致性套件**：

| 出向接口 | 契约 | 一致性套件 |
|---|---|---|
| 外部循环 | `proto/yanshi/v1/loop.proto`（ADR-0062） | 已有 `internal/extloop/looptest` |
| MCP 与 yanshi 扩展（`_meta` 的身份、`yanshi/captures`、`yanshi/page_options`、`yanshi/page`） | 现在只有文字（[旁听](./captures.md) §12），Persona 自行复刻（`persona/mcpserver`）。先用语言无关的 JSON Schema 冻结线上格式，再由各语言 SDK 封装类型 | 新增，校验身份元数据、分页选项与结构化页 |
| 上下文策略 | ADR-0056 | 随 ADR-0056 实施时新增 |
| 评测夹具 | 现有夹具契约（[Persona 架构](./persona-architecture.md) §3.4、Q33） | 随评测适配协议（§10）新增 |

**参考业务线**：在仓库中建一条最小的参考业务线（不用 Persona，只用外部循环与 MCP，业务很简单），覆盖全部接口，接入 `make check` 与 `internal/sim`。它同时是规范的可执行示例、出向套件的被测对象、新业务线的脚手架，也是"规范没有被 xinli 绑住"的反向验证。

## 7. 业务线之间的交互

只有两种，都经内核中转：

### 7.1 调用：跨业务线委托

A 的 Run 调用 B 导出的 Agent：内核在 B 名下建子 Session，由 B 的 AgentDef 处理，结果写回 A。复用委托的全部机制：路由调用、能力交集、相邻委托并行与 `max_fanout`、工件复制交接（ADR-0055）、后台转交（ADR-0058）、追踪的 `link_trace_id`（ADR-0065）。异步联动（A 的结果触发 B 做事）用后台委托实现，不在内核中另建业务事件订阅。

这取代 ADR-0031 中"委托不跨业务线"的限制（现在 `internal/delegation/delegator.go` 中子 Session 沿用父 Session 的业务线），兑现 [M7 Agent 生态](./m7-agent-ecosystem.md) §4 与 Q25 的预留。

### 7.2 数据：经 Grant 读取 Memory

沿用 ADR-0003 与 ADR-0064：只读、撤销即时生效、记录访问；只在同一身份域内。业务领域数据（例如 Persona）经业务线自己的对外 MCP 与 OAuth 共享，内核不代管业务库。工件不共享引用，一律复制交接。

### 7.3 不开放的交互

- **不直接调用对方的工具**：A 的模型直接驱动 B 的 MCP 写入，会绕过 B 自己的 AgentDef、写入闸门与审批策略。A 要 B 做事，只能请 B 的 Agent 去做。
- **不用服务令牌代表对方**：A 的服务令牌不能以 B 的身份提交输入。业务侧之间若要联动，A 调用 B 自己的业务 API，或经 A2A 入口。

### 7.4 跨业务线调用的规则

| 方面 | 规则 |
|---|---|
| 身份 | 只在两条业务线声明了相同的非空 `identity_domain` 时走平台内委托；子 Session ID 按 EndUser 的槽位派生（ADR-0051），只有同一身份域才能保证父子是同一个人。不同身份域或不同单元一律视为三方，走 A2A 与 OAuth（ADR-0048） |
| 授权 | 三道条件都满足：B 在清单中导出了该 Agent；A 在清单中引用了它、并在 AgentDef 白名单中列出（`agent:<业务线>/<名>`）；EndUser 给过调用授权（Grant 从 Memory 类别扩展出 `kind: delegate`） |
| 权限 | 子 Run 的能力 = B 的 AgentDef 白名单 ∩ B 导出时声明的能力上限 ∩ A 方各祖先的白名单 ∩ 用户授权；不把 A 的 MCP 与 Memory 透传给 B |
| 来源与信任 | 双向都是外部内容：B 收到的任务由 A 的模型写成，不是用户原话；A 拿到的结果来自 B。听过他人旁听的 Session 不能跨业务线委托（[M7 Agent 生态](./m7-agent-ecosystem.md) §5） |
| 审批与提问 | 子 Run 发起的审批与提问在调用方的端上显示时必须标明来源业务线，防止冒充 |
| 计量与配额 | 默认记在执行方 B，同时记录调用方业务线（只记 ID，供对账）；B 可在导出时为每个调用方设置预算或速率上限。调用方付费以后有明确需求再加 |
| 删除 | 子 Session 的删除期限不晚于父 Session；父 Session 删除时，Janitor 的 `deleteChildren`（`internal/janitor/janitor.go`）跨业务线删除子 Session 及其工件副本；EndUser 注销按业务线清理并撤销双向 Grant。纳入 `internal/sim` 的删除不变量并运行 `make verify` |
| 故障隔离 | 对 A 而言，B 不可用就是一次失败或超时的调用结果，走既有调用语义；B 的负载经专属 Worker 池与并发上限隔离 |

### 7.5 导出与 A2A 入站共用一种声明

清单中的导出同时描述"给其他业务线委托"和"给三方经 A2A 调用"两种暴露方式，共用一份 Agent 描述（Agent Card 由它生成），但按暴露方式分别做加载校验：A2A 入站的 AgentDef 必须 `memory.recall: 0`、`context.scope: run`、白名单中没有 `captures`、`memory_save` 与 `a2a:*`（[M7 Agent 生态](./m7-agent-ecosystem.md) §3.2）；同一身份域内的委托专员可以召回本业务线的 Memory。

## 8. 生命周期

```
validated ──接入──▶ active ⇄ draining ──确认──▶ offboarding ──清理完成──▶ purged
```

| 阶段 | 语义 |
|---|---|
| **接入** | 提交业务线目录 → CI 运行清单校验、出向一致性套件与评测基线（ADR-0020）→ GitOps 发布到目标单元 |
| **升级** | 定义的灰度与撤回沿用 `releases.yaml`（[灰度发布](./m4-agent-rollout.md)）；公钥追加轮换（ADR-0014）；删档位前先迁移用户（[M7 内核原语](./m7-kernel-primitives.md) §8） |
| **停用（draining，可逆）** | 按操作拒绝：新 Session、新 Oneshot、新的入站跨业务线委托、新的定时触发与外部循环步令牌签发；存量 Run 收尾；读接口、出站流、删除与用量查询保持可用，以便排空与对账；跨业务线 Grant 立即失效 |
| **卸载（offboarding，不可逆）** | 见下文 |
| **purged** | 清理完成，才允许从配置中删除该业务线；启动时发现有未到 purged 的业务线被删除配置，拒绝启动 |

停用不能用"拒绝新令牌"实现：令牌校验是无状态的（`internal/auth/auth.go`），分不清新旧令牌；拒绝服务令牌还会堵死出站流的排空与删除查询；无令牌的定时触发与不经业务线令牌中间件的步令牌也拦不住。所以停用是按操作的检查。

**卸载**：

1. 在控制库写入持久的业务线删除屏障（与 EndUser 删除屏障同理，[M7 内核原语](./m7-kernel-primitives.md) §12），全部写入入口经 `lifecycle.Recheck` 一类的复查拒绝写入；撤销公钥。
2. Janitor 不再依赖保留策略配置（现在保留策略只遍历已配置的业务线，`internal/janitor/janitor.go` 中 `Retention` 的循环，删除配置后数据无人清理），按分片分批删除该业务线的全部 Session（复用 `app.SessionData` 与 `deleteChildren`），并清理按 EndUser 分片的业务线数据：Memory、Grant、档位、同意、Node 与 Inbox、推送登记（`pg.Tables` 中 ByEndUser 一类）。每个事务只涉及一个分片键（ADR-0028）。
3. 用量不物理删除：按 ADR-0019 匿名化，保留到对账期满；出站流的删除信封按出站保留规则淘汰（[M7 内核原语](./m7-kernel-primitives.md) §6）。
4. 全部清理完成后进入 purged。

**热加载分级**：`releases.yaml` 保持现有的 10 秒热加载；停用开关、配额、公钥追加、`allow` 收紧这类应急与软限制字段扩展为同样的快照热加载（失败保留旧快照）；定义文件、MCP 与外部循环登记、令牌密钥、价格表仍走 GitOps 滚动发布——它们牵涉 Worker 与网关之间的强一致（[部署](./deployment.md)），业务线在数十条以内时 GitOps 加评测门禁比控制面数据库更安全。

## 9. 同一单元内多业务线的隔离

- **节点唯一键**：`nodes` 的唯一键是 `(end_user, node_id)`，不含业务线（`internal/pg/migrations/0035_nodes_end_user_key.sql`）。ADR-0064 第 5 条把它列为残留风险（不同身份域的同名 EndUser 使用相同 `node_id` 时后注册方被拒绝，不会泄露数据）。多业务线规范落地时按它的重审条件改为包含业务线或身份域。
- **出站流水位**：同一个库里任何一条业务线的长事务都会拖住全部业务线的出站流水位（[M7 内核原语](./m7-kernel-primitives.md) §6）；在线角色须设置语句与空闲事务超时。
- **吵闹的邻居**：数据库 IOPS 与模型速率还没有跨副本的公平隔离；高敏感或高负载的业务线应独立成单元（代价：不能跨单元共享 Memory，ADR-0003）。

## 10. 与现有原则的关系

- **ADR-0043**：2026-11-14 修订明确，"第二条业务线也需要"的判据只约束业务能力进入内核，不约束内核既有职责的完善。本文的清单、命名空间、生命周期、契约与 SDK 都是内核承接业务线的职责，不引入业务实体；定时、出站流、单次调用、`attests_speakers` 在清单中是可选项，不强加给其他业务线。
- **ADR-0031**：跨业务线委托取代其中"不跨业务线"的限制，需新 ADR。
- **ADR-0060**：`allow` 列表由"目录即归属 + 引用"逐步取代，入口检查的位置不变。
- **ADR-0064**：沿用身份域边界；按其重审条件修改节点唯一键。
- **评测**：xinli 的评分代码有意留在 `internal/eval`（被测方不给自己打分）。通用的评测适配协议要把"评分进程与被测业务进程分离"写成原则，修订 [Persona 架构](./persona-architecture.md) §3.4 与 Q33 的"夹具不提供 Check"：断言可以由业务线提供，模型、时钟、评判调用与基线比较仍由内核掌控。需新 ADR（参考 `docs/review/2026-11-27-eval-xinli-decoupling-study.md`）。
- **内核不变量**：事件日志是唯一事实源、`Worker.Step` 确定性、来源由平台推导、物理删除与复查、一个事务只涉及一个分片键、请求前缀稳定、全部角色合在一个进程中仍能运行——全部不放松。

## 11. 落地顺序

1. **本设计定稿与 ADR**：业务线清单与定义命名空间；业务线的停用与卸载；跨业务线委托（取代 ADR-0031 的限制）；评测适配协议。
2. **清单、命名空间与生命周期**（第二条业务线写入生产数据之前必须完成）：清单与校验命令（兼容旧目录）；规范名与别名；停用与卸载（删除屏障、Janitor 按业务线清理，接入 `internal/sim` 的删除不变量与 `make verify`）；节点唯一键；应急字段热加载；参考业务线骨架。
3. **契约**：入向路由的 schema 与 Go、Python 服务端 SDK；MCP 扩展的 JSON Schema 与一致性套件。
4. **迁移**：参考业务线补齐全部接口；xinli 迁移到同一 SDK。
5. **按需**：上下文策略（ADR-0056）、同身份域的跨业务线委托、评测适配协议的实现。

## 13. 评审记录

- 第一轮：只给 Gemini 目标、要求与现状，独立提出方案。它以"微内核 + 能力安全"为主干，提出分级推理、停用与卸载状态机、删除屏障、分级热加载，以及节点唯一键与出站流水位两个隔离风险。
- 第二轮：对照 Claude 的方案（以 SaaS 应用平台为主干）评审。采纳 Gemini 的：主干改为微内核 + 能力安全，只借应用清单的打包与导出语义；停用按操作检查而不是拒绝令牌；用量匿名化保留、不物理删除；导出与 A2A 入站共用描述、分层校验；入向不另建一致性套件；`_meta` 先用 JSON Schema 冻结；补上上下文策略扩展点与否决入核形式的论证。保留 Claude 的：最小参考业务线；跨业务线不直接调用对方工具；落地顺序先生命周期后契约（双方最终一致）。唯一的分歧（§12 第 1 项）由负责人决定采用 `proto/`。
- 事实核对：Gemini 引用的 `-worker-business-lines`、`deleteChildren`、ADR-0043 修订、ADR-0064 第 5 条、出站流水位、用量匿名化均已核对原文；它关于"protojson 默认 lowerCamelCase 所以不宜用 proto"的论据不成立，现有事件接口已使用 `UseProtoNames`。
