# xinli 的建模：实体、变更集与交谈

> 状态：已实现（2026-10-25；实现见 `internal/xinlimock`，流程与工具见 [captures-xinli.md](./captures-xinli.md)） · ADR-0042 · 来由：[评审：用一个完整工作日模拟验证 xinli](../review/2026-10-25-xinli-workday.md) §6–§8 · 依赖：[旁听业务线 xinli](./captures-xinli.md)、[旁听](./captures.md)（ADR-0036、ADR-0037）、[Memory 与 Grant](./m4-memory-grant.md)（ADR-0038）· 实现时：改写 captures-xinli.md 的 §2–§6、§12 与 captures.md §5，按 §3 改 `CONTEXT.md` 中交谈的定义

## 1. 为什么改

现在的 xinli 以交谈为身份：平台按 5 分钟停顿切出交谈，交谈 ID 由切分位置派生；`file_exchange` 以它为键，摘要、项目归属、承诺都挂在交谈上，重交也只能取代同一段交谈。评审的几项主要发现都出自这里：

- **切错改不了**（F2）：相隔四五分钟的两通电话并成一段，法务的事随之归进绿源，失眠混进这段的摘要。五种模型配置都栽在这里。
- **一段只能归一个项目**（F4）：老板一次谈三件事，怎么归都错。
- **承诺无法跨交谈修改**（F1）：改期、换人后旧承诺一直 open，五种配置 20/20；新旧承诺同在一个上下文里也一样，缺的是写入手段。

切分本身也做不好：设备收不到手机通话，一通电话在旁听里只有佩戴者一侧的独白；同一批人换了话题，停顿与说话人都看不出来。任何从信号推出的切分都会出错，所以模型须容许切分出错、事后改正，不能让下游的身份建在它上面。

## 2. 原则

1. **原文不可变，引用编号是地址。** Capture 与 `#57.3` 由平台保证，不变。
2. **知识按实体维护，以变更集写入。** 承诺、交谈、项目各有稳定的 ID；一次整理交出一个变更集，其中每个操作都引用依据的原话。
3. **不改写历史。** 改期、作废、合并都记为新的修订，旧的保留并指向新的（与 ADR-0038 对 Memory 的做法相同）。已经按旧期限发出的提醒仍有据可查。
4. **宁可少合并。** 错误的合并修不回来，重复可以事后收拾：切分宁可切碎、由当天整理合并；两条承诺拿不准是否同一件事时不动作。
5. **确定的事确定地做。** 日期换算、说话人核对、健康内容检查、同日重复的候选，由业务线按规则做；模型只做判断。
6. **就近修订，空闲时做。** 有新原话为据的改动（改期、作废、完成）在用户空闲时触发的整理里就做，提醒随之更正；没有新原话、要全天视角的整理（合并重复、合并交谈、改正归属）留给当天最后一次。负载随各用户的作息分散，不集中在深夜。
7. **边界不变**（ADR-0037）：实体与变更集由业务线保存；平台只提供 Capture、引用编号、读取位置与引用核对。

## 3. 术语（已写入 `CONTEXT.md`）

- **时段**（新，平台）：相邻两段说话时间相隔不超过间隔的一段连续旁听，平台按停顿确定性地切出，是 `captures` 分页与判断"是否已结束"的单位。它就是现在 captures.md §5 的"交谈"，改名后只承担分页，不再承担语义。
- **交谈**（Exchange，改义，业务线）：一段谈话，由整理的模型在旁听上划定范围 `[from, to]` 交给业务线；是摘要、时间线与"今日"页的单位，可以关联多个项目，可以被合并。承诺不以它为身份。
- **变更集**（Changeset，新，业务线）：一次整理交给业务线的一组操作（新建交谈与承诺、修订或关闭承诺、合并），附来源与作者；按来源去重，重交时整体取代上一次。
- **修订**（Revision，新，业务线）：承诺的一次改动（期限、内容、对方、状态），带依据、说话时间与记录时间。

## 4. 实体

**承诺**是一条带状态机的记录，当前状态由它的修订依次叠加得出：

```
Commitment {
  id: "C-0012", kind: mine | theirs, content, counterpart,
  due: {date?, text?},                 // 期限是截止时刻，不是生效时刻
  project?, exchange,                  // exchange 只是出处，用于展示
  status: open | done | cancelled,
  merged_into?: "C-0031",              // 被判定为重复时指向保留的那条，不参与提醒
  revisions: [{changeset, fields, refs, reason, spoken_at, recorded_at}]
}
```

- 改期、改内容、换对方都是 `revise`，ID 不变。提醒总是按当前状态：改期后按新期限，作废或合并后停止。
- "钢琴课改由爱人送"是佩戴者的承诺被 `close: cancelled`，理由写明转交；爱人的安排不是佩戴者与他人之间的承诺，不新建。
- 核对规则照旧（captures-xinli.md §6）：`mine` 至少引用一段佩戴者的话，`theirs` 至少一段他人的话，否则未核实、不提醒。

**交谈**：

```
Exchange {
  id: "x57.0",                         // 取自 from，由模型划定，不再由平台切分派生
  from: "#57.0", to: "#63.4",          // 同一旁听 Session 内的范围
  title, summary, decisions, risks, awareness,
  projects: [{match, id?, name?}],     // 可以多个；四档归属照旧（captures-xinli.md §5）
  merged_into?: "x52.0"
}
```

**项目**不变；时间线由关联到它的交谈与逐项带 `project` 的决定、承诺组成。

**人**这一版不建模：`counterpart` 仍是按原话的称呼。语音识别只能区分一批之内的不同的人（`speaker_key`），不能指出是谁，建了模也无从可靠地把称呼与说话人对上。当天整理判断重复时由模型结合上下文判断"黄总"与"黄总监"是否同一人；称呼对不上而漏召回、漏合并的失败案例攒够之后再定（§12）。

## 5. 变更集

### 结构

`file_exchange` 换成 `file_changes`：

```
{
  source: {from: "#57.0", to: "#80.2"},       // 这次依据的旁听范围；"整理今天"的当天整理为 {day: true}
  exchanges: {
    create: [{from, to, title, summary, projects, decisions: [{text, project?}], risks, awareness}],
    merge:  [{into: "x52.0", from: ["x57.0"], title, summary, projects?}],   // 只在当天整理中
    revise: [{id, title?, summary?, projects?}]                             // 只在当天整理中：改正归属
  },
  commitments: {
    create: [{id?, exchange: "x57.0", kind, content, counterpart, due_date?, due_text?, project?, refs}],
    revise: [{id, rev, due_date?, due_text?, content?, counterpart?, project?, refs, reason}],
    close:  [{id, rev, status: done | cancelled, refs, reason}],
    merge:  [{into, from: [id], reason}]                                             // 只在当天整理中
  }
}
```

- 承诺的 `project` 缺省时随所在交谈；交谈关联了多个项目时必填。
- 当天整理"改正归属"（§6）用 `exchanges.revise` 改交谈的 `projects`、用承诺的 `revise` 改 `project`（实现时补上的两个字段：原先的结构里没有改正归属的写法）。
- `rev` 是模型看到的修订序号（`find_related` 与 `day_ledger` 给出）。账本里这条承诺之后又被改过（用户在 App 中改了，或另一次整理改了），这个操作就被拒绝，结果附上当前状态让模型重新判断：与 `session.Store.Update` 的乐观并发同理。
- **按来源去重**：键是（旁听 Session，`source.from`），当天整理的键是（旁听 Session，day）。同一个键再交一次，业务线撤销上一次的全部效果、再应用新的。Run 被接管或重试时安全，与现在按交谈取代的保证相同，只是键从平台的切分换成了模型交出的来源。
- **重交时承诺 ID 的沿用**：创建项与旧变更集中的创建项以同一 `kind`、`refs` 至少有一个相同的原话编号（`#seq.index`）对应，只在双向唯一时沿用旧 ID，不按数组位置或内容措辞猜。创建项可用 `id` 显式指定这个 source 上次新建的承诺，优先确定对应；同一个旧 ID 不能重复使用，不能指定其他来源的 ID。只有 `C-` 加数字的 `id` 才指定旧承诺，只填上次回执中的 ID；其他形式（包括 `#` 开头、模型自拟名称）都按临时 ID 忽略。显式对应确定后，其余创建项在剩下的旧承诺中检查，一对多、多对一都不对应。
- **对应不上的处理**：旧承诺若已被其他变更集按 ID 修订、关闭、合并（包括作为合并的目标），或被用户在 App 中修改，整个重交被拒收，不创建项目、不分配 ID。回执列出不能撤去的承诺及上次创建项的 ID、内容、kind 与原话引用，要求保留这些承诺，以同 kind 引用同样的原话或显式写明旧 ID 后重交。未被引用的旧承诺可以消失，未对应的新创建项分配新 ID。新项目仍按名称沿用 ID。
- **一页一次调用**：一个时段里有几段交谈、几条承诺，都在一个变更集里交出，不按事实逐条调用（Graphiti 每条事实一两次调用，成本随图增长）。

### 业务线的检查

变更集整体校验，不通过就整体拒绝，并在结果中写明原因让模型改正后重交（与现在的"未核实"相同的反馈方式）：

| 检查 | 规则 |
|---|---|
| 范围 | 交谈的 `[from, to]` 在 `source` 之内、互不重叠；引用都存在（`cite_captures` 的 `missing`） |
| 作用域 | 白天的变更集可以 `revise`、`close`，但引用必须落在本次的 `source` 之内：只有新说出的原话才能改动已有的承诺。`merge` 只能出现在当天整理中（§6） |
| 版本 | `revise`、`close` 的 `rev` 与账本当前的修订序号一致 |
| 依据 | `xinli-day` 的 `revise`、`close` 至少引用一段原话；`xinli-project` 的引用交谈（§6 归集）；合并不需要引用，但须同为 open、同 `kind` |
| 日期 | 按被引用原话的说话时间（§7）换算 `due_text`，与 `due_date` 不一致时拒绝并给出换算结果 |
| 健康 | 交谈、决定、风险、觉察、项目名中出现健康信息（包括他人的）时拒绝（F3 的兜底；指令仍须写明） |
| 用户优先 | 用户在 App 中改过的承诺（标完成、改期限），模型不再改动这些字段，相应操作忽略并在结果中说明 |

用户在 App 中的改动同样记为变更集，作者是用户。账本的每一处当前值都能追溯到一个变更集，再追溯到原话与说话人。

## 6. 每日流程

**白天**（"整理交谈"，由 ADR-0040 的触发在用户空闲时开启）：

1. `captures{after: "new"}` 读一个时段（一页，长的分几页续读）。
2. 在这个时段里划出值得记录的交谈（可以是零段、一段或几段），寒暄闲聊不交。每段用 `find_related{query, counterparts}` 取回候选项目，以及与这段的对方或主题相关的未完成承诺（不限哪天、包括归属 `none` 的家事，带 ID 与 `rev`）。它取代 `find_projects`，调用次数不变。
3. 用一次 `file_changes` 交出这个时段：新的交谈与承诺；这个时段里的原话改动了已有承诺的（"验收方案改到下周二""钢琴课让孩子爸送"），直接 `revise` 或 `close` 那一条，而不是新建一条。再读下一个时段。

**为什么是空闲时。** 触发的条件是流上有未读的旁听、且静默超过 `quiet`（m5 §6）：用户说完一段话、停下来之后才整理，修订离说出改动的时刻只差一个静默期，提醒随之更正。触发是后台工作类别，准入时让交互调用优先，超额时这一次不开启、等下一次条件满足（m5 §6、model-calls.md），所以用户多时负载随各人的作息分散，也不会挤占交互。没开启的那次留下的修订，由下一次触发或当天整理补上。

**白天修订的限度。** 只做有新原话为据的改动：引用必须落在本次读到的范围内（§5 的检查）。它看到的只是 `find_related` 召回的几条，判断不了"这两条旧承诺其实是同一件事"，这类没有新原话的整理留给当天整理。

**当天整理**（"整理今天"）：

1. 照白天的做法读完余下的时段并交出。
2. `day_ledger` 取回今天的交谈与承诺（带 ID、`rev`、引用与说话时间），以及与今天的对方或项目相关的、之前未完成的承诺；业务线附上确定性的提示：同一对方、内容相近的承诺对，相邻且归属相同的交谈。
3. 用一次 `file_changes` 交出当天整理：合并重复的承诺，合并被停顿切开的交谈，改正归属，补上白天漏掉的修订（引用可以是今天的任何原话）。拿不准的不动作。
4. `file_day` 交出当天总览与觉察。业务线只接受"整理今天"那次 Run 的 `file_day`（F7）。

**当天整理的时机也按空闲分散。** 业务线不在固定的午夜统一提交，而是按各用户的空闲提交：当地傍晚之后旁听静默超过较长的时间（如 2 小时）即提交，最迟到次日凌晨的某个时刻，并加随机抖动。之后可以改为平台触发：同一个流上再声明一个 `quiet` 更长、输入为"整理今天"的触发；这需要每个触发分别记录触发到的位置（ADR-0040 现在按流记录），另行扩展。

**归集**照旧，`xinli-project` 保留按 ID 对账（`update_commitments`，现有评测 `capture-project-reconcile` 3/3 通过）。它在当天整理之后运行，看到的已是白天修订与当天整理之后的状态，起兜底作用：称呼对不上、`find_related` 没有召回的承诺，在项目层面按摘要还能对上。接入新模型的方式：

- `update_commitments` 交出的是一个变更集，作者为 `xinli-project`，键是（项目 Session，日期），重交时整体取代。
- 每个操作带 `rev`（`day_summary` 给出），账本在它之后又被改过就拒绝，与白天的修订同一套检查。所以项目 Run 不会用过时的视图覆盖白天依据原话做的修订；两边意图相同时，后到的一方因 `rev` 不符被拒、看到当前状态后不再重复。
- 它看不到原话，依据是交谈：操作引用 `exchanges: ["x57.0"]`，修订记为"依据摘要"，与"依据原话"区分开展示，供之后评估这条路径的准确率。
- 新增承诺仍只来自 `xinli-day`。

**每周回顾**不变。

## 7. 时间

三种时间分开存放，不互相代替：

| 时间 | 含义 | 来源 |
|---|---|---|
| 说话时间 | 原话在何时说出（观察时间） | Capture 的 `spoken_at`；`cite_captures` 的 `_meta` 附上每条引用的 `spoken_at` 与 `time_zone`（平台改动，F6） |
| 期限 | 承诺的截止时刻 | 模型给出 `due_text` 与 `due_date`，业务线按说话那天换算核对 |
| 有效区间 | 一条修订从何时起成立、何时被取代 | 修订的 `spoken_at` 起、下一条修订的 `spoken_at` 止；`recorded_at` 记交出的时刻 |

验收方案在 10:40 记为"下周三前"（10-28），15:03 改为"下周二"（10-27）：一条承诺两条修订，10:40–15:03 之间的状态与按它发出的提醒都可以重现。

## 8. 切分

- **平台只切时段**：算法不变（按停顿，`exchange_gap` 随读取位置记下），改名为时段，`captures` 的页首写"时段 #57.0 起"，不再称交谈。间隔不再承担语义，不必按 ADR-0030 在留出集上调：它只影响一页的大小与"是否已结束"，5 分钟照用。
- **模型在时段内划交谈**：两通电话、午饭转谈测试平台、一次谈三件事，都由模型按内容划开或逐项归属。电话独白只有佩戴者一侧，靠内容判断。
- **当天整理时合并被切开的**：康宁会议因 7 分钟静默跨了两个时段，由当天整理合并为一段交谈。白天不合并交谈：切碎的代价小（原则 4），合并需要看到前后两段。跨天不合并（旁听 Session 按天分开）。
- **不做**按说话人切分（跨批的 `speaker_key` 无法比较，评审 §8.1），也不要求 HostApp 标注边界。通话起止这类系统事件，将来可以作为一个新的流提交（[m5](./m5-inputs-triggers-loops.md) §5），作为划分的提示，不在这一版。

## 9. 成本

- 白天每个时段的处理只依赖这一页与召回的候选，不依赖前面的时段。现在一个 Run 内的上下文仍逐页累积（单次调用从 4k 涨到 22k），交出之后的页可以从上下文中丢弃，成本随交谈数线性增长。[m2-long-runs](./m2-long-runs.md) §11 试过按规则省略旧的调用结果，因汇总任务需要每条结果中的数据而未采纳；这里不同的是，交出的页已经由变更集交给业务线，当天整理读 `day_ledger` 而不读旧页。是否成立仍要评测验证（模型可能回头重读），单独设计，不在这一版。
- 每个时段固定一次 `file_changes`，加上每段交谈一次 `find_projects`。`find_projects` 能否并进 `file_changes`（业务线代为召回、在结果中请模型确认）留待评测比较纯度后再定（评审 F9）。
- 当天整理一次调用，输入规模是一天的交谈与承诺（约几十条），不随旁听字数增长。白天的修订不增加调用：相关承诺随 `find_related` 一起返回，修订随 `file_changes` 一起交出。

## 11. 评测

- 已有用例改用新接口；`capture-exchange-split` 改为"一个时段内两段交谈"。
- 新增：上午答应、下午改期（下午那次白天整理就修订，只剩一条 open，有两条修订）；改由他人去做（原承诺作废）；一个时段里两通电话，只有佩戴者一侧（划成两段、归属不同）；被静默切开的会议（当天整理合并为一段）；之前几天的承诺今天说已完成（白天关闭）；白天引用旧原话修订（被拒绝）；用户在 App 中改过的承诺（模型的修订因 `rev` 不符被拒绝）。`capture-project-reconcile` 改用带 `rev` 的接口，另加一例：白天已依据原话改期，项目 Run 不再重复改动。
- 断言增加：open 承诺中的过时条目数（F1）、每天承诺数上限（F5，需先给运行器加 `commitments_count`）、交谈的纯度与碎片率照旧。
- 评测运行器按约 1 分钟一批提交旁听、每批重新编号 `speaker_key`，与真实的 HostApp 一致（现在 100 段一批、key 全天不变，掩盖了跨批的问题）。
- `capture-workday` 与 oneshot 作为整体回归，重跑评审 §6 的模型矩阵（lite 与 GLM-5.3-flash）再定模型。

## 12. 定下的参数与观察项

- **召回范围**：`find_related` 与 `day_ledger` 只取回最后一次修订在 30 天内的未完成承诺；`find_related` 每次至多 10 条，按对方与主题的相关度排序。更早的仍在账本里、照常提醒，由用户在 App 中处理。上限是起点值，按评测中的漏召回调整。
- **漏改期间的提醒**：同一 `kind`、同一对方称呼、内容相近（业务线给当天整理的同一条确定性规则）的两条 open 承诺，只按较新的一条提醒，两条都照常展示。它只是提醒规则，不改账本，当天整理合并或作废之后自然失效；不自动合并（原则 4）。已实现于 `internal/xinlimock/ledger.go` 的 `State.Reminders`，与 `day_ledger` 共用重复判断，按成对传递分组，用户修改过的承诺优先，同等优先级下以最后修订的说话时间（缺失时用记录时间）、记录时间、ID 依次选择较新者。
- **当天整理的时机**：当地 18:00 之后旁听静默满 2 小时提交；到当地 04:00 仍未满足的，在 04:00 起的 30 分钟内随机提交。由业务线做；平台触发（ADR-0040）的第 2 步实现之后，再评估是否扩展为同一个流上的第二个触发。
- **人（观察项）**：不建模（§4）。评测与试用中记录称呼对不上导致的漏召回、漏合并；案例足够说明问题时再设计。

## 13. 决定

| 决定 | 选择 | 没有选的 |
|---|---|---|
| 写入与身份的单位 | 变更集，承诺与交谈各有 ID，每个操作附依据 | 交谈为单位（现状，F1、F2、F4 的来源）；会话窗口加撤回（只修时间上的错）；逐条事实（粒度太细，每条都要消解实体，成本高）；项目活文档（提醒要结构化数据，改写会漂移） |
| 交谈的边界 | 模型在时段内划定，当天整理时可以合并 | 平台按停顿或说话人切分（电话独白与同一批人换话题无从判断；`speaker_key` 跨批不可比较）；HostApp 标注边界（需要契约字段） |
| 矛盾在哪里消解 | 有新原话的改动在空闲触发的白天整理里就做；合并等没有新原话的整理在当天整理里做；都是可撤销的标记 | 只在深夜一次（提醒更正不及时，用户多时负载集中）；每段交谈时做全部对账（视野只有召回的几条，判断不了旧承诺之间的重复，mem0 的经验）；读取时按时间排序（mem0 只追加后过时事实浮上来；提醒需要唯一的当前状态） |
| 项目层面的对账 | 保留 `xinli-project` 按 ID 对账作为兜底，记为依据摘要的修订，受 `rev` 约束 | 去掉，只允许依据原话的修订（失去称呼对不上时的兜底，现有对账效果也已验证） |
| 修订与历史 | 不删除，修订带说话时间与记录时间 | 直接覆盖（已发出的提醒无从解释） |
| 重复的判断 | 业务线给出确定性的候选，模型决定，拿不准不动作 | 自动合并（错误的合并修不回来） |
| 人 | 不建模，称呼按原话 | 引入人与别名（语音识别不能指出是谁，对不上说话人；先看失败案例） |
