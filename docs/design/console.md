# 调试控制台

> 状态：已实现（2026-10-11 重做为三个视图） · 依赖：[多端双工通道](./m3-duplex-channel.md)、[M1 设备即节点](./m1-device-nodes.md)、[端侧 SDK](./m3-client-sdks.md)、[卡片](./cards.md)、[委托](./m5-multi-agent.md)、[Call](./m3-call.md)、[旁听](./captures.md) · 契约：[`node.proto`](../../proto/yanshi/v1/node.proto) · ADR-0032、ADR-0033

## 1. 目的

章程 G1 的多端语义很难让人看见，也难以手工复现，只靠单元测试与 e2e 不够。这些语义包括：同一 Session 多台设备同时在线、跨端接续、设备即 Node、委托给其他 Agent、执行中的故障恢复。

调试控制台（`serve` 的 `/console`）在一个页面里提供四个视图，共用一组模拟设备与当前 Session：

| 视图 | 做什么 |
|---|---|
| **对话** | 一台设备全屏展示聊天，支持文字、图片与文件、按住说话、实时通话。Agent 的卡片、审批与提问都在对话里处理 |
| **设备** | 每个 EndUser 的手机、电脑、手表、音箱、车机与网页，各自一条 Connection。可以上线、下线、断网、崩溃，查看模拟应用的状态，切换能力的执行方式，查看调用账本。每台设备有自己的迷你对话 |
| **旁听** | 旁听业务线这一侧：今日、项目、承诺、待确认、觉察（§2.1），需要 `serve -xinli-mock` |
| **控制台** | 时间线、事件、帧、投影、服务端故障注入、进程指标、验证场景 |

控制台只使用公开的 Connection 协议与 HTTP API，不比其他客户端多任何权限。

调试专用的接口只有故障注入与进程指标（`/v1/debug/*`，只在 `serve -faults` 时存在，ADR-0033），以及模拟的 xinli 业务线（`GET /v1/debug/xinli` 与 `POST /v1/debug/xinli/resolve`，只在 `serve -xinli-mock` 时存在）。

## 2. 对话

对话视图分三栏：
- **左侧**：会话列表。显示首句消息、Agent 与时间，可以搜索、关闭会话。委托派生的子会话不在列表中显示，从调用详情跳过去。
- **中间**：对话。
- **右侧**：详情抽屉。

快捷键：Esc 中断进行中的 Run，⌘K / Ctrl+K 新建会话。

对话视图用一台模拟设备作为会话客户端，默认是该 EndUser 的网页设备，没有时自动添加一台。也可以选手机、电脑等设备：经 Connection 的输入会注明来源设备（`UIContext.device`），模型据此在多台设备中选择（[判断](./m6-decisions.md) §3）。

| 输入 | 做法 |
|---|---|
| 文字 | `SubmitInput`；Run 进行中时并入它，等回答时作为回答。进行中的委托里恰好一个子 Agent 的提问在等回答、且本 Session 自己没有时，文字以 `answer` 发往子 Session，输入框显示"回答子 Agent：<问题>"；已被别的设备回答（conflict）时保留文字并提示，不改投本 Session（`SessionView.typedAnswerTarget`，[委托](./m5-multi-agent.md) §4）。带附件或界面上下文时照旧提交。去向由 `routeInput` 决定，对话与验证场景共用 |
| 图片、文件 | 选择、粘贴或拖入后，经 HTTP 上传为工件（`POST /v1/sessions/{id}/artifacts`），随下一条消息以 `media`（`artifact://`）提交。还有附件在上传时，发送等它们完成再决定去向。模型能看图（`doubao-seed-2-1-lite`） |
| 拍照 | 文件选择加 `capture`：手机上直接打开相机 |
| 按住说话 | 按住 🎤 录音，在浏览器中编码为 16 kHz 的 WAV，松开后经服务端识别成文字、作为文字输入发出；这一轮完成时把回复合成语音播放，🔊 停止，再次按住说话时打断（[按住说话](./speech.md)）。模型只看到文字。需要 `VOLC_SPEECH_API_KEY` |
| 界面上下文 | 可选：随下一条消息附上界面与可见内容（`UIContext`） |
| 卡片动作 | 点卡片上的按钮或列表项（`CardAction`，[卡片](./cards.md) §4） |
| 旁听 | 🎧：以 HostApp 的身份逐段写下转写、手选说话人（佩戴者、他人 A、他人 B），整批以 `SubmitCaptures` 提交，不开启 Run（[旁听](./captures.md) §3）。**持续收音**：浏览器的语音识别（Web Speech API，`zh-CN`）在页面内把麦克风转成文字，扮演 HostApp 的转写，音频不发给 yanshi（ADR-0036）；它不区分说话人，每句话按当时选中的说话人记，可随时切换；每 10 秒自动提交一批，停止时提交余下的。识别在静音后自行结束，收音期间随即重启。Chrome 的识别服务要访问 Google，网络不通时改用 Safari（macOS 需开启听写）。提交失败的一批单独保留，再交时沿用它的 `capture_id`、服务端按 ID 去重，之后的段另起一批。只有开启旁听的 Agent 接收（`console-capture`、`xinli-day`），其余为 invalid：面板打开时若当前会话的 Agent 不在其中、或提交被以 invalid 拒绝，停止收音、段留在本批，并提示"新建 xinli-day 会话"，点后尚未提交的段交到新会话，面板在新会话中保持打开 |
| 通话 | 📞：经同一条 Connection 的 `CallStart` / `CallAudio`，上行 16 kHz、下行按到达顺序播放，说话时打断（[Call](./m3-call.md)）。设备断开时通话在本地结束，停止采集与播放。需要 `VOLC_SPEECH_API_KEY`，且 AgentDef 配置了 `call`（`concierge`、`assistant`）；其余 Agent 被拒绝时提示可通话的 Agent |

发送失败（被拒绝、超时、断线后结果未知）时：

- 输入框仍为空，就把整份草稿放回：文字、附件（含语音消息）、界面上下文。原样再发时沿用原来的 `input_id`，已经生效的不会重复生效（服务端返回 duplicate）；改过的内容是新输入，用新的 ID。
- 用户已经开始写下一条，就不覆盖，只提示哪段内容没有发出。
- 子 Agent 提问的文字回答失败时同样处理，回答没有 `input_id`，按 `call_id` 去重。

事件流的呈现：

- **助手的一轮**：同一个 Run 的回复归在一起。每次模型调用依次显示：
  - 思考过程：可折叠；生成中实时展开，正文开始后收起（ADR-0034）；
  - 正文：悬停时可以复制，或跳到控制台的时间线；
  - 本次调用：多个时折叠成一行（"N 个调用 · 全部完成"）；
  - 模型信息行：模型、输入（缓存）、输出、思考 token、首字延迟、耗时、结束原因。
- **回复**：Markdown 只渲染安全的子集（`markdown.js`），直接构造 DOM、不经 innerHTML。链接只允许 `https:` 与 `artifact://`，图片只允许本 Session 的工件。用户自己的输入按纯文本显示。
- **调用**：每个调用一行：排队、执行中、待审批、出错、完成，带耗时。出错后被模型改正（同名调用随后成功）的调用弱化显示。Run 中断或失败时还没有结果的调用显示"已终止"，不再一直显示执行中或待审批。
- **详情抽屉**（`drawer.js`）：点调用、模型信息行或卡片，在右侧显示全部信息：
  - 调用：状态、所属 Attempt、路由目标（设备、子 Session，可跳过去；用户本人）、执行次数（重新投递或接管后会多于一次）、审批；
  - 调用的各步时间：发起、审批、派发、子 Run 开始与结束、结果；
  - 参数与结果：带语法高亮、可折叠、可复制的 JSON；
  - 模型调用：token、首字与耗时、结束原因，思考过程与回复全文；
  - 卡片：每一版与已执行的动作（作为提问回答的另行标出）。
- **卡片**（`cards.js`）：同一 `card_id` 只显示最新版。点过的动作在所有设备上显示为已选，判断依据是事件流中输入里的 `card_action`，以及 Run 等回答时作为回答的 `ToolResult.card_action`（`cardActionOf`，与网页 SDK 同名同义）；任一动作执行后整张卡片不再接受动作。同一 Run 的后续消息会重建卡片，已填写的字段保存在对话面板中，重建后恢复。
- **待处理**：审批与 `ask_user` 提问以卡片样式显示在输入框上方，任一设备处理后从所有设备上收起。进行中的委托（递归）里子 Run 的审批与提问也显示在这里，标出子 Agent，处理结果发往子 Session：它们路由到用户本人，但写在子 Session 里，父 Session 不一并展示的话，父 Run 会一直等着委托（`SessionView.pendingWithDelegations`）。
  - 提问在派发给用户（`ToolCallStarted{node_id: "@user"}`）之后才显示：模型同一轮返回委托与提问时，提问要等委托结束才派发。
  - 单选且没有字段的提问点选即回答；有字段时点选只是选中，由"提交"一起发出。
- **后台调用**（ADR-0035）：转入后台的调用在调用行显示"后台排队中"，所在的一轮下面注明设备离线、已排队。设备迟到的结果、到期与取消显示为平台的说明（📬、⌛、🚫），不是用户的气泡；结果带设备返回的文字与工件。未了结的后台调用列在输入框上方，各带"取消"按钮。详情抽屉显示后台状态、截止时间与转入后台、了结的时刻。
- **旁听**：每批转写按日志顺序显示为一块，佩戴者与他人的话分色标出，依据是结构化的说话人字段；被内容安全拦截的段只显示占位。旁听不打断进行中的一轮。还没有输入的会话以第一段转写为标题。
- **状态行**：Run 在等什么（设备、子 Agent、你的回答、模型），思考或输出中，中断按钮（Esc），在场的其他设备与"正在输入"。
- **新消息**：不在底部时有新内容，显示"↓ 新消息"。
- **草稿与平滑输出**：正在生成的思考与正文单独渲染，从收到的内容中按稳定节奏逐字显示：至少每秒 40 字，积压多时约 250ms 内追上。模型一阵一阵地吐字（方舟实测：多块常同时到达，再停一下）时，界面上仍然均匀。已提交的部分只在有新事件时重建，在场的变化只更新状态行；用户展开或收起的思考块、调用组在重建后保持原状。

`-auth jwt` 时工件要带令牌下载，`<img src>` 带不上令牌，所以先下载成 blob 再显示（`ui.js` 的 `Artifacts`）。

### 2.1 旁听视图（`static/console/xinli.js`）

旁听业务线 xinli 这一侧的数据，按心力球 App 的页面组织（[旁听按交谈整理](./captures-by-exchange.md) §5–§7）。数据来自模拟的 xinli MCP Server，经 `GET /v1/debug/xinli`（鉴权同 Memory 的列表：用户令牌只看本人）读取，视图可见时每 3 秒刷新：

| 页签 | 内容 |
|---|---|
| 今日 | 每次每日整理（`file_day`）一张卡片：日期、一句话总览、要点；当天交出的各段交谈（`file_exchange`）的摘要、定下的事、承诺、风险与归属。点项目名跳到"项目" |
| 项目 | 每个项目一张卡片：现状、下一步、待解决（`xinli-project` 经 `set_status` 更新）、未完成的承诺，展开后是按天的交谈 |
| 承诺 | 承诺账本：我答应的、别人答应我的、已完成或取消的；未核实的（引用的原话不是承诺人说的）注明原因 |
| 待确认 | 归属拿不准的交谈：替用户"归入"候选项目或"新建"（`POST /v1/debug/xinli/resolve`），页签上显示条数 |
| 觉察 | 按天的沟通习惯与"下次可以"；下面是本 EndUser 的 Memory（含旁听写入的，health 类别标红） |

每张卡片可以打开对应的 Session（每日整理的 `xinli-day`、项目的 `xinli-project`），在"对话"视图中查看模型读了什么、调用了什么。

## 3. 设备

### 3.1 模拟设备（`static/console/device.js`）

模拟设备直接按协议以 **protojson 文本帧** 接入，不经网页 SDK。原因有两个：网页 SDK 只作会话客户端（ADR-0026），而控制台要模拟提供 Capability 的手机与电脑；文本帧也让每一帧可读、可手工构造。语义与 SDK 一致，便于用它检查网关：

- 断线自动重连，按各订阅最后收到的 seq 续订，丢弃不比它新的事件；
- 带 `input_id` 的提交在响应之前断线时，以同一 ID 重试；
- 请求 30 秒没有响应时以超时失败、结果未知，不再等它（迟到的响应丢弃）。对话面板保留失败的草稿与它的 `input_id`；
- 调用按 `call_id` 记账，同 `sdk/nodesdk.Executor`：
  - "执行中"先记下、再执行；
  - 重复投递返回已有结果；
  - 执行中崩溃后再投递时，幂等能力重新执行，否则返回 outcome unknown；
  - 结果在收到 `ResultAck` 之前，重连后重发；
- 能力的结果可以带工件：如拍照时先把照片上传为调用所属 Session 的工件，再以 `media` 返回。

`device.js` 与 `scenarios.js` 不依赖 DOM，在浏览器与 Node.js 中都能运行。

### 3.2 设备类型与模拟应用

| 设备 | 能力 |
|---|---|
| 📱 手机 | `get_location`、`take_photo`（需审批）、`send_sms`（需审批）、`set_alarm`、`list_alarms`、`cancel_alarm`、`create_event`、`list_events`、`play_music` |
| 💻 电脑 | `read_file`、`list_dir`、`write_file`（需审批）、`open_url` |
| ⌚ 手表 | `set_alarm`、`list_alarms`、`start_timer`、`get_heart_rate` |
| 🔊 音箱 | `play_music`、`set_volume`、`set_alarm` |
| 🚗 车机 | `navigate`、`set_climate`、`play_music`、`get_location` |
| 🌐 网页 | 只作会话客户端 |

每台设备有模拟应用的状态（`SimDevice.apps`）：闹钟、日程、计时器、已发短信、相册、正在播放、导航、空调、浏览器、文件。能力的处理函数读写它，设备卡片的"应用"页签实时显示，例如"手机上多了一个 07:00 的闹钟"。

同一种能力分布在几台设备上（闹钟、音乐），用于观察设备歧义消解。

### 3.3 执行方式与连接故障

每个能力可以切换执行方式：

| 方式 | 行为 | 用来观察 |
|---|---|---|
| 自动执行 | 按预置的处理函数返回（可设耗时） | 能力路由 |
| 手工填写结果 | 调用停在设备上，由人填写结果或错误 | 挂起、多端看到同一个等待 |
| 返回错误 | 返回错误结果 | 错误结果交还模型 |
| 不回应 | 永不返回 | 结果截止时间到期 |
| 执行中崩溃 | 收到调用后断开连接、留下"执行中"记录，随后自动重连 | 重新投递与按 `call_id` 去重 |

设备卡片可以折叠（"全部折叠 / 展开"），网格可以只看在线的设备；设备收到调用、等待手工填写结果时，卡片闪一下。卡片头部是上线/下线，其余操作在"⋯"菜单中。

三种连接故障：

- **下线**：断开且不再重连。设备离线时 Run 先挂起等待它；离线超过宽限期，调用转入后台（ADR-0035），对话不再等它。
- **断网**：断开后自动重连，观察续订与重试。
- **崩溃**：执行中的调用留下"执行中"记录，随后自动重连。

设备 ID 保存在浏览器中，刷新后同一台设备重新上线。

## 4. 控制台

| 页签 | 内容 |
|---|---|
| 时间线 | 当前 Session 的每个 Run 一块，带甘特条：每个 Attempt 一段，每个调用一段，注入的故障是红线。下面按时间列出输入、Attempt 开始（标出接管或恢复）、模型调用（模型信息行与思考字数）、调用及其路由目标、结果、审批、挂起、压缩、判断（`DecisionMade`）、后台调用（转入后台、迟到的结果、到期、取消，列在发起它的 Run 下面）、内容安全拦截与注入的故障，左侧标出所属的 Attempt。时间是相对 Run 开始的偏移（悬停看时刻），长文字单行截断（悬停看全文），可按类型筛选。委托的子 Session 嵌套在委托调用下面，递归展开。对话中的"在时间线中查看"定位到对应的 Run |
| 事件 | 任一设备视角下已提交的事件，可过滤，点开看带语法高亮、可折叠、可复制的 JSON |
| 帧 | 每台设备收发的每一帧（音频帧除外），可按设备、方向过滤；可以手工构造帧发给网关（订阅、提交、卡片动作、不合法的请求） |
| 状态 | HTTP API：Session 投影、Node 目录、Session 列表、事件、工件、Memory、配额与用量 |
| 故障注入 | 服务端故障注入（§7） |
| 指标 | 本进程的 `yanshi_*` 指标，每 2 秒刷新。上方是关键指标，带速率与趋势小图（计数器画每次刷新的增量），包括 Run 完成与失败、模型调用与重试、Attempt（含接管）、注入的故障、队列；下方按类别分组列出全部指标 |
| 验证 | 验证场景（§5），一键运行 |

控制台在"对话"所用的设备上订阅委托出去的子 Session（发现 `@agent/<子 Session>` 的 `ToolCallStarted` 即订阅）。所以时间线、调用条与委托树都是实时的。

订阅的生命周期：

- 订阅被网关结束的视图不算有效订阅。委托仍在进行时，以 `not_found`（子 Session 可能还没创建）或 `error` 结束的子订阅按退避（200ms 起翻倍，至多 5 秒）从已收到的位置重订；以 `limit` 结束的视图在下次用到时再订；`deleted` 不再订阅。
- 切换 Session 或 EndUser 时，在所有设备上退订并丢弃之前的 Session 及其委托派生的子 Session（新 Session 恰是其后代时保留它）。网关对一条 Connection 至多 32 个订阅，只增不减会很快用完。
- 只有"对话"视图可见时，它所用的设备把当前 Session 报告为前台。切换 Session、更换对话设备、离开"对话"视图或页面隐藏时，先撤下之前报告的前台状态：提醒据此判断用户是否在看。
- 会话列表与新建会话的响应返回时，EndUser、业务线或令牌已经变了，就丢弃结果。

## 5. 验证场景（`static/console/scenarios.js`）

每个场景新建自己的设备与 Session，以检查项断言网关的行为，结束时断开设备。Session 保留，可在控制台中查看事件。场景超时后，它此后的等待、创建设备、Session 与故障规则一律失败，不在后台继续留下资源。

| 场景 | 检查 |
|---|---|
| 多端实时同步 | 三台设备收到相同的事件序列与实时增量，草稿被提交的消息取代 |
| 晚加入者补齐草稿 | 生成中途订阅，第一条增量是从头开始的 snapshot，snapshot 加上其后的增量恰好是脚本输出的全部内容（不漏、不重、顺序正确），并补齐此前的事件 |
| 断线续传 | 生成中途断线重连，事件 seq 连续、无重复；断线期间 Run 被中断，重连后草稿随终态清除 |
| 输入去重 | 同一 `input_id` 只生效一次；请求发出后断线，重连后以同一 ID 重试 |
| 设备能力路由 | 调用派发到目标 Node、执行一次、结果回到 Run；设备的错误作为错误结果 |
| 高风险能力的审批 | 各设备都看到审批；批准前设备收不到调用；拒绝时不执行；重复审批返回 conflict |
| 设备离线：宽限期内上线 | Run 挂起，投影显示在等离线的设备；设备在宽限期内上线后执行并完成，调用没有转入后台 |
| 设备离线超过宽限期 | 调用转入后台（ADR-0035），模型得到"已排队"的结果，Run 完成；会话列出这个后台调用，投影中设备离线；期间的输入开启新的一轮并得到回应；设备上线后执行一次，结果开启新的一轮（注明由后台调用开启），模型看到带说明的结果 |
| 取消后台调用 | 取消写入日志、不开启新的一轮；再次取消为 conflict；设备上线后收不到已取消的调用 |
| 执行中崩溃 | 同一调用投递两次：非幂等能力只执行一次并报告结果未知，幂等能力重新执行 |
| 提问 | 在另一台设备上点选回答，提问随之收起；重复回答返回 conflict；Run 等回答时输入的文字作为回答 |
| 插话与中断 | 另一台设备的输入并入进行中的 Run；中断后新输入开启新 Run |
| 在场 | 前台、正在输入、取消订阅在其他设备上实时更新 |
| 隔离 | 另一个 EndUser 的订阅、提交、中断、关闭都是 not_found |
| 思考过程 | 思考以单独的增量推送；中途订阅的设备在 snapshot 中补齐；提交后写入 `reasoning`，带思考 token、结束原因与耗时 |
| 卡片 | 卡片多端可见；同一 `card_id` 再次展示即替换；点按钮作为输入，标签由平台填写；两台设备连点只生效一次；卡片上没有的动作被拒绝 |
| 等回答时点卡片 | 先展示卡片再提问；在手机上点按钮，动作作为提问的回答，回答的 `ToolResult.card_action` 是规范化后的动作，不出现在任何输入中；网页把按钮显示为已选；再点为 duplicate |
| 委托 | 调用派发到子 Session；子 Session 的输入是任务；子 Run 的回复写回父 Run |
| 子 Agent 提问 | 子 Run 的提问在父 Session 的待处理中可见；回答发往子 Session，经子 Run 写回，父 Run 完成 |
| 文字回答子 Agent | 去向由对话面板所用的 `routeInput` 决定：唯一待回答的子 Agent 提问被选中，文字以 `answer` 发往子 Session，父 Run 完成，父 Session 没有新增输入；带附件、界面上下文时照旧提交，附件上传中时先等。另一台设备抢先回答时为 conflict，父 Session 仍没有新增输入。两个待回答的提问时不选中（脚本化模型造不出两个，在视图上多放一个提问检查规则本身）；父 Session 自己有提问时不选中，文字作为它的回答 |
| 同一轮的委托与提问 | 模型同一轮返回委托与 `ask_user`（脚本命令 `together`）：委托结束之前父 Session 的提问不算待回答，文字选中子 Agent 的提问；委托结束后父 Session 的提问才派发 |
| 子 Agent 审批 | 子 Run 调用高风险能力：父 Session 的待处理中看到这个审批，发往子 Session；批准后设备执行，父 Run 完成；再次审批为 conflict |
| 服务端故障注入 | 需要 `-faults`，否则跳过。模型调用失败后 Worker 重试、Run 完成；Worker 崩溃后租约过期被接管（新的 Attempt）、Run 完成 |
| 图片与工件 | 上传的图片以工件引用随输入提交；手机拍照（需审批）把照片作为工件带回 Run |
| 旁听 | 手机提交一批旁听，网页实时看到带结构化说话人的转写，没有开启 Run；同一 `capture_id` 再交为 duplicate；未开启旁听的 Agent 为 invalid；Run 经 `captures` 读出，佩戴者与他人的话分别注明 |

`make check` 中由 `internal/e2e` 的 `TestConsoleScenarios` 以 Node.js 运行全部场景（`internal/webui/testdata/run-scenarios.mjs`，需要 `YANSHI_TEST_NODE`）。e2e 的实例始终装配故障注入，租约 5 秒，后台调用的宽限期 3 秒、后台时限 1 分钟（到期由 Go 的 e2e 测试覆盖）。新增多端语义时，同时在这里增加场景。

EndUser 的选取：

- `-auth none` 时，每次运行使用新的 EndUser（`qa-<随机>-a/b`），新登记的设备立即出现在工具中。
- `-auth jwt` 时，使用控制台中前两个带令牌的 EndUser。此时新登记的设备至多 10 秒后才出现在 Agent 的工具中（`Catalog.NodeCacheTTL`），场景在脚本回复 "no such tool" 时稍后重试。

## 6. 脚本化模型（`internal/model/script`）与演示 Agent

没有模型密钥时，演示与验证需要一个结果确定、能按指令发起工具调用的模型。`script/any`（Agent `console`）按最后一条用户输入中的命令行事，每行一条：

| 命令 | 行为 |
|---|---|
| `call <工具> [JSON]` | 调用名称等于它、或以它结尾的工具；多行依次调用，每收到一个结果调用下一个。卡片：`call show_card {…}`；委托：`call agent__console-helper {"task": …}` |
| `ask <问题> \| 选项 \| 选项` | 经 `ask_user` 提问 |
| `stream <n>` | 约 n×20ms 内逐段输出（插话、中断、晚加入者） |
| `think <n>` | 每次模型调用先流式输出 n 段思考过程（ADR-0034） |
| `together` | 剩下的 `call` 与 `ask` 在同一次模型调用中一起返回（一轮多个调用），Worker 再按顺序推进。例如委托与提问同一轮：提问要等委托结束才派发 |

`console-capture` 是开启旁听的脚本化 Agent（白名单为 `captures`、`memory_save`）：用 🎧 提交转写后发 `call captures {}` 读出。

调用全部完成后回复 `done: <最后一个结果>`；没有命令时复述输入。卡片动作与真实提供商一样呈现为一行文字，脚本复述它。后台调用的了结与取消（以"[后台调用"开头的说明，ADR-0035）不是命令，脚本同样复述它。插话开启新的命令序列。e2e 测试使用同一个模型。

真实模型的演示 Agent（火山方舟，`ARK_API_KEY`）：

| Agent | 做什么 | 白名单 |
|---|---|---|
| `concierge`（总管） | 把领域任务委托给专员，汇总成卡片 | 委托三位专员；设备能力只列出专员需要的（没有 `send_sms`、`write_file`） |
| `schedule`（日程管家） | 闹钟、计时器、日程；需要时发提醒短信 | 闹钟、日程、计时器、`send_sms` |
| `travel`（出行助手） | 导航、空调、音乐、音量 | 车机与音乐 |
| `research`（研究员） | 读文件、开网页、在沙箱中计算 | `device:*`、`sandbox:*` |

旁听业务线的 `xinli-day`（每日整理）与 `xinli-assistant` 依赖业务线的 MCP Server（`mcp:xinli/*`，[旁听](./captures.md) §6）。开发部署以 `serve -xinli-mock <业务线>` 在进程内登记模拟的 xinli MCP Server（`internal/xinlimock`，与评测共用；数据只在内存中，重启即清空），控制台的默认业务线是 `demo`。在 `xinli-day` 的会话中用 🎧 提交一天的对话，再发"整理今天"：模型读完旁听、查已有项目、调用一次 `file_day`，佩戴者说过的偏好写入 Memory，他人的话按外部内容对待。随后模拟的业务线为涉及的项目提交"整理 <日期>"，`xinli-project` 得出承诺；结果在"旁听"视图中查看（§2.1）。

委托不扩大权限：子 Run 的工具是自身白名单与每个祖先白名单的交集（ADR-0031）。所以经总管委托时，日程管家不能发短信，直接和日程管家对话时可以（需审批）。评测 `concierge-no-escalation` 检查这一点。

## 7. 服务端故障注入（ADR-0033）

`serve -faults` 时，控制台的"故障注入"页签可以对当前 Session（或全部 Session）注入以下故障，并指定次数：

| 故障 | 注入点 | 观察 |
|---|---|---|
| 模型服务端错误（503） | 模型提供商（`model.Guard` 之内） | 真实提供商先在提供商层退避重试；脚本模型没有 Guard，Worker 这一步失败、下一步重来，连续 3 次 Run 失败 |
| 模型限流（429，Retry-After） | 同上 | 按 Retry-After 等待后重试 |
| 流式输出中断 | 同上，转发 N 个字符后失败 | 草稿被丢弃，Worker 重新调用（已输出过增量，提供商层不重试） |
| 模型延迟 | 同上 | 插话、中断、晚加入的设备 |
| Worker 崩溃 | Worker 写完一步之后 | 不释放租约；租约过期（`-lease-ttl`）后被接管，开启新的 Attempt |
| 内容安全不可用 | 内容安全提供商 | 输入被拒绝（503，不写日志）；输出的这一步重试 |
| 设备目录不可用 | 解析工具时查询设备目录 | 这一步重试 |

规则只在进程内存中，只影响本进程。每次注入记录规则、类型与 Session ID，在时间线上以红线标出，计入 `yanshi_faults_injected_total`。

用户令牌只能对自己的 Session 注入；不限 Session 的规则需要服务令牌或 `-auth none`。

设备侧的故障（下线、断网、崩溃、不回应、返回错误）在"设备"视图中，经公开协议模拟，不需要 `-faults`。

## 8. 鉴权

- `-auth none`：设备在 Hello 中自报业务线与 EndUser；HTTP API 不校验身份。默认只允许监听回环地址。
- `-auth jwt`：每个 EndUser 填写令牌（`yanshi token -key demo.key -user <用户>`），设备与 HTTP 请求都以令牌为准。令牌只保存在本机浏览器的 localStorage 中。也可以用链接带入：`/console#token.u1=<令牌>&token.u2=<令牌>`，片段不随请求发给服务端，读入后从地址栏清除。
- 在同一网络的其他设备上使用，有两种方式：
  - `serve -addr 0.0.0.0:<端口> -auth jwt`，再把带令牌的链接发到那台设备上；
  - 调试阶段不想管令牌时用 `serve -addr 0.0.0.0:<端口> -auth none -insecure-remote`：同一网络中的任何人都能冒充任意用户、读写任意 Session，所以只在可信的局域网里用，启动时会打印警告，生产禁止（上线检查清单）。
- 手机浏览器打开后，对话视图的"拍照"直接调用相机（文件选择）。按住说话、通话与旁听的持续收音要用麦克风，浏览器只在 localhost 或 HTTPS 下允许，所以在局域网 IP 上用 http 打开时不可用。

## 9. 控制台发现的问题

- 已修复：Run 结束后重复审批同一调用返回 not_found，与 `node.proto` 中"审批、回答重复执行返回 conflict"不一致（回答已是 conflict）。`service.Decide` 现在对请求过审批的调用返回 conflict。

- 已修复（2026-10-11）：总管在交给专员的任务里写了编造的日期。指令改为不确定的日期先调用 `clock_now`，否则照用户的原话转述。
