# 旁听每周回顾

> 状态：已实现（2026-10-24）；评测结果见 [m4-eval.md](./m4-eval.md) §12· 依赖：[旁听与 Project](./captures.md)、[旁听按交谈整理](./captures-by-exchange.md)、[Memory 时效](./m4-memory-grant.md) §11 · 术语：`CONTEXT.md` 的 Project、Exchange、Commitment、Awareness

每晚的整理只看一天；跨天才能看出的问题留给每周一次的回顾。本文还补上评测中缺少的两类指标：项目归集的纯度与碎片率，摘要的覆盖率。

## 1. 要解决的问题

1. **项目会碎片化。** 每晚的归属判断只对比召回的候选。名称不同、指的是同一件事的项目（"新办公室装修"与"办公室搬迁"）一旦分开，之后各自归集，不会再合并；只出现过一次的项目长期挂在列表里，干扰之后的召回。Zep 指出，增量归类会逐渐偏离整体重算的结果，需要定期整体刷新；TopicGPT 的做法是用嵌入找出相似的话题对、交给模型判断是否合并，并清理低频话题。
2. **项目现状会漂移。** `set_status` 每天在前一天的现状上增量修改。BooookScore 的结论是：滚动更新细节多、但容易累积错误，需要定期依据完整的时间线整体重写。
3. **觉察只看一天。** 一天里的偶然表现会被当成习惯，每天的建议前后不一致。Generative Agents 的"反思"是在积累到一定量之后才汇总。
4. **评测量不到碎片化。** 现有用例只断言某一段交谈归入了哪个项目，没有"一个主题拆成了几个项目""一个项目混进了几个主题"的指标，也没有摘要漏了多少要点的指标。

## 2. 概要

业务线服务端每周日深夜做三件事，都由它编排，yanshi 不新增调度：

| 步骤 | 谁做 | 结果 |
|---|---|---|
| 归档 | 业务线，按规则，不调用模型 | 30 天没有新交谈、也没有未完成承诺的项目移到"归档" |
| 回顾 | `xinli-week` 的 Run | 提议合并相似的项目（交给用户确认）；交出本周觉察 |
| 重写现状 | 本周有新交谈的每个项目的 `xinli-project` Run | 依据完整时间线整体重写现状 |

## 3. 归档

- **规则。** 30 天没有新交谈、且没有未完成的承诺，项目就归档。归档的项目不在 `find_projects` 与 `list_projects` 中出现，App 中可以查看、取消归档。
- **不调用模型。** 判断只依据数据，确定性、可复现。
- **新的交谈照样可以归入。** 归档只影响召回：用户取消归档后照常召回；每晚整理归属 `new` 时，业务线发现名称与某个归档项目相同，提示用户是否恢复它，不自动恢复。

## 4. 回顾（`xinli-week`）

**Session。** 每个 EndUser 每周一个 `xinli-week` Session（`agents/xinli-week.yaml`），业务线提交"回顾本周"。它只读业务线的数据（调用结果，外部内容），不读旁听原文。Retention 与 `xinli-day` 相同：整理后关闭，7 天后删除，写下的 Memory 保留（它不写 Memory，见 §8）。

**工具**（xinli MCP Server，`internal/xinlimock` 同步实现）：

| 工具 | 说明 |
|---|---|
| `week_overview`（只读） | 本周每天的总览、每段交谈的标题与归属、每天的觉察。 |
| `similar_projects`（只读） | 业务线按相似度（生产用嵌入，模拟服务用字符二元组）找出的至多 5 对可能重复的项目，附各自的现状与最近几段交谈的标题。 |
| `propose_merge` | `{into, from, reason}`：提议把 `from` 并入 `into`，进业务线的"待确认"。 |
| `file_week` | `{habits: [{habit, days, example}], suggestions}`：本周的觉察。`days` 是这个习惯出现的日期，至少两天。 |

**流程：**

1. 用 `similar_projects` 取回候选对，逐对判断是否指同一件事（同一个对象、同一批人、同一个目标）。是的，用 `propose_merge` 提议合并；只是主题相近的（两次不同的装修）不提议。
2. 用 `week_overview` 取回本周的觉察，归纳出至少在两天出现过的沟通习惯，各附一个例子，再给出建议，用 `file_week` 交出。只出现一天的不算习惯。
3. 用一两句话回复。

**开发部署。** `serve -xinli-mock` 下，调试控制台的"旁听"视图有"每周回顾"按钮（`POST /v1/debug/xinli/week`），模拟服务扮演业务线服务端做 §2 的三步：同一周重复触发复用同一个回顾 Session，输入 ID 由本周的第一天派生；"待确认"中可以接受或拒绝合并提议（[调试控制台](./console.md) §2.1）。

**合并由用户确认。** 这与拿不准归属时的做法一致（[旁听按交谈整理](./captures-by-exchange.md) §6）。用户确认后，业务线合并时间线，把承诺移到 `into`，关闭 `from` 的 `xinli-project` Session，以后的归集都交给 `into`。合并不调用 yanshi：Project Session 只是业务线编排的对象，删除仍按 Session 进行（ADR-0037）。

## 5. 重写现状

业务线向本周有新交谈的每个项目提交"重写现状"。`xinli-project` 收到它时：

1. 用 `project_digest` 取回完整的时间线（按交谈）与未完成的承诺。
2. 不参考之前的现状，依据时间线整体重写，用 `set_status` 交出。

日常的"整理 <日期>"仍做增量更新。指令中写明两种输入各自的做法。

## 6. 评测

### 新指标

**项目归集的纯度与碎片率**（TopicGPT 用纯度评价话题分配）：

- 多天用例的数据文件给每段旁听标上主题（`topic`），无关的闲聊不标。
- 评测运行器在最后一轮之后，把每段交出的交谈对应到它第一段的主题，计算：
  - **碎片率**：每个主题平均分散在几个项目中，理想值为 1；
  - **纯度**：每个项目中占多数的主题所占的比例，理想值为 1。
- 断言形如 `expect.xinli.grouping: {topics: 3, fragmentation: {max: 1.0}, purity: 0.9}`，实际的数值写在断言的说明中。

**摘要的覆盖率**（SummHay 按覆盖率与引用准确率评分）：

- 用例列出旁听中的要点（`expect.xinli.covers: {points, min}`）。
- 评分模型逐条判断要点是否出现在交出的交谈与总览中，覆盖率是出现的比例。判断依据整理结果的结构化数据，而不是回复文字。
- **引用准确率**是通过核对的承诺占全部承诺的比例，确定性计算（`expect.xinli.verified_rate`）。

### 用例

| 用例 | 要点 |
|---|---|
| `capture-week-grouping` | 5 天、3 个主题、夹着闲聊；每天一轮整理（`new_session`）。断言碎片率、纯度与覆盖率。 |
| `capture-week-merge` | 预置"新办公室装修"与"办公室搬迁"（同一次搬迁）、"家里厨房装修"（不同的事）：只提议合并前两个。 |
| `capture-week-awareness` | 预置一周的觉察："答应时给出期限"出现在三天，"会后发纪要"只出现一天：只交出前者。 |
| `capture-project-rewrite` | 预置一份过时的现状（仍写着"等报价"）和完整的时间线（报价已确认、合同已签）：重写后不再提"等报价"。 |

`capture-week-grouping` 的数据由模板与手写的关键交谈组合生成（`evals/data/`）。主题与闲聊交替出现，同一个主题在不同的天里换不同的说法（"装修""新办公室""搬家的事"），专门考察碎片化。

## 7. 不在这一版

- **每周整理 Memory**（找出相互矛盾的记忆并标为失效）：见 §8 第 4 条。
- **自动合并**：合并会改变用户看到的项目结构，第一版一律交给用户确认。
- **按月的回顾**：先看每周回顾的效果。

## 8. 决定（2026-10-24）

| 决定 | 选择 | 没有选的 |
|---|---|---|
| 替换旧记忆 | 标记失效、保留历史 180 天（m4-memory-grant.md §11，ADR-0038） | 维持删除 |
| 计划的有效期 | `memory_save` 可写 `valid_until`，过期不召回 | 不做，靠模型自己判断 |
| 合并项目 | 模型提议，进"待确认"，由用户确认 | 判断把握大时自动合并 |
| 每周整理 Memory | 不做。回顾的 Run 读的是业务线的数据，属于外部内容；在外部内容影响下让旧记忆失效，相当于放宽写入闸门（ADR-0023）。矛盾仍在每晚整理中、依据用户本人的话用 `replaces` 处理 | 做，失效的操作需要用户批准 |
