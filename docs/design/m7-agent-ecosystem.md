# M7 Agent 生态：对接三方 Agent

> 状态：设计（2026-10-27），经 Codex 两轮评审后修订（[评审记录](../review/2026-10-27-persona-architecture-review.md)），未实现 · ADR-0048 · 来由：[xinli 与 persona agent 的整体架构](./persona-architecture.md) §9 · 依赖：[MCP 适配](./m5-mcp.md)（ADR-0017）、[委托](./m5-multi-agent.md)（ADR-0031）、[输入、触发与外部循环](./m5-inputs-triggers-loops.md)（ADR-0039、ADR-0041）、[后台调用](./m1-device-nodes.md)（ADR-0035）、[Memory 与 Grant](./m4-memory-grant.md)（ADR-0003、ADR-0016）、[鉴权](./auth.md)（ADR-0014）
>
> 2026-11-14：ADR-0036、ADR-0039、ADR-0050 与 ADR-0037 的内核部分已整合进 [ADR-0052](../adr/0052-attested-results-and-provenance.md)，ADR-0040 已取消，ADR-0010 已被 [ADR-0053](../adr/0053-self-hosted-sandbox-isolation-baseline.md) 取代。本文引用这些 ADR 之处，现行规则以 ADR-0052、ADR-0053 为准（[ADR 索引](../adr/README.md)）。

persona agent 要走进更大的生态：调用三方 Agent 办事（订票、报销），让三方 Agent 来问"他这周答应过什么"，让三方开发的 Agent 运行在 yanshi 上。三个方向的信任问题各不相同，本文分开设计，共用一条原则：**三方给的一切都是外部内容，三方拿到的一切都经用户逐项同意，旁听原文不给任何三方。**

## 1. 三个方向

| 方向 | 例子 | 信任问题 | 落地 |
|---|---|---|---|
| 出站（§2） | 前台把"订周五去上海的高铁"交给出行 Agent | 结果是外部内容；发出去的是用户的个人信息 | 最先 |
| 入站（§3） | 用户的另一个助手经 A2A 问"他这周答应过谁什么" | 调用方不是用户本人，输入不能算用户原话 | 其次 |
| 托管（§4） | 三方开发者的 Agent 上架，用户在 xinli 中使用 | 三方的指令不可信；跨业务线的数据与权限 | 注册中心里程碑 |

## 2. 出站：三方 Agent 是一种 Capability

内核新增 `a2acap` 包，与 `mcpcap` 并列，实现 A2A 客户端。

**登记**（`a2a/*.yaml`，与 MCP 登记同样由部署配置分发）：

```yaml
name: travel
business_line: xinli
card_url: https://agent.example.com/.well-known/agent.json   # Agent Card；私有化部署只来自显式登记（ADR-0001）
auth: {type: oauth2, token_url: ..., client_id: ${TRAVEL_CLIENT_ID}, client_secret: ${TRAVEL_SECRET}}
read_only: false        # 三方声明的只读不可信，默认 false
timeout: 60s            # 同步等待的上限；超过即转为后台调用
```

**语义**：

- **模型看到的形态**：工具名 `a2a__<名称>`，描述取自 Agent Card，输入为 `{task, context?}`，与委托的 `agent__<名称>` 同构。白名单条目 `a2a:<名称>`；工具按名称排序，前缀稳定。
- **结果是外部内容**：名称含 `__`，来源推导为外部（ADR-0039），进入注入判断、使写入闸门生效。
- **总是需要审批**：审批界面展示将要发出去的 `task` 与 `context` 原文，这是用户对"向这个三方提供这些信息"的单独同意（§5）。与 MCP 不同，登记中的 `no_approval` 与 `read_only` 都不能免去它：出境同意独立于"是否有副作用"。
- **数据最小化**：只发出模型写在调用参数中的内容；平台不附带上下文、Memory 或 Persona 数据。
- **听过他人旁听的 Session 不能调用三方**：见 §5。
- **长任务**：三方任务超过 `timeout` 未完成时按后台调用处理（ADR-0035）：模型得到"已受理"，Run 照常继续；三方的推送或轮询到的终态作为一条输入回到 Session，至多了结一次。三方要求补充信息（A2A 的 `input-required`）时，转为对用户的 `ask_user`。
- **外部 Agent 的过程不可见**：它在自己的系统里做什么，平台管不到，与 MCP Server 相同。所以出站只给"办事"用，不给它任何能回调平台的凭据。
- **计量**：按调用计数；三方自己的模型用量不经平台。

## 3. 入站：三方 Agent 调用我们

分两档。

### 3.1 数据档：Persona 对外的 MCP

- Persona 对外提供一个 MCP Server，用 OAuth 2.1 授权：用户在 App 中为某个三方授予范围（`commitments:read`、`projects:read`、`notes:read`、`entities:read`、`proposals:write`），可随时撤销。
- **只读整理后的知识**：摘要、项目、承诺、实体、本人的笔记。**不开放旁听原文**，无论是否在保留期内。
- **提议写入**：三方只能交出"提议"，作为作者为三方、来源为外部的变更集进入"待确认"，用户在 App 中确认后才生效。三方永远不能直接写入内核的 Memory。
- 每次访问记录（三方、范围、对象 ID、时间，不含内容），用户可在 App 中查看，与 Memory 的访问记录同一形态。
- 这一档完全在 Persona 与应用层，不改内核。

### 3.2 对话档：A2A 入口

三方 Agent 想和用户的 persona agent 对话（"他明天下午有空吗？帮我约个会"），需要一个 Run。内核在网关上实现 A2A 服务端：

- **Agent Card**：业务线登记哪些 AgentDef 对外开放（`a2a_inbound: {agent: xinli-a2a, skills: [...]}`），网关据此发布 Agent Card。
- **身份**：调用方以 OAuth 令牌证明自己是哪个三方、代表哪个 EndUser 授权过（令牌由业务线的授权服务签发，网关按 ADR-0014 的方式验证，新增 `scope: a2a`，带 `client` 声明）。用户没有为这个三方授权对话时拒绝。
- **Session**：每个 (EndUser, 三方) 一个 Session，AgentDef 为业务线专门写的 `xinli-a2a`，白名单比前台更小（只读的 Persona 工具、`ask_user`）。对外开放的 AgentDef 加载时校验：`memory.recall: 0`（召回只认 EndUser 与业务线，不认三方与授权范围，`internal/runtime/recall.go`）、`context.scope: run`（之前的回答不进入之后的上下文，撤销后不能被追问出来）、白名单中没有 `captures`、`memory_save` 与 `a2a:*`。
- **来源按入口推导**：A2A 入口写入的 `RunRequested` 带平台写入的 `origin: {kind: a2a, client, grant_version}`；来源推导为**外部**，不是本人。`origin` 只能由网关写入，客户端提交中带有它一律拒绝，`Apply` 再校验（与触发标记、`redo_of` 相同的"平台专属"规则）。这是 ADR-0037 当年没有选的"派生自不可信内容的标记"：那里有更简单的替代（MCP 拉取），这里没有，因为对话的输入本来就要进入 Run。
- **不插话、不重答**：有活跃 Run 时 A2A 请求直接返回忙（A2A 的任务状态），不产生 `Steered`（插话的来源现在按用户原话推导）；重答在这类 Session 中被拒绝。限制在 service 中按 AgentDef 执行，不只在网关的适配器中，任何入口都不能向这类 Session 提交不带 `origin` 的输入。
- **授权上下文随调用传递**：Run 对 Persona 的 MCP 调用带上 `origin`（`_meta["yanshi/origin"]`），Persona 按三方与授权版本逐次检查范围。
- **出口检查**：同步响应、任务查询、订阅与推送在返回之前都检查授权版本仍然有效；撤销时取消在途 Run、删除该三方的 A2A Session。已经交给三方的内容收不回，这一点写进授权界面。
- **审批与提问路由到用户**：Run 需要审批或 `ask_user` 时，照常推送到用户的 Device（ADR-0025）；调用方只能等，不能代为批准。`ask_user` 的提问上平台标明"<三方名称> 想知道"，用户的回答会交给这个三方，回答本身就是一次单独同意。
- **回复**：Run 的回复作为 A2A 的任务结果返回，经内容安全检查（与模型输出相同）。

## 4. 托管：三方开发的 Agent 运行在 yanshi 上

现在只定方向、预留契约，在注册中心里程碑（章程 M5）实现。

- **三方开发者是一个 BusinessLine。** 它有自己的签名密钥、配额、保留策略与 Memory 归属，现有的租户隔离全部沿用；它的 AgentDef 由它发布，经平台的评测与审核后上架。
- **跨业务线使用经用户授权。** Grant 从"读取 Memory 的类别"扩展为两类：
  - **调用授权**：允许 xinli 的 Agent 委托给三方业务线的某个 Agent。委托因此可以跨业务线（ADR-0031 现在不允许），子 Session 属于三方业务线，计量与配额记在三方。
  - **数据授权**：三方 Agent 可读取哪些 Persona 范围（经 §3.1 的 OAuth）与哪些 Memory 类别（现有 Grant）。
- **权限是交集**：子 Run 的能力是三方 AgentDef 的白名单、调用方白名单与用户授权三者的交集；跨业务线的委托结果对调用方是外部内容。听过他人旁听的 Session（§5）不能委托给三方业务线。
- **三方的指令不可信**：上架的 AgentDef 只能使用平台允许三方使用的能力集合（不含设备的高风险能力、不含旁听读取）；上架前跑平台的安全评测（注入、越权、数据外流）。
- **发布**：三方 AgentDef 的版本、灰度与撤回沿用发布配置（ADR-0020）；注册中心保存 Agent Card、版本、审核状态与评测结果。

## 5. 同意与数据外流

个人信息保护法要求向第三方提供个人信息时取得单独同意：

- **出站**：每次调用的审批就是单次同意，审批记录在日志中（`ApprovalDecided`），附三方名称与发出的内容。
- **入站与托管**：每项授权（三方 × 范围）是一条可撤销的同意记录，带创建与撤销时间；撤销立即生效（与 Grant 相同，检索时实时检查）。
- **访问记录**：三方的每次读取都记 ID 级的访问记录，用户可查。
- **旁听原文不给任何三方**，由结构保证，不靠文字比对：
  - **听过他人旁听的 Session 不能调用三方。** 投影中记一个只增不减的标记（拟名 `HeardOthers`）：`captures` 的结果中出现过未拦截的他人片段即置位，压缩不清除它（压缩会裁掉 History，只扫描当前上下文不够）。委托时子 Session 继承父的标记，子 Run 的结果回到父 Session 时，子的标记一并带回。置位的 Session 中，`a2a__*` 调用一律拒绝。
  - 入站与托管拿不到 `captures` 能力；Persona 不保存原文（`cite_captures` 不给文字），它的对外接口自然不含原文。
  - **残留风险**：Persona 中由模型写成的摘要可能逐字引用了原话。这部分按用户授权的范围提供；整理的指令要求转述，Persona 的检查对超过一定长度的逐字引用（与引用片段的字符重合）拒绝。承诺因此写成"不开放旁听原文，也不开放读过原文的 Agent 对外调用"，而不是"任何形式都不外流"。

## 6. 协议

- Agent 之间用 A2A，工具用 MCP，用户授权用 OAuth 2.1。协议适配都在网关与能力层的适配器中，内部仍以 `proto/` 的契约为准（ADR-0006）：A2A 的消息在边界上转换为 `ContentBlock`。
- 国内平台（扣子、飞书 aily 等）不支持标准协议时，在应用层写专用适配器，对内仍按 §2 的登记形态出现。
- 外部地址只来自显式登记；私有化部署可以不登记任何三方（ADR-0001）。

## 7. 落地顺序与验收

| 步 | 内容 | 验收 |
|---|---|---|
| 0 | 授权上下文与出境规则：`HeardOthers` 标记及其在压缩、委托中的传递；`origin` 与平台专属校验；对外 AgentDef 的加载校验；同意记录 | 模拟测试：读他人旁听 → 压缩或委托 → 调用三方被拒绝；`origin` 不能由客户端写入 |
| 1 | 出站：`a2acap`、登记、审批展示（不可放宽）、后台调用衔接 | 单元与模拟测试（三方超时、重复回调、迟到结果）；评测：委托三方办事、三方结果中的注入不生效 |
| 2 | 入站数据档：Persona 对外 MCP、OAuth 范围、提议写入、访问记录 | Persona 的契约测试；撤销立即生效 |
| 3 | 入站对话档：网关的 A2A 服务端、忙时拒绝、出口检查、`xinli-a2a` | 授权矩阵测试；撤销后的同步响应、查询与推送都被拦下；评测：三方诱导的写入需要用户批准 |
| 4 | 托管：注册中心、跨业务线委托、Grant 扩展、上架评测 | 注册中心里程碑另行设计 |

## 8. 决定

| # | 决定 | 选择 | 没有选的 |
|---|---|---|---|
| Q22 | 范围与顺序 | 三个方向都预留，按出站、入站、托管落地 | 只做出站；先做托管（最重，信任问题最多） |
| Q23 | 出站 | 内核的 A2A 能力，结果是外部内容，默认审批，只发调用参数，长任务按后台调用 | 应用层自己调三方（平台的审批、来源与同意都管不到） |
| Q24 | 入站 | 数据档：Persona 对外 MCP，只读加提议写入；对话档：内核 A2A 入口，来源按入口推导为外部 | 三方以服务令牌提交输入（变成用户原话） |
| Q25 | 托管 | 三方开发者是独立 BusinessLine，跨业务线委托经用户 Grant，现在只预留 | 三方 AgentDef 放进 xinli 业务线（数据与配额混在一起，指令的信任无法区分） |
| Q26 | 协议 | A2A、MCP、OAuth 2.1，内部以 proto 为准；国内平台在应用层适配 | 自定义协议 |
| Q27 | 同意 | 按三方 × 范围单独同意，有访问记录；旁听原文不开放，听过他人旁听的 Session 不能调用三方（评审后由"一律不外流"收窄，见[评审记录](../review/2026-10-27-persona-architecture-review.md)） | 一次性总授权；按文字重合拦截（启发式，可绕过） |
