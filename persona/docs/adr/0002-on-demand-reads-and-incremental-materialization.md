# Persona ADR-0002：按需读取与增量物化，变更集仍是事实源

> **第一期（按需读取）已实现（2026-11-16），第二期（增量物化）尚未实现。** 只读查询与只读工具按读取计划装载物化行；写事务照旧整体装载非原文账本、整体叠加。实施记录见文末。来源：[ADR 评审](../../../docs/review/2026-11-14-adr-review.md) §3.2。

[Persona ADR-0001](./0001-entities-by-changeset.md) 让 xinli 的知识以变更集为日志、叠加出交谈与承诺。P4 的存储形状（[Persona 架构](../../../docs/design/persona-architecture.md) §13 Q93）是："原文按 owner / 业务日 / 批次独立存储并惰性读取；其余账本分类表、键列加 JSONB，**每事务整体装载非原文账本**"。现行实现（2026-11-14 核对）：

- 所有读写都经 `Store.Update` 与 `Store.View`（`persona/store/store.go`），两者都先整体装载该 owner 的账本：`pgstore` 对 18 张分类表逐表读取，条件只有 `business_line` 与 `end_user`（`persona/store/pgstore/rows.go` 的 `loadBook` 与 `loadRows`）。写入侧按行比较、增量保存；读取侧没有增量。
- 每次提交变更集都对全部变更集重新叠加（`persona/domain` 的 `refold`）；擦除删除依据相交的变更集后同样重新叠加。
- 原文是例外，按页惰性读取。
- **成本已经实测**（Persona 架构 §13 的 P4 成本报告，2026-10-29，Mac mini，一年账本）：PG 上每事务读入约 7.4 MB，23–96 条 SQL；只读查询 p50 约 185–225 ms，写事务约 400–460 ms；每次操作分配约 166–391 MiB。报告的结论是：一年用户的单次工具调用已达数百毫秒，为 Q93 推迟的"账本按需有界查询"提供了依据；"交谈与承诺按日期或状态分页装载、物化查询读表"列为 P4 之后的优化项。

## 提议的决定

1. **变更集仍是事实源，不降为审计日志。** 交谈、承诺、项目仍由有效变更集叠加得出；物化的表是可以从变更集重建的投影，与内核"投影快照只是缓存"同一原则。
2. **增量物化。** 提交一个变更集时，只重新叠加受它影响的实体（它新建、修订、关闭、合并的实体，以及来源重交时被整体取代的上一份变更集涉及的实体），并在同一事务中更新物化表。全量重叠加只在重建、迁移与校验时进行。
3. **按需读取。** 查询与工具调用只装载需要的实体：按日期、状态、项目或 ID 读物化表（例如 `day_ledger` 只读当天，`list_commitments` 只读符合条件的承诺），不再装载整本账本。
4. **保持现有的语义不变：**
   - **来源取代的顺序**：同一来源重交时整体取代上一次，取代后的叠加结果与全量叠加一致；
   - **`rev`**：承诺的 `rev`（修订数）与交谈、项目的内容版本照常校验，读取到的版本必须是该实体的当前版本；
   - **擦除重算**：去掉依据相交的变更集（传递闭包）后，受影响的实体按剩余变更集重算；
   - **处理进度**：处理进度与变更集、物化表在同一个本地事务中提交。
5. **以全量叠加为裁判。** 实现期间保留全量叠加作为校验：一致性套件与差分测试中，增量物化的结果必须与全量叠加逐项相同。

## 实施前核对的现状（2026-11-16）

定稿之前核对了代码，下列事实决定了答案：

- **叠加依赖变更集之外的全局输入。** `fold` 按变更集顺序对整本账单遍执行，还依赖项目合并（`canon`，项目是直接事实，不经变更集）、Session 到业务日的绑定（`sessionDays`，交谈按 (业务日, ID) 查找）、Book 级计数器（`next`、`nextC`、`nextCS`）与全局的承诺 ID。交谈合并吸收 `from` 在合并时刻的状态，结果与路径有关。
- **物化行已经存在但从不读取。** `exchanges`、`commitments` 两张表每次 `Update` 都写入 `State()` 的结果，装载时却被丢弃、再整体叠加；没有任何版本标记说明这些行由哪一版规则产生。
- **每行只有整块 JSONB。** 没有按日期、状态、项目、期限可查的列，也没有"实体 → 变更集"的索引。
- **一次写事务整体叠加三到四次**（装载、提交、来源重交的 `foldWithout`、写回时的 `State()`），`State.Reminders()` 与 `day_ledger` 的重复提示是对承诺两两比较的 O(n²) 聚合。
- **`domain.Book` 对存储是整本的领域对象**，MCP 工具、用户命令与应用层查询都直接依赖它。按需读取要在 `domain` 增加读接口，影响面大于存储层。

## 定稿的答案（2026-11-16）

0. **分两期。** 第一期只做**按需读取**：只读查询与工具读物化行，写事务仍整体装载、整体叠加。第一期完成后用成本测试复测，再决定是否做第二期**增量物化**（写事务只重算受影响的实体）。读路径的收益最大、风险最小；写路径的路径依赖与全局输入放到有实测依据之后。
1. **受影响实体（第二期）。** 一个变更集触及的实体 ID，加上触及这些 ID 的其余全部变更集，加上交谈与承诺的整个合并连通分量，按原变更集顺序重放。项目合并、Session 换绑业务日、擦除与预置（`Seed`）改变了全局输入，对该 owner 整体重算；它们不常发生，不做精细失效。
2. **复用现有物化行。** 不新增查询专用的表，`exchanges`、`commitments` 照旧同事务写入，并新增可查询的列：承诺的状态、项目、期限、`MergedInto`；交谈的业务日与项目；变更集的业务日与 `Source.Date`。另加"变更集 → 实体 ID"的旁表（第二期使用）。列与索引只经新增迁移添加，大表上的索引用 `CREATE INDEX CONCURRENTLY`。
3. **叠加规则带版本号。** `book_meta` 中记录 Persona 的叠加版本（与内核 `session.ProjectionVersion` 同一原则）；叠加逻辑或物化行的形状改变时递增。装载发现版本不符时，在 owner 锁内整体重算并写回；另有后台遍历全部 owner 逐个重建。**启用新读路径之前，全部 owner 先按当前版本整体重建一次**：现有物化行从未被读取或校验过，不能直接信任。
4. **仍然整体装载的操作：** 擦除（传递闭包）、项目合并、`Archive`、Session 换绑业务日、`Seed`；第一期中全部写事务。擦除按业务日限定范围是之后的优化。
5. **内存实现保持整体叠加，作为参照。** `memstore` 不改为按需；新增差分测试（接入 `persona/store/storetest`）逐项比较按需读取与整体叠加的结果；现有的内存与 PG 对拍（`TestStoreParity`）保留。
6. **提醒与重复提示只读未完成的承诺。** `State.Reminders()` 只看 `reminderEligible`（未完成、未合并、有期限、无待核实），`day_ledger` 的重复提示只比较未完成的承诺，按状态索引读出即可，结果与现在一致，以差分测试为裁判。顺序依赖账本顺序的地方（`Reminders`、`related` 的稳定排序）按物化行的 `ordinal` 读取。

## 必须验证

- `persona/store/storetest` 的全部子套件在新实现上通过；新增"增量物化与全量叠加一致"的差分测试。
- 来源取代的顺序、`rev` 冲突、擦除后的重算、处理进度与业务写入同事务提交，结果与现有领域逻辑一致。
- 成本：用 P4 成本测试（`persona/store/costtest`）以同一份一年账本复测，报告账本装载量、SQL 数、p50 / p99 与内存，与 2026-10-29 的结果对比。
- 评测：工具结果的文字不变，`capture-*` 用例与基线一致。

## Considered Options

- **维持整体装载，只加缓存**：读路径变快，但写事务仍要装载整本账本，多实例下缓存的一致性还要另做。
- **把变更集降为审计日志，实体表成为事实源**：读写都简单，但来源重交的整体取代与擦除的传递闭包都依赖变更集叠加，降级后这两种语义要在实体表上重新实现，且无法再以全量叠加校验。
- **按时间分段的快照加尾部叠加**（类似内核的投影快照）：减少叠加量，但读取仍要装载快照全体，没有解决按需读取。

## Consequences

- 批准后修订 Persona 架构 §13 Q93 的存储形状，并更新 [Persona ADR-0001](./0001-entities-by-changeset.md) 中"每次操作按 EndUser 全量装载账本"一条。
- 存储实现变复杂：物化表与变更集要在同一事务中保持一致，全量重建要可以随时执行。

## 重审条件

- 批准、实施或放弃本提案时更新状态；
- 复测的成本未达到预期，或增量物化与全量叠加的差分测试出现无法消除的差异。

## 第一期实施记录（2026-11-16）

- **读取计划**（`persona/domain/reads.go`）：`day_ledger`、`list_commitments`、`find_related` 三个只读工具与应用查询的 `commitments`、`history`、`day` 按计划装载；其余只读工具与查询没有计划，照旧整体装载。计划在只含小表的 Book 上运行（`Book.MarkPartial`），按条件读物化的承诺、交谈、变更集与日总览；部分装载的 Book 不能叠加、取 `State` 或提交。
- **存储**：`store.Store` 增加 `ViewPlanned` 与 `StaleOwners`。PG 先装载小表，`book_meta` 中的叠加版本不是 `domain.FoldVersion` 时退回整体装载；SQL 只做粗选，精确条件由领域的 `Match` 判断（含 U+0000、以 JSON 字符串保存的行一律粗选进来）。暂不加表达式索引：按 owner 主键前缀扫描已足够，复测再定。内存实现默认整体装载，是参照；`PartialReads` 只供测试检查计划本身。
- **叠加版本**：每次提交随物化行写入当前 `FoldVersion`。`storetest` 的 `TestFoldVersionDigest` 固定一份账本叠加出的交谈与承诺的摘要，摘要变了必须递增版本。编排器在到期扫描的同一周期中对 `StaleOwners` 各做一次空的 `Update`（`RebuildStale`），按当前规则重建。
- **差分测试**：`storetest` 的 `partial_reads`（内存与 PG，PG 另有要求确实走部分装载的 `TestPartialReads` 与版本失效的 `TestStaleFoldVersion`）在一份覆盖来源重交、修订、关闭、合并、擦除后换绑、项目对账、用户修改、项目合并与 U+0000 的账本上，逐项比较每个计划与整体装载；成本测试在一年账本上再逐字对照一次。故意删去 `day_ledger` 计划中的未完成承诺后，差分测试会失败。
- **成本**（Mac mini，N=10，同日对照 main）：三个查询的 p50 从 142–174 ms 降到 35–46 ms，账本装载量从 7.4 MB 降到约 1.3 MB，每次分配从约 167 MiB 降到约 26 MiB；写事务不变（约 320–360 ms）。详见 [Persona 架构](../../../docs/design/persona-architecture.md) §13 的成本报告。
- **评测**：工具与查询的文字由差分测试证明与整体装载逐字相同，给模型看的文本没有变化，所以没有重跑 `make eval`。
- **第二期**：写事务的成本仍在，是否做增量物化在之后有真实负载或更大账本的需要时再决定。
